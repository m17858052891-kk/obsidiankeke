
PEPNet 的作用是给共享模型加入动态个性化能力。

EPNet 放在 OneTrans 前，对底层 embedding 做场景适配。因为当前订单的履约会受到产品、时段、区域供需、接驾距离等场景因素影响，同一个特征在不同场景下的重要性不同。EPNet 将场景先验输入 Gate MLP，经过 2 × sigmoid 生成范围在 (0, 2) 的逐维 gate，再与 embedding 逐元素相乘：大于 1 表示增强该表示通道，小于 1 表示抑制。  

PPNet 放在 OneTrans 后，解决的是同一份司乘联合表示如何服务不同任务。它将 OneTrans 输出的联合表示 z，与该任务对应的可观测先验拼接后送入 Gate MLP，为 D、O、OD 各自任务塔的每层 hidden 生成逐维 gate。它不是重新挑选原始特征，而是调节“交互后联合表示”的哪些 hidden 通道应被该任务更重视。

OneTrans 位于中间，负责将经过场景适配的乘客历史、司机历史以及当前订单、画像、上下文等静态特征统一 Token 化，放入同一个 Transformer 中建模。每笔历史订单被编码为一个行为 token，并加入角色、相对时间和位置编码；当前订单 token 则带着价格、接驾距离、时段、供需等条件。通过 self-attention，当前订单可以主动从双边历史中选择与自身最相关的行为，同时学习司乘跨序列交互和序列—静态特征交互。4 层交互后，末尾 Order token 的 hidden 形成联合表示 `z`，即“当前订单条件下从司乘双边历史读出的履约表征”。

## 详细逐字稿（约 8—10 分钟）

### 1. 项目背景与要解决的问题

> 我做的是一个司乘双边履约的离线序列建模项目。给定当前订单、乘客历史、司机历史和实时上下文，模型同时预测乘客履约 D、司机履约 O，以及司乘联合履约 OD。这个项目基于既有 PLE 架构来源开展离线改造，目标不是简单把特征加多，而是解决传统统计特征和串行序列网络无法充分表达“当前这笔订单与双方历史是否匹配”的问题。

> 一开始的模型能够使用乘客、司机、订单和上下文的静态特征，例如乘客和司机画像、起终点区域、报价、接驾距离、时段与供需等；但历史往往被压成完单数、取消率、均值这类统计量。这样会损失三类关键消息：第一，历史行为的顺序，例如最近一次取消和半年前一次取消的含义不同；第二，历史事件距当前订单的时间间隔；第三，当前订单的价格、接驾距离和供需条件，无法在读取历史的当下参与判断。与此同时，乘客和司机是两条行为链路，如果分别把它们编码成两个向量后才拼接，也会丢失 token 级的司乘交互。

> 这里还要区分预测层和策略层：序列模型要先提升履约相关结果的排序能力，而接驾距离、ETP 等交易效率目标需要在后续 PK/O 选 D 的策略中显式优化。接驾距离进入特征，只说明模型可以用它判断履约风险，并不等于模型会主动选择更短接驾的司机；所以这份项目材料的核心证据仍然是离线 AUC，而不是线上交易效率收益。

### 2. 双边序列样本与特征构造

> 所以这个项目的主线不是继续堆宽 MLP，而是先把双边历史建成可用的序列样本，再用 PEPNet × OneTrans 同时解决场景个性化、双边序列交互和多任务差异。数据层面，我以当前订单的 `prediction_time` 为锚点：只取 `event_time < prediction_time` 且预测时点已经可获得的历史事件。事件侧通过 Attempt 串联冒泡、发单、应答、取消到完单链路，再沉淀成 Attempt/订单宽表和双边历史序列。这样做的核心不是 SQL 形式，而是防止把当前订单、未来订单或预测时点后才回刷的结果塞进历史。乘客和司机历史都按 `event_time + stable_event_id` 稳定排序，截断到固定长度，不足部分 padding 并用 mask 屏蔽。面对大规模历史回查，采用“主体 ID + 时间戳预排号、订单锚点截断候选区间、再回表取字段”的方式，避免直接范围 Join 造成笛卡尔积膨胀。

> 特征进入模型时，我把每一笔历史订单视为一个事件。类别字段，例如区域、产品、行为状态，先查 embedding；连续字段，例如价格、行程距离、接驾距离和距当前时间差，先归一化后经过 MLP 投影；最后将同一笔事件的字段拼接，经 MLP 融合成 128 维事件表示。乘客和司机的每笔历史都按这个方式形成事件 embedding。当前订单和静态特征不做成一长串散特征，而固定分为五组：PassengerProfile、DriverProfile、Context、Statistics 和 Order；每组同样经过 `Concat → MLP → 128 维` 投影。这样每种输入最终都落到同一个 128 维 token 空间。

### 3. EPNet：先做当前场景下的底层表示适配

> 第一层核心设计是 EPNet。EPNet 不直接区分 D、O、OD，它解决的是同一个底层特征在不同订单场景下是否应该以不同强度参与后续计算。比如同样是 2.8 公里接驾距离，在平峰供需宽松和早高峰供需紧张下，代表的等待成本与履约风险不同。这里我把产品、小时和工作日、起终点区域、区域供需以及乘客和司机基础画像组成场景先验。场景先验与基础 embedding 经过一个两层 Gate MLP，生成一组 `[B,1,128]` 的 gate，取值范围是 0 到 2；再广播乘到当前样本的全部底层字段和事件 embedding 上。小于 1 的维度被抑制，大于 1 的维度被增强。这里 gate 调的是 embedding 的隐向量维度，而不是手工修改“2.8 公里”这个原始数值。为避免 gate 支路反向破坏共享 embedding，gate 的输入读取 embedding 时使用 stop-gradient；但 embedding 主路径仍然正常从履约损失接收梯度。

### 4. OneTrans：统一 token 后的早期交互与联合表示

> 经 EPNet 调节后，再进入 Tokenizer 和 OneTrans。当前模型固定的 token 顺序是：先放司机历史，从早到晚排列；接一个司机—乘客分隔符；再放乘客历史，从早到晚排列；接一个序列—静态分隔符；最后依次放 PassengerProfile、DriverProfile、Context、Statistics 和 Order。每个 token 除内容向量外，还加上角色、相对时间和位置编码。Order token 放在最末尾是有意的：在 causal attention 下，它可以读取此前全部司机历史、乘客历史和静态上下文，因此天然适合作为当前订单的联合 readout。

> OneTrans 是第二个核心。传统做法是分别编码司机和乘客，再和静态特征拼接；OneTrans 则把全部输入放进同一个 Transformer。当前讲解配置使用 4 层 OneTrans，hidden size 为 128、4 个 attention head、FFN 为 512。历史 S-token 共用一套 Q/K/V 和 FFN 参数，因为司机和乘客历史都属于结构相近的行为事件；五类静态 NS-token 各自使用专属 Q/K/V 和 FFN，避免把订单、上下文和画像当成同一种无差别字段。模型使用 causal mask，但当前离线短序列版本不启用 Pyramid 压缩和 KV cache：前者主要解决更长历史的计算成本，后者主要解决增量线上推理的重复 K/V 计算。

> 用一笔订单举例。假设当前是工作日早高峰，快车，接驾距离 2.8 公里，区域供需紧张；乘客两天前在相近早高峰、3.5 公里接驾的订单中取消过；司机近期既有相近时段的完单，也有长接驾取消。Order token 在每层 attention 中会以当前订单条件作为 query，去读取这些历史 token：它会把“乘客过去相似条件下的取消”“司机相近场景下的服务状态”以及“当前供需紧张”合并起来。4 层交互完成后，最后一个 Order token 的 hidden 就是联合表示 z。这里的价值在于，模型不是先得到一个泛化的乘客兴趣向量、最后才知道当前订单接驾距离；而是让当前订单从一开始就参与决定该读取哪些历史。

### 5. PPNet 与 D/O/OD 多任务输出

> 有了联合表示 z 后，才进入 PEPNet 的第二部分 PPNet。这里才真正区分 D、O、OD。三个任务各自使用一套 PPNet gate，在每层任务 MLP 的 hidden 前做逐维调节：D 分支强调乘客历史、价格和接驾距离相关通道；O 分支强调司机近期服务状态和时空条件；OD 分支强调双方状态是否和当前订单匹配。最后三个 head 分别输出乘客履约、司机履约和司乘联合履约的 logit。训练使用三项二分类交叉熵的加权和；材料未保留精确 loss 权重，因此我不会在面试中硬报具体数值。

### 6. 实验对照、结果与消融结论

> 实验上，我把比较分成两层。第一层是序列化基础能力：在 6 月和 12 月数据中，PEPNet 加 Positional Self-Attention 相比 PLE base，对 D 和 OD 更稳定，O 的收益更依赖数据和配置。第二层才是 OneTrans 是否替换原有序列交互的问题。严格的 PEP × OneTrans 对照是 `pep-seq`，不是 PosSA。epoch=9 时，`pep-seq` 的 OD/O/D AUC 为 0.7421、0.7339、0.8036；接入 OneTrans 后为 0.7503、0.7613、0.8697，因此相对提升分别为 +0.82pp、+2.74pp、+6.61pp。乘客任务 D 的提升最明显，说明在这组实验里，让当前订单同时读取司乘历史比原有序列交互更有效。

> 我也没有只看最优结果。把 OneTrans 拆成只建模司机或只建模乘客的版本，指标都低于统一版本，说明当前设置下硬拆分削弱了跨主体交互；序列长度从 10 扩到 20 在一组 6 月数据里表现最好，但在 12 月没有稳定复现，所以不能说“长度 20 全局最优”；给序列加入时空特征曾改善部分指标，也说明 O 对序列窗口、特征表达和训练协议更敏感。针对 O 增益不稳定，拆 O tower 和移除 O 的序列输入都没有带来改善，因此不能简单归因为多任务冲突或“序列是 O 的噪声”。此外，Batch Size=256 在多组记录中出现较强正向现象，但需要在固定总 step、学习率策略、样本量和随机种子后才能判断它究竟来自优化噪声还是其他训练差异。

### 7. 结论、边界与下一步

> 这个项目最后让我形成的判断是：序列模型的关键不只是把历史拉长，也不是把 Transformer 堆深，而是让信息在正确阶段对齐。历史事件首先要满足时间可用性；当前场景要先通过 EPNet 调节底层表示；当前订单再通过 OneTrans 主动从双边历史中选择相关行为；最后再通过 PPNet 按 D、O、OD 的目标差异做任务级解释。当前结论只到离线 AUC：OneTrans 相对 `pep-seq` 在三项任务上都有增益，尤其 D 为 +6.61pp。
>
> 下一步我会补三类验证。第一，回到训练 SQL 核查 D/O/OD 的标签窗口和样本空间，特别是是否因对侧取消/拒单而产生条件样本选择偏差；如有，再将全样本三分类作为标签建模消融，而不是混入 OneTrans 结构结论。第二，除 AUC 外补 ECE、校准曲线与候选集回放，确认模型分数能否作为履约约束的基线。第三，若用于 PK/O 选 D，再在策略层显式优化“履约约束 + 接驾距离”，独立验证完单、CR、ETP、接驾时长和商家份额。这样才能把离线模型收益和交易效率业务价值真正闭环。
