# 当前模型架构总览：PEPNet × OneTrans

> 本文只讲当前模型如何计算，不讲 PLE、PosSA、AUC、序列长度或 Batch Size 对比。它们见 [[背景与实验-入口]]。

## 1. 一句话

将乘客历史、司机历史和当前订单/上下文统一组织为模型输入；OneTrans 负责联合序列与静态特征交互，PEPNet 的 EPNet/PPNet 负责在底层表示和任务表示上做个性化调节，最终输出 D/O/OD 三个履约预测。

## 2. 主数据流

```text
乘客历史序列 ─┐
司机历史序列 ─┼─> 字段 Embedding / 基础表示 ─> EPNet
当前订单与上下文 ┘                                ↓
                                           Unified Tokenizer
                                                   ↓
                                             OneTrans backbone
                                                   ↓
                                         PPNet（OD / O / D）
                                                   ↓
                                          D / O / OD 任务头
```

| 模块 | 输入 | 输出 | 核心职责 |
|---|---|---|---|
| 输入层 | 双边历史、订单、用户、上下文 | 结构化字段 | 使历史和当前请求可被同一模型消费 |
| EPNet | 基础表示 + 场景先验 | 个性化 embedding | 按场景调节底层特征通道 |
| Tokenizer | 序列表示 + 静态表示 | S-token / NS-token | 建立统一交互空间 |
| OneTrans | 全部 token | 共享联合表示 | 时序、跨序列、序列—静态特征交互 |
| PPNet | 共享表示 + 任务/主体先验 | 任务表示 | 按 OD/O/D 逐层调节 hidden 通道 |
| Head | 任务表示 | 三个 logit | 输出三项履约预测 |

## 3. 四个应当讲清的设计

1. **双边输入：** 乘客和司机不是两套完全隔离的模型，而是角色不同、可在统一交互空间中传递信息的历史序列。
2. **早期个性化：** EPNet 在 token 交互前调节底层表示，使同一订单字段在不同场景权重不同。
3. **统一交互：** OneTrans 避免“先把序列压成一个向量、再拼静态特征”的硬边界。
4. **晚期个性化：** PPNet 为 OD/O/D 任务提供不同的有效 hidden 通道，避免完全共享造成任务 seesaw。

## 4. 只在代码确认后才能说的细节
