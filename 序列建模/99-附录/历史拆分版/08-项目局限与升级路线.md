# 项目局限与升级路线

## 1. 当前局限

### 1.1 实验族之间不能直接横比

PEP × OneTrans、PLE × OneTrans、6/12 月 PosSA、不同 Batch Size 的数据切分和训练协议并不完全一致。因此只能在各自实验族内归因，不能拿 `.9370`、`.8697` 等绝对 AUC 直接宣布全局最优。

### 1.2 OneTrans 的工程实现细节未被材料确认

OneTrans 的论文机制可以解释统一 token、混合参数化、因果注意力与 Pyramid，但当前材料没有确认本项目的实际 token 排列、层数、hidden size、attention head、loss 权重和 EPNet 与 tokenizer 的精确调用顺序。

### 1.3 O（司机履约）收益不稳定

已排除简单的多任务 trade-off 和“序列纯噪声”解释；但长度、时空字段、样本分布与优化超参都影响 O，12 月未稳定复现 6 月 L20 的正向结果。

### 1.4 未完成线上验证

当前只有离线 AUC，没有线上一致性、时延、吞吐、长期漂移和业务指标结果。

## 2. 优先级最高的补强

1. 固定数据、总 step、随机种子与学习率策略，完成公平的 `PLE base / PLE+PosSA / PEPNet / PEPNet+PosSA / PEPNet+OneTrans` 矩阵。
2. 用固定协议比较 BS=`128/256/512/1024`，区分 batch 噪声、训练步数和学习率缩放效应。
3. 对 L10/L15/L20/L25、时空字段、乘客/司机来源、D→O hidden/logit 输入逐项消融。
4. 明确 `pep-seq` 的代码配置，确认它和 PosSA 的关系。
5. 若转线上，先做序列快照 diff 和模型输出对齐，再评估延迟与业务指标。

## 3. 可研究的升级方向

- **任务交互：** 将 D hidden 或 stop-gradient 的 D logit 输入 O tower，避免真实标签泄漏。
- **特征升级：** 强化司机接驾偏好、订单供需、时空匹配、司乘关系和行为时间差。
- **结构升级：** 统一 OneTrans backbone + role embedding + soft gate，而不是完全独立 driver/pass 分支。
- **稳健性：** 分活跃度、冷启动、区域、时段、长短接驾距离分桶，排查收益是否只来自某些样本。

## 面试一句话

> 当前最重要的不是继续堆模型，而是先用统一训练协议把 PosSA、OneTrans 与优化超参数的贡献拆干净，再判断是否值得线上化。
