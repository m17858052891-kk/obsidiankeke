# 司乘序列面试深挖问答（一）：业务、样本与架构

> **事实边界：** 当前项目是 PEPNet × OneTrans 的**离线建模与实验探索**，没有线上 A/B 或业务收益结论。D 是乘客任务、O 是司机任务、OD 是司乘联合任务；完整字段、token 精确顺序、loss 权重和真实训练配置须以代码为准。

## 一、项目价值与整体叙事

### Q1：这个项目一句话解决什么问题？

它将司机历史、乘客历史、当前订单及上下文统一为 token，由 OneTrans 联合建模，再用 PEPNet 做个性化调节，离线预测乘客、司机和司乘联合行为。核心目标是减少传统统计特征和“先分别编码、再拼接”结构带来的信息损失。

### Q2：为什么不能只用统计特征或普通 MLP？

统计特征将“发生了什么、先后顺序、相隔多久”压成均值/计数，难表达短期状态变化；普通 MLP 也无法主动从长历史中选择与当前订单相关的行为。它们仍是必要 baseline，但对双边时序交互的表达能力有限。

### Q3：为什么要同时建模司机和乘客？

订单结果由乘客需求、司机供给偏好和当前时空供需共同决定，只看单侧会遗漏另一侧的条件。离线结果中，统一 OneTrans 优于司机/乘客完全拆分版本，支持跨侧交互有价值；但这不是对所有场景的普适结论。

### Q4：输入、模型、输出和业务动作分别是什么？

输入是双边历史事件、用户/司机画像、订单和上下文特征；OneTrans 输出共享表征，EPNet/PPNet 分别调节 embedding 与任务隐藏表示，D/O/OD head 给出三个预测分数。当前工作止于离线预测和架构探索，未把预测直接接入线上派单、定价或补贴动作。

### Q5：baseline 是什么，短板是什么？

可从 pep-seq、PLE-seq 等序列/多任务 baseline 出发：它们保留既有结构但较难让静态特征、司机序列和乘客序列在统一 token 空间内早期交互。OneTrans 的对照价值在于验证统一 token 化和混合参数化是否提供额外表达能力。

### Q6：为什么选择 PEPNet + OneTrans？

OneTrans 解决“多种 token 如何统一交互”，PEPNet 解决“不同域/任务下共享表示如何个性化”；两者分工互补。离线表中 pep-seq-onetrans 相比 pep-seq 的 OD/O/D AUC 均有提升，说明该组合是当前较有潜力的方向。

### Q7：个人工作边界怎么说？

应按真实贡献回答，例如：负责样本/序列构造、特征口径审计、OneTrans 与 PEPNet 的组合实验、长度/Batch/过滤消融和结果归因。不要把论文原始模块、未完成线上部署或他人维护的特征服务表述为自己已落地的成果。

### Q8：最可信的离线结论是什么？

在当前记录的同一实验口径下，PEPNet + OneTrans 优于 pep-seq，且统一双边结构优于完全拆分结构；长度、Batch 和过滤方式会显著影响结果。AUC 提升只支持离线区分能力改善，不支持线上 CR、取消率或接驾距离已改善。

### Q9：离线 AUC 提升代表什么，不代表什么？

AUC 表示随机抽取一对正负样本时模型将正样本打分更高的概率，说明排序区分能力更好。它不代表概率已校准、特定阈值收益更高，也不代表因果或线上业务收益提升。

### Q10：只保留一个创新点会保留什么？

我会保留“统一 token 化的双边序列—静态特征联合建模”：让司机、乘客、订单和上下文在被过早压缩前发生交互。PEPNet 的门控和多任务 head 是在这个统一表征基础上进一步解决域/任务差异。

## 二、任务、标签与样本锚点

### Q11：D、O、OD 分别是什么？

D 是乘客任务，O 是司机任务，OD 是司乘联合任务；它们分别用对应业务行为标签训练独立 head。现有材料未给出三个标签的完整业务字段定义，面试时应说明“精确 label 口径以样本 SQL/代码为准”，避免虚构具体事件。

### Q12：为什么多任务而非三个独立模型？

三任务共享订单、时空和双边历史信息，联合训练可让样本量更大的任务为其他任务提供表征监督。代价是梯度冲突，所以不能只共享底座后等权相加，需要监控任务损失、AUC 和可能的负迁移。

### Q13：三个任务有什么关系？

它们共享同一司乘交易场景，但预测对象和标签不完全相同，因此既有共同因素也有任务特异因素。OD 可以学习双边共同结果，D/O 学习单侧响应；这正是共享 backbone 加任务个性化 gate 的动机。

### Q14：样本锚点是什么？

稳妥定义是“当前司乘订单/请求在模型作出预测的时刻”，并以该时刻作为所有历史序列和特征窗口的右边界。具体是冒泡、发单、派单还是应答阶段，必须从实际任务样本左表确认，不能由模型结构倒推。

### Q15：为什么预测时刻必须先定义？

因为它决定哪些状态可见、哪些行为属于历史，以及标签是否泄漏。例如预测当前订单的响应时，当前订单结果、后续应答/取消/完单都不能进入输入；只要锚点模糊，任何“历史统计”都可能穿越。

### Q16：如何证明没有 label leakage？

为每个特征记录事件时间和可用时间，强制 `feature_time < anchor_time`；历史 join 使用严格早于锚点的条件，并检查同订单、未来分区和结果字段没有回填。还应做抽样回放：对单条样本打印锚点、历史末事件和标签时间进行人工核验。

### Q17：取消、无应答、异常、改派样本怎么处理？

首先按任务定义决定它们是负样本、单独状态还是剔除样本，不能为了提高 AUC 任意过滤。处理后必须报告保留比例、各类样本标签分布和对训练/验证口径的影响；改派或多阶段订单尤其要避免同一事实被重复计数。

### Q18：正负样本比例和样本权重为什么重要？

极度不平衡时 BCE 梯度可能被大量简单负例主导，AUC 也可能掩盖关键正样本表现；可考虑权重、难负样本或采样。当前材料未确认实际负采样和权重，因此只能说应以代码核对，并在真实分布验证 LogLoss/校准。

### Q19：三个任务各看什么指标？

离线可先分别看 D/O/OD 的 AUC，且应补充 LogLoss、校准、正负样本切片、城市/时段/新老用户或司机切片。若任务最终服务于排序，还应检查同请求或同订单候选内的排序指标，而不能只报全局 AUC。

### Q20：OD 是 D 和 O 的简单组合吗？

不是简单将两个单侧分数相乘或相加；它应由自己的任务 head 学习司乘共同发生的条件。三者有关联但标签、难度和最优表征可能不同，因此保留独立输出头更合理。

### Q21：将 D 输入 O 会不会泄漏？

若输入的是当前样本的真实 D 标签，必然泄漏；若输入的是同一前向中由可见特征生成的 D 预测或表示，则理论上不泄漏，但会引入误差传播与训练—推理不一致风险。当前资料把 D→O 视为待验证消融，而不是已经确认有效的模块。

### Q22：某任务无标签时怎么办？

该样本仍可用于有标签任务的 loss，缺失任务通过 mask 不回传对应 head 的 loss；共享底座仍接收其他任务梯度。必须区分“真实未发生”与“标签缺失/不可观测”，否则会把缺失误当负样本。

## 三、序列与特征

### Q23：司机和乘客序列包含什么？

它们由各自历史订单/行为事件组成，事件可携带时间、时空、价格、状态、行为类型等字段。完整字段清单在当前材料中未固化，面试应讲清设计原则：每一项都必须在锚点前可得，并与当前任务有明确行为语义。

### Q24：历史事件应以什么粒度存储？

通常以一次可排序、可复现的订单或行为事件作为一个 token；若同订单存在多个阶段，需明确是拆阶段还是聚合为订单快照。选择标准是标签预测时能否获得、是否保留对决策有用的顺序和状态变化。

### Q25：序列按什么排序？

按事件可用时间升序，当前样本只读取锚点前历史；时间相同的事件需给确定性的次级排序键，如事件类型优先级或唯一事件 ID。无稳定排序会导致训练和推理 token 顺序随机，从而破坏时序含义。

### Q26：历史窗口和最大长度如何选？

先由业务记忆周期、存储成本和线上可获取范围提出候选，再做严格长度消融。当前记录中长度 20 优于 10、30、40，但这只在对应数据、特征和训练配置下成立，不能抽象成通用最优长度。

### Q27：长序列为何可能退化？

更久历史可能与当前状态弱相关、噪声更大，且 padding、计算和优化难度增加；固定 token budget 下还可能挤掉更关键的近期信息。长度增益应由验证集与切片共同判定，而不是默认“更多信息更好”。

### Q28：截断如何做？

最基础是保留最近 (L) 个严格早于锚点的事件；若业务证明长期兴趣重要，可加入分层采样、时间衰减或 summary token。无论哪种方式，训练和推理必须使用相同排序和截断规则。

### Q29：双边长度不一致如何处理？

可分别截断并在 batch 内 padding/mask，或用 ragged 表示减少无效计算；统一 tokenizer 仍需保留 role/type 标记。关键不是强行把两侧补成等长，而是让模型知道 token 来自哪个角色及其时间位置。

### Q30：同一订单重复进入两侧历史怎么办？

它可以作为司机和乘客各自的历史事实存在，但需确认当前目标订单没有被放入历史，也要避免重复 join 造成同侧重复 token。若同一事件在两侧保留，role embedding 使模型区分“司机视角”和“乘客视角”。

### Q31：如何防止当前订单进入历史？

join 条件除 `event_time < anchor_time` 外，还应排除相同 order/request ID；对于同秒事件，要使用可用时间和稳定次序确保当前事件不提前出现。抽样检查当前订单 ID 是否出现在任一历史数组中是必要的单测。

### Q32：短时间乘客序列过滤为什么不能直接说有效？

过滤可能去掉噪声很大的短序列，也可能只是改变样本量、活跃度分布和任务难度；当前实验记录明确指出存在这种混杂。应在保持样本量/分布尽可能一致的对照中验证，或报告分层效果。

### Q33：召回与排序序列如何保持一致？

应统一事件定义、时间右边界、去重、排序、截断、缺失填充和词表版本；两阶段可用不同长度，但必须能解释差异。当前项目把“召回序列线上一致性 check”列为待落实事项，因此不能声称已经完全解决。

### Q34：静态特征为什么也要 token 化？

用户、司机、订单和上下文不是只有最终 MLP 才能使用的附加信息；变成 NS-token 后，它们可以在 attention 中与历史事件交互，影响“模型从哪些历史读取什么”。这样避免先压缩序列再拼接静态向量造成的信息隔离。

### Q35：稀疏、连续和事件特征怎么编码？

稀疏 ID 用 embedding，连续值经归一化/投影，事件 token 将多字段嵌入融合后加入 type、role 和时间信息。精确的字段融合和投影维度属于实现细节，应以代码为准。

### Q36：为什么不直接拼统计特征？

统计特征高效且应保留，但它们是历史压缩摘要，通常丢失顺序和条件相关性；序列 token 允许模型按当前订单选择相关历史。合理方案不是二选一，而是让统计特征作为上下文/NS-token，与事件序列互补。

### Q37：S-token 与 NS-token 是什么？

S-token 指相对同质、可重复出现的历史序列事件；NS-token 指用户、司机、订单、上下文等语义不同的非序列字段组。区分它们使模型可以对同质事件共享参数、对异质实体保留专属参数。

### Q38：token 排列为什么重要？

在 causal attention 中，排在前面的 token 才能被后面读取，排列直接决定信息方向；即使非 causal，位置和 role 也影响注意力模式。当前材料没有确认精确排列和是否严格时间交错，因此应说明原则而非编造具体顺序。

### Q39：role/time embedding 有什么作用？

role embedding 告诉模型 token 是司机、乘客、订单还是上下文，避免同一数值向量被误解为同类事件；时间/位置编码表达先后与间隔。两者共同让 attention 知道“谁在何时发生了什么”。

### Q40：如何处理 OOV、冷启动和低频 ID？

使用 OOV/UNK bucket、共享层级特征和默认/缺失 token，避免线上新 ID 直接查表失败；冷启动样本要单独评估。只靠随机初始化的新 embedding 通常不稳定，静态上下文和群体特征可提供回退信息。

## 四、PEPNet 与 OneTrans

### Q41：EPNet 解决什么？

EPNet 在 embedding 侧根据 domain/场景先验生成逐元素 gate，使共享 embedding 可随场景自适应。它解决的是“同一个 ID 或特征在不同场景下语义/重要性不同”，不是重新训练一套独立 embedding 表。

### Q42：PPNet 解决什么？

PPNet 在更上层的 hidden representation 上，根据用户、司机、订单等先验生成 task/domain gate，调节不同任务使用共享表示的方式。直觉上，EPNet 调“底层看见什么”，PPNet 调“高层如何用于具体任务”。

### Q43：为什么 gate 用逐元素乘法？

逐元素缩放参数量和计算量低，能对不同 embedding/hidden 维度进行细粒度强调或抑制，同时保持原表示空间。生成完整矩阵虽然更灵活，但成本高且更易过拟合。

### Q44：为什么 gate 范围设计为 0 到 2？

以 (2\sigma(\cdot)) 为例，1 对应不改变原表示，低于 1 是抑制、高于 1 是增强；相比只在 0 到 1 内，模型不只能“关掉”，还能放大重要维度。具体实现和范围应以实际代码确认。

### Q45：EPNet 为什么使用 stop-gradient？

stop-gradient 用于避免 gate 的先验输入或共享部分被反向路径过度耦合，使门控学习更稳定、减少通过改变 gate 输入投机降低 loss 的可能。它不是“完全不训练 embedding”，而是控制特定支路的梯度流。

### Q46：OneTrans 相比传统双 encoder 有何不同？

传统结构常先分别将司机/乘客序列压成向量，再与静态特征交互；OneTrans 将序列与非序列 token 放入统一 Transformer，使交互发生在压缩之前。代价是 token 数更多、mask 和参数化设计更复杂。

### Q47：为什么不能完全拆成两套 Transformer？

完全拆分降低了司机与乘客历史之间直接交互的机会，也让当前订单/上下文只能在后期融合；当前离线结果显著低于统一版本。更严谨的说法是“该数据与配置下，完全拆分不如统一建模”，不是说任何双塔都一定差。

### Q48：完全共享一个 Transformer 又有什么问题？

司机历史事件、乘客历史事件与订单/上下文字段的语义和分布不同，完全共享所有参数可能产生负迁移。OneTrans 通过 S-token 共享、NS-token 专属的混合参数化，在共享统计规律和保留异质语义间折中。

### Q49：什么是 Mixed Parameterization？

对相对同质的 sequence token 共享 attention/FFN 参数，对语义差异大的 non-sequence token 使用 token-specific 参数或投影。它不是每个样本生成一套模型，而是按 token 类型选择不同参数路径。

### Q50：为什么 S-token 共享参数？

历史事件尽管来自不同司机或乘客，本质上都遵循“事件序列中的状态变化”这一可复用模式；共享参数能提升样本利用率并控制模型规模。role/type embedding 仍保留来源差异。

### Q51：为什么 NS-token 需要专属参数？

用户画像、司机画像、订单属性和上下文条件的字段语义异质，强行共用同一投影/FFN 容易混淆统计分布。专属参数允许各类静态 token 以更合适的方式进入统一空间。

### Q52：Mixed Causal Attention 如何防穿越？

mask 应保证当前预测 token 只能读取锚点前可见历史与当前可用上下文，不能读取未来事件或结果 token；同时允许业务上合理的跨侧历史交互。精确 mask 矩阵需由代码确认，面试不能把推测的排列当事实。

### Q53：OneTrans 的 attention 在学习什么？

它可学习“当前订单和供需上下文下，哪些司机/乘客历史行为更相关”，例如近期同类行程、价格敏感、接驾偏好或时空状态变化。不是任意地把所有历史平均融合，而是条件化分配信息读取权重。

### Q54：Pyramid 为什么存在？

长序列 token 两两交互和逐 token FFN 都昂贵，Pyramid 逐层压缩 token 数，降低后续层的计算与显存。代价是细粒度信息可能丢失，因此要在长度、压缩率和离线指标间消融。

### Q55：KV Cache 在当前项目中是什么定位？

它是潜在的推理复用思路：相同司机/乘客历史在同一请求的多个候选或相邻请求中不必反复计算 K/V。当前项目没有线上时延、QPS 或缓存命中率结果，不能声称 KV Cache 已上线获益。

### Q56：为什么使用 RMSNorm / Pre-Norm？

Pre-Norm 为残差主干保留更直接的梯度路径，RMSNorm 用更简单的尺度归一化稳定深层训练；这与 OneTrans 的深层 attention/FFN 堆叠相适配。具体层位置仍应以实现为准。

### Q57：OneTrans 最容易犯的实现错误是什么？

最危险的是 mask 或 token 时间顺序错误导致未来泄漏；其次是训练/推理 tokenizer、padding、role/type embedding 或截断规则不一致。统一结构越强，任何一处错位造成的污染范围也越大。
