# 3.6 Buffer 自动调整项目总结

> 总结日期：2026-09-03  
> 当前状态：baseline 与 guardrail 的正式/空跑 PySpark 已实现；当前处于空跑分析和上线前核对阶段。

## 1. 项目背景

现有联合决策 buffer 主要依赖人工配置。由于城市实际供需补贴率会受流量、完单 GMV、核销延迟和实验分组等因素影响，目标补贴率与实际补贴率之间容易长期存在偏差。

人工调整需要逐城市观察实花并反复修改 buffer，维护成本高，也难以稳定覆盖城市和 LambdaGroup 维度。因此，本项目在现有发布链路前增加日级自动校准能力，让 buffer 根据目标率与实际率的偏差自动递推。

## 2. 项目目标

项目希望实现以下能力：

- 按城市和 LambdaGroup 每日计算 buffer；
- 周一至周四、周五至周日分别维护两条状态链；
- 实际少花时提高 buffer，实际超花时降低 buffer；
- 实验切流、目标率无效或实际率无效时不调整；
- 输出表继续兼容现有发布字段和 `dt` 分区；
- baseline 与 guardrail 使用相同框架，仅替换目标率表和输出表；
- 支持每日独立空跑以及上线后的连续状态递推。

自动任务只负责计算并落表，不重新执行全国预算腾挪，也不修改策略目标补贴率表。最终线上发布仍由下游发布任务完成。

## 3. Buffer 的含义

Buffer 是作用在策略补贴率上的乘法调节系数：

```text
buffer > 1：放大补贴
buffer = 1：不调整
buffer < 1：缩小补贴
```

它的作用是根据历史目标率和实际率偏差，修正下一期同类型状态，使实际补贴率逐步接近目标补贴率。

## 4. 当前整体方案

每日任务按照以下顺序执行：

```text
生成城市 × LambdaGroup 键空间
→ 读取同日期类型上一期 old_buffer（正式）或固定为 1（空跑）
→ 读取同日期类型上一期目标率
→ 读取并聚合同日期类型上一期实际率
→ 检查自然日 T-1 是否切流
→ 执行不调整判断或 buffer 公式
→ 写入当天 dt=T 分区
```

### 4.1 键空间

```text
dim_city.dt=T 的 distinct city_id
× platform_greedy_solver_lambda_dict 的 distinct stg_group
× object_group=max_order_v1
```

结果业务键为：

```text
dt + city_id + object_group + stg_group
```

其中 `stg_group=LambdaGroup`。实验组与 LambdaGroup 的映射由运筹平台负责，自动 buffer 任务不使用实验组作为关联键。

### 4.2 日期类型

- weekday：周一至周四；
- weekend：周五至周日；
- `T^-d`：与 T 同日期类型、且早于 T 的最近一期；
- old buffer、目标率、实际率均读取 `T^-d`；
- 切流只检查自然日 `T-1`；
- 新结果始终写入 `dt=T=${BIZ_DATE_LINE}`。

典型边界：

```text
周五 T → 回看上周日
周一 T → 回看上周四
```

因此两条状态链不会在周四到周五、周日到周一之间串用。

### 4.3 目标率

目标率为城市粒度，进入计算后按 `city_id` 展开到该城市的全部 LambdaGroup。

| 策略 | 目标率表 | 字段 |
|---|---|---|
| baseline | `kflower_strategy.platform_price_anchor_union_strategy_budget_dict` | `total_subsidy_rate` |
| guardrail | `kflower_strategy.platform_price_anchor_union_strategy_budget_guardrail_dict` | `total_subsidy_rate` |

当前代码读取 `dt=T^-d`。

### 4.4 实际率

实际数据来自：

```text
kflower_strategy.pltf_union_stg_budget_control_dashboard
```

看板中同一 `city_id + lambda_group` 可能包含多个实验组。任务排除全国、城市汇总和未分组 Lambda 后，统一汇总金额和 GMV：

```text
actual_rate
= ROUND(
    (SUM(cost) + SUM(delay_cost))
    / SUM(gmv_amt)
    * 100,
    2
  )
```

最终实际率粒度为：

```text
city_id + LambdaGroup
```

它通过 `city_id + stg_group` 与 buffer 键空间关联。

### 4.5 切流

切流数据来自：

```text
kflower_strategy.pltf_union_stg_exp_evaluation_pas_tag
```

在自然日 `T-1` 内，只要任一 PID 命中多个 `exp_group`，就认为存在实验切流。当次任务全部键不调整：

```text
new_buffer = old_buffer
```

切流是一个全局布尔判断，不需要映射到城市或 LambdaGroup。

### 4.6 计算公式

正常调整：

```text
raw_buffer = old_buffer × target_rate / actual_rate
new_buffer = min(2.99, raw_buffer)
```

不调整条件：

- 自然日 `T-1` 发生切流；
- 目标率缺失或小于等于 0；
- 实际率缺失或小于等于 0。

当前只设置 `2.99` 上限，不设置下限和单日调整比例上下限。因此很低的正 buffer 符合当前算法定义，并不直接表示代码错误。

## 5. 正式与空跑架构

### 5.1 正式任务

正式任务读取自身输出表同日期类型上一期的 `union_buffer` 作为 `old_buffer`。具体城市或分组没有历史值时，按键初始化为 `1.0`。

| 策略 | 正式脚本 | 输出表 |
|---|---|---|
| baseline | `auto_buffer_job.py` | `platform_union_strategy_budget_buffer_auto_baseline_by_city_object_stg` |
| guardrail | `auto_buffer_job_new.py` | `platform_union_strategy_budget_buffer_auto_guardrail_by_city_object_stg` |

### 5.2 空跑任务

空跑任务不读取历史 buffer，每天令所有键：

```text
old_buffer = 1.0
```

因此每天结果是目标率与实际率比例的独立快照，不会累计前一天结果。

| 策略 | 空跑脚本 |
|---|---|
| baseline | `reset_previous_buffer_for_dry_run.py` |
| guardrail | `reset_previous_buffer_for_dry_run_new.py` |

空跑和正式任务当前写相同结果表；同一天运行会互相覆盖，正式上线前必须停止空跑调度。

## 7. 排查过程与关键结论

### 7.1 早期 buffer 全部为 1

根因不是公式没有执行，而是 LambdaGroup 无法关联：

```text
旧 manually_update 字典：
pltf_union_stg_v2_only_ds
pltf_union_stg_v2_only_ds_only_box

实际率看板：
pltf_union_stg_v3_only_ds_acc_cr_thre
```

目标/实际输入关联失败后触发“不调整”，空跑结果自然全部为 1。改用 `platform_greedy_solver_lambda_dict` 后，活跃 V3 LambdaGroup 可以命中实际率。

### 7.2 实际率行数异常膨胀

看板保留 `exp_group` 维度，同一城市和 LambdaGroup 可能对应多个实验组。因此不能删除实验组字段后直接假设唯一。

当前解决方式是先汇总：

```text
GROUP BY city_id, lambda_group
SUM(cost), SUM(delay_cost), SUM(gmv_amt)
```

再计算唯一的 `actual_rate`，避免关联后把 buffer 结果重复展开。

### 7.3 8 月 31 日分布与其他日期不同

空跑中 old buffer 每天都是 1，因此分布差异完全来自 `target_rate / actual_rate`。

8 月 31 日是周一，读取的是 weekday 上一期 8 月 27 日，而不是自然日前一天 8 月 30 日。8 月 27 日输入比例分布更极端，因此 baseline 在 8 月 31 日出现更多低于 1 和命中 2.99 的记录。

该现象符合当前日期类型算法，但提醒我们必须单独关注周一、周五的跨类型边界。

### 7.4 大量 buffer 等于 1

等于 1 不一定表示目标率恰好等于实际率，还可能来自：

- 城市没有目标率；
- 目标率小于等于 0；
- 城市与 LambdaGroup 没有实际率；
- 实际率小于等于 0；
- 自然日 `T-1` 发生切流；
- 字典中存在未生效 LambdaGroup。

因此上线验收必须同时统计“不调整原因”，不能只看 buffer 分位数。

## 8. 当前结果判断

目前空跑结果从代码机制上可以解释：

- 中位数、p75、p90 多数为 1，说明绝大多数键没有调整；
- 少量大于 1 的结果会把平均值拉高；
- 原始结果超过 2.99 时正确截断；
- 极低正值来自目标率/实际率比例，当前无下限，因此属于预期输出；
- baseline 与 guardrail 使用不同目标率表，分布不需要完全一致。

不过“代码结果可解释”不等于“业务上已经可以直接发布”。极端低值、连续上限和大量不调整仍需结合原因拆解评估。

## 10. 项目总结

本项目完成了城市 × LambdaGroup 粒度的日级自动 buffer 校准框架，将人工 buffer 调整转化为由目标补贴率、实际补贴率和历史状态共同驱动的自动递推过程。方案支持 weekday/weekend 双状态链、实验切流冻结、异常输入保持、2.99 上限以及 baseline/guardrail 双策略输出。

工程上已经打通建表、空跑、正式递推和上线前重置的主要环节，并解决了 LambdaGroup 命名不一致、实际率多实验组重复和目标/实际日期对齐等关键问题。当前重点从“能否正确计算”转向“上线前输入就绪、活跃分组筛选、极端值风险和调度互斥”的最终核验。
