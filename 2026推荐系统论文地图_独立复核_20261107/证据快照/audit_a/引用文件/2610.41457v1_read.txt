Abstract.

Modern recommender models scale sparse representations and dense computation together. They process thousands of heterogeneous feature fields, long user-behavior sequences, and trillion-scale Embedding parameters, while their dense networks increasingly use large Transformer architectures. The resulting execution mismatch creates fine-grained operations within stages, load imbalance and synchronization delays across devices, and GPU resource bubbles between stages. As models grow, these costs become a primary limit to scalable recommender training. Although existing systems improve Embedding caching and data prefetching, these inefficiencies still coexist in the GPU-centric workloads we study and jointly limit end-to-end throughput.

We present RecIS, a unified framework for GPU-centric recommender training. RecIS treats the complete path from input features to dense computation as one optimization target and coordinates three complementary mechanisms. First, adaptive fusion combines fragmented feature transformations with vectorized memory access. Second, a GPU Embedding engine uses hash-based sharding and hierarchical communication to balance request placement and eliminate redundant transfers; it also specializes aggregation for forward and backward index structures. Third, a multistage pipeline overlaps input preparation for future iterations with dense computation in the current iteration. Together, these mechanisms reorganize a fragmented sparse front end into a dataflow that continuously feeds dense computation.

We evaluate RecIS on representative industrial recommender models across distributed training platforms. Compared with PICASSO and TorchRec, RecIS reaches up to 2.62\times and 1.15\times their throughput, respectively, while reducing step latency by up to 61.5% and 12.9%. RecIS provides an efficient and scalable training system for large recommender models.

Recommender systems, GPU training, Embedding communication, Operator fusion, Pipeline scheduling

1. Introduction

Modern recommender training places two nearly opposite execution paradigms on the same GPU dataflow. The sparse front end processes thousands of heterogeneous feature fields, long behavior sequences, and trillion-scale embedding parameters through fragmented transformations, random lookups, and irregular communication (Naumov et al., 2019; Acun et al., 2021; Zhang et al., 2022). The dense back end is evolving toward billion-parameter Transformers and sparse mixture-of-experts models (Vaswani et al., 2017; Fedus et al., 2022; Zhai et al., 2024; Yan et al., 2026) that require regular, continuous, and compute-intensive tensor pipelines. As both sides scale, the central systems challenge is no longer to accelerate sparse or dense components in isolation. It is to reorganize fragmented, skewed, and unevenly arriving sparse work into a stable stream that continuously feeds dense computation.

This mismatch creates a chain of bottlenecks whose effects compound along the dataflow. Thousands of variable-length transformations decompose input processing into small kernels and scattered memory accesses. Skewed feature accesses further create imbalanced embedding lookups and all-to-all communication, allowing the slowest device to determine the iteration time. Coarse iteration boundaries finally expose sparse-side tail latency to the dense network, leaving compute, memory, and communication resources idle in turn. In other words, task granularity determines sparse execution efficiency, device load determines its tail latency, and iteration scheduling determines whether that latency can be hidden by dense computation. Existing systems improve operator packing, embedding caching, or data prefetching (Zhang et al., 2022; Ivchenko et al., 2022; Pan et al., 2024; Agarwal et al., 2023), but these mechanisms are generally designed around a particular stage or a fixed execution boundary. When the three problems occur together, accelerating one stage can simply move the bottleneck to the next point in the dataflow.

We present RecIS, a unified framework for GPU-centric recommender training. RecIS treats the path from raw features to dense computation as a schedulable dataflow and reorganizes sparse work at three connected levels:

• 

Across operators. Adaptive fusion regularizes task granularity by grouping compatible transformations across fields into fewer CUDA kernels while preserving dependencies. Vectorized memory access reduces instruction overhead and improves bandwidth utilization.

• 

Across devices. Hash-based sharding distributes ownership of distinct IDs across workers in expectation. Hierarchical communication merges requests within each source node to reduce inter-node traffic, then deduplicates requests at each owner to reduce physical lookups. Index-aware aggregation reduces irregular memory access and atomic contention.

• 

Across iterations. The multistage pipeline overlaps future input preparation that is independent of parameter updates with current dense computation, using their complementary resource demands to hide sparse-side overhead.

Together, these mechanisms reduce sparse-stage overhead and overlap the remaining preparation work, allowing the sparse front end to feed dense computation more continuously. The source code of RecIS is publicly available at https://github.com/alibaba/recis.

2. Background and Motivation

2.1. Feature-Preprocessing Bottlenecks

GPU-centric training systems increasingly move feature preprocessing from CPUs to GPUs (Zhang et al., 2022; Pan et al., 2024). Offloading hashing, bucketization, and sequence truncation does not by itself ensure high throughput.

Production models contain thousands of heterogeneous feature fields, each with a chain of two to five preprocessing operations. Executing each field independently launches many short kernels, whose launch and scheduling overhead can exceed their useful computation (Figure 1). Fusion reduces these costs, but feature fields differ in both operator dependencies and sequence lengths. Small fusion groups leave substantial launch overhead, whereas overly coarse groups can introduce divergence and long-running tasks. Effective fusion must therefore account for both the operator structure and the distribution of input sizes.

Memory access presents a separate constraint. Hashing and modulo operations have low arithmetic intensity and are often limited by global-memory bandwidth (Williams et al., 2009). Scalar accesses add memory instructions and can underutilize the bandwidth available to contiguous, aligned transfers.

Figure 1. A profiling timeline exposes fragmented feature-preprocessing work and frequent kernel launches.A GPU timeline contains many short preprocessing kernels separated by launch and scheduling gaps.

2.2. Repeated Requests and Embedding Imbalance

Embedding accesses are highly skewed. Popular IDs recur both within and across GPUs, amplifying lookup and communication work. Even a balanced distribution of stored parameters need not yield a balanced distribution of requests. Table-wise and contiguous row-wise sharding place parameters by table size or ID range, which need not match the access distribution of a particular batch (Ivchenko et al., 2022; Ma et al., 2023; Zhang et al., 2022). Unequal lookup and all-to-all traffic loads leave dense computation waiting for the slowest device.

Aggregation remains expensive after requests reach their owners. Forward outputs follow ordered compressed sparse row (CSR) segments defined by offsets, whereas backward contributions can target embedding rows in an arbitrary and highly concentrated order. Using the same element-wise atomic scatter for both paths introduces unnecessary forward atomics and contention at popular rows during backward execution. The embedding engine must therefore address request imbalance, duplicate accesses, and index-dependent aggregation costs together.

2.3. Idle Time at Iteration Boundaries

Training systems commonly organize execution around fixed iteration boundaries. Even with prefetching or local communication overlap, input I/O, feature processing, embedding operations, and dense computation often follow a largely sequential schedule. Our profiling shows that these stages stress different resources. Executing them in sequence leaves compute, memory, and I/O resources idle at different points in the iteration.

Some of this idle time comes from scheduling constraints rather than data dependencies. Work independent of parameter updates can begin before the current iteration finishes. However, prefetching a single batch is insufficient when preparation exceeds the available overlap window, and unrestricted background execution can interfere with dense kernels. Effective scheduling must expose more parallelism while preserving parameter consistency and controlling contention.

3. RecIS System Design

RecIS jointly optimizes feature preprocessing, distributed embedding operations, and pipeline scheduling. Each component reduces overhead that would otherwise delay the next stage of the sparse-to-dense dataflow.

3.1. Fused and Vectorized Feature Processing

FeatureEngine addresses kernel-launch overhead, work imbalance across feature fields, and inefficient scalar memory access.

Dependency-aware fusion.

Feature fields differ in both their transformation chains and input lengths. Small fusion groups retain substantial launch overhead, whereas overly coarse groups can introduce divergence and long-running tasks. FeatureEngine therefore fuses independent operations of the same category while preserving the dependencies of each feature.

The transformations in Figure 2 include bucketization, modulo, hashing, sequence truncation, and masking. The scheduler first topologically orders these operations. For example, SeqTrunc must finish before Hash for Feature 4. Independent operations from other fields can join the same fusion group when they are of a compatible category. Fusion thus shares execution across fields without reordering a dependent transformation ahead of its input.

For F feature fields, let d_{i} be the number of operations on field i and \mathcal{G} the resulting fusion groups. The kernel-launch counts satisfy

Each group replaces multiple launches when fields share compatible transformations; otherwise, the inequality allows equality.

Thread mapping for skewed inputs.

Fusion exposes more work to each kernel, but equal treatment of feature fields would not imply equal work for threads. Long behavior sequences can contain many more elements than short categorical fields. Static assignment by field would carry this skew into the fused kernel, leaving some threads idle while others process long sequences.

FeatureEngine flattens elements across fields into one logical index space and partitions it into equally sized tiles. A grid-stride mapping distributes these tiles to threads, which use feature-boundary indices to locate the corresponding input intervals. Work is therefore divided by element count rather than by the number of fields. This mapping reduces idle threads and limits the execution tail of long inputs without changing the transformation assigned to each element.

Vectorized memory access.

Fusion does not by itself eliminate memory-instruction overhead. Hashing and modulo have low arithmetic intensity and are often limited by memory bandwidth (Williams et al., 2009). Element-wise operators use fixed-width vector loads and stores where dependencies, alignment, and boundaries permit. Packed kernels process groups of elements; select_pack_size selects the largest valid pack at compile time, with up to 16 bytes accessed per thread per memory instruction. Smaller valid packs accommodate stricter alignment or boundary constraints. Contiguous, aligned transfers reduce instruction count and improve effective bandwidth.

Per-feature transformation chains are reordered by dependency and combined into shared kernels for compatible operator categories.

Figure 2. FeatureEngine preserves operator dependencies while fusing compatible transformations across feature fields.Per-feature transformation chains are reordered by dependency and combined into shared kernels for compatible operator categories.

In summary, FeatureEngine regularizes feature preprocessing through these three complementary mechanisms, consolidating thousands of heterogeneous transformation chains into a small set of regular, high-throughput GPU kernels. This design improves data preparation for subsequent embedding lookups and pipelined execution across stages.

3.2. Embedding Engine with Hierarchical Communication

Hash-based sharding.

Balanced storage need not imply balanced requests: table-wise and contiguous row-wise placement can concentrate popular tables or ID ranges. RecIS hashes IDs to spread ownership across workers in expectation, reducing this dependence on table size or ID range. Sharding distributes distinct IDs; repeated requests for the same ID still require deduplication.

Hierarchical communication.

Flat communication (Figure 3(a)) deduplicates IDs per GPU but still sends separate requests for IDs shared across GPUs. RecIS merges these requests within each source node over NVLink, routes them to their owners over same-rail links, and distributes each returned vector locally to the requesting GPUs.

Figure 3(b) shows the forward path. Each deduplication stage retains an inverse map for restoring the original requests.
\ding Local Reduce-ID: each GPU removes duplicate IDs from its local requests.
\ding Intra Shuffle-Reduce-ID: NVLink routes requests to the source-node GPU with the same local GPU index as the owner, where duplicates from different GPUs are merged.
\ding Inter Shuffle-Reduce-ID: same-rail groups connect corresponding GPUs across nodes and route remote requests to their owners, which merge duplicates from all source nodes.
\ding Lookup Embed: each owner performs one lookup per unique ID in its local shard.
\ding Inter Flatten-Shuffle-Embed: the inverse map from step \ding expands responses for return over the same rails, with one vector per ID per remote source node.
\ding Intra Flatten-Shuffle-Embed: the inverse map from step \ding expands vectors for NVLink delivery to the requesting GPUs.
\ding Local Flatten-Embed: the inverse map from step \ding restores the original request order and multiplicity.

Index-aware segment reduction.

Restoring gathered embeddings to the original ragged layout requires weighted segment aggregation. Let \mathbf{E}\in\mathbb{R}^{U\times D} denote the unique embedding matrix, \mathbf{o} the CSR offsets defining S segments, \mathbf{i} the reverse indices mapping N contributions to embedding rows, and \mathbf{w} their weights. Although forward and backward share the same reduction semantics, their destination indices exhibit different access patterns, motivating specialized GPU kernels. Algorithm 1 outlines their execution workflows.

Forward.
The CSR offsets define a contiguous contributor range [o_{s},o_{s+1}) for each output segment s. RecIS directly traverses these ranges and computes \mathbf{Y}_{s,:}=\sum_{r=o_{s}}^{o_{s+1}-1}w_{r}\mathbf{E}_{i_{r},:}. Each thread owns one or more non-overlapping feature packs of an output segment, gathers the corresponding embedding values, and accumulates the weighted sum in registers. Once the segment is processed, the thread commits its result through a vectorized store. Even when embedding IDs repeat within a segment, all contributions to each output element are handled by its unique writer. Empty segments produce zero. This ownership-based mapping eliminates global atomic operations and their associated read-modify-write traffic.

Backward.
In contrast, backward scatters gradients to embedding rows indexed by \mathbf{i}, whose entries may appear in arbitrary order and contain highly frequent duplicates. Each contributor r generates w_{r}\mathbf{G}_{s(r),:}, where s(r) is its forward segment ID and \mathbf{G} is the output gradient. RecIS assigns a group of GPU lanes to each contributor row. Lanes cooperatively load contiguous feature packs, then redistribute values through shuffle operations to enable coalesced feature-wise updates. Within each wave, row groups with identical destination IDs are identified and their contributions are reduced using lane shuffles. Only the leader row group performs atomic additions for the merged feature values. For k contributions targeting the same row within a wave, this reduces the number of scalar atomic updates from kD to D. Contributions targeting the same row across different waves or thread blocks are still combined through global atomics, preserving correctness without sorting destination indices.

3.3. Multistage Pipeline Execution

Fixed iteration boundaries can serialize input preparation with dense computation even after the feature and embedding engines reduce sparse-stage costs. A largely sequential schedule leaves different resources idle at different times. The multistage pipeline in RecIS begins independent work earlier while preserving the dependencies of parameter access and updates.

Resource demands and dependencies.

Two observations guide scheduling. First, stages stress different resources. Input I/O uses host processing and interconnect bandwidth; feature transformations and request formatting mainly consume memory bandwidth; physical embedding lookup accesses device memory; and dense forward and backward passes mainly use Tensor Core computation. Overlapping these partly complementary demands can use otherwise idle capacity.

Second, iteration boundaries can impose waits beyond those required by training semantics. RecIS restricts asynchronous cross-iteration preparation to modules that do not participate in backpropagation and do not depend on parameter values updated by the current iteration. Input loading, feature transformation, and ID request formatting satisfy these conditions and can proceed before the current update finishes. Physical embedding lookup, dense forward and backward computation, and all parameter updates remain in the main training workflow with their original ordering dependencies. In particular, preparation does not prefetch embedding values. The next iteration reads them only after the preceding updates on which it depends have completed. This separation preserves parameter-access and update semantics while allowing independent preparation to overlap training.

Stage decomposition and scheduling.

We divide each iteration into six stages: SPARSE_FORWARD, DENSE_FORWARD, METRICS_OP, BACKWARD, OPTIM_STEP, and PRE_FORWARD. SPARSE_FORWARD performs physical embedding lookups. PRE_FORWARD contains input I/O, feature transformations, and embedding request formatting and partitioning. Stage descriptors distinguish this preparation from the parameter-dependent training path.

Figure 4 shows the resulting schedule. Iteration t follows its dependency order on the default stream. Independent preparation for subsequent iterations runs in a separate asynchronous workflow, the Group Stream, alongside compatible current-iteration stages. For example, input loading, feature transformations, and request formatting for iteration t+1 can overlap DENSE_FORWARD of iteration t. The prepared requests then feed SPARSE_FORWARD when its parameter dependencies are satisfied. The overlap pattern is configurable to suit the dependencies and resource demands of each model.

A comparison of serial and overlapping schedules shows future-iteration preparation on a Group Stream alongside current computation on the default stream.

Preparation depth and contention.

Preparation time varies with the model and input. Prefetching a single batch is insufficient when this work exceeds the available overlap window: the unhidden remainder still delays the next iteration. RecIS supports multiple preparation stages that distribute work across threads and asynchronous streams. Figure 4 illustrates preparation for successive iterations in separate Group Stream workflows, allowing preparation to extend beyond the overlap window of a single iteration.

More concurrency is useful only when contention remains manageable. Background kernels can compete with dense kernels for execution resources and memory bandwidth even when the dense computation is dominated by Tensor Core GEMMs. Asynchronous streams therefore use the conservative StreamPriority.DEFAULT policy to limit interference while exploiting otherwise idle capacity. Stage count and overlap topology provide controls for different workloads; the appropriate schedule depends on preparation time relative to the available overlap window.

The pipeline hides preparation work that remains after feature and embedding optimization, while retaining the order required for parameter-dependent computation.

4.2. End-to-End Performance

Figure 5 reports throughput per GPU and step latency. RecIS achieves the highest throughput and lowest latency on all three workloads. It delivers 1.04–1.15\times the throughput of TorchRec with 3.9%–12.9% lower step latency, and 1.48–2.62\times the throughput of PICASSO with 32.3%–61.5% lower latency. These results establish the end-to-end benefit of the combined system; the component experiments examine the underlying reductions in sparse work and exposed latency.

RecIS reaches 924 IPS at 1,299 ms per step on Ad, 1,268 IPS at 202 ms on Search, and 2,058 IPS at 498 ms on Lazada Ad. These workloads use different deployment scales, so comparisons use a fixed training configuration for each model. The maximum gain over PICASSO occurs on Search, whereas the largest relative gain over TorchRec occurs on Ad.

5. Related Work

Wide & Deep, DeepFM, xDeepFM, and DCN V2 model feature interactions (Cheng et al., 2016; Guo et al., 2017; Lian et al., 2018; Wang et al., 2021), while DIN and DIEN model user interests from behavior sequences (Zhou et al., 2018; Zhou et al., 2019). To support these workloads, TensorFlow and PyTorch provide general execution primitives (Abadi et al., 2016; Paszke et al., 2019), while DeepRec, HugeCTR, TorchRec, and PERSIA specialize in large-scale recommendation training (DeepRec Contributors, nd; Wang et al., 2022b; Ivchenko et al., 2022; Lian et al., 2022).

Feature heterogeneity motivates tailored GPU execution. RecFlex adapts schedules to heterogeneous features (Pan et al., 2024). RecIS groups compatible transformations across fields while preserving dependencies, using fusion and vectorized access to reduce preprocessing overhead.

Embedding optimizations target execution, storage, and communication. Kwon and Rhu optimize GPU embedding execution (Kwon and Rhu, 2022), while EL-Rec reduces storage via tensor-train representations (Wang et al., 2022a). ScaleFreeCTR and HET cache embeddings to reduce remote access (Guo et al., 2021; Miao et al., 2021); FEC combines embedding tiering with prefetching to reduce communication overhead (Ma et al., 2023). RecIS merges repeated IDs across GPUs in each source node before inter-node exchange, reducing both transmitted requests and returned vectors.

Scheduling complements these optimizations by overlapping preparation and training. RAP co-schedules GPU preprocessing and training (Wang et al., 2024), while Bagpipe uses future minibatches to prefetch embeddings (Agarwal et al., 2023). PICASSO coordinates embedding-operation packing, interleaved execution, and hierarchical caching (Zhang et al., 2022). GPipe and PipeDream pipeline model stages across devices (Huang et al., 2019; Narayanan et al., 2019). RecIS pipelines preparation across iterations: parameter-independent feature processing and request preparation overlap current dense computation, while parameter accesses and updates retain their required ordering.

6. Conclusion

RecIS coordinates three aspects of GPU-centric recommender training: operator granularity, embedding request distribution, and execution order. Adaptive fusion and vectorization reduce preprocessing overhead; sharding, hierarchical communication, and index-aware aggregation reduce embedding costs; and multistage scheduling overlaps future preparation with current dense computation. Across the evaluated workloads, RecIS achieves up to 1.15\times the throughput of TorchRec and 2.62\times that of PICASSO, with step-latency reductions of up to 12.9% and 61.5%, respectively.
