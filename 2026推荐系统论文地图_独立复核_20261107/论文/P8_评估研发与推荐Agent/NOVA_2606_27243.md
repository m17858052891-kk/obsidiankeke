# NOVA: A Verification-Aware Agent Harness for Architecture Evolution in Industrial Recommender Systems

- 机构：Tencent；广告pCVR架构研发。首发2026-06-25；阅读v3（2026-07-28）。
- 主源：[版本史](https://arxiv.org/abs/2606.27243)、[v3正文](https://arxiv.org/html/2606.27243v3)。
- 分类：推荐研发Agent、语义验证、实验预算；位置：研发迭代循环，不是线上请求中的推荐Agent。

## 为什么通用代码Agent还不够

推荐模型改动往往横跨特征schema、token化、交互模块、任务loss和服务接口。能运行的代码也可能把某个辅助loss连到另一任务标签，或者在shape正确时违反论文结构语义；AutoML固定空间不能自然表达这种跨文件改造。失败候选占训练GPU，重复犯语义错又浪费人工。NOVA把“生成代码”改成固定评估预算内的多轮可验证架构搜索。

## 每轮输入与输出

先解析任务、论文与生产骨干，形成生产约束及知识库。每轮Solution Design给4个修改计划，Code Generation落实。Quality Review先按规则过滤：规则来自论文要求、此前确认的错误、历史知识库，并记录来源/适用范围/条件；再由GPT、Claude Opus、Gemini、Kimi四家judge对存活候选做五维打分，选一个本地测试和离线训练。其他LLM阶段用Claude Sonnet4.6。

Trajectory Memory保存语义失败、本地执行结果和离线指标变化，生成弱项、改进方向和禁止重复的模式。结果异常可触发代码检查，发现新的错误后转成后续规则。最多10轮、每轮至多一次离线评估；线下选择最佳有效模型，再做独立生产AB。在线跑的是产出的pCVR模型，不是LLM反复推理架构。

## 真实例子比框架名更有用

§5.6案例1将TokenMixer-Large的Mixing-and-Reverting、PerToken-SwiGLU和AuxLoss迁入RankMixer。首次有效但参数超过2倍；去AuxLoss损伤其他目标；恢复并加目标1专属loss仍不佳，检查发现预测/标签索引连错。修正索引、屏蔽目标3后继续试MLP和加权，结果全面下降，于是回退再减小loss权重，第6轮三目标AUC提升达到+0.15/+0.02/+0.09个百分点。案例2多序列MixFormer仅+0.05/+0.02/+0.02点，未达门槛，**没有上线AB**。不能把所有Agent生成创新都说成已验证业务提升。

## 最新版本结果

§5.2中L2使用RankMixer式骨干，模型总规模限在生产基线±10%；L3是论文模块迁移。各候选均从同一个月、十亿级交互数据从头训练，特征超过千字段。任务、样本、最大离线评估次数受控，不等于LLM费用或人力成本受控。

§5.2–5.4每类20任务、最多200轮，自动化方案最大离线评估预算相同，但LLM调用成本未匹配，人类行是回顾性参考。有效通过EPR的分子是产生相对初始baseline AUC至少+0.10个百分点候选的轮次数，分母是所有已执行搜索轮次N_iter（包括语义失败、本地测试失败轮）；它不是20个任务的成功率，也不是仅进入离线训练者的条件成功率。停止门槛为最佳候选达到+0.15点。v3表1：L2 ScaleUp EPR53.3%，L3 Literature-to-Production51.7%；最强自动基线R&D-Agent29.2%/28.3%。旧v1摘要54.5%/60.0%不能混进最新版。

表2去trajectory memory/结构反馈，L3 EPR51.7→23.8%；去历史KB下降37.4个百分点。这显示知识/记忆很重要，同时也提醒性能可能依赖私有积累。§5.7表4只将案例1第6轮模型上线：六天、用户随机、5%生产流量；三pCVR目标GMV+1.25/+1.70/+2.02%，绝对pCVR偏差相对减少58.8/66.7/37.3%。偏差定义为|预测总转化/真实总转化−1|，不是AUC提升。v3写计划推进全量，不能沿用早期二次摘要“全量部署”或“迭代13倍”作最新版事实。

## 互补和限制

可帮助移植ReST、CCFormer、SequenceO1等，但不是这些方法的替代；它优化研发漏斗，而不直接改变召回/粗精排阶段数。和TGR-EvoDAG同属研发自动化，后者针对tokenizer→预训练→对齐的跨阶段成本/共同适配，不能从各自不同EPR/Hit指标直接判高低。知识库未完全公开、judge版本和权重、生产约束、任务选择均影响可复现性；人工参考不等预算，不能推断已超越研发团队。

**逐项复核**：v3优先已核；EPR分母/阈值/最大预算已核；LLM成本未匹配已标；案例2未上线已核；GMV来自案例1产物已标；全量状态与旧摘要冲突已处理。

## 收益链路：证据逐环对照

1. 【论文证据】§5.6辅助loss标签索引错能通过已有规则和执行，指标异常后检查才定位；正确运行不代表方法正确。
2. 【论文证据】§4和Table2表明语义规则、轨迹反馈与KB是可移除组件；线上部署的是产出网络。
3. 【作者解释】作者认为验证和轨迹指导共同提高有效迭代比例。【我的推断】规则挡错与记忆减少重复试错，使同训练预算更多投向有效候选；多judge本身是否优于单个强judge需额外成本对照。
4. 【论文证据】EPR分母为所有已执行搜索轮，含失败轮；Table1失败漏斗可观测，不能解读为任务成功率或仅训练成功者比例。
5. 【论文证据】Table4支持一个选中架构的业务提升，第二案例未达门槛没有AB；【证据缺口】未随机比较采用不同研发流程的一批任务平均上线收益。
6. 【我的推断】只有规则可转移、任务足够多、节省GPU和人力超过额外LLM费用，且严格留出后仍找到可部署候选，才成立研发投资回报；不把单次GMV传给全部任务。

**目前最可信来源：**每轮4个候选→语义规则→多judge挑1个→本地测试与离线训练→记录结构化失败/反馈。

**可观测中介：**独立专家确认的语义失败率、有效训练占比、相同错误复发、单位训练及LLM预算内最佳留出AUC。

**机制证据强度：**中：故障漏斗与消融支持流程作用；等LLM成本、跨新任务和平均研发业务收益证据不足。

**仍不能排除：**多模型judge额外推理预算、历史私有KB质量、候选组合和任务熟悉度；离线挑最佳的赢家偏差。

**强弱场景预测【我的推断】：**适合schema复杂、标签路由易错、训练昂贵且已有复用知识库的团队；任务简单、数据管道问题主导或缺乏客观离线评估时收益小。

**证伪与替代解释对照【我的推断】：**固定基础模型、候选数、累计token/美元预算上限、训练评估次数和初始KB，对规则review与通用review随机分配未见论文/骨干任务；让错误率和有效训练数自由变化。若仅训练预算匹配有效而等总成本无优势，削弱研发效率结论。

与ReAct/OpenHands/R&D-Agent+相同skills是实际流程基线；Optuna仅L2条件竞争。与Spotify/ATLAS仅研发闭环思想类似，搜索对象分别是网络代码、prompt、服务Agent参数。 跨论文提升不作排名或相加；组合无增益也可能源于优化冲突、预算拥挤、数据质量或统计功效，不单归因信息冗余。

## 七问迭代卡


### 1. 什么现象值得考虑

可运行但语义错误的架构修改浪费训练预算；固定搜索空间难以迁移跨文件论文模块。

### 2. 在哪里改动

每轮4个候选→语义规则→多judge挑1个→本地测试与离线训练→记录结构化失败/反馈。 研发LLM通过调用生成/审查代码，没有宣称在本任务中训练这些LLM权重。每个候选推荐网络均在同一工业数据上从头训练；历史KB在比较时固定，单任务轨迹逐轮增长。线上只部署最终网络；研究/测试标签不能作为服务特征。

### 3. 为什么可能有效

中：故障漏斗与消融支持流程作用；等LLM成本、跨新任务和平均研发业务收益证据不足。 重点观测：独立专家确认的语义失败率、有效训练占比、相同错误复发、单位训练及LLM预算内最佳留出AUC。

### 4. 最小实验与数据工程条件

先给一个RankMixer类骨干建设shape/label-routing/线上特征可得性契约，固定一月数据快照、训练配置和未见任务；只加错误账本与规则review，再决定是否上4候选与多judge。

### 5. 中间量和护栏

中介：语义错漏检/误杀、复发、训练有效率、best-AUC@总预算；护栏：参数/FLOPs、在线特征泄漏、人工复核时间、LLM/API与GPU成本、其他任务损失。

### 6. 无效后怎样诊断

实现：规则引用错误或评估器错误；数据：跨任务泄漏/KB含测试答案；机制：挡错但错杀创新导致best-AUC不升；场景：主要失败是数据问题非架构语义。记录被拒候选盲抽训练检验误杀。

### 7. 何时扩量或停止

【我的推断】在未见任务族重复证明等总预算成功率改善，再扩大自动化；只提高可运行率而最终留出质量不升，或全靠同任务KB则停止扩大搜索，保留验证助手定位。线上推广仍逐个模型单独AB。
