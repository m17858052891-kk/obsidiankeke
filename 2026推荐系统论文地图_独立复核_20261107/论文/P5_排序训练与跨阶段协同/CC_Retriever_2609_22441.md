# CC Retriever

**完整题名：** Connected Content Retriever: Dense Graph Edge Features Powering Pre-Ranking at LinkedIn

## 1. 身份与选题边界

Akhilesh Gupta et al；作者单位及实际平台均为 LinkedIn。abs题名含“Powering”，v1正文题头为“Dense Graph Edge Features for Pre-Ranking at LinkedIn”；同一arXiv ID，不新增一篇。 首次公开：2026-09-18；会议日期：本轮原文未披露可核实日期；最新版本：v1；最新修订：2026-09-18。

主问题：P5_排序训练与跨阶段协同；次级标签：关系特征、GPU特征拼接、粗排、服务预算。当连接网络候选达数万条、早期粗排无法用viewer–author交叉信号时考虑。

一手入口：[版本原文](https://arxiv.org/html/2609.22441v1)；[作者与版本记录](https://arxiv.org/abs/2609.22441v1)。核验日：2026-11-07（Asia/Shanghai）。本轮重新取得原文与可用附录；旧笔记仅用于识别需要纠正或补充的说法。

## 2. 输入、计算与训练/服务路径


流程为网络关系候选筛选→CPU/GPU特征定位→GPU深度粗排→数百候选进入原精排。请求级输入含用户序列排序器生成的 embedding；物品有内容/行为 embedding；viewer–author 边包含互动次数、距离、时效等密集交叉信号。成员表示为3个50维兴趣medoid，物品50维，构造3个余弦相似度；计数取log并用float16存储。网络用多任务 MLP 预测点击、贡献/长停留等，最后按任务权重和新鲜度规则融合。训练位置偏差分量在服务时置零；原文未给足所有损失权重，不能自补统一BCE公式。

在线关键不是全库GPU ANN：关系索引已经筛到数万候选，GPU sorted-search 将本次 viewer 对作者的边特征拼到文档，复杂度描述为 $O((N+K)\log K)$，join约5–10ms。文档ID→存储位置的查找后来迁到CPU并行hash；**边特征join仍在GPU**，不要把两步混为一谈。

近线 CDC 将静态和动态特征分开刷新，通常分钟级陈旧度、摄取lag低于1分钟；每日清理无效文档。batch cold insertion 的52倍是子系统改善。请求batching、padding和显存布局支持更大网络；训练更新频率未披露。大模型、特征、服务系统一起上线，不能把整体收益都归关系特征。

## 4. 六环收益链与可证伪机制

①【论文证据】数万连接候选受120ms p99限制，传统早期模型难使用密集边信息 → ②【论文证据】加入GPU边join、深度模型与增量更新 → ③【作者解释】关系亲和信息提前改变粗排评分，系统优化释放计算预算 → ④【论文证据】去边后Recall@10下降、服务吞吐提高；【证据缺口】oracle为下游模型而非无偏真实价值 → ⑤【论文证据】整体AB时长和职业互动增长 → ⑥【我的推断】需有效关系图、可持续的特征刷新及同预算下的候选覆盖，才可能迁移。

**机制归因强度：中。** 同网络去特征的Recall消融支持边信息有用；线上AB只支持系统包。

**替代解释与适用分层：** 预训练用户序列向量、新鲜度、容量及更少特征陈旧也能贡献；网络关系密集且边反馈丰富者可能更强，新作者/无边用户收益未证明。

**可证伪对照：** 固定候选、架构、训练预算，比较有/无边特征及参数扩展；另以新鲜度×边特征2×2区分数据刷新。随机抽取粗排丢弃候选补独立业务标签，若只复现精排偏好而真实价值不升则否证链条。固定输入刷新策略可测边作用，但若研究刷新机制则不能锁死缓存年龄。

## 5. Pipeline、基线与选型关系


直接基线是原生产连接内容粗排。它保留网络候选生成、后续精排和任务效用融合；GPU-RAR是“对已筛候选完整打分”，并未让所有十亿条文档进入深网。资源判断要同时计GPU常驻文档特征、CPU索引、CDC和峰值batch，不能只看参数数。论文同特征消融比整体前后AB更适合解释信息增益。


- UniRec：**互补**。CC增加粗排可用信息，UniRec协调阶段融合；共同接入需重新校准。
- UNIQUE：**条件替换**。都可减少早期信息丢失，但UNIQUE生产只贡献一个召回源，CC承担连接内容粗排，不能直接按收益排名。

## 6. 七问迭代卡


1. **何时用？** 先检查早期漏失是否集中在有强viewer–author关系、但内容相似度低的候选。
2. **改哪里？** 粗排特征join、存储和GPU评分；保留召回与精排接口。
3. **最可信机制？** 边特征补足内容embedding缺的信息，表2直接支持。
4. **最小实验？** 用一类网络候选，同架构做边特征开关，配随机淘汰样本复核；测真实峰值负载而非单请求。
5. **中介/护栏？** 边覆盖/新鲜度、高值存活、oracle与真实标签差异；p99、OOM、CDC lag、新作者曝光为护栏。
6. **失败怎么分？** 机制：边只复制精排偏见；实现：ID/作者join错配或padding浪费；数据：边陈旧/缺失；场景：弱社交或冷作者占比高。
7. **何时扩量/停止？** 建议预算匹配且真实业务CI排除伤害、尾时延满足既有SLO后扩量；只有oracle提升或峰值超预算则停。
