## 先排查哪一种故障

| 问题 | 最低证据 | 工具分工 | 必做区分/干预 |
|---|---|---|---|
| 新特征无收益 | join 命中率/缺失/时间穿越检查，逐样本预测，分群指标 | 数据检查由现有管线；Captum 看使用；torch 看梯度/更新；日志工具关联配置 | 完全没送进模型、重复信息、标签噪声、训练不足、竞争/抑制分别设实验 |
| 扩容无收益 | 同数据/预算/早停口径的小大模型学习曲线；训练与验证误差；梯度与参数更新 | W&B 或现有日志汇总；Profiler 判断新增容量是否耗在算力/通信/输入；torch 验证优化 | 增加训练步数、调学习率/正则、容量位置消融；不能只看最终 AUC |
| 多任务梯度冲突 | 同一 batch、共享参数上各任务梯度；任务损失缩放、采样比例 | torch.autograd 或 torch.func；记录夹角、范数比、冲突比例 | 负夹角只是局部信号；先检查损失量纲，再做单任务、权重/采样、梯度处理对照 |
| 梯度饥饿/特征竞争 | 特征组梯度、预测贡献、学习轨迹、强弱信号对照 | torch + Captum + 固定消融 | 小梯度也可能是已收敛、输入没出现、饱和、detach、梯度累积口径；必须操纵竞争信号/训练机制并复现 |
| 稀疏 embedding 更新异常 | ID 曝光次数、有效梯度非零频次、更新间隔、optimizer state、实际参数差分 | 训练代码定制采样/hook + 日志；通用库仅辅助 | 未曝光行的零梯度是正常负例；必须区别未进 optimizer、学习率为零、AMP skip、低频采样 |
| 性能瓶颈 | 固定硬件/数据/批量，预热后的吞吐/P95、CPU/CUDA trace、峰值内存 | Profiler 定位；torchao/ONNX Runtime 可作后续干预 | 加速不是预测增益；评估量化精度损失、导出兼容性和端到端收益 |

## PyTorch 梯度与 Profiler

接入固定 batch、checkpoint、分任务 loss 和 optimizer 参数组，在同一批数据上同时观察梯度、真实参数增量和触达 ID。记录 AMP 是否跳步。Profiler 用短窗口定位耗时和显存，解释同预算下的吞吐差异。

**接入与成本**　传统训练框架，资料参考 2.15.0。按层、任务和时间采样以控制额外反向、显存和 trace 存储，vmap 不兼容时使用原生 autograd 与参数差分。

**验收与换路**　用解析线性模型对齐逐样本 autograd，再植入 detach、漏加参数组、学习率为零和相反任务。保留正常未触达 ID、收敛分支作负对照。按 ID 频次比较实际更新，观察到负夹角后做单任务或权重干预，再判断是否负迁移。

> [!example]- 展开调用示例（待试）
> ```python
> import torch
> from torch.func import grad, vmap
>
> w = torch.tensor([0.2, -0.3], dtype=torch.float64)
> x = torch.tensor([[1., 2.], [3., 0.], [0., 1.]], dtype=torch.float64)
> y = torch.tensor([1., 0., -1.], dtype=torch.float64)
> def one_loss(w, x, y):
>     return (x.dot(w) - y).square()
> g = vmap(grad(one_loss), in_dims=(None, 0, 0))(w, x, y)
> manual = 2 * (x @ w - y)[:, None] * x
> assert g.shape == (3, 2)
> torch.testing.assert_close(g, manual)
>
> with torch.profiler.profile(
>     activities=[torch.profiler.ProfilerActivity.CPU]
> ) as p:
>     with torch.profiler.record_function("toy_diagnostic"):
>         vmap(grad(one_loss), in_dims=(None, 0, 0))(w, x, y)
> print(p.key_averages().table(sort_by="self_cpu_time_total", row_limit=10))
> ```

[逐样本梯度教程](https://docs.pytorch.org/tutorials/intermediate/per_sample_grads) · [Profiler API](https://docs.pytorch.org/docs/2.15/profiler.html) · [函数变换限制](https://docs.pytorch.org/docs/2.15/func.ux_limitations.html) · [Embedding行为](https://github.com/pytorch/pytorch/blob/v2.15.0/torch/nn/modules/sparse.py)

## W&B Models MCP

已有 W&B runs 时，给出 project、run、指标名与 step 范围，从原始记录提取配置差异和异常所在的时间段。diagnose_run 的曲线规则可提示在哪里看，真正的梯度需由训练侧另行记录。

**接入与成本**　连接器，源码候选版本 0.4.3，实际部署渠道需确认。已有账号与日志规范时接入较轻，平台费用、历史读取和 LLM 上下文按实际用量计。

**验收与换路**　拿两条已知不同的曲线和一个缺指标的 run，与 SDK 原始导出逐项比对。错轴、截断和稀疏记录应列为缺失。核对数字、覆盖区间、检索耗时和人工改错量，读数失真就回到 SDK。

## Captum

先指定要解释的是单样本分数、候选分差或任务输出，再提供业务上合理的 baseline 和特征组 mask。用积分梯度或组消融看哪些样本依赖新特征，将排名交给受控消融实验。

**接入与成本**　传统 PyTorch 解释库 0.9.0。计算随解释步数、样本和特征组增长，主要人工成本是构造合法扰动。

**验收与换路**　固定 checkpoint 与样本，放入已知信号、随机模型和强相关的可替代特征。比较不同 baseline、逐组置换和重训消融的稳定性。结果随 baseline 翻转时仅保留探索结论。

> [!example]- 展开调用示例（待试）
> ```python
> import torch
> from captum.attr import IntegratedGradients, FeatureAblation
> def score(x):
>     return 2 * x[:, 0] - 3 * x[:, 1]
> x = torch.tensor([[4., 5., 7.]])
> expected = torch.tensor([[8., -15., 0.]])
> a, delta = IntegratedGradients(score).attribute(
>     x, baselines=torch.zeros_like(x), n_steps=32,
>     internal_batch_size=8, return_convergence_delta=True)
> b = FeatureAblation(score).attribute(x, baselines=0)
> torch.testing.assert_close(a, expected)
> torch.testing.assert_close(b, expected)
> assert delta.abs().max() < 1e-5
> ```

[IG 文档](https://captum.ai/api/integrated_gradients.html) · [分组消融文档](https://captum.ai/api/feature_ablation.html) · [FAQ](https://captum.ai/docs/faq)

## BackPACK

已定位到优化问题且确实需要逐样本方差或曲率时，让支持的模型与损失运行扩展反向，读取参数上的 grad_batch 等统计。先在小层验证，再决定是否增加采样。

**接入与成本**　传统库 1.7.1。完整逐样本梯度的存储随 batch×参数量增长，兼容性和二阶计算都要单独计费。

**验收与换路**　与朴素逐样本反向或 torch.func 对齐同一 reduction 和参数，加入不支持模块、跨样本归一化和稀疏 embedding。1.7.1 的 Embedding 实现要求 sparse=False、padding_idx=None、max_norm=None、scale_grad_by_freq=False。真实稀疏表直接按触达行读实际更新。

> [!example]- 展开调用示例（待试）
> ```python
> import torch
> from backpack import backpack, extend
> from backpack.extensions import BatchGrad
> torch.manual_seed(7)
> model = extend(torch.nn.Linear(2, 1))
> loss_fn = extend(torch.nn.MSELoss(reduction="sum"))
> x, y = torch.randn(3, 2), torch.randn(3, 1)
> with backpack(BatchGrad()):
>     loss_fn(model(x), y).backward()
> for p in model.parameters():
>     assert p.grad_batch.shape[0] == 3
>     torch.testing.assert_close(p.grad_batch.sum(dim=0), p.grad)
> ```

[扩展 API](https://docs.backpack.pt/en/master/extensions.html) · [固定版本Embedding实现](https://github.com/f-dangel/backpack/blob/1.7.1/backpack/core/derivatives/embedding.py) · [支持层](https://docs.backpack.pt/en/master/supported-layers.html)

## RD-Agent

有隔离执行环境、固定候选数据和独立评估器时，可试自动生成假设、代码和训练实验。限制尝试次数和总预算，输出代码差异、运行结果和失败记录，再交给外部评估器。

**接入与成本**　独立 LLM 系统 1.0.0，对当前业务属于研究候选。需要 Linux/Docker、模型后端、算力与人工审查。命令中的竞赛名须换成已准备的任务。

**验收与换路**　和工程师配合编码助手在同样尝试次数下对比。加入测试集不可见、无信号特征和执行失败案例，检查预算、复现率及独立留出集表现。生成代码能改评估器或只会增加失败重跑时停止。

> [!example]- 展开调用示例（待试）
> ```bash
> rdagent data_science --competition toy-fixed-split --loop-n 1 --timeout 30m --no-checkout
> ```

[官方仓库](https://github.com/microsoft/RD-Agent) · [CLI 源码](https://github.com/microsoft/RD-Agent/blob/v1.0.0/rdagent/app/cli.py) · [自定义数据指南源码](https://github.com/microsoft/RD-Agent/blob/v1.0.0/docs/scens/data_science.rst)

## 训练或服务成本过高

固定硬件、并发、批量和预热条件，比较加载、通信、算子及端到端 P95/P99。只有真实服务剖析指向相应瓶颈时，再试量化、共享计算或缓存。与原精度版本比较逐样本输出、校准、NDCG、吞吐和尾延迟，收益须在目标硬件重测。[torchao 推理工作流](https://docs.pytorch.org/ao/stable/workflows/inference.html) · [ONNX Runtime 量化](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)
