# Prefix2Query

Prefix2Query 这个模块是整个 OneSug 架构的“眼睛”，它决定了系统能否在用户刚敲下一两个字的时候，就“看透”用户的真实心思。
在搜索框里，用户输入的前缀（Prefix）通常非常短，包含的信息量极低，也就是所谓的“语义稀疏”。比如用户敲了一个“水”字，ta 到底是想搜“水果”、“水杯”、还是“水杨酸精华”？

Prefix2Query 表示增强模块就是为了打破这种模糊性而设计的。我们可以把它拆解为“上下文增强”**和**“商业特征对齐（RQ-VAE）”两个核心维度来理解。

# 1. 基础增强：用“历史”和“关联”给前缀加料

为了让干瘪的“前缀”丰满起来，这个模块首先会拉取两路辅助信息，将它们与前缀拼接或进行注意力（Attention）交互：

- **用户的交互历史 (User Interaction History)：** 机器会回忆这个用户最近的行为。如果该用户过去 10 分钟都在浏览“美妆护肤”类目，那么当 ta 输入“水”时，系统就会赋予“水杨酸”或“爽肤水”更高的权重，而不是“水果”。这赋予了前缀**个性化**的色彩。
- **语义关联 (Semantic Association)：** 基于全平台的搜索日志，将当前前缀与高频的完整 Query（查询词）进行图谱式或共现特征的关联，提前划定意图的“候选圈”。

# 2. 核心黑科技：RQ-VAE 与语义 ID

如果说上面那一步是常规操作，那么引入 **RQ-VAE（残差量化变分自编码器）** 生成**语义 ID（Semantic ID）**，则是 OneSug 最精妙的一笔。

在传统的搜索系统中，商品和 Query 的 ID 通常是无意义的一串数字（比如哈密瓜的商品 ID 是 `789234`，苹果是 `789235`），它们在字面上看不出任何关联。

**RQ-VAE 的作用，就是给全平台的 Query 和商品重新发放一套“带有层级语义的身份证”**。它的工作原理如下：

1. 把文本或商品特征压缩成一个稠密向量（Dense Vector）。
2. 将这个向量逐层进行“残差量化”，映射到一个离散的密码本（Codebook）中，生成一串层级 ID（例如：`[ID_1, ID_2, ID_3]`）。

这就像是图书馆的分类号：

- **一级 ID (如 10)：** 代表大类目（比如“食品”）。
- **二级 ID (如 10-5)：** 代表细分类目（比如“水果”）。
- **三级 ID (如 10-5-8)：** 代表具体实体（比如“苹果”）。

|**表达方式**|**示例**|**优缺点**|
|---|---|---|
|**纯文本**|"苹"|极度稀疏，歧义大（苹果手机 vs 苹果水果）。|
|**传统 ID**|`Hash(12345)`|完全孤立，毫无规律，模型很难举一反三。|
|**语义 ID (RQ-VAE)**|`[10, 5, 8]`|结构化，带有层级逻辑。前几位相同，说明它们意思相近。|

# 3. 巧妙的“连接桥梁”：对齐输入与商业特征

生成了这些 Semantic ID 后，Prefix2Query 模块就完成了一次极其漂亮的“特征跨界连接”。

当用户输入模糊前缀时，模型不再仅仅预测下一个“字”是什么，而是**同步预测该前缀在 RQ-VAE 空间中对应的 Semantic ID 是什么**。

这样做带来了巨大的好处：

**它将自然语言（NLP）领域的文本问题，与电商业务的商业特征强绑定了。**

电商平台的商业特征往往蕴含在类目、品牌、价格段等结构化数据中，而这些信息已经被 RQ-VAE 编码进了 Semantic ID 里。当模型通过前缀预测出 Semantic ID 的前几位时（例如预测出大类是“3C数码”），它就瞬间继承了这个类目下所有的商业上下文，从而在后续解码生成完整的 Query 时，既符合语法，又绝对贴合电商平台的商品供给池，绝不会生成平台根本没在卖的“废词”。

简单来说，Prefix2Query 通过 RQ-VAE 搭建了一座桥，让“干瘪的几个字”瞬间挂载了“整个电商平台的商品结构树”。
