# 08 项目局限与升级路线

## 1. 当前版本的局限

### 输入不是原始 13 亿行日志

当前 notebook 以预聚合 `hstu_seq_chunk_00.parquet` 为输入，重点验证模型链路。若强调大数据工程，需要补充 raw log → sequence 的分片处理脚本、耗时、峰值内存和产物规模。

### SID 是协同语义，不是完整内容语义

当前 SID 的输入主要来自行为共现学习到的 Item2Vec embedding。它能反映用户行为相似性，但对新 item、少交互 item 和文本/图像语义覆盖不足。

### 训练不是端到端联合优化

Item2Vec、RQ-VAE 和 HSTU decoder 分开训练。量化器追求 embedding 重构，推荐模型追求 next-item prediction，两者目标不完全一致。

### 无法真正解决冷启动

没有历史行为的 item 没有可靠的 collaborative embedding，不能凭空得到高质量 collaborative SID。需要 content encoder、类目/品牌特征或热门回退。

### HSTU 是简化原型

项目实现参考了 HSTU 的关键思想，但不应把简化代码表述成官方完整实现或生产级 kernel 优化。

## 2. 优先级最高的改进

1. 改 temporal OOT split，确认没有未来信息泄漏。
2. 校验 Action 映射和 time_gap 单位。
3. 补充 codebook 使用率、collision rate、OOV rate、prefix invalid rate。
4. 负采样排除已知正样本，增加 hard negative。
5. 对热门/长尾分桶报告，防止只学到 popularity。

## 3. 研究/算法升级

### 内容与协同融合 SID

构造：

```text
z_item = α * z_collaborative + (1-α) * z_content
```

其中 content 可以来自标题、类目、品牌、图像或多模态 encoder。对新 item 使用 content 分支生成初始 SID，再通过交互数据更新。

### 推荐目标联合量化

在 RQ-VAE 重构损失之外加入推荐损失：

$$
\mathcal{L}=\mathcal{L}_{rec}+\lambda\mathcal{L}_{RQ}
$$

让 code 不仅重构 item embedding，也有利于预测真实下一 item。

### 分层或自适应 code

按 head/torso/tail 使用不同 codebook 容量；或将 collision token 改成可扩展的局部地址，控制 code 空间和搜索复杂度。

### 更强的生成训练

加入 sequence-level ranking loss、contrastive prefix loss、hard negative SID 和 scheduled sampling，减少 teacher forcing 与 inference 的差异。

## 4. 工程/生产升级

- 用 Flink/Spark/SQL pipeline 生成滚动用户序列。
- 用 ANN 做 Item2Vec 初始召回或量化前近邻搜索。
- 预计算 prefix trie 和 SID 到 item 的反向索引。
- 生成候选后接轻量 ranker，融合实时库存、价格、曝光和业务规则。
- 对 SID 做版本化、灰度发布和回滚。
- 建立覆盖率、OOV、invalid SID、热门集中度和延迟监控。

## 5. 面试时的防守句

如果面试官指出项目不是完整工业系统，可以回答：

> 这份项目定位是离线生成式推荐原型，重点验证 Semantic ID、HSTU 序列建模和约束解码是否能串起来。我没有把它包装成线上系统；如果继续工程化，我会优先补时间 OOT、内容冷启动、联合训练和版本化部署。
