可以。这个项目可以拆成一条完整链路来理解：

> 淘宝行为日志 → 协同商品表征 → Semantic ID → 用户序列建模 → SID 自回归生成 → 约束 Beam Search → 商品推荐与评估

下面按知识点逐个讲，并在最后给出那 8 个问题的“可直接面试回答版”。

---

## 1. 淘宝 UserBehavior 数据集

每条数据通常包含：

```text
user_id, item_id, category_id, behavior_type, timestamp
```

行为类型包括：

- `pv`：点击/浏览
- `fav`：收藏
- `cart`：加入购物车
- `buy`：购买

它本质上是隐式反馈数据：没有显式评分，只能通过行为强弱推断用户兴趣。

一个常见的行为权重设计是：

\[
w_{\text{pv}} < w_{\text{fav}} < w_{\text{cart}} < w_{\text{buy}}
\]

例如：

\[
w_{\text{pv}}=1,\quad
w_{\text{fav}}=2,\quad
w_{\text{cart}}=3,\quad
w_{\text{buy}}=4
\]

这些权重不是概率，只表达“不同行为提供的兴趣信号强度不同”。

### 为什么不能只保留购买？

购买信号强，但非常稀疏。只使用购买会导致：

- 训练样本太少；
- 很多用户没有足够长的序列；
- 模型难以学习兴趣形成过程；
- 点击到购买之间的意图变化被丢弃。

因此一般用所有行为做序列预训练，再用购买行为做目标导向的微调。

---

## 2. 时间切分与数据泄露

推荐系统不能随机切分交互，因为随机切分可能把用户未来行为放进训练集。

正确方式是按用户时间排序：

```text
过去行为 → 训练
较新的行为 → 验证
最后行为 → 测试
```

例如用户序列：

```text
A → B → C → D → E
```

可以构造：

```text
训练：A,B,C → D
测试：A,B,C,D → E
```

这样才模拟线上场景：根据过去预测未来。

---

# 第一部分：协同 Semantic ID

## 3. 为什么不直接预测 Item ID？

假设有 100 万个商品，传统分类模型最后需要预测：

\[
P(item\mid user),\qquad item\in\{1,\dots,10^6\}
\]

这会带来三个问题：

### 输出层巨大

若隐藏维度为 256，输出矩阵大小约为：

\[
256\times 10^6
\]

仅参数就有约 2.56 亿个。

### Item ID 没有结构

商品 `12345` 和 `12346` 的编号相近，不代表它们语义相近。Item ID 本质上是随机标签。

### 新增商品不友好

每增加一个商品，都要扩展分类层或者重新维护词表。

因此项目将一个商品映射成多个离散码：

\[
item_i\rightarrow(s_i^1,s_i^2,s_i^3)
\]

例如：

```text
手机 A → (17, 83, 24)
手机 B → (17, 83, 91)
运动鞋 → (201, 42, 7)
```

相似商品可能共享前缀。模型不用一次从 100 万个商品中分类，而是连续生成三级离散码。

---

## 4. 什么是协同语义？

这里的“语义”不是商品标题的文本语义，而是用户行为产生的协同语义。

如果大量用户在相近时间内同时浏览、收藏或购买商品 A 和 B，那么即使不知道它们的标题，也可以认为 A 和 B 具有协同相关性。

比如：

```text
iPhone 手机壳 ↔ iPhone
咖啡机 ↔ 咖啡豆
婴儿车 ↔ 婴儿用品
```

它们不一定属于同一个具体商品类别，但存在消费行为上的关联。

---

## 5. 稀疏 item-item 共现样本

首先在每个用户的时间序列中构造滑动窗口：

```text
用户序列：A, B, C, D
窗口大小：2
```

得到近邻商品对：

```text
(A,B), (A,C), (B,C), (B,D), (C,D)
```

不能把每个用户的所有商品两两组合，因为复杂度可能达到：

\[
O(L^2)
\]

长序列会产生大量样本。因此通常限定局部窗口、最大序列长度和最大采样对数。

---

## 6. Weighted Item2Vec

普通 Item2Vec 把用户序列类比成自然语言：

- 商品对应单词；
- 用户行为序列对应句子；
- 邻近商品对应上下文。

Skip-gram 的目标可以写为：

\[
\max \sum_{(i,j)\in\mathcal D}
\log P(j\mid i)
\]

采用负采样后：

\[
\log\sigma(v_i^\top v_j)
+
\sum_{n\in\mathcal N}
\log\sigma(-v_i^\top v_n)
\]

项目增加了样本权重：

\[
w_{ij}
=
w_{\text{behavior}}
\cdot
w_{\text{time}}
\cdot
w_{\text{activity}}
\]

最终损失是：

\[
\mathcal L
=
-\sum_{(i,j)}
w_{ij}\mathcal L_{ij}
\]

### 行为强度

购买、加购一般比普通点击权重更高：

\[
w_{\text{buy}}>w_{\text{cart}}>w_{\text{fav}}>w_{\text{pv}}
\]

### 时间衰减

时间间隔越小，共现关系越可信：

\[
w_{\text{time}}
=
\exp\left(-\frac{|\Delta t|}{\tau}\right)
\]

其中 \(\tau\) 控制衰减速度。

### 用户活跃度惩罚

超活跃用户可能浏览成百上千个商品，如果不降权，他们会制造大量噪声共现。

可采用：

\[
w_{\text{activity}}(u)
=
\frac{1}{\log(1+N_u)}
\]

其中 \(N_u\) 是用户行为数。

这和 TF-IDF 的思想相似：不能让高频用户支配整个协同空间。

---

## 7. RQ-VAE 残差量化

Item2Vec 得到连续向量：

\[
x_i\in\mathbb R^d
\]

但生成式模型需要离散 token，因此使用 RQ-VAE 将向量转成多级离散码。

### 编码

编码器将商品向量映射到潜空间：

\[
z_i=E(x_i)
\]

### 第一级量化

从第一个码本中找最近向量：

\[
c_i^1
=
\arg\min_k
\|z_i-e_k^1\|^2
\]

对应残差：

\[
r_i^1=z_i-e_{c_i^1}^1
\]

### 第二级量化

继续量化残差：

\[
c_i^2
=
\arg\min_k
\|r_i^1-e_k^2\|^2
\]

\[
r_i^2=r_i^1-e_{c_i^2}^2
\]

第三级同理。

最终：

\[
\hat z_i
=
e_{c_i^1}^1+e_{c_i^2}^2+e_{c_i^3}^3
\]

Semantic ID 就是：

\[
SID_i=(c_i^1,c_i^2,c_i^3)
\]

### 为什么使用残差量化？

如果三个码本各有 256 个 code，理论组合空间为：

\[
256^3=16,777,216
\]

模型每一步只预测 256 类，却能够覆盖千万级组合。

前一级通常描述较粗粒度兴趣，后一级补充更细粒度差异。不过这种层级语义是训练形成的，不应机械理解成“第一级一定是类目、第二级一定是品牌”。

---

## 8. RQ-VAE 损失

典型损失包含：

\[
\mathcal L_{\text{RQ-VAE}}
=
\mathcal L_{\text{recon}}
+
\beta\mathcal L_{\text{commit}}
+
\mathcal L_{\text{codebook}}
\]

### 重建损失

\[
\mathcal L_{\text{recon}}
=
\|x_i-D(\hat z_i)\|^2
\]

衡量量化后能否恢复原始商品向量。

### Commitment Loss

约束编码器输出靠近选择的码本向量，防止编码器不断漂移。

### Codebook Loss

推动被选择的码本向量靠近编码器输出。

### Codebook Collapse

如果绝大多数商品只使用少数 code，就会发生码本塌缩：

```text
code 17：50 万商品
code 23：20 万商品
其他 code：几乎无人使用
```

这会导致：

- SID 分布严重不均衡；
- 热门前缀拥挤；
- 碰撞率上升；
- 生成模型偏向少量 token。

---

## 9. 曝光容量约束

这里“曝光”可以理解为商品在行为日志中的加权出现频率：

\[
p_i=\text{exposure mass of item }i
\]

普通最近邻量化只考虑距离：

\[
c_i
=
\arg\min_k\|r_i-e_k\|^2
\]

容量约束额外要求每个 code 承载的曝光质量不能超过上限：

\[
\sum_{i:c_i=k}p_i\le C_k
\]

例如总曝光质量为 \(P\)，码本有 \(K\) 个 code，容量因子为 \(\alpha\)，则可以设：

\[
C_k=\alpha\frac{P}{K}
\]

项目中 \(\alpha=1.2\)，即每个 code 最多承载平均曝光量的约 1.2 倍。

### 一种实际实现方式

先计算商品到各个 code 的距离，然后按商品曝光量或分配置信度排序：

1. 尝试分配给距离最近的 code；
2. 如果该 code 已达到曝光容量；
3. 就尝试次近 code；
4. 直到找到仍有容量的 code。

也可以把硬约束写成软惩罚：

\[
c_i
=
\arg\min_k
\left[
\|r_i-e_k\|^2
+
\lambda\phi\left(\frac{L_k+p_i}{C_k}\right)
\right]
\]

其中 \(L_k\) 是当前 code 已承载的曝光质量。

### 为什么约束曝光，而不是商品数量？

100 个冷门商品和 100 个爆款商品对训练分布的影响完全不同。

如果只平衡商品个数，一个 code 仍可能包含大量热门商品，从而占据绝大多数训练 token。平衡曝光质量更接近模型实际看到的 token 分布。

---

## 10. 容量约束和量化误差的 trade-off

容量约束一定可能增加量化误差。

无约束量化选择最近 code：

\[
k^*=\arg\min_k d(i,k)
\]

加入容量约束后，最近 code 可能已满，商品只能选择第二近或第三近 code。因此：

\[
\mathcal E_{\text{capacity}}
\ge
\mathcal E_{\text{nearest}}
\]

项目实验中：

```text
embedding MSE：
无约束   0.01070
容量约束 0.01141
```

大约增加了 6.6%。

这不是实现错误，而是用局部重建精度换取：

- 更平衡的码本负载；
- 更均匀的训练 token；
- 避免热门 code 过载；
- 改善生成模型的学习稳定性；
- 增加冷门商品获得有效编码的机会。

真正需要比较的不是“量化误差有没有增加”，而是：

\[
\text{最终推荐质量收益}
-
\text{量化误差代价}
\]

因此应该做容量因子消融，例如：

\[
\alpha\in\{1.0,1.1,1.2,1.5,2.0,\infty\}
\]

同时报告量化误差、负载 Gini、碰撞率和 HR/NDCG。

---

## 11. SID 碰撞

碰撞指不同商品获得完全相同的 SID：

\[
SID_i=SID_j,\qquad i\ne j
\]

例如：

```text
商品 A → (17, 83, 24)
商品 B → (17, 83, 24)
```

当模型生成这个 SID 时，无法确定究竟推荐 A 还是 B。

### 常用指标

碰撞商品率：

\[
\text{collision rate}
=
\frac{\#\{\text{位于碰撞桶中的商品}\}}
{\#\{\text{全部商品}\}}
\]

还应统计：

- 唯一 SID 数；
- 碰撞桶数量；
- 最大桶大小；
- P95 桶大小；
- 曝光加权碰撞率；
- 热门商品碰撞率。

项目当前结果是：

```text
无约束碰撞商品率：约 8.74%
容量约束后：约 18.18%
```

这说明容量平衡和组合唯一性并不是同一个目标。容量约束迫使商品离开最近 code，可能把更多商品推入相同的三级组合。

### Collision Token

一种直接解决方法是在三级 SID 后追加冲突编号：

```text
商品 A → (17,83,24,0)
商品 B → (17,83,24,1)
商品 C → (17,83,24,2)
```

前三层仍表示共享协同语义，最后一层仅负责消歧。

优点：

- 映射可以做到一一对应；
- 不必扩大所有层的码本；
- 共享前缀仍然保留。

缺点：

- 生成长度增加；
- 最后一级语义很弱；
- 大碰撞桶会导致 collision token 词表增大；
- 冲突编号可能对新增商品不稳定。

其他解决方法还包括增大码本、增加量化层、加入去碰撞损失、重新训练码本，以及只在冲突桶内做二阶段商品排序。

# 第二部分：用户兴趣序列

## 12. 从商品序列转换为 SID 序列

原始行为：

```text
(item_A, pv)
(item_B, cart)
(item_C, buy)
```

转换后可表示为：

```text
[BOS]
[行为=pv] [SID_A_1] [SID_A_2] [SID_A_3]
[行为=cart] [SID_B_1] [SID_B_2] [SID_B_3]
[行为=buy] [SID_C_1] [SID_C_2] [SID_C_3]
```

具体实现也可以不把行为作为独立 token，而是把多个 embedding 相加：

\[
h_t
=
e_{\text{SID}}
+
e_{\text{behavior}}
+
e_{\text{position}}
+
e_{\text{time-gap}}
\]

其中时间间隔可以离散分桶：

```text
0–1 分钟
1–10 分钟
10–60 分钟
1–24 小时
1–7 天
7 天以上
```

时间间隔通常比绝对 Unix 时间更有意义，因为它能描述用户行为的连续性和兴趣漂移。

---

## 13. 长度差异和截断

用户序列可能从 1 条到几万条不等。如果全部输入：

- 显存开销大；
- 训练速度慢；
- 早期行为可能已经过时；
- 注意力复杂度通常随长度平方增长。

因此一般保留最近 \(L\) 条：

\[
S_u'
=
S_u[-L:]
\]

本项目最长序列设为 200。

### 为什么通常从左侧截断？

推荐更关注近期兴趣，所以保留最后 200 条，删除最早行为。

### Padding 和 Mask

短序列补 PAD：

```text
[PAD, PAD, A, B, C]
```

模型通过 mask 保证 PAD 不参与注意力和损失。

### 更好的长序列方案

除了硬截断，还可以：

- 近期行为完整保留；
- 远期行为降采样；
- 将历史按 session 压缩；
- 构造长期兴趣摘要；
- 多尺度序列建模；
- 检索与候选商品最相关的历史片段。

当前项目主要采用截断，这是可复现且成本较低的方案，但不是长序列问题的最终答案。

---

## 14. 冷启动用户

完全没有行为的新用户无法使用序列模型，因为不存在：

\[
P(SID_{\text{next}}\mid history)
\]

因此需要 fallback。

### 当前可落地方案

没有行为时推荐：

- 全局热门商品；
- 最近时间窗口的趋势商品；
- 按曝光去偏后的购买热门商品。

### 有少量侧信息时

如果知道地区、设备、时间、入口或人群标签，可以使用：

\[
P(item\mid region,device,time,channel)
\]

### 有一次或少量行为时

立即从热门召回切换到短序列模型，或者将热门先验与模型分数混合：

\[
score(i)
=
\lambda score_{\text{model}}(i)
+
(1-\lambda)score_{\text{popular}}(i)
\]

### 更深入的研究方向

- 新用户 onboarding 兴趣选择；
- session-based recommendation；
- 用户侧特征编码；
- 元学习；
- bandit 探索；
- 大模型根据实时上下文生成初始兴趣。

所以更准确的答法不是“截断解决冷启动”，而是：

> 截断解决长序列计算问题；冷启动是另一个问题，需要热门、上下文或用户侧特征作为回退。

# 第三部分：HSTU 兴趣建模

## 15. HSTU 是什么？

HSTU 常指 Hierarchical Sequential Transduction Unit，面向超大规模生成式推荐序列建模。

它和标准 Transformer 都利用序列中的 token 交互，但更强调：

- 推荐场景中的行为序列；
- 门控交互；
- pointwise 非线性；
- 相对时间与位置关系；
- 对长序列和大规模训练的效率优化。

需要严谨说明：当前项目实现的是 **HSTU-style 模型**，复现了门控、SiLU、相对时空偏置等核心思想，不应声称与工业版本的所有算子和训练系统完全一致。

---

## 16. Pointwise SiLU

SiLU 定义为：

\[
\operatorname{SiLU}(x)
=
x\sigma(x)
\]

与 ReLU 相比，它是平滑的，也允许小幅负值通过。

“Pointwise”表示对每个位置、每个通道独立应用非线性，而不是在序列维度进行卷积。

推荐序列中常使用类似：

\[
U=\operatorname{SiLU}(W_uX),\quad
V=\operatorname{SiLU}(W_vX)
\]

分别构造门控分支和内容分支。

---

## 17. 门控交互

简化理解可以写成：

\[
H'
=
U\odot \operatorname{Interaction}(Q,K,V)
\]

其中：

- `Interaction` 聚合历史行为；
- \(U\) 决定哪些维度应当通过；
- \(\odot\) 是逐元素乘法。

门控的作用是根据当前上下文动态决定：

- 哪些历史行为有用；
- 哪些兴趣维度需要增强；
- 哪些噪声需要抑制。

和固定加权相比，它更适合多行为场景，因为一次点击和一次购买对未来行为的意义不同。

---

## 18. 相对位置与时间偏置

普通绝对位置只告诉模型“这是第 37 个行为”，但推荐场景更关心：

- 两次行为间隔多久；
- 某个行为离当前预测多远；
- 是否发生在同一个短期 session。

注意力或交互分数可以写为：

\[
a_{ij}
=
q_i^\top k_j
+
b_{\text{pos}}(i-j)
+
b_{\text{time}}(\Delta t_{ij})
\]

其中：

- \(b_{\text{pos}}\)：相对位置偏置；
- \(b_{\text{time}}\)：相对时间偏置。

例如两次行为都只相隔一个位置，但：

```text
A → 1 分钟后 → B
A → 30 天后 → B
```

兴趣连续性显然不同，时间偏置可以表达这种差异。

# 第四部分：生成式训练

## 19. Teacher Forcing

假设目标 SID 是：

```text
(17, 83, 24, 2)
```

训练时：

```text
输入 BOS       → 预测 17
输入 BOS,17    → 预测 83
输入 BOS,17,83 → 预测 24
输入 ...,24    → 预测 2
```

训练阶段每一步输入真实的上一 token，而不是模型自己生成的 token，这就是 Teacher Forcing。

优点是训练稳定、并行度高；缺点是训练和推理存在 exposure bias：推理时如果前一级预测错，后面只能在错误前缀上继续。

---

## 20. 多级交叉熵

对于 \(M\) 级 SID：

\[
\mathcal L_{\text{SID}}
=
\sum_{m=1}^{M}
\lambda_m
\operatorname{CE}
\left(
P(s^m\mid s^{<m},H_u),
s^m
\right)
\]

前一级错误通常影响更大，因此可以给粗粒度层更高权重。

也可以对碰撞 token 降权，因为它主要负责标识，而不是表达兴趣语义。

---

## 21. 预训练和 LoRA-SFT

项目采用两个阶段：

### 阶段一：多行为预训练

使用点击、收藏、加购、购买等全部行为，学习通用用户兴趣转移。

目标可以是预测任意下一商品的 SID。

### 阶段二：购买目标 SFT

只保留或重点采样购买目标，让模型更贴近最终推荐目标：

\[
P(SID_{\text{buy}}\mid history)
\]

这里的 SFT 是监督微调，不是自然语言项目中“指令问答格式”的必然含义。

---

## 22. LoRA

LoRA 不直接更新原始权重 \(W\)，而是学习低秩增量：

\[
W'=W+\Delta W
\]

\[
\Delta W
=
\frac{\alpha}{r}BA
\]

其中：

\[
A\in\mathbb R^{r\times d_{\text{in}}},
\quad
B\in\mathbb R^{d_{\text{out}}\times r}
\]

并且：

\[
r\ll\min(d_{\text{in}},d_{\text{out}})
\]

项目使用 rank 16。

### 为什么使用 LoRA？

- 冻结预训练主体，降低显存；
- 训练参数少；
- 防止购买样本较少时过度破坏通用兴趣；
- 便于为不同目标保存不同 adapter；
- 线上可以切换“购买优化”“点击优化”等 adapter。

LoRA 常插在线性投影层，如注意力的 Q/K/V/O 或 FFN 投影。回答时应以代码中实际插入的层为准，不应笼统声称“所有层都使用 LoRA”。

---

## 23. SFT 样本怎么构造？

对每个用户按时间排序，找到购买事件：

```text
A(pv), B(cart), C(pv), D(buy), E(pv), F(buy)
```

可以构造：

```text
输入 A,B,C       → 目标 SID(D)
输入 A,B,C,D,E   → 目标 SID(F)
```

关键原则：

1. 输入只能包含目标购买之前的行为；
2. 不能把目标商品本身泄露到历史中；
3. 历史保留行为类型和时间间隔；
4. 过长历史保留最近 \(L\) 条；
5. 无历史购买样本可以丢弃或交给冷启动分支；
6. 同一用户的验证和测试目标必须晚于训练目标。

为了控制热门商品偏置，还可以：

- 对热门购买降采样；
- 对冷门购买加权；
- 限制单用户贡献的最大样本数；
- 增加未购买商品作为辅助负样本。

# 第五部分：约束解码

## 24. 为什么不能直接逐级取最大概率？

逐级贪心可能得到：

```text
(17, 83, 199)
```

但数据集中可能不存在任何商品对应这个组合。

模型各层 token 都合法，不代表组合合法。因此要建立合法 SID 前缀树，也叫 Trie。

例如合法 SID：

```text
(1,3,7)
(1,3,9)
(1,5,2)
(4,8,6)
```

那么：

```text
前缀 (1)   → 只能扩展 3 或 5
前缀 (1,3) → 只能扩展 7 或 9
```

约束解码将非法 token 的概率设为负无穷：

\[
\log P(s_t\mid\cdot)=-\infty
\]

这样最终生成的一定是合法 SID。

---

## 25. Prefix-Constrained Beam Search

Beam Search 每层维护 \(B\) 个候选前缀：

```text
第一层：保留 B 个一级 token
第二层：对每个前缀扩展合法二级 token
第三层：继续扩展
最后：保留得分最高的完整 SID
```

序列得分通常是：

\[
score(s_{1:M})
=
\sum_{m=1}^{M}
\log P(s_m\mid s_{<m},H_u)
\]

生成完整 SID 后：

1. SID 映射回商品；
2. 删除用户已经交互过的历史商品；
3. 去重；
4. 取 Top-K。

### Beam 越大越好吗？

不一定。

Beam 增大会提高搜索覆盖率，但也会：

- 增加延迟；
- 增加显存；
- 有时降低多样性；
- 在概率校准不佳时偏向保守热门结果。

因此要同时报告效果和延迟。

---

## 26. KV Cache 能否复用？

可以，但要区分两个层面的复用。

### 用户历史的 Encoder 表示

对一个用户推荐多个候选时，用户历史只编码一次：

\[
H_u=\operatorname{Encoder}(history_u)
\]

所有 Beam 共享 \(H_u\)，不需要每个候选重新运行 HSTU Encoder。

这是最重要的复用。

### SID Decoder 的 KV Cache

生成第三级时，前两级 token 已经计算过。Decoder 可以缓存这些 token 的 Key/Value，不需要重新计算整个 SID 前缀。

如果父 Beam：

```text
(17,83)
```

扩展为：

```text
(17,83,24)
(17,83,91)
(17,83,105)
```

三个子 Beam 的 `(17,83)` 部分完全相同。应当：

1. 对父 Beam 只计算一次前缀 cache；
2. 子 Beam 引用或重排父 cache；
3. 只对新 token 进行一次 decoder step；
4. Top-K 选择后按父 Beam 索引重新排列 cache。

概念上：

```text
parent_cache
    ├── child token 24
    ├── child token 91
    └── child token 105
```

而不是把完整序列分别跑三遍。

### 如何避免重复计算？

- 合并所有 Beam 为一个 batch；
- 每层只调用一次 decoder step；
- 用 `parent_beam_index` 重排 KV；
- 同一父前缀共享历史 cache；
- 在 Trie 节点上预存合法 child token；
- 只对合法 child 计算或筛选概率；
- 对重复前缀进行 hash/dedup。

由于 SID 通常只有 3～4 层，Decoder KV Cache 的绝对收益可能不如长文本生成大；真正的大头往往是用户长历史编码。因此线上还应缓存用户兴趣表示。

# 第六部分：指标与延迟

## 27. HR@K

如果真实目标商品出现在 Top-K 中：

\[
Hit@K=1
\]

否则为 0。对全部用户求平均：

\[
HR@K
=
\frac{1}{N}
\sum_u Hit_u@K
\]

它只关心“有没有命中”，不关心排第几。

---

## 28. NDCG@K

NDCG 会奖励更靠前的正确结果。

单个真实目标时：

\[
DCG@K
=
\frac{\mathbf 1[\operatorname{rank}\le K]}
{\log_2(\operatorname{rank}+1)}
\]

真实商品排第 1，比排第 10 得分更高。

---

## 29. 类目多样性

一种简单定义是 Top-K 中不同类目比例：

\[
Diversity@K
=
\frac{|\{category(i):i\in TopK\}|}{K}
\]

也可以计算商品之间的平均类目距离或 embedding 距离。

需要注意：多样性不能脱离准确率单独评价。推荐结果全是不同类目但都不相关，也没有价值。

---

## 30. 生成式推荐的延迟来自哪里？

主要有：

1. 用户历史编码；
2. SID 多步自回归；
3. Beam 扩展；
4. 合法前缀查询；
5. SID 到商品映射；
6. 历史过滤和 Top-K 排序。

项目中的降延迟方法可以概括为：

- 用 Semantic ID 将百万级分类拆成少量小词表分类；
- 限制最大历史长度；
- 用户历史只编码一次；
- 使用增量解码和 KV Cache；
- Beam 并行批处理；
- Trie 前缀约束，提前剪除非法分支；
- 预存 Trie 节点的合法子 token；
- 在 GPU 上批量完成 Beam 打分；
- 只在最终 SID 上做 item 映射；
- 缓存活跃用户兴趣向量；
- 对无历史用户直接走热门 fallback；
- 根据线上 SLA 减小 Beam 或采用贪心/两阶段解码。

应该分别报告：

```text
Encoder latency
每个 SID step latency
Beam search latency
SID→Item latency
端到端 P50/P95/P99
```

只报告平均延迟是不够的。

# 8 个问题的可直接回答版

## 1. 曝光容量约束怎么实现？

> 我们先统计每个商品在训练行为中的加权曝光质量，然后在每一级 RQ 量化时，不仅考虑商品残差到 codeword 的距离，还维护每个 code 已承载的曝光质量。容量设置为平均曝光质量乘容量因子，例如 1.2。若最近 code 已达到容量，就选择距离次近且仍有容量的 code。这样平衡的是各 code 对训练 token 的实际承载量，而不只是商品数量。

## 2. 是否会增大量化误差？

> 会，这是明确的 trade-off。无约束最近邻本来就是局部最优，容量约束可能迫使商品选择第二近 code。项目中 embedding MSE 从约 0.01070 上升到 0.01141，增加约 6.6%。代价换来的是更平衡的码本负载和训练 token 分布，因此最终要结合 HR、NDCG、碰撞率和负载 Gini 判断，而不能只看重建误差。

## 3. SID 碰撞率和解决办法？

> 我们统计了完整 SID 的碰撞商品率、最大桶大小和 P95 桶大小。无约束碰撞率约 8.74%，加入容量约束后约 18.18%，说明负载均衡不等于组合唯一。项目通过在冲突 SID 后追加 Collision Token 进行桶内消歧，从而保证最终 SID 到商品一一映射。进一步可以增加码本或量化层，并加入去碰撞正则。

## 4. 使用什么方式 SFT？

> 先用全行为下一商品预测进行预训练，再以购买行为作为目标进行监督微调。微调采用 LoRA，冻结主干参数，在关键线性投影上学习 rank 16 的低秩增量。这样能够减少显存和可训练参数，也能降低购买数据较稀疏时对通用兴趣表示的破坏。

## 5. SFT 样本怎么构造？

> 对每个用户按时间排序，以每次购买事件作为监督目标，只使用该购买之前的点击、收藏、加购和购买历史作为输入。目标商品转换成多级 SID，训练时通过 Teacher Forcing 逐级预测。历史最长保留最近 200 条，并限制单用户样本数，防止超活跃用户主导训练。

## 6. 序列长度差异与冷启动怎么处理？

> 长序列采用最近行为截断，短序列通过 padding 和 attention mask 对齐。截断主要解决计算和兴趣时效性问题。完全没有行为的新用户属于冷启动，无法依赖序列模型，项目使用全局或分场景热门商品作为 fallback；如果有地区、设备、入口等侧信息，可以进一步采用分群热门或上下文模型。冷启动和长序列截断是两个不同问题。

## 7. 如何降低生成式推荐延迟？

> 主要做了六点：将百万级 Item 分类拆成小词表 SID 生成；限制用户历史长度；用户历史只编码一次；Decoder 使用增量推理和 KV Cache；使用合法前缀 Trie 提前剪枝；将 Beam 扩展批量并行化。此外线上可以缓存活跃用户表示，并根据延迟要求调整 Beam 宽度。

## 8. 分层 Beam Search 能否复用 KV Cache？

> 可以。所有 Beam 首先共享同一个用户历史表示；SID Decoder 中，同一父 Beam 的历史 token 也共享 KV Cache。每层扩展时只计算新 token，子 Beam 通过父 Beam 索引复制或重排 cache，而不是重新计算完整前缀。合法子节点直接从 Trie 获取，所有父 Beam 的扩展合并成一个 batch，再进行全局 Top-K。由于 SID 只有几层，Decoder cache 的收益有限，但用户历史编码复用非常关键。
