# Sona：共享用户状态的生成召回与排序

[Sona Technical Report](https://arxiv.org/abs/2608.11015)，Yandex Music，2026-08-11首发，阅读08-12 v2。[全文](https://arxiv.org/html/2608.11015v2)。线上范围是智能音箱My Vibe入口。

## 原pipeline与问题

原生产链路有15个以上候选源，再经粗排、精排，使用数百特征与Argus等Transformer信号。多个阶段维护不同目标和用户状态；单纯生成SID只代表“像历史下一首”，未必兼顾点赞、时长等排序偏好。

Sona把生成候选和排序放入共享encoder的单一部署模型，保留硬业务规则；**单模型不等于内部没有生成和排序模块**。

## 数据流与关键模块

- 离线tokenizer：冻结Qwen2.5-Omni处理音频前90秒及元数据 → 协同pair对比学习与内容对齐refinement → 残差量化，形成3层、每层32000码的SID。相同SID可对应多首歌。
- 用户历史编码：最近与更早事件先交叉读取，再做一次全历史自注意力，深层只处理最近2048事件；最终输出保留全部8192位置，更旧位置编码较浅。这是分配计算深度，不是简单丢弃老历史。
- decoder以共享历史状态生成合法SID beam；SID映射展开所有冲突歌曲。
- Ranking Module用候选ID、SID及前缀特征cross-attend同一历史状态，输出多反馈分数，用固定权重排序。
- 训练联合正反馈SID NTP与教师蒸馏。教师对当前生成候选和历史曝光候选都提供多头分数，学生用MAE学习；梯度共同更新encoder。最终线上不部署教师，早期实验1–4曾临时带教师，必须分开。

## 收益链路

以下传导关系是本库的**机制推断**；其中引用的消融或A/B是支持证据，不代表每一环节都已被独立因果识别。

**表示与候选链路：**音频/文本内容先验+共听关系对齐 → SID兼顾内容相似与实际可替代性 → 生成分支更符合音乐偏好 → 改善候选覆盖。若只用内容量化，可能把听感类似但使用场景不同的歌合并。

**生成—排序协调链路：**同一用户状态接受NTP与多反馈排序监督 → 状态既能产候选也能分辨其业务价值 → 减少多级模型表征不一致；候选展开后排序还能处理SID碰撞。联合训练收益与消融可支持“共享有用”，但不能宣称完全消灭所有目标冲突。

**质量—成本链路：**强教师把复杂排序能力蒸馏给共享模型 → 线上不用再编码一遍长历史 → 成本允许扩大上下文 → 长期偏好与短期意图共同作用。蒸馏有质量损失，实验4教师仍明显更好，收益来自整个取舍而非“学生无损超越老师”。

## baseline与替换关系

相对OneRec：同属生成式推荐，但Sona明确保留模型内部Ranking Module与多反馈教师蒸馏；不能将概率生成视为最终utility排序。相对GenRec：GenRec直接目录head打分，Sona先SID生成再对生成候选排序。与Gryphon共享生成/排序设计；与Google长序列Folding都是计算预算分配方案，但压缩方式不同。最终替换了该入口原候选源、粗排、精排级联，仍依赖目录映射与硬规则。

## 最小实验与失败判据

- **假设A：共享encoder有正迁移。**固定候选tokenizer、参数和计算，比较分离encoder与共享encoder，监控两任务梯度夹角、召回与排序双指标；只改善排序却压低召回时需分支或loss重配。
- **假设B：教师是在教业务排序。**同候选比较概率排序、蒸馏排序与直接教师；按反馈类型分析，排除只是候选源变化。
- **假设C：长历史有效而非数据或上线周期变化。**同场AB做2k/8k × 有无压缩；固定训练时间或同时报告成本，不跨实验直接相减。
- 灰度前检查SID冲突展开、无效ID、热门偏置、目录更新及业务硬规则；先作为新召回源再扩大替换范围，是我的迁移建议，不是论文的唯一上线顺序。
