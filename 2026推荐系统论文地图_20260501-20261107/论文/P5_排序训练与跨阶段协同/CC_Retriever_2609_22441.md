# CC Retriever：让粗排用上实时关系交叉特征

[Connected Content Retriever: Dense Graph Edge Features Powering Pre-Ranking at LinkedIn](https://arxiv.org/abs/2609.22441)，2026-09-18 v1。[全文](https://arxiv.org/html/2609.22441v1)。

## 为什么做、解决哪一层

LinkedIn关系内容占大量曝光；一二度关系展开后，单次请求仍有数万候选，粗排必须在120ms p99预算内筛出数百条。双塔易部署，但“当前用户与作者关系强不强”属于pair特征，不能完整分解成静态物品向量。CPU粗排受成本限制，难用复杂关系信号。

本文保留图关系候选筛选和后续精排，重做**连接内容的粗排**；不是对十亿文档逐个跑大型精排网络。

## 方法与系统数据流

图过滤先得到候选文档ID → 请求带入用户向量、请求特征和按作者ID组织的关系特征 → GPU取预存文档向量/属性 → 在线join用户—作者边特征 → MLP多目标打分 → top-k进入下游。

关键区分两个查找：

- **边特征join：**把用户的作者亲密度表排序，对候选作者ID并行二分查找，复杂度从朴素$O(NK)$变成约$O((N+K)\log K)$，join约5–10ms。
- **文档ID定位：**后来移到CPU并行hash map，GPU专注gather和矩阵计算；不能把两者混写成“所有查找都在GPU”。

模型拼接内容embedding、用户向量、关系交叉与物品特征，预测click、贡献行为、long-dwell，线性权重合成分数；训练带位置去偏头，推理固定位置。索引静态特征与动态互动统计分流更新，兼顾新鲜度。

## 收益链路：为什么能传到业务

**关系信息链路：**粗排获得即时用户—作者关系 → 能区分语义类似但社交价值不同的帖子 → 减少精排本来会选中的内容被粗排提前丢弃 → 下游可选集合更好 → 时长和互动提高。边特征消融支持信息增量；精排oracle recall是中间证据，线上AB证明整套系统有效。

**工程使能链路：**高效join、索引和batching → 交叉特征模型能在既定SLA服务 → 复杂评分从“离线可行”变成“真实可用”。纯内核提速不会自动增加用户收益，只有省下预算用于更好的候选选择才会传导。

**我的推断：**在强关系社交场景，关系信息的价值可能大于内容语义升级；在陌生人推荐或匿名电商，收益顺序可能相反。

## 替换、互补与迁移边界

与LiNR/GPU-RAR属于把更多评分计算搬到候选阶段的系统路径；相较纯双塔，新增不可分解pair特征，代价是在线组装和批处理复杂度。与精排序列模型互补，本文甚至使用其用户向量；与生成式召回可作为并行来源或后续粗排，不能仅凭“retriever”名称当作同接口替换。

## 最小验证

1. **假设A：主要漏选来自关系信号缺失。**固定候选集合，构建精排oracle recall；逐组加关系特征，统计强关系/弱关系/陌生人的差异。若边特征无收益，先别做昂贵GPU join。
2. **假设B：大模型而非新增信号主导。**相同特征比较小MLP/大MLP，相同网络比较有/无边特征，测Recall@k、实际点击质量、p99和单位请求成本。
3. 做影子流量回放检查索引更新延迟、缺失边默认值、CPU查找与GPU队列，避免离线优势被陈旧特征和尾延迟抵消。
