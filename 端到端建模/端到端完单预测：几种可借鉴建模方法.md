# 1. 漏斗多任务架构：V1 MMoE/PLE 与 V2 AITM/Sequential Funnel

# 1.1 这是什么

这类方法把“端到端完单”建模成一个多阶段漏斗，并且在网络结构里显式区分不同阶段任务。
打车链路可以抽象成：

```text
冒泡
  -> 发单
  -> 应答
  -> 未取消
  -> 完单

```

模型同时预测多个阶段：

```text
p_call       = P(发单 | 冒泡)
p_accept     = P(应答 | 冒泡)
p_no_cancel  = P(未取消 | 冒泡)
p_finish     = P(最终完单 | 冒泡)

```

这类方法和 ESMM/ESM2/HM3 的关系是：

```text
ESMM/ESM2/HM3:
  更偏任务拆分、样本空间、辅助标签设计
MMoE/PLE/AITM:
  更偏真正的网络结构，解决多阶段任务怎么共享、怎么交互

```

所以这里重点讲架构，而不是只讲 loss。

# 1.2 V1: MMoE / PLE 漏斗架构

V1 的目标是：不同漏斗阶段共享一部分信息，但又允许每个阶段使用不同的专家表示。

因为打车各阶段依赖的信息不完全一样：

```text
p_call:
  更依赖用户历史、价格、ETA、当前意图
p_accept:
  更依赖当前供需、区域应答率、在线司机数
p_no_cancel:
  更依赖等待时间、价格、用户历史取消习惯、供需压力
p_finish:
  综合依赖用户意图、供给可得性、取消风险

```

# MMoE 怎么做

MMoE 的结构是：

```text
输入特征 x
  -> shared experts
       expert_1(x)
       expert_2(x)
       ...
       expert_k(x)
  -> 每个任务一个 gate
       gate_call
       gate_accept
       gate_no_cancel
       gate_finish
  -> 每个任务得到自己的表示
  -> 各阶段 head

```

迁移到当前场景：

```text
pid_history_seq_30
当前用户特征
当前冒泡/请求特征
当前供需特征

        ||

        v
UserSeqEncoder + FeatureEncoder

        ||

        v
MMoE experts

        ||

        v
p_call / p_accept / p_no_cancel / p_finish

```

它的好处是：不同任务可以通过 gate 自动选择不同 expert。例如发单任务更选用户意图 expert，应答任务更选供需 expert。

# PLE 怎么做

PLE 比 MMoE 更进一步，把 expert 分成：

```text
shared experts
task-specific experts

```

结构可以理解成：

```text
输入特征 x
  -> shared experts
  -> call-specific experts
  -> accept-specific experts
  -> cancel-specific experts
  -> finish-specific experts
  -> progressive extraction
  -> task heads

```

迁移到打车：

```text
call-specific experts:
  学用户是否愿意发单
accept-specific experts:
  学当前供需下是否能应答
cancel-specific experts:
  学等待、价格、历史取消习惯
finish-specific experts:
  学最终综合完单

```

PLE 适合任务差异比较大的场景。打车漏斗里，发单是用户意图任务，应答更偏供给任务，取消是用户和履约混合任务，所以 PLE 比单纯 shared-bottom 更合理。

训练目标：

```text
Loss = L_finish
    + λ1 * L_call
        + λ2 * L_accept
        + λ3 * L_no_cancel

```

其中 `L_finish` 是主任务，中间阶段任务是辅助监督。

# 1.3 V2: AITM - Sequential Funnel 漏斗架构

V2 更进一步：不仅多任务共享参数，还显式建模阶段之间的依赖关系。

AITM 的核心思想是：多阶段转化任务之间不是并列关系，而是有顺序依赖。前一阶段任务表征会影响后一阶段任务。

迁移到打车，就是：

```text
发单任务表示
  -> 应答任务表示
  -> 未取消任务表示
  -> 完单任务表示

```

结构可以写成：

```text
h0 = Encoder(x)
h_call = Tower_call(h0)
p_call = Head_call(h_call)
h_accept = Transfer_accept(h0, h_call)
p_accept = Head_accept(h_accept)
h_no_cancel = Transfer_cancel(h0, h_accept)
p_no_cancel = Head_cancel(h_no_cancel)
h_finish = Transfer_finish(h0, h_no_cancel)
p_finish = Head_finish(h_finish)

```

这里的 `Transfer` 可以是 attention、gate、MLP 或者 cross-stitch 类模块。关键是后一阶段不是孤立预测，而是接收前一阶段的任务表示。

也可以更直接地做 Sequential Funnel：

```text
h1 = f_call(h0)
p_call = head_call(h1)
h2 = f_accept(concat(h0, h1, p_call))
p_accept = head_accept(h2)
h3 = f_cancel(concat(h0, h2, p_accept))
p_no_cancel = head_cancel(h3)
h4 = f_finish(concat(h0, h3, p_no_cancel))
p_finish = head_finish(h4)

```

注意：这里传递的是预测值或隐层表示，不能传真实 label，否则会标签泄漏。

# 1.4 这些方法能借鉴什么

| 方法            | 主要思想                                               | 对当前场景的作用                       |
| ------------- | -------------------------------------------------- | ------------------------------ |
| Shared-Bottom | 所有任务共享底层 encoder，各阶段独立 head                        | 最简单的漏斗 baseline                |
| MMoE          | 多个 expert，每个任务用 gate 选择 expert 组合                  | 适合不同阶段依赖不同特征                   |
| PLE           | shared experts + task-specific experts，逐层抽取共享/独有信息 | 适合发单、应答、取消、完单差异较大的任务           |
| AITM          | 显式建模多阶段任务的顺序依赖                                     | 最贴近“冒泡 -> 发单 -> 应答 -> 完单”的漏斗结构 |

# 1.5 为什么这么做

这样做的好处是：

- 不同阶段可以学习不同的信息侧重。
- 比单个 `p_finish` head 更可解释。
- 比简单多个并列 head 更能表达漏斗依赖。
- 如果用 AITM/Sequential Funnel，可以显式把“前一阶段影响后一阶段”建进网络。
需要注意的是：

- 任务更多，loss 权重需要调。
- AITM/Sequential Funnel 要避免真实标签泄漏，只能传预测值或隐层表示。
- 后段任务样本更少，训练时需要 mask 或样本权重。
- 如果强制链式乘法，误差可能累积；第一版可以最终仍用 direct `p_finish`，漏斗任务主要辅助训练和解释。

# 2. 不用漏斗：直接做序列/表征模型

# 2.1 这是什么

不显式拆发单、应答、取消等阶段，而是直接预测：

```text
P(完单 | 当前冒泡, 用户历史, 当前供需)

```

模型只需要一个主任务：

```text
p_finish

```

这是最直接的端到端建模方式。

# 2.2 怎么做

输入：

```text
用户历史行为序列 pid_history_seq_30
当前用户特征
当前冒泡/请求特征
当前供需特征

```

结构：

```text
pid_history_seq_30
  -> GRU / Transformer / DIN-style attention
  -> h_user
当前冒泡特征 + 当前供需特征
  -> MLP
  -> h_context
concat(h_user, h_context)
  -> MLP
  -> p_finish

```

用户历史 event 可以包含：

```text
event_type
event_time_gap
是否发单
是否应答
是否取消
是否完单
历史价格
历史 ETA
历史距离
历史供需状态

```

# 2.3 为什么这么做

优点：

- 最简单，最容易做 baseline。
- 直接优化最终目标，不需要设计漏斗公式。
- 不会出现链式概率误差累乘。
- 对数据要求更低，只要有最终完单标签即可。

缺点：

- 可解释性弱。
- 完单标签稀疏时可能不如多任务稳定。
- 不知道模型低分是因为不发单、供给差、还是取消风险高。

# 2.4 适合什么时候用

适合作为第一版 baseline：

```text
V0 = 用户历史序列 + 当前冒泡特征 + 当前供需特征 -> p_finish

```

如果这个模型已经效果不错，可以在它上面再加辅助任务，而不是一开始就做复杂漏斗。

# 2.5 可借鉴论文

|                                       |                                                          |                                                |
| ------------------------------------- | -------------------------------------------------------- | ---------------------------------------------- |
| 论文/方法                                 | 主要思想                                                     | 在当前场景怎么借鉴                                      |
| DIEN: Deep Interest Evolution Network | 用 GRU 提取用户兴趣序列，再建模兴趣随时间演化                                | 把用户历史冒泡、发单、取消、完单当作行为序列，学习用户出行意图变化              |
| DSIN: Deep Session Interest Network   | 把用户行为按 session 分组，session 内 self-attention，session 间建模演化 | 打车天然有 trace/session，可用于建模多次冒泡、改地址、取消重发         |
| SASRec / BERT4Rec                     | 用 Transformer 直接建模行为序列                                   | 可作为通用序列 baseline，直接用 `pid_history_seq_30` 预测完单 |
| ~~HSTU~~                              | ~~面向大规模高基数行为序列的生成式推荐序列架构~~                               | ~~当前长度 30 不一定需要，但如果后续扩展到更长用户历史，可以参考其序列表征思路~~   |

优先级建议：

```text
DIEN / DSIN > SASRec / BERT4Rec > HSTU

```

因为当前打车场景更关注“行为演化”和“session/trace 结构”，DIEN 和 DSIN 更贴近。

# 3. Retrieval + Attention 方法

# 3.1 这是什么

Retrieval + Attention 的核心想法是：用户历史很多，但不是每条历史都和当前冒泡相关。先从历史里找出和当前场景最相似的行为，再做 attention 聚合。

例如当前是：

```text
工作日晚高峰
相似 OD
相似价格
相似 ETA
相似供需

```

那模型应该更关注用户过去在类似场景下是否发单、取消、完单。

# 3.2 怎么做

第一步，把当前冒泡表示成 query：

```text
q = Encoder(当前冒泡特征 + 当前供需特征)

```

第二步，把用户历史每个 event 表示成 key/value：

```text
k_i, v_i = Encoder(历史第 i 条行为)

```

第三步，计算当前冒泡和历史行为的相关性：

```text
score_i = sim(q, k_i)

```

第四步，选出 topK 或直接 attention pooling：

```text
α_i = softmax(score_i)
h_history = Σ α_i * v_i

```

最后预测：

```text
concat(q, h_history)
  -> MLP
  -> p_finish

```

# 3.3 在当前场景怎么用

历史行为序列可以是 `pid_history_seq_30`。每条历史包含：

```text
event_type: 冒泡/发单/应答/取消/完单
历史 OD / 城市 / 格子
历史价格 / ETA / 距离
历史供需
历史结果
距离当前时间间隔

```

当前 query 包含：

```text
当前 OD
当前价格
当前 ETA
当前供需
当前时间
当前城市/格子

```

模型会自动学习：

```text
当前场景更像用户过去哪几次出行尝试？
那些尝试最后是取消还是完单？

```

# 3.4 为什么这么做

优点：

- 比普通序列模型更关注“和当前请求相关”的历史。
- 用户历史行为可解释：可以看到模型关注了哪些历史事件。
- 对长度 30 的序列很合适，计算成本不高。
- 很适合打车这种强上下文场景，因为同一个用户在不同 OD、价格、供需下行为差异很大。

缺点：

- 需要设计好 event 表示和当前 query 表示。
- 如果历史很短或用户很新，收益有限。
- 如果只用 topK retrieval，召回规则会影响效果。

# 3.5 冷启动怎么处理

Retrieval + Attention 遇到冷启动时，不建议简单把历史序列全填 0。更稳的做法是区分三种情况。

第一种，没有用户历史：

```text
pid_history_seq_30 为空

```

可以使用：

```text
history_mask = 0
h_history = learned_empty_history_embedding

```

也就是给模型一个可学习的“无历史表示”，而不是让模型误以为历史特征真的都是 0。此时模型主要依赖：

```text
当前冒泡特征
当前供需特征
当前用户基础特征
城市/区域/时间段统计 prior

```

第二种，历史不足 30 条：

```text
真实 event 3 条
PAD event 27 条
mask = [1, 1, 1, 0, ..., 0]

```

attention 时只看真实 event：

```text
PAD 位置 attention score = -inf

```

同时加入：

```text
history_len

```

让模型知道这个用户历史较短。

第三种，有历史但和当前场景不相似：

```text
topK similarity 都较低

```

这时可以用 gate 控制历史和当前上下文的融合权重：

```text
h_history = RetrievalAttention(history_seq, current_query)
h_context = Encoder(current_attempt_features, supply_features, user_profile)
g = sigmoid(MLP(history_len, max_similarity, avg_similarity, h_context))
h_final = g * h_history + (1 - g) * h_context

```

如果历史充分且相似，`g` 更大；如果无历史、历史短或不相关，`g` 更小，模型自然退化为当前上下文模型。

还可以补充群体统计特征作为冷启动 prior：

```text
城市-区域-时间段完单率
OD 类型完单率
价格分桶完单率
ETA 分桶完单率
供需分桶完单率
新用户完单率
相似用户群完单率

```

一句话：冷启动不是硬凑历史，而是用 `PAD + mask + learned empty embedding + history_len/similarity 特征 + context fallback + 群体 prior`，让模型在无历史或历史不可靠时仍然能稳定预测。

# 3.6 可借鉴论文

|                                      |                                               |                                                  |
| ------------------------------------ | --------------------------------------------- | ------------------------------------------------ |
| 论文/方法                                | 主要思想                                          | 在当前场景怎么借鉴                                        |
| DIN: Deep Interest Network           | 用当前候选 item 作为 query，对用户历史行为做 target attention | 用当前冒泡作为 query，attention 用户历史冒泡/发单/取消/完单          |
| ~~SIM: Search-based Interest Model~~ | ~~先从超长历史中检索相关行为，再对检索结果做精排 attention~~         | ~~如果未来用户历史从 30 条扩展到几百/几千条，可以先召回相似历史再 attention~~ |
| ~~TWIN / TWIN V2~~                   | ~~面向超长生命周期行为，做压缩、检索和 target attention~~       | ~~适合工业级长序列升级，不建议第一版就做~~                          |
| MIND / ComiRec                       | 把用户表示成多个兴趣向量，再和当前候选匹配                         | 如果用户出行目的差异大，如通勤、机场、跨城、夜间出行，可以借鉴多兴趣建模             |

优先级建议：

```text
DIN > SIM > TWIN/TWIN V2 > MIND/ComiRec

```

当前序列长度只有 30，最适合先做 DIN-style target attention；如果后续历史长度显著增加，再考虑 SIM 或 TWIN。
