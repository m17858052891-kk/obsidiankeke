# D3-Subsidy：城市级司机补贴的序贯控制

论文：[D3-Subsidy: Online and Sequential Driver Subsidy Decision-Making for Large-Scale Ride-Hailing Market](https://arxiv.org/abs/2605.20036)

版本：arXiv v4，2026-05-28
作者：Taijie Chen 等
场景：滴滴网约车司机侧补贴控制
代码/数据：论文未在摘要页给出公开代码链接

> **一句话总结：**D3-Subsidy 面向城市级司机补贴控制：先根据已经观察到的城市运营历史，用前缀条件扩散模型生成未来供需与 KPI 轨迹，再通过条件逆动力学反推出当前城市补贴强度，最后用拉格朗日对偶映射将城市级控制快速转换成订单—司机级补贴。

## 1. 总览

在一天的运营过程中不断观察城市供需状态，然后每隔一段时间调整整体补贴强度。

可以把它理解成下面这条闭环：

```text
城市当前状态
  -> 城市级补贴强度
  -> 司机接单和完单行为
  -> Rides、GMV、补贴消耗
  -> 更新下一窗口状态
  -> 继续调整补贴
```

D3-Subsidy 的主要决策对象是低维的城市级控制信号，而不是实时为每一个订单—司机组合运行一个复杂优化器。随后，系统用一个解析的对偶映射，把这个城市级信号转换成细粒度的司机补贴。

- D3-Subsidy 决定城市在当前时间窗口应该多激励司机；
- D3-Subsidy 的反馈是司机接单、完单和城市供需变化。

## 2. Abstract 摘要

### 2.1 原文内容的对应翻译

网约车平台运行在高度动态的环境中，需要平衡司机供给和乘客需求。司机侧补贴是调节供需的重要手段，可以提升完单量（Rides）和总交易额（GMV）等关键指标。

但要把补贴策略部署到生产环境，同时需要满足三个条件：

1. 对随机供需冲击具有响应能力；
2. 严格满足补贴率上限；
3. 能够在城市规模上低延迟执行。

这些要求使得昂贵的逐订单优化不适合生产部署，因此需要一个面向城市、能够前瞻规划并显式考虑约束的在线序贯决策控制器。

论文提出 D3-Subsidy，即 Dynamic Driver-side Diffusion-based Subsidy，一个面向城市级补贴控制、可部署的层级扩散框架。

为了解决训练阶段和推理阶段之间的信息差异，论文使用前缀条件扩散模型：根据不可修改的历史观测，生成可能的未来轨迹，使训练过程与线上固定历史的部署形式保持一致。

随后，论文使用上下文条件逆模块，将生成的未来计划解码成低维的城市级控制信号。为了实现大规模执行，论文又通过拉格朗日对偶推导出的映射，把城市级计划连接到细粒度调度，并将补贴率上限直接嵌入订单—司机激励中，不需要每次再运行迭代优化。

此外，论文采用多城市预训练和参数高效微调，使模型能够迁移到运营特征不同的城市。

离线实验显示，D3-Subsidy 可以提升 Rides 和 GMV，同时改善补贴率约束满足情况；真实线上 A/B 测试也显示，在预算相关违约指标保持在运营阈值内的情况下，业务指标得到提升。

### 2.2 摘要在整篇论文中的作用

摘要已经给出了完整方法链：

```text
城市历史前缀
  -> 扩散生成未来轨迹
  -> 逆动力学解码城市级控制
  -> 对偶映射为订单—司机级补贴
  -> 约束下提升 Rides / GMV
```

其中最关键的不是“用了扩散模型”本身，而是三个工程问题被同时处理：

- 未来规划：不能只对当前窗口做反应，要考虑补贴对后续预算和供需的影响；
- 约束执行：补贴率上限不能只写进 reward 后就不管；
- 规模部署：不能把复杂求解器放在每个订单—司机对的实时链路上。

## 3. Introduction 引言

### 3.1 运营背景：为什么需要司机侧补贴

网约车平台连接乘客和司机，系统中的运营决策来自三方的持续互动。乘客发起订单后，平台观察局部供需、附近司机可用性等信息，并决定是否给司机提供额外补贴。

司机收到的补贴会改变订单对司机的吸引力，从而影响司机是否接受并完成订单。订单被处理后，平台的司机分布、剩余供给、空间需求和后续匹配机会都会发生变化。

因此，补贴不是一次性促销，而是一个闭环控制变量：

```text
补贴
  -> 司机接受意愿
  -> 完单和司机供给
  -> 乘客服务质量与平台收入
  -> 下一时刻供需状态
```

### 3.2 补贴为什么是一个长期序贯问题

平台通常给补贴设置一个较长周期的预算或补贴率上限，例如一天内总补贴不能超过总 GMV 的某个比例。

这意味着当前窗口的补贴决定会产生两个同时存在的影响：

- **即时影响：**提高当前司机的接单和完单概率；
- **未来影响：**消耗剩余预算，改变后面时间窗口可以使用的补贴空间。

因此，目标不是简单地让当前窗口完单量最大，而是：

> 在整个运营周期内最大化平台累计收益，同时让补贴支出保持在约束范围内。

### 3.3 现有生产机制的两个特点

论文指出，生产系统通常采用两层机制：

1. 平台在较粗的时间粒度上决定一个城市级补贴强度；
2. 系统再根据订单价值、接驾距离等可观测特征，将城市级强度映射到具体订单—司机对。

这么做有三个好处：

- 决策维度低，能够满足城市级低延迟要求；
- 同类订单—司机条件可以使用一致的补贴规则；
- 细粒度补贴的计算可以使用解析公式，而不是实时调用大型优化器。

### 3.4 为什么不能直接用普通在线 RL

标准在线 RL 需要通过试错探索来学习策略，但司机补贴有严格预算约束。激进探索可能带来：

- 补贴预算提前消耗；
- 后续时间段没有足够补贴；
- 运营指标或补贴率超过阈值；
- 探索失败造成不可逆的业务损失。

另一方面，城市供需环境具有随机性和非平稳性，普通 RL 还可能需要大量在线交互和较长时间才能稳定学习。

因此论文选择离线学习：先利用历史城市运营轨迹学习策略，再在仿真环境和线上 A/B 测试中评估。

### 3.5 论文提出的核心思路

论文的中心想法可以拆成四步：

1. **把城市级补贴控制写成序贯决策问题。**当前补贴会影响后续状态和剩余预算；
2. **用前缀条件扩散生成未来轨迹。**历史前缀是真实已经发生的部分，不能被改写，只对未来后缀进行生成；
3. **用上下文条件逆动力学从轨迹反推控制信号。**同样的状态变化在不同目标和补贴率约束下，可能对应不同的补贴动作，所以动作解码必须显式读入上下文；
4. **用约束感知得分和对偶映射控制可行性。**轨迹评分惩罚补贴率超限，部署时用解析映射快速生成订单—司机级补贴。

### 3.6 引言贡献的对应总结

论文在引言中强调了三类贡献：

#### 贡献一：把司机补贴定义成城市级在线序贯控制

它不把补贴看成静态的个体分配，而是建模当前激励、未来预算可行性和城市 KPI 之间的耦合。

#### 贡献二：提出扩散式离线控制框架

框架包含：

- 前缀条件扩散，用历史前缀生成未来城市轨迹；
- 约束感知得分，鼓励补贴率可行的轨迹；
- 上下文条件逆动力学，把轨迹解码为可控的城市级动作。

#### 贡献三：验证跨城市迁移和线上效果

论文使用三个城市的数据进行离线评估，并报告真实线上 A/B 测试结果。摘要和引言报告的线上提升是：Rides 提升 1.59%，GMV 提升 2.06%，同时保持补贴率约束。

## 4. Preliminary：预备知识

Preliminary 主要完成三件事：

1. 解释网约车补贴在平台运营中扮演什么角色；
2. 将补贴问题写成带预算约束的优化问题；
3. 把原本的细粒度补贴分配，压缩为城市级的在线序贯控制。

### 4.1 2.1 Operations in Ride-hailing Platforms：网约车平台中的运营流程

#### 4.1.1 原文内容的对应翻译

在网约车平台中，运营决策来自乘客、司机和平台之间的持续交互。乘客提交出行请求后，平台首先评估局部供需情况，例如附近可用司机数量、预计需求等，然后决定司机侧补贴，以影响司机参与。

补贴作为额外报酬提供给附近司机，目的是提高司机接受并完成订单的意愿。司机会根据补贴、行程距离和订单带来的收益判断是否接受。

在司机对补贴做出反应后，平台再将订单匹配给一个或多个候选司机，并更新系统状态，例如司机可用性、司机空间分布以及当前供需关系。

这个过程会在城市内、多个区域和连续时间窗口中反复发生，形成一个大规模动态市场。补贴干预是平台影响司机行为、改善司机—乘客匹配结果的重要控制手段。

#### 4.1.2 通俗解释

平台不能简单地理解为“给钱就能得到更多司机”。补贴的影响要经过司机行为才能体现：

```text
补贴强度
  -> 订单对司机的吸引力
  -> 接单概率
  -> 完单概率
  -> 司机供给和乘客服务
  -> 后续城市状态
```

而且这个影响会因城市、区域、时间和订单特征发生变化。因此模型需要同时看当前城市状态和运营上下文，而不能只根据单个订单的静态特征决定补贴。

#### 4.1.3 这一节在论文中的作用

这一节把补贴从一个“金额预测问题”定义成了“市场状态控制问题”。后面的状态、动作、奖励和转移，都来自这里的闭环运营过程。

### 4.2 2.2 Problem Formulation：问题建模

#### 4.2.1 原文内容的对应翻译

下面沿用论文含义，用统一记号重写；变量名和论文排版可能不完全一致。

论文考虑一种基于广播的订单调度系统。当一个订单被广播给候选司机时，平台可以提供一定金额的补贴，激励司机接受并完成订单。

每个订单—司机对都有一个订单特定的补贴上限。同时，平台希望在全局日补贴率约束下最大化总收益。补贴率约束可以理解为：整个运营周期内的补贴支出不能超过总收入或 GMV 的某个比例，并允许一个由平台设定的容差，以适应需求波动和测量噪声。

对一个订单—司机对，记：

- $y_{ij}$：在补贴 $s_{ij}$ 下完成订单的概率；
- $r_{ij}$：订单完成后平台获得的收益或 GMV；
- $s_{ij}$：给该订单—司机对的补贴金额；
- $B$：全局补贴率约束或预算上限；
- $u_{ij}$：该订单—司机对是否被选择或是否完成。

论文的核心优化可以概括为：

$$
\max_{s_{ij}}
\sum_{i,j} y_{ij}(s_{ij})r_{ij}
$$

同时满足：

$$
\sum_{i,j} y_{ij}(s_{ij})s_{ij}
\leq
B\sum_{i,j}y_{ij}(s_{ij})r_{ij}
$$

以及每个订单—司机对的补贴范围约束：

$$
0\leq s_{ij}\leq \bar s_{ij}.
$$

这里的核心不是公式中的具体符号，而是：提高补贴可能提升完成概率和平台收益，但同时会消耗更多补贴，因此需要在收益和补贴率之间做全局权衡。

#### 4.2.2 为什么使用拉格朗日对偶

如果直接对数百万个订单—司机对同时求解补贴，实时计算成本会很高。论文对全局补贴率约束引入拉格朗日乘子，将约束问题转化为带惩罚价格的局部决策。

直观上，拉格朗日乘子表示“补贴预算有多紧”：

- 补贴率约束宽松时，补贴的影子价格低，系统可以更积极；
- 补贴率约束紧时，补贴的影子价格高，系统会抑制补贴。

在局部线性完成概率模型下，论文得到一个可闭式计算的订单—司机级补贴形式。可以抽象写成：

$$
s_{ij}^{*}
=
\operatorname{clip}
\left(
\text{订单/司机上下文收益项}
-
\text{全局约束乘子}
\times
\text{补贴成本项}
\right).
$$

论文进一步把这个细粒度规则改写为城市级控制量的映射：模型只需要决定一个城市级补贴强度，具体订单—司机补贴由解析规则计算。

#### 4.2.3 这个闭式映射到底解决了什么

它解决的不是“让模型预测每个司机应该拿多少钱”，而是把实时决策维度从大量订单—司机对压缩为一个低维的城市级动作：

```text
城市级控制 u_t
  -> 对偶映射
  -> 每个订单—司机对的补贴 s_{ij,t}
```

这样既保留了订单和上下文之间的差异，又避免在线逐对求解复杂优化问题。

#### 4.2.4 这一节在论文中的作用

2.2 给出了 D3-Subsidy 的执行接口：

- 学习模型负责预测和生成城市级控制；
- 对偶映射负责将控制信号转成细粒度补贴；
- 补贴率上限通过全局乘子和 clipping 进入部署链路。

后续模型并不是直接对订单—司机补贴做扩散生成，而是对城市级运营轨迹和低维动作做建模。

### 4.3 2.3 Sequential Subsidy Decision-Making：序贯补贴决策

#### 4.3.1 原文内容的对应翻译

前面的对偶公式给出了在给定全局乘子时的订单—司机级补贴规则，但在实时环境中，直接对数百万个订单—司机对做优化仍然不可行。

因此，生产系统在较粗的时间频率上更新一个城市级控制信号，例如每两分钟更新一次，然后在当前时间窗口内使用该信号生成具体激励。

论文将这个在线控制过程建模为一个马尔可夫决策过程（MDP）。

#### 4.3.2 状态 State

状态表示当前时间窗口下可观察到的城市市场状态，例如：

- 供需缺口；
- 司机供给和空间分布；
- 订单需求和空间分布；
- 时间上下文；
- 当前已经实现的补贴率；
- 当前累计 Rides、GMV 或其他 KPI。

为了追踪全局约束是否满足，论文还把相对于 GMV 的已实现补贴率加入状态。于是状态不只描述“城市现在缺多少司机”，还描述“今天的补贴额度已经用了多少”。

可以写成：

$$
s_t=
\bigl[
\text{market state}_t,
\text{realized subsidy rate}_t,
\text{time context}_t
\bigr].
$$

这里的状态是城市级状态，不是一个订单—司机对的个体特征。

#### 4.3.3 动作 Action

动作是一个标量的城市级控制量：

$$
a_t=u_t.
$$

它表示当前时间窗口整体应该采用多强的司机补贴策略。系统拿到 $u_t$ 后，再通过前面的对偶映射生成每个订单—司机对的补贴。

因此要区分：

- **模型动作：**城市级补贴控制 $u_t$；
- **执行补贴：**订单—司机级补贴 $s_{ij,t}$；
- **司机行为：**是否接受和完成订单；
- **环境结果：**Rides、GMV、DRV、补贴率和下一窗口状态。

#### 4.3.4 从城市级控制到订单—司机级补贴

在当前窗口，系统执行：

$$
u_t
\xrightarrow{\text{dual mapping}}
s_{ij,t}.
$$

这个映射使一个低维动作能够影响大量订单—司机对。它还能够根据订单价值、接驾距离等上下文产生不同金额的补贴，同时保持相同可观测条件下的规则一致性。

#### 4.3.5 奖励 Reward 和状态转移 Dynamics

当前窗口执行补贴后，司机产生接受和完单结果，系统得到该窗口的 KPI。论文将时间窗口奖励定义为目标 KPI 的聚合，例如：

$$
r_t=\text{Rides}_t
$$

或者使用窗口 GMV 等业务指标。

环境根据执行结果更新状态：

$$
(s_t,a_t)
\rightarrow
(r_t,s_{t+1}).
$$

状态转移包含随机市场动态，例如需求变化、司机流入流出、订单完成情况以及补贴率变化。

完整的一天可以写成：

$$
\tau=
(s_1,a_1,r_1,s_2,a_2,r_2,\ldots,s_T,a_T,r_T).
$$

平台想学习的是一条策略：在每个时间窗口，根据当前城市状态、目标和约束，选择城市级补贴动作，使整天累计业务收益最大，同时满足补贴率约束。

#### 4.3.6 这一节在论文中的作用

2.3 完成了从静态补贴分配到动态控制器的转换：

```text
城市状态 s_t
  -> 城市动作 u_t
  -> 订单—司机补贴 s_{ij,t}
  -> Rides / GMV / subsidy rate
  -> 下一状态 s_{t+1}
```

这为第三章的方法铺路：D3-Subsidy 要生成的不是单个订单补贴，而是符合当前历史和目标约束的未来城市轨迹，并从轨迹中解码每个时间窗口的城市控制量。

## 5. Preliminary 部分的整体逻辑

Preliminary 可以压缩成一句话：

> 平台通过城市级补贴控制影响司机行为和供需状态；由于补贴率约束跨越整天、决策需要连续更新且不能逐单求解，论文将问题写成低维动作的城市级在线序贯控制，再用对偶映射执行到订单—司机层。

对应关系如下：

| 论文小节 | 回答的问题 | 为后文提供什么 |
|---|---|---|
| 2.1 运营流程 | 补贴为什么能影响平台结果 | 状态转移和业务闭环 |
| 2.2 问题建模 | 补贴目标和全局约束是什么 | 目标函数、预算率约束、对偶映射 |
| 2.3 序贯决策 | 模型每次到底决策什么 | 城市级状态、标量动作、窗口奖励 |

## 6. 和 GAVE、AIGB、GRM 的关系

### 6.1 和 GAVE 的关系

GAVE 在广告自动出价中使用 DT backbone，线上主要直接生成当前 multiplier。D3-Subsidy 没有沿用 DT 的自回归动作生成，而是使用扩散模型生成未来城市状态轨迹。

| 对比项 | GAVE | D3-Subsidy |
|---|---|---|
| 业务对象 | 广告曝光竞价 | 网约车司机补贴 |
| 状态 | campaign 预算、CPA、流量等 | 城市供需、司机分布、补贴率等 |
| 主要规划对象 | 动作序列/动作附近探索 | 未来城市轨迹 |
| 最终动作 | 广告 multiplier | 城市补贴控制 |
| 约束处理 | score-based RTG，主要是软引导 | 约束感知得分 + 对偶映射 + 部署约束 |

### 6.2 和 AIGB 的关系

两者都采用“先生成未来状态，再通过逆动力学得到动作”的思想：

```text
AIGB：未来广告状态轨迹 -> 当前广告 multiplier
D3：未来城市运营轨迹 -> 当前城市补贴控制
```

区别在于，D3-Subsidy 更强调生产部署的低延迟和约束执行：它把控制动作压到城市级，再用解析映射落到订单—司机级。

### 6.3 和 GRM 的关系

GRM 预测不同 multiplier 下的未来响应曲线，再求预算根和 CPA 根；D3-Subsidy 生成未来城市轨迹，再用对偶映射和约束感知得分控制补贴。

两者都在尝试把长期业务约束放进控制链路，而不是只训练一个短期动作预测器。但 D3-Subsidy 的论文重点是城市级补贴轨迹和跨城市迁移，不是广告 multiplier 响应曲线求根。

## 7. 读到方法章节时要记住的三个问题

后续阅读第三章时，可以一直追问：

1. **未来轨迹是如何生成的？**历史 prefix 是否保持不变，扩散只作用于未来 suffix？
2. **轨迹如何转成动作？**逆动力学是否读入目标 KPI、预算 regime 和城市上下文？
3. **约束如何真正落地？**约束是只进入 score，还是还进入了对偶映射、补贴 clipping 和线上监控？

这三个问题正好对应论文的三个核心机制：prefix-conditioned diffusion、context-conditioned inverse dynamics、constraint-aware score 与 dual mapping。

## 8. 本部分的汇报版总结

> 这篇论文研究的不是单个订单应该给多少补贴，而是城市在连续运营过程中，如何根据供需状态和剩余补贴空间，持续调整整体补贴强度。论文先把订单—司机级补贴问题通过拉格朗日对偶压缩成一个城市级控制变量，再把它建模成带全局补贴率约束的序贯决策问题。与直接预测下一步动作不同，D3-Subsidy 使用前缀条件扩散模型，根据已经发生的城市历史生成未来运营轨迹，再用上下文条件逆动力学从未来轨迹反推出当前控制信号，最后通过解析映射生成细粒度补贴。这样既能利用长期轨迹信息，又能满足城市级低延迟部署和补贴约束要求。
