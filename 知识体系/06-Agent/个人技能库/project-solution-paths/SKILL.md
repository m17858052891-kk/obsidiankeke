# 项目思考路径

把“当前怎么做、希望做到什么”转成一条有依据、可执行、能被检验的解题路线。方法自包含；无需读取或关联任何 LR、内部案例库或历史文档。根据用户提供的信息开展分析，默认用中文。

## 接收项目

最低输入只有两项：**当前框架**与**项目目的**。接受自由描述，不要求用户填写完整表格。整理为：

- 当前框架：输入 → 关键处理/判断 → 决策或动作 → 交付/执行 → 反馈；标明可以修改的环节。新项目可以只有设想。
- 目的：为谁、改善什么结果、为何值得做；区分业务结果与中间指标。
- 若已提供，再提取：现象与基线、硬约束与可接受取舍、已有证据、数据/工程条件、时间要求。

关键缺口只有在会改变问题定义或路线排序时才追问，一次优先问最重要的一至两项；其余用明确假设给出条件分支。没有历史数据时，设计获取信息的办法，不把“信息不足”变成停止构思的理由，也不编造数字。

## 选择路径

先判断任务处于**探索新方案、改进已有方案、解释异常**中的哪种状态。根据具体矛盾选择一条主路径，必要时组合一至两条辅助路径；不要机械展示全部六条。路径是分析视角，方案是对项目的具体改动，两者分开表达。

| 路径 | 优先使用的信号 | 详细方法 |
|---|---|---|
| 目标倒推 | 方向不清；技术指标变好但业务没变；不知道该优化哪里 | [从结果倒推决策](references/thinking-paths.md#p1) |
| 瓶颈定位 | 链路已运行，但表现不佳、离在线不一致或原因有争议 | [分层定位与区分假设](references/thinking-paths.md#p2) |
| 结构重构 | 单一模型、规则或流程在不同人群、阶段、时间尺度之间反复妥协 | [检查问题的拆法](references/thinking-paths.md#p3) |
| 增量与资源分配 | 需要选择给谁干预、做什么、投入多少，且有预算或容量限制 | [从自然表现走向干预价值](references/thinking-paths.md#p4) |
| 系统联动 | 多方共享资源；局部收益与整体收益冲突；多个策略相互影响 | [从局部看系统净效应](references/thinking-paths.md#p5) |
| 验证迭代 | 方案众多但证据薄弱；评价标准不可信；需要快速试错或扩大应用 | [让不确定性逐步减少](references/thinking-paths.md#p6) |

按需读取所选路径的详细方法。新项目通常从目标倒推开始，用结构重构打开设计空间，再用验证迭代选择最小起点；已有项目按证据定位，不必重新走完整流程。

## 形成项目专属路线

1. 用一句话定义核心矛盾，例如“需要提升实际解决率，但当前改动只作用于已进入链路的少量用户”。这是一项待检验的项目判断，不能把推断写成事实。
2. 给出所选路径及选择理由，把项目里的具体环节、变量、对象填进路径。展示可核查的论证链：**已知现象 → 关键假设 → 可以怎样改 → 用什么现象检验**。不要只复述方法名称或输出冗长的内部思考过程。
3. 围绕关键假设形成少量实质不同的候选方案。保留当前做法或最简单可行方案作为比较基线；若有意义，可比较低成本局部改进与改变问题结构的方案。不要求每次凑足固定数量，也不把换模型大小当作两种不同思路。
4. 每个方案说明：改哪里、为什么可能有效、前置条件、主要代价、最小验证、什么结果支持继续或需要改道。证据薄弱时，首选可以是诊断实验；探索性方案明确标为假设。
5. 推荐先做什么以及升级条件。排序考虑：硬约束是否满足 → 与当前问题的匹配程度 → 可实施性 → 验证成本与信息价值 → 潜在收益。不能按技术新颖程度排序；不为填表杜撰收益、权重、阈值或置信区间。

主目标、不可突破的约束、诊断指标、业务代理指标分开表述。预测准确不等于干预有效，离线可行不等于线上可复现；跨方案比较尽量保持预算、口径、样本及评价条件一致。具体评估强度与决策风险相称，不把完整线上实验或复杂因果方法强加给每个小改动。

## 交付形态

按问题复杂度调整篇幅，通常包含：

- **当前判断**：核心矛盾、已有依据、关键未知；新项目说明首要待验证假设。
- **适用的思考路径**：为什么选它，以及如何应用在这个项目上。
- **候选方案与取舍**：具体改动、适用条件、收益机制、代价与验证方式；明确推荐顺序。
- **下一步**：优先完成的一至三项具体工作，预期获得什么信息，以及继续/停止/切换方案的判据。用户未给阈值时提出确定阈值的方法，不擅自设成业务承诺。

每条建议应能对应“输入中的哪个现象或哪项假设”。最终结果不附 LR 编号、案例链接或来源映射。提供方案不等于已经验证方案有效，也不自动授权上线、改生产参数或对外发布。
