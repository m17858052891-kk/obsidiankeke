# 工程一致性与离线边界

## 1. 训练样本与未来信息

一个样本由 `prediction_time` 锚定。历史序列必须同时满足：

```text
event_time < prediction_time
且该事件在该时点理论上已完成落库并可供线上读取
```

当前订单的未来取消/完单结果只能作为 `D/O/OD` 标签，不能回填到当前时刻的输入。排序采用 `(event_time, stable_event_id)`，避免同一时间戳下离线、线上顺序漂移。

## 2. 序列特征契约

```text
sample = {
  passenger_seq, driver_seq,
  x_static,
  mask / role_id / relative_time,
  y_D / y_O / y_OD   # only training
}
```

离线训练、召回过滤、排序推理应对齐同一份契约：序列长度、截断方向、padding/mask、缺失值、特征字典、主体角色和时间窗口都不能各自实现一套。

## 3. 大规模序列构造

对亿级样本直接按主体和时间做范围 Join，容易造成候选历史笛卡尔积膨胀。当前思路是：

```text
主体 ID + 时间戳预排号
→ 用当前预测锚点截断候选区间
→ 再回表取得所需字段
```

它降低候选历史的连接规模，但当前资料没有端到端耗时、资源或线上吞吐数据，不能量化表述为“降低 XX% 成本”。

## 4. 线上 PLE 来源与离线实验边界

材料中的“线上 base 模型抽取”说明 PLE 是改造的架构来源；当前 PLE/PEP/OneTrans 表格均为离线验证集 AUC。以下说法目前不成立：

- 已上线 OneTrans 或 PEPNet 序列模型；
- 已完成 A/B 或获得 CR、取消率、接驾距离改善；
- 已获得线上 P99、QPS、显存或 KV Cache 命中率。

## 5. 进入线上前的检查清单

- 同一 `attempt_id` 的离线/线上序列字段级 diff；
- 当前订单是否误入历史序列；
- event-time、可用时间、截断窗口是否一致；
- 两侧序列长度、padding、mask、role id 是否一致；
- 特征哈希、Embedding 表、模型版本是否一致；
- 逐层检查 token/embedding/logit diff；
- 对缺失特征、延迟事件、空序列准备降级逻辑。

## 面试一句话

> 序列项目最容易失败的不是模型，而是训练、验证、线上构造的时间语义不一致；因此我把 prediction-time 截断和特征契约作为数据链路的第一原则。
