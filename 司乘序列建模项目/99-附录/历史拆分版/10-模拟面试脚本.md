# 模拟面试脚本

## 1 分钟介绍

> 这是一个基于既有 PLE base 架构来源开展的司乘履约离线序列化改造项目。任务同时预测乘客履约 D、司机履约 O 和司乘履约 OD。针对统计特征压缩历史、司乘链路割裂的问题，我将冒泡到完单的事件按预测时点组织成乘客和司机双边历史订单序列。主 baseline 是 PEPNet + Positional Self-Attention：先分别编码两条序列，再通过 EPNet/PPNet 做场景与任务个性化。随后探索 OneTrans，将司乘历史和静态上下文统一 token 化做联合交互。在 PEP × OneTrans、epoch=9 实验族中，OneTrans 相对 `pep-seq` 的 OD/O/D AUC 分别提升 `.82/2.74/6.61pp`。项目目前仅有离线实验，不表述为线上收益。

## 3 分钟介绍

按以下五段展开，每段只回答一个问题：

1. **业务问题：** 为什么履约模型需要同时看乘客、司机和当前订单，为什么统计特征不够。
2. **数据链路：** Event → Attempt/订单宽表 → `prediction_time` 样本 → 双边序列/静态特征；强调防穿越。
3. **主 baseline：** PEPNet + PosSA，解释 `[B,10,10]` 双边序列、EPNet、PPNet 和 six-tower 场景路由。
4. **迭代过程：** PLE 序列化带来 D/OD 增益但 O 有权衡；针对 O 做 tower、过滤、输入拆分、长度、时空、BS 排查。
5. **OneTrans 与结果：** 从先编码后融合升级到统一 token 交互；随后限定 `+6.61pp` 是相对 `pep-seq` 的离线结果。

完整逐字稿见 [[06-面试叙事主线：3分钟讲清项目]]。

## 高频追问路线

```text
“为什么不用统计特征？”
  → 行为顺序/时间间隔/时空上下文丢失
“为什么 PEPNet？”
  → EP/PP gate 按场景与任务调节序列信号
“为什么 OneTrans？”
  → 先编码后融合无法让静态特征充分参与序列表示学习
“为什么 O 不升？”
  → 已排除简单冲突/噪声，当前看窗口、字段和训练协议
“线上效果？”
  → 只报告离线，线上验证仍是后续工作
```

## 不能越界的表述

- 不说 OneTrans 直接相对 PosSA `+6.61pp`；
- 不说 PLE/OneTrans 已在线上运行；
- 不说 L20 全局最优或 BS=256 已证明因果机制；
- 未确认的 token 顺序、层数、loss 权重必须说“需要回查代码/配置”。
