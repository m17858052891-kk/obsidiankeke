# 模型层级的其他尝试

## 面试问题

> 除了最终的 PEPNet × OneTrans，你还做过哪些模型层面的尝试？

回答时不要只罗列模型名称，而要按照“为什么尝试、怎样对照、结果如何、得到了什么判断”展开。这个项目中最值得讲的是下面两类实验。

## 1. 序列编码方式：从独立 Positional Self-Attention 到 PEPNet 个性化

### 1.1 为什么先做这一步

最初的 PLE base 主要依赖乘客、司机、订单和上下文的静态特征，历史行为更多以统计量形式进入模型。这样会损失历史事件的顺序、时间间隔和短期状态变化。

因此，第一个模型改造是分别保留乘客历史和司机历史，并在两侧各自加入 Positional Self-Attention：

```text
乘客历史 → Positional Self-Attention → 乘客序列表示
司机历史 → Positional Self-Attention → 司机序列表示
静态特征 + 两侧序列表示 → PLE / PEPNet → D、O、OD
```

这一步主要验证：相比把历史压缩成计数、均值和比率，显式建模历史顺序是否能改善履约预测。

### 1.2 为什么进一步结合 PEPNet

只加入 Self-Attention，仍然缺少场景和任务个性化。同样一段历史，在不同产品、时段、区域供需和接驾距离下，重要性可能不同；D、O、OD 三个任务需要关注的表示通道也不完全相同。

因此进一步引入 PEPNet：

- EPNet 在序列交互前，根据当前场景调节底层表示；
- PPNet 在共享表示之后，分别为 D、O、OD 调节任务塔的隐藏表示。

### 1.3 实验现象

在现有 6 月和 12 月离线记录中，Positional Self-Attention 以及后续的 PEPNet + Positional Self-Attention 对 D 和 OD 的提升相对稳定，但 O 的收益更依赖月份和训练配置。

以记录中的同口径实验为例：

| 模型 | 数据 | OD 相对 PLE base | O 相对 PLE base | D 相对 PLE base |
|---|---|---:|---:|---:|
| PLE + PosSA | 2025-06 | +1.07pp | -1.08pp | +3.30pp |
| PLE + PosSA | 2025-12 | +1.12pp | -2.74pp | +4.02pp |
| PEPNet + PosSA | 2025-06 | +2.12pp | +0.15pp | +4.89pp |
| PEPNet + PosSA | 2025-12 | +1.88pp | -0.85pp | +3.97pp |

这些结果说明：

1. 显式序列编码对乘客侧 D 和联合任务 OD 有较稳定价值；
2. PEPNet 的场景与任务个性化能够进一步改善部分任务；
3. O 的收益并不稳定，只增强两条单侧序列的内部编码，还没有充分解决司机、乘客和当前订单之间的双边交互。

## 2. 统一建模与拆分建模：OneTrans 是否应该同时读取双边历史

### 2.1 为什么做统一建模

独立 Positional Self-Attention 的基本路径是：司机和乘客历史分别编码成两个向量，之后才与当前订单和静态特征融合。

这个结构的问题是，当前订单条件进入得较晚。例如接驾距离、价格和供需状态无法在历史读取阶段直接决定：

- 乘客哪些历史取消更相关；
- 司机哪些历史完单或取消更相关；
- 双方历史之间是否存在匹配或冲突。

OneTrans 因此将司机历史、乘客历史、当前订单、画像和上下文统一组织成 Token，让当前 Order Token 在 Transformer 中直接读取双边历史。

### 2.2 做过哪些拆分对照

为了确认收益是否真的来自双边联合交互，而不只是换用了更大的 Transformer，实验中比较了：

```text
统一版本：司机历史 + 乘客历史 + 静态 Token → 同一个 OneTrans

拆分版本：
1. 只建模司机侧的 OneTrans
2. 只建模乘客侧的 OneTrans
3. 司机、乘客分别编码后再做后期融合
```

现有记录中，统一 `pep-seq-onetrans` 优于只保留司机侧或只保留乘客侧的拆分版本。

### 2.3 结果说明什么

这个对照支持的不是“统一模型永远优于拆分模型”，而是：在当前司乘履约任务和实验设置下，当前订单的结果不能被充分表示为两个单侧判断的简单组合。

统一建模的价值在于：

- 当前 Order Token 可以同时读取司机和乘客历史；
- 司机历史中的状态可以影响模型如何解释乘客历史；
- 价格、接驾距离、时段和供需等订单条件能够在历史读取阶段参与交互；
- 双边信息不必先被各自压缩成固定向量，再在末端被动拼接。

因此最终选择统一 OneTrans，不只是因为模型容量更大，而是因为它提供了更符合司乘履约问题的结构归纳偏置：**在 Token 层联合建模司机状态、乘客状态和当前订单条件。**

## 3. 面试口述版本

> 模型层面我主要做过两类尝试。第一类是序列编码方式：最开始从 PLE base 出发，分别给司机和乘客历史加入 Positional Self-Attention，之后再结合 PEPNet，用 EPNet 做场景级个性化、用 PPNet 做 D、O、OD 的任务级个性化。这个方向对 D 和 OD 的提升比较稳定，但 O 在不同月份和配置下波动较大。这说明显式建模单侧历史是有价值的，但只增强司机和乘客各自序列内部的表示，还没有充分解决双边交互。
>
> 第二类是统一建模和拆分建模的对照。我比较过司机、乘客分别编码后再融合，也比较过只建模司机或只建模乘客的 OneTrans 版本。结果统一版本更好。我的理解是，当前订单的履约不是先独立判断乘客和司机、最后再把两个分数拼起来；价格、接驾距离、时段和供需会同时影响模型应该读取双方哪些历史。统一 OneTrans 让 Order Token 在 Token 层直接和司乘双边历史交互，因此能保留更细粒度的跨主体信息。

## 4. 30 秒压缩版

> 我主要做过两条模型路线。第一条是从 PLE base 出发，给司机和乘客历史分别加入 Positional Self-Attention，再结合 PEPNet 做场景和任务个性化。它对 D、OD 提升较稳定，但 O 波动较大，说明单侧序列增强还不够。第二条是比较司乘拆分编码和统一 OneTrans。只建模司机、只建模乘客以及后期融合都不如统一版本，说明履约结果需要在 Token 层联合建模司机历史、乘客历史和当前订单上下文，而不是先做两个独立判断再组合。

## 5. 表述边界

- 上述结果均为离线 AUC 现象，不能直接表述为线上履约率、取消率或业务收益提升。
- `PEPNet × OneTrans` 的严格对照是 `pep-seq`，不要把 OneTrans 的增益直接与 PosSA 实验混为同一组对照。
- 不要宣称统一建模在所有数据和任务上必然更优；准确说法是它在当前实验设置下优于完全拆分版本。
- D→O、HyFormer、Pyramid 和 KV Cache 属于后续研究或工程方向，不能放进“已经完成的模型尝试”。
