# PCVRHyFormer 面试深挖问题地图

下面这份可以当作你这个项目的“面试深挖地图”。面试官通常不会随机提问，而是沿着“业务合理性 → 数据正确性 → 模型机制 → 实验可信度 → 工程落地 → 反思与扩展”逐层追问。

你要始终守住一条主线：

> 这个模型不是简单堆 Transformer，而是针对 PCVR 中“多域历史异质、候选相关性强、时间语义容易错位”三个问题，先分域保留语义，再用候选感知 Query 检索，最后让跨域信息循环反馈。

---

## 0. 开场：面试官最可能先问什么

### Q1：你的 baseline 是什么？为什么它到了瓶颈？

**关注点：** 你是否有明确的对照对象，而不是把复杂模型当作 baseline。

回答框架：

- Baseline 是“静态特征 + 四路行为序列”的常规 PCVR 排序模型。
- 序列侧通常做 pooling / DIN 摘要，静态侧与序列摘要拼接后经 MLP 输出。
- 它的瓶颈不只是容量，而是三类信息损失：
  1. 四路序列语义不同，过早拼接会混淆行为含义；
  2. 普通 mean pooling 对候选不敏感；
  3. 一次性压缩序列后，后面的特征交叉无法再回到原始历史中补充证据。

一句话版本：

> Baseline 的核心问题是“先把历史压成一个向量，再做交叉”，一旦压缩错了，后续 MLP 无法重新读取用户的原始行为证据。

---

### Q2：为什么做 PCVR，而不是直接做 CVR？

**关注点：** 你是否理解标签和样本空间。

回答框架：

- PCVR 本质是在全曝光或排序样本空间中预测转化相关概率，避免只在点击样本上训练 CVR 造成样本选择偏差。
- 如果标签定义是 post-click conversion，需要讲清楚分母、曝光/点击条件以及线上使用方式。
- 追问时要说明：若是 ESMM 风格，会联合建模 CTR 与 CTCVR；而当前代码主干是单任务二分类 BCE，应如实表述，不能虚构多任务结构。

---

## 1. 数据与特征：最容易被抓住细节追问的部分

### Q3：四路行为序列分别是什么？为什么不能直接合成一条序列？

**关注点：** 分域是否有业务依据。

回答框架：

- 四路序列对应不同强度、不同意图的历史行为，例如浏览、收藏、加购、购买。
- 浏览代表弱兴趣，购买代表强偏好；两者频率、稀疏度、时间衰减规律都不同。
- 如果直接拼成一条序列：
  - 高频弱行为会淹没低频强行为；
  - 不同行为的字段语义和缺失模式不同；
  - 一个共享序列编码器需要同时拟合差异很大的分布。

你模型的选择是：

> 先用域独立 Transformer 做域内演化；跨域关系不在原始序列层硬混，而是经 Query 与 RankMixer 受控交换。

---

### Q4：一条历史行为是怎么变成 Token 的？

这是高频问题，建议直接举例。

假设浏览序列第 5 条记录是：

```text
商品 ID = 10086
类目 = 手机
品牌 = Apple
价格 = 6999
距当前请求 = 3 小时
```

处理过程：

1. 每个字段先各自 Embedding：
   $$
   e_{\text{id}}, e_{\text{cate}}, e_{\text{brand}}, e_{\text{price}}
   \in \mathbb{R}^{64}
   $$

2. 字段级拼接：
   $$
   x_t = [e_{\text{id}};e_{\text{cate}};e_{\text{brand}};e_{\text{price}}]
   \in \mathbb{R}^{256}
   $$

3. 每个域用独立投影层压回 64 维：
   $$
   h_t=\operatorname{GELU}(W_mx_t+b_m)\in\mathbb{R}^{64}
   $$

4. 加上“距当前请求时间”的 Time-Bucket Embedding：
   $$
   \tilde h_t=h_t+e_{\text{time-gap}}
   $$

最终，一个行为位置就是一个 64 维 S Token。

**常见追问：这是拼接还是相加？**

- 同一条行为中的不同字段：先拼接，再投影；
- 时间差特征：与投影后的行为 Token 相加；
- 静态 ID 与严格位置对齐的统计特征：使用逐元素相加融合。

---

### Q5：为什么时间特征要用“行为距请求时刻”，而不是绝对时间？

**关注点：** 是否理解时间语义对齐。

回答框架：

- 请求时间回答“用户现在处于什么场景”，如周末晚上；
- 行为距请求的时间差回答“这条历史现在还新不新鲜”。
- 二者不等价：同一条凌晨浏览记录，在请求后 10 分钟与 30 天后，价值完全不同。
- 绝对时间容易记住偶然周期；相对时间更贴近推荐决策中的新鲜度与兴趣衰减。

可以补充：

> 当前模型同时保留请求时间静态 Token 和 request-to-event time bucket，因此既能理解当下场景，也能理解历史行为的时效性。

---

### Q6：Time Bucket 为什么不是直接输入连续时间差？

**关注点：** 特征工程与泛化。

回答框架：

- 时间差通常长尾极强：秒、分钟、小时、天、月的尺度跨度很大；
- 直接用连续值要求模型拟合复杂非线性且对异常值敏感；
- 分桶相当于把“非常近、近期、中期、远期”的语义离散化，再交给 Embedding 学习；
- 桶边界会在短时间段更细、长时间段更粗，符合兴趣衰减通常呈非线性的事实。

追问：为什么不只做 time decay？

- 固定衰减假设所有行为按同一个函数衰减；
- Time-Bucket Embedding 允许不同业务、不同序列、不同上下文学习不同的衰减模式。

---

### Q7：序列字段不齐、长度不一致怎么办？

**关注点：** 数据工程严谨性。

回答框架：

- 每个域生成有效长度与 padding mask；
- Attention 中对 padding 位置 mask，避免无效位置参与 Softmax；
- 同一行为位置的多个字段必须在上游完成时间/位置对齐；
- 当前实现取各 side field 的最大有效长度，因此更要确保“第 \(t\) 个位置确实描述同一条行为”。

这是一个可加分的反思：

> 对多字段序列，真正危险的不是 embedding 维度不一致，而是上游位置错位；一旦 item ID 与价格、类目来自不同事件，模型会学习到伪组合，离线指标和线上稳定性都会受影响。

## 2. 静态特征与 Token 化

### Q8：为什么把静态特征拆成 8 个 NS Token，而不是全部拼接成一个向量？

**关注点：** Token 化是否有必要。

回答框架：

- 一个总向量会过早混合用户、商品、上下文信息；
- 拆为多个 NS Token 后，模型能保留语义槽位，例如用户离散、用户稠密、商品离散、请求时间；
- RankMixer 可以在 Token 维度学习“哪些语义组应该交互”，而不是只让 MLP 在一个大向量中隐式猜测。

注意表述：

> 8 不是理论最优值，而是当前特征分组和算力约束下的设计点。它是一个可做消融的超参数。

---

### Q9：为什么有些 ID 特征和统计值用加法融合？

回答框架：

$$
z_j = E(\text{ID}_j) + W\cdot \text{stat}_j
$$

- 前提是 ID 与统计值严格一一对齐，比如某个商品 ID 对应它自己的 CTR、价格或统计分；
- 加法将统计特征视为对实体语义的连续修正；
- 相比乘法融合更稳定：乘法可能放大噪声、压缩梯度，且统计值标度不稳时更危险；
- 若二者不严格对齐，不能硬加，应作为独立字段或独立 Token。

## 3. 前置 DIN / Target Attention：最值得被深挖的模块

### Q10：你这里的 DIN 到底做了什么？

精确回答：

1. 两个 item NS Token 取平均，形成候选商品向量：

   $$
   q_{\text{item}}=
   \operatorname{Mean}(\text{Item NS Tokens})
   $$

2. 对每一路序列分别计算候选相关性：

   $$
   e_{m,t}
   =
   \frac{(W_mh_{m,t})^\top q_{\text{item}}}{\sqrt d}
   $$

3. 对有效历史位置做 Softmax：

   $$
   \alpha_{m,t}=\operatorname{softmax}(e_{m,t})
   $$

4. 得到该域的候选相关摘要：

   $$
   s_m=\sum_t\alpha_{m,t}h_{m,t}
   $$

四路序列得到四个摘要 \(s_A,s_B,s_C,s_D\)。

---

### Q11：DIN 是对每个字段做 Attention 吗？

不是。

字段已经在单条行为内部拼接并投影为一个 64 维行为 Token。DIN 做的是：

> 对一条行为序列中，不同“行为位置”做候选相关加权。

例如候选是 iPhone，历史中“手机壳浏览”可能权重更大，“洗衣液浏览”权重更小。

---

### Q12：为什么前置 DIN 不直接作为最终序列表示？

**关注点：** 你是否理解它只是 Query 初始化。

回答框架：

- DIN 输出是一次候选相关的加权摘要，适合告诉模型“当前应该关注什么”；
- 但它会将长序列压成单向量，仍有信息损失；
- 所以当前模型把 DIN summary 用来生成 Query，而不是丢弃原始序列；
- 后续 Query 对完整序列做 Cross-Attention，完成更细粒度的检索。

一句话：

> 前置 DIN 是粗召回式的 Query 初始化；HyFormer Cross-Attention 才是保留全序列证据的精读阶段。

---

### Q13：为什么不把 DIN 放在最后做残差？

**关注点：** 你是否做过结构取舍。

回答框架：

- 后置 DIN 是“HyFormer 已经融合完成后，再额外加一条候选注意力残差”；
- 前置 DIN 则影响 Query 的初始语义，因此会影响两层 HyFormer 后续所有检索路径；
- 对候选相关性很强的 PCVR，前置方式更符合“先明确检索目标，再读历史”的流程；
- 但不能夸张声称前置版本一定更优：应说当前主线采用前置设计，最终结论必须以同预算消融为准。

---

## 4. Query Generator：面试官最爱问“为什么要造 Query”

### Q14：为什么要生成 2 个 Query / 域？为什么不是一个？

**关注点：** 多兴趣与容量控制。

回答框架：

- 一个 Query 等价于“每个域只允许一种检索意图”；
- 一个用户的浏览序列可能同时包含价格敏感、品类兴趣、品牌偏好等信号；
- 两个 Query 给同一域提供有限的多视角检索能力；
- 选 2 是容量与计算的折中：4 域 × 2 Query = 8 个 Query，后续 RankMixer 的全局 Token 数固定为 16。

追问：为什么不更多？

- Query 数增大会提高 Cross-Attention 成本和模型自由度；
- 小数据下可能出现 Query 同质化或过拟合；
- 应通过 \(1/2/4\) Queries per domain 消融，而不是凭直觉说 2 最优。

---

### Q15：Query 是怎么生成的？

对第 \(m\) 域：

$$
g_m=
[
\operatorname{Flatten}(\text{8 NS Tokens});
s_m
]
$$

维度是：

$$
8\times64+64=576
$$

然后经 LayerNorm 和两个独立 FFN：

$$
[q_{m,1},q_{m,2}]
=
\operatorname{FFN}_m(g_m)
$$

最终是 4 域 × 2 = 8 个 64 维 Query。

面试表达：

> Query 不是自由参数，也不只是 item embedding；它由全局静态画像和该域的候选相关历史共同条件化生成，因此是“当前用户、当前候选、当前场景下”的检索指令。

---

### Q16：为什么 Query 要同时看 NS Token 和 DIN summary？

- 只看 NS：知道用户和候选是谁，但不知道这个域近期发生了什么；
- 只看 DIN summary：知道历史里什么相关，但缺少用户长期画像、上下文和候选外部语义；
- 二者拼接后，Query 能决定“结合用户当前身份和场景，应该从哪一域、按什么视角找证据”。

---

## 5. HyFormer Block：架构的核心深水区

### Q17：一个 HyFormer Block 内部到底发生了什么？

按顺序回答：

1. 四路序列各自经过一个 Transformer Encoder，完成域内 Sequence Evolution；
2. 每个域的 Query 对对应序列做 Cross-Attention；
3. 得到 Decoded Query Tokens，即“从该域历史中读出的候选相关证据”；
4. 把 8 个 Decoded Query 与 8 个 NS Token 拼成 16 个全局 Token；
5. RankMixer 做横向 Token 交互和纵向 Channel 混合；
6. 得到更新后的 Query 和 NS Token，输入 Block 2；
7. Block 2 用已经融合了跨域信息的 Query，再回头检索各自原始域的更新序列。

最关键的一句：

> Block 1 是第一次按域取证，Block 2 是带着跨域上下文做第二次检索，因此不是机械堆层，而是“检索—融合—再检索”的闭环。

---

### Q18：域内 Transformer 为什么独立参数？不能共享吗？

**关注点：** 参数效率和语义隔离的 trade-off。

回答框架：

- 独立参数的优点：不同域的行为强度、频率、字段构成和时间规律不同；
- 共享参数的优点：参数更少，对小样本长尾域可能更友好；
- 当前优先语义隔离，是因为四域异质性较明显；
- 如果数据规模有限或域之间更相似，可以尝试共享底层 Encoder + 域特定 Adapter / FiLM，而不是非黑即白。

---

### Q19：RoPE 在这里做了什么？为什么不只用位置 Embedding？

$$
\operatorname{RoPE}(q_t),\operatorname{RoPE}(k_j)
$$

RoPE 作用在 Attention 的 Q/K 投影后，使注意力分数自然包含相对位置差 \(t-j\)。

- 位置 Embedding 是把“第几个位置”加到输入；
- RoPE 直接改变 Query/Key 的几何关系，更自然表达“相隔多远”；
- 在序列变长时，相对位置语义通常比绝对位置更容易泛化。

但要分清：

> RoPE 负责行为之间的顺序距离；Time-Bucket 负责行为相对当前请求的真实时间新鲜度。两者是互补的。

---

### Q20：为什么域内 Transformer 默认双向 Attention？线上会信息泄漏吗？

**关注点：** 这是一个高危问题。

回答框架：

- 如果每条历史序列只包含请求时刻之前发生的事件，则序列内部双向注意力不涉及未来标签或未来行为，不构成时间泄漏；
- 双向表示让每条历史行为能结合同一历史窗口中的其他行为，适合排序任务；
- 如果要做严格自回归下一行为预测，或需要按流式时序增量服务，才更适合 Causal Mask；
- 真正需要审计的是特征截断时间：所有历史、统计特征必须只使用请求时刻之前可见的信息。

---

### Q21：Cross-Attention 中 Q、K、V 分别是什么？

- \(Q\)：当前域的两枚 Query；
- \(K,V\)：该域经过 Sequence Evolution 后的完整历史行为 Token；
- 输出：每个 Query 从长历史中读到的候选相关证据。

$$
\operatorname{Attention}(Q,K,V)
=
\operatorname{softmax}
\left(
\frac{QK^\top}{\sqrt d}
\right)V
$$

这里不是让所有原始序列 Token 两两跨域 Attention，而是用少量 Query 做压缩检索。

---

## 6. RankMixer：第二个最容易被问的模块

### Q22：RankMixer 做了什么？和堆 MLP 有何区别？

回答框架：

- 输入是 8 个 Query + 8 个 NS，共 16 个全局 Token；
- 普通 MLP 通常把它们展平成一个大向量，特征槽位关系被隐式混合；
- RankMixer 保留 \([B,T,D]\) 的二维结构：
  - 横向：不同 Token 间交互，例如“购买域 Query 是否要参考用户稠密画像”；
  - 纵向：每个 Token 的 channel 非线性变换；
- 它通过重排 Token 维度与子空间维度，让共享 FFN 在结构化视角上进行混合。

面试中不要说 RankMixer 是 Attention 的完全替代。更严谨的说法是：

> 它是面向小规模全局 Token 集合的结构化 mixing 模块，重点是低成本做跨 Token 与通道融合；长序列检索仍由 Cross-Attention 完成。

---

### Q23：为什么不直接用 Self-Attention 做 16 个 Token 的融合？

回答框架：

- 16 个 Token 用 Self-Attention 的成本并不高，确实是一个合理对照；
- RankMixer 的动机不是单纯省算力，而是利用 Token/Channel 两个方向的显式结构，且实现上更硬件友好；
- 应准备一个消融：RankMixer vs MLP vs Self-Attention；
- 如果没有该实验，诚实回答：这是基于现有 HyFormer/RandMixer 结构的工程选择，目前不能仅凭理论断言绝对优于 16 Token Self-Attention。

---

### Q24：为什么 Block 2 还要再做 Cross-Attention？

回答框架：

- Block 1 的 Query 主要带着本域候选感知和静态画像检索；
- RankMixer 后，Query 已经吸收了其他域的线索；
- Block 2 再读取本域序列，相当于让“跨域结论”反过来修正“本域应该关注哪些历史”。

例子：

> 用户有购买过母婴用品的信号，同时最近浏览了手机。Block 1 的浏览域可能偏向手机兴趣；经全局融合后，Block 2 可以结合购买域的强意图，重新判断这些浏览是独立兴趣、礼品需求，还是弱噪声。

## 7. Loss、训练与优化器

### Q25：损失函数是什么？为什么这样选？

当前是单任务二分类：

$$
\mathcal L_{\text{BCE}}
=
-\frac1N\sum_i
\left[
y_i\log \sigma(z_i)
+
(1-y_i)\log(1-\sigma(z_i))
\right]
$$

其中 \(z_i\) 是 PCVR Logit。

追问：为什么用 `BCEWithLogitsLoss`？

- 数值上比先 Sigmoid 再 BCE 更稳定；
- 可以内部稳定处理极端 Logit；
- 当前没有多任务 loss 权重，不应讲成 ESMM 或多头任务。

---

### Q26：为什么稀疏 Embedding 用 Adagrad，稠密层用 AdamW？

简短版本：

- 高基数 Embedding 是稀疏、长尾更新：Adagrad 为每个参数累积梯度平方，热门 ID 自动降步长，长尾 ID 保持更大的有效学习率；
- Attention、MLP、投影层几乎每个 batch 都更新：AdamW 用动量稳定稠密梯度，并通过 decoupled weight decay 控制权重规模；
- 全部 AdamW：长尾 embedding 可能学得慢；
- 全部 Adagrad：稠密网络有效学习率长期衰减，后期可能过早停滞。

当前超参数要能背出：

```text
Sparse Embedding: Adagrad, lr = 0.05, weight_decay = 0
Dense modules: AdamW, lr = 1e-4, betas = (0.9, 0.98), weight_decay = 0.01
Global gradient clipping: 1.0
Dropout: 约 0.01
```

---

### Q27：为什么要做 Gradient Clipping？

- 长序列 Attention 在早期训练或异常 batch 中可能产生较大梯度；
- 全局 clip \(=1.0\) 限制单次更新上界，避免一次异常更新破坏 AdamW 动量状态；
- 它是稳定性措施，不是解决模型不收敛的根本方法；如果长期频繁触发，仍要检查学习率、特征分布和 mask。

---

### Q28：为什么 Dropout 很低？

- 推荐数据量通常较大，过高 Dropout 容易破坏稀疏离散特征和短期兴趣信号；
- 当前结构已经有 LayerNorm、Weight Decay、梯度裁剪等约束；
- 低 Dropout 是保留表示能力与抑制过拟合的折中；
- 最好准备不同 Dropout 的实验或承认这是待调超参。

---

## 8. 指标、实验与可信度：面试官会故意挑战你

### Q29：最优分数到底是多少？0.8255 是不是最优？

最安全的回答：

> 0.8255 是一版已明确记录、可复现的结果，但并不是我会断言的历史全局最优。历史注释中有约 0.826 的结果，不过当时完整配置没有完全固化。因此项目复盘中，我将“已复现配置”和“历史最佳记录”严格区分，后续需要通过固定数据切分、随机种子和配置快照重跑确认。

这比硬说“516 提升了多少”更专业。

---

### Q30：你如何证明提升来自模型，而不是随机波动？

回答框架：

- 固定训练/验证切分、特征版本、样本窗口与随机种子；
- 单因素消融，而不是多改动同时上线；
- 每个改动至少重复多个 seed，报告均值与方差；
- 对比训练曲线、分桶 AUC、冷启动/活跃用户/短序列/长序列分群；
- 显著性检验或 bootstrap 置信区间；
- 线上再看校准、转化、延迟和稳定性。

---

### Q31：你最有价值的三个改动是什么？

建议只讲以下三项：

1. **ID 与统计特征的语义对齐**  
   对严格一一对应的 ID 和统计值逐元素加法融合，避免无语义的粗拼接。

2. **请求—行为时间双尺度对齐**  
   请求时间建模当前场景，行为时间差建模兴趣新鲜度。

3. **前置候选感知 Query 初始化**  
   用 item-aware DIN summary 与全局静态画像生成 Query，再由 HyFormer 保留完整历史做多轮检索。

避免把“堆更多层”“增大序列长度”“调学习率”讲成 S 级创新。

---

### Q32：有没有失败实验？为什么失败？

这是加分项。可以讲：

- 将序列长度扩展至 1024 后，历史记录从约 0.826 降至 0.8255；
- 说明更多历史不必然更好，远期行为引入的噪声可能超过增量信号；
- 这促使后续更关注时间对齐、候选相关检索和可学习压缩，而不是盲目堆长度。

也可以讲：

- 对严格对齐的 ID+统计值，乘法融合不如加法融合；
- 原因是统计特征尺度/噪声会直接调制 embedding 幅度，梯度更不稳定；加法更像连续残差修正。

---

## 9. 生产与工程化：高级面试一定会问

### Q33：线上延迟如何评估？最耗时模块是什么？

回答框架：

- 最主要成本是四路序列的 Self-Attention，近似与 \(\sum_mL_m^2\) 相关；
- Query Cross-Attention 约为 \(\sum_mN_qL_m\)，因为每域只有两个 Query，通常相对可控；
- RankMixer 只有 16 个全局 Token，成本很低；
- 实际 profiling 还要看 Embedding lookup、数据组装、kernel launch、padding 比例和 batch size，不能只报理论复杂度。

---

### Q34：如何做多候选打分优化？

回答框架：

- 当前模型中的候选 item 会进入前置 DIN 和 Query，因此不是所有中间结果都可跨候选复用；
- 但候选无关的用户静态特征、部分历史序列表征理论上可以缓存；
- 受限点在于当前 Token 含“相对当前请求时刻”的 Time-Bucket，因此跨请求缓存需要谨慎；
- OneTrans 的跨请求 KV cache 是值得借鉴的方向，但需先拆分用户历史基座表示与请求/候选相关增量。

---

### Q35：线上线下一致性怎么保证？

回答框架：

- 特征字典、分桶边界、默认值、时区、归一化参数统一版本；
- 历史序列只截断到请求时间；
- 离线/线上共用或严格校验 Feature Pipeline；
- 对时间特征尤其要验证 UTC/CST 转换；
- 用离线样本回放线上特征，检查 embedding index、序列长度、mask、time bucket 是否完全一致。

---

### Q36：冷启动用户或空序列怎么办？

回答框架：

- 空序列必须用 padding mask，Attention 输出安全置零；
- 此时模型退化为静态 NS Token + Query Generator 的静态路径；
- 冷启动主要依赖用户基础属性、候选商品、上下文与请求时间；
- 需要单独报告短序列/空序列分桶指标，不能只看整体 AUC。

---

## 10. 论文与横向比较

### Q37：HyFormer 的核心思想是什么？你改了什么？

HyFormer 原始思想：

- 不先把长序列永久压成一个向量；
- 用少量全局 Query 对长序列 Cross-Attention 做 Query Decoding；
- 用 RankMixer 做 Query Boosting；
- 多层迭代“检索—融合—再检索”。

你的改动：

- 多域独立序列 Token 化与域内 Transformer；
- 显式 request-to-event Time-Bucket；
- 8 个静态 NS Token；
- 以候选 item 为条件的前置 DIN pooling 参与 Query 初始化。

关键边界：

> 前置 DIN 是你的工程改造，不是原始 HyFormer 的标准模块。

---

### Q38：当前模型与 OneTrans 的最大差别？

一句话：

> HyFormer 是“分域序列记忆 + Query 受控跨域交互”，OneTrans 是“序列和静态特征从第一层起进入统一 Transformer 的端到端联合交互”。

继续展开：

- OneTrans：所有 S Token 与 NS Token 同一 Token 流，Causal Attention；
- 当前模型：原始序列不直接跨域混合，只通过 Query/NS 这个瓶颈交换信息；
- OneTrans 更适合统一扩深扩宽和 KV cache；
- 当前模型的前置 DIN 对候选相关性有更强显式归纳偏置，可能更适合数据有限、业务域差异强的情况。

---

### Q39：为什么不直接改成 OneTrans？

回答框架：

- 统一 Transformer 的表达上限更高，但不等于在当前数据规模、特征成熟度和延迟约束下必然更优；
- 当前四域行为异质性强，先分域建模有明确先验；
- 当前优先验证“时间语义对齐 + 候选感知检索”的增益；
- 若要吸收 OneTrans，我会先试 Pyramid 式序列压缩或可缓存的历史基座表示，而不是一次性推翻整个链路。

---

## 11. 终局反思题：最能拉开高级算法差距

### Q40：这个模型最可能的失效模式是什么？

建议答四个：

1. **时间泄漏**：统计特征或历史截断不严格；
2. **多字段位置错位**：同一位置的 item、类目、价格并非同一条行为；
3. **Query 同质化**：两个 Query 学成相似检索头；
4. **长序列噪声**：历史越长不代表有效信息越多。

---

### Q41：如果再给你两周，优先做什么？

推荐优先级：

1. 先补齐严格可复现的实验矩阵，确认 0.826 历史最佳对应的完整配置；
2. 做关键消融：时间特征、前置 DIN、Query 数、Block 数、RankMixer；
3. 增加分桶评估：冷启动、短/长序列、不同时间差、不同候选类目；
4. 观察 Attention/Query 的可解释性与 Query 同质化；
5. 再尝试可学习的序列裁剪或 Pyramid 压缩，而不是先加深加宽。

---

### Q42：你对这个项目最重要的反常识结论是什么？

推荐你背这一段：

> 我们一开始容易把问题理解成“历史不够长、模型不够大”，但实验提醒我并不是这样。把序列长度扩到 1024 并没有带来收益，反而略有下降。真正有效的不是无差别增加历史，而是先把时间语义与候选意图对齐，再让 Query 从完整序列中有选择地取证。对排序模型而言，信息质量和检索路径往往比单纯容量更重要。
