# 1、项目背景

承接网约车和顺风车融合导流需求，支持乘客端同呼，决定改造召回和PK模块，保证流量分配公平性，同时提升平台效率。

# 2、策略部分

### 2.1、召回过滤

对召回进入PK的顺风车司机进行过滤，保留的司机需要满足以下两个条件：

1. ~~顺风车的顺路度大于50%；~~

2. 顺风车的接驾距离小于6km。

### 2.2、PK打分

当前平台对网约车和顺风车的决策相互独立，不宜直接合并各自的履约数据进行建模。因此，计划进行两阶段模型迭代。

#### 初始版本

设定简单的策略逻辑，使顺风车过渡到和网约车共同参与PK决策，同时合理控制顺风车份额，保证建模样本的分布正常。

顺风车的倾斜前PK打分逻辑：

- 顺风车的倾斜前PK打分 = 顺风车的模型打分 x 折扣系数；

- 折扣系数 = 顺风车的司乘履约率 / 网约车的司乘履约率，全国统一系数。

#### 迭代版本

考虑优化特征逻辑并进行模型迭代，使顺风车和网约车能够在同一套特征标准下进行考核，兼顾平台效率的最大化。

迭代版本的优化点：

- 标签定义：采用司乘分开建模的框架，明确标签定义，例如将乘客长时间未预付款的司机取消记为乘客取消；

- 司机行为：扩充司机维度差异化特征场景，对于顺风车订单，仅考核司机历史顺风车取消率和完单数，网约车同理；

- 乘客偏好：引入乘客维度差异化特征，对于顺风车订单，仅统计乘客历史的顺风车发单率和取消率，网约车同理；

- 场景标识：增加是否顺风车的二值特征，等价于对顺风车整体进行正向或负向加权，直接反应顺风车的履约情况。

### 2.3、人群倾斜

运营方给出需要倾斜的人群标签。对于各类乘客的发单，平台会对参与PK的顺风车司机赋予相应的加权分。

倾斜人群标签逻辑：

- 顺风车核心忠实用户：近30天只有顺风车发单，没有网约车发单；

- 顺风车主导用户：近30天既有顺风车发单也有网约车发单，顺风车发单订单数占比≥x%；

- 高价值顺风车用户：近30天既有顺风车发单也有网约车发单，顺风车发单订单数占比<x%，但近30天顺风车累计GMV位列前y%。

顺风车的倾斜后PK打分逻辑：

- 顺风车的倾斜后PK打分 = 顺风车的倾斜前PK打分 + 倾斜分；

- 倾斜分大于0，倾斜方法待定。

### 2.2、配置参数

针对PK打分和人群倾斜两个需求点，工程需要提供可配置相关参数的功能。

- PK打分：配置是否进行顺风车倾斜（is_sfc_pk_tilt），和顺风车的折扣系数（coef_sfc_pk_tilt）；

- 人群倾斜：配置顺风车的目标人群的倾斜系数（coef_sfc_pas_tilt）。

### 2.3、改造链路

针对以上需求，工程需要根据以上逻辑，开发所有涉及顺风车的功能点。

- 召回过滤：在召回层，判断是否顺风车，若是，执行召回过滤的逻辑；

- PK打分：在PK层，判断是否顺风车举手，若是，读取配置参数，计算倾斜前PK打分；

- 人群倾斜：在PK层，判断是否目标人群发单且顺风车举手，若是，读取配置参数，计算倾斜后PK打分。

### 2.4、兼容规则

保证PK动态窗口的有效性，设置规则约束顺风车不能触发策略，也不能因为网约车触发策略而提前胜出。

- 当前时刻是顺风车举手，一律不触发提前胜出；

- 当前时刻是网约车举手，但PK打分低于已经在窗口中的顺风车，此时也不触发提前胜出。

- 在延长窗口的过程中，顺风车司机一律不触发提前胜出。
