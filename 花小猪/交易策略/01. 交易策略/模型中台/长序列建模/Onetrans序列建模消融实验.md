本阶段围绕司机、乘客历史行为序列完成了 OneTrans 十余组结构实验。从“把司机最近订单送进 Transformer”开始，逐步扩展到司机与乘客双序列、独立时间轴、序列边界、近期 Query、论文式 Tokenizer、全 Token 读出、DCNv2 与 Dual DIN 混合前端、人工语义分组和相对位置编码。

这条路线解决三个问题：历史订单在数据表中如何还原成时间序列，序列和当前订单的异质字段如何进入同一个模型，以及增加深度、Token 数量和参数量是否能够稳定转化为 AUC 收益。所有正式版本均在 4 张 H200 上完成多卡训练。

## 历史订单构造序列

单笔当前订单只能描述当下的城市、时段、路线、供需和司乘画像，无法完整反映司机和乘客近期行为。历史订单能够补充以下信息：

- 司机近期是否频繁拒单、取消或完单；

- 乘客近期呼叫后是否得到应答、是否取消以及取消类型；

- 近期订单的 ETA、接驾距离、订单距离和价格；

- 行为发生的先后顺序、距离当前订单的远近和历史长度；

- 当前订单与历史行为之间的相关性。

这些信息既包含连续数值，也包含类别状态和时间字段。直接做窗口聚合会丢失事件顺序，而直接把全部历史字段展平又会把不同时间步混在一起。OneTrans 将每笔历史订单编码成一个 S-token，把当前订单的结构化字段编码成 NS-token，再通过统一 Backbone 建模跨时间、跨字段和跨业务域的关系。

### 原始存储方式

Hive 表采用“按字段存数组”的方式保存历史序列。一行仍对应一笔当前订单，但司机或乘客的每个历史字段都是一个定长 Array。相同下标表示同一笔历史订单。

以第一版司机序列为例，一行包含 5 个长度为 30 的 Array：

```PlainText
d_seq_pk_time
d_seq_hands_up_time
d_seq_is_finish
d_seq_eta
d_seq_driver_order_finished_1d_cnt
```

读取后按下标对齐并堆叠为：

```PlainText
5 个 Array(30)
    → 按相同历史下标堆叠
30 个时间步 × 5 个字段
```

模型批量输入的形状为 `B × 30 × 5`。后续版本把司机每个时间步扩展到 8 个字段，并加入独立的乘客序列。司机和乘客各自最多保留 30 笔历史订单。

### 时间顺序与 padding

原始数据按“最近到最远”排列。数据管道将真实历史部分反转为“最远到最近”，再在左侧补齐固定长度。最近发生的订单始终靠近序列尾部。

```PlainText
原始：最近 → 最远
反转：最远 → 最近
左补齐：[padding ... padding | 最远 ... 最近]
```

固定 30 个位置不代表每条样本都有 30 笔真实历史。若一名司机只有 14 笔历史，则模型仍接收 30 个位置，其中左侧 16 个位置是 padding，右侧 14 个位置是真实订单。

### -999、0 和 mask

数据层使用 -999 表示原始缺失或补齐位置。入模前，非有限值和 -999 被替换为 0，同时生成 mask：

| 表示 <br> | 作用 <br> |
| --- | --- |
| - `999` <br><br> | 数据层的缺失与补齐标记 <br> |
| `0` <br> | 清洗后实际进入神经网络的数值 <br> |
| `mask=False` <br> | 该时间位置不存在真实历史订单 <br> |

mask 标记的是“这笔历史订单是否存在”，不是“某个字段是否缺失”。padding Token 保留在固定形状张量中，但不能作为有效 Key 被其他 Token 关注；每个 Block 结束后，padding 位置再次清零，避免无效历史向有效表示传播。

## 序列特征和非序列特征转成 Token

### 序列 Token

同一历史时间步的多个字段分别编码到统一维度后相加或融合，形成一个 S-token。字段数量增加只会增加每笔历史事件携带的信息，不会增加时间 Token 数量。

第一版的数据流为：

```PlainText
司机历史：30 × 5
    → 每个时间步融合 5 个字段
30 个 S-token，每个 256 维
```

司机序列扩展到 8 维后，仍然是 30 个 S-token。乘客序列接入后，模型同时拥有 30 个司机 S-token 和 30 个乘客 S-token。

### 非序列 Token

当前订单的类别字段通过 Embedding 编码，连续字段先按固定统计量归一化，再通过独立数值投影编码。早期版本把 160 个当前订单字段逐字段转换成 160 个 NS-token。

论文式 Tokenizer 将非序列字段从“每字段一个 Token”压缩为固定数量的聚合 Token。V5 使用 12 个 Auto-Split NS-token；V9 则按业务语义把 160 个字段分为订单上下文、司机画像、乘客画像和供需环境四组，每组独立完成 DCNv2、Deep MLP 和 Token Projection，并各自产生 3 个 Token，最终仍保持 12 个 NS-token。

人工语义分组让字段组织方式从机械切分转为业务可解释分组，但进入 OneTrans 后仍通过固定 Token 位置区分不同语义槽位。

## OneTrans Backbone

### 混合参数化

OneTrans 区分两类 Token：

- S-token 表示可重复的历史事件，不同时间位置共享 Q、K、V 和 FFN 参数；

- NS-token 表示含义固定且彼此异质的当前订单特征，每个位置拥有独立 Q、K、V 和 FFN 参数。

这种设计既利用历史事件的重复结构，又避免城市、司机画像、供需和距离等完全不同的字段被迫共享同一套变换。

每个 OneTrans Block 使用 Pre-LayerNorm、注意力残差和 FFN 残差。使用 PyTorch 原生点积注意力，序列和非序列 Token 进入同一个 Backbone。

### 金字塔历史裁剪

模型在浅层保留完整历史，在更深层减少发出 Query 的旧历史位置。以两层模型、每侧 30 个历史位置、保留率 0.8 为例，第二层只让最近 24 个历史位置继续更新。

V4.2 将这一机制明确为“近期 Query、完整历史 K/V”：旧历史不再发出 Query，但近期 Token 仍然可以读取全部历史 Key 和 Value。该版本完成稳定训练，但 AUC 没有超过 V4 和 V3。

## 司机与乘客独立时间轴

早期版本先接入司机序列，随后增加乘客历史。司机和乘客的历史订单并不共享同一业务时钟：同一个数组下标只表示各自“第几近的一单”，不代表两侧事件发生在相同时间。

V4 为司机和乘客分别建立事件编码、位置顺序和 mask，再将两条独立序列与当前订单 Token 放入同一 Backbone。实验完整训练 2 个 epoch，Best AUC 为 0.628653。该结果略低于 V3 的 0.630367，因此它确认了独立时间轴实现能够稳定运行，但没有形成 AUC 增益。

## SEP、相对位置和近期 Query

### SEP 序列边界

V4.1 在司机序列与乘客序列之间加入可学习的 \[SEP\] Token，用于显式标记两类行为边界。Best AUC 为 0.628468，比 V4 低 1.85 bp。单次实验没有观察到 SEP 带来的收益。

### 近期 Query 与完整历史 K/V

V4.2 在深层只更新近期历史 Query，同时保留全部历史作为 K/V。Best AUC 为 0.628243，比 V4.1 低 2.25 bp。该实验验证了机制可训练，但没有证明更长的可读历史改善排序效果。

### 位置编码

在 V8.1 上完成了相对位置 Embedding 实验。司机和乘客共享一张 30 档位置表，最右侧始终表示最近第 1 单，左侧依次表示更早历史。位置向量在 DIN 和 OneTrans 之前加到事件表示中。

该实验只增加 7,680 个参数，Best AUC 从 0.747705 提升到 0.749803，增加 20.98 bp。

## NS-token数量、Concat与Pooling

### 最后一个 Token 读出

早期 OneTrans 固定读取最后一个 NS-token 的输出作为预测表示。虽然配置中存在 mean pooling 或 cls token 选项，工程实现实际使用的是最后位置读出。

### 全 NS-token Concat

V5.1 将最终 12 个 NS-token 全部拼接后送入任务塔。Best AUC 为 0.743162，与 V5 的 0.743186 基本持平，同时参数增加 360,448。单独改变聚合方式没有观察到收益。

V8.1 在 V8 混合前端上再次使用全 NS-token Concat，并同时把任务塔从浅层扩大为四层隐藏层。Best AUC 从 0.744497 提升到 0.747705，增加 32.08 bp；最终 AUC 提升 44 bp。由于 Concat 和任务塔深度同时变化，这一收益只能归属于组合改动，不能拆分到单个组件。

### 100个 NS-token

V7 将 NS-token 从 12 个扩展到 100 个，参数量从约 1,919 万增加到约 1.464 亿，是 V5 的 7.63 倍。Best AUC 为 0.739721，比 V5 低 34.65 bp。直接增加 Token 数量和位置独立参数没有转化为收益。

## 模型深度和容量扩展

V6 把 OneTrans 从 2 层增加到 6 层，参数量显著上升，Best AUC 为 0.741780，比 V5 低 14.06 bp。实验说明 6 层金字塔结构可以完整训练，但更深 Backbone 没有提高当前任务的 AUC。

V7 的 100 NS-token 实验进一步表明，扩大位置独立参数规模同样没有带来收益。两组实验共同说明，OneTrans 的效果不随层数、Token 数量或参数量简单单调增长。

V10 在保持输入、Token 数量、Attention 和读出不变的情况下，将 Backbone FFN 的 GELU 替换为参数量近似的 SwiGLU。记录 AUC 为 0.746532，低于 V8.1 的 0.747705 和 V9 的 0.749411。当前配置下，激活函数替换没有形成收益。

## DCNv2与Dual DIN混合前端

### 引入原因

早期 OneTrans 同时承担字段编码、序列聚合和跨域交互。V8 将这些职责拆开：

- DCNv2 显式建模当前订单静态字段交叉；

- Driver DIN 使用当前订单上下文选择相关司机历史；

- Passenger DIN 使用独立参数选择相关乘客历史；

- OneTrans 继续负责司机、乘客和当前订单 Token 的跨域交互。

完整 Token 顺序为：

```PlainText
[司机历史 30 | SEP 1 | 乘客历史 30 | NS-token 12]
```

V8 在 4 张 H200 上完成 2 个 epoch，Best AUC 为 0.744497，比 V5 提升 13.11 bp；参数量为 20,892,027，只比 V5 增加 8.89%。由于 DCNv2 和两路 DIN 同时接入，这个结果证明的是混合前端整体有效，不能单独归因于其中某一路。

### 与传统强基线对照

为了判断收益来自序列信息还是 OneTrans Backbone，另外实现了不含 OneTrans 的 DCNv2 + Dual DIN Baseline。该模型只有 1,785,083 个参数，Best AUC 为 0.752399，高于 V8.1 的 0.747705，差值为 46.94 bp。

这项对照说明，在当前数据和训练口径下，成熟的 DCNv2 与 Dual DIN 组合以更少参数取得了更高 AUC。OneTrans 的额外容量和跨域 Backbone 尚未超过传统强基线。

## 阶段性结论

1. 司机和乘客历史必须按各自时间轴处理，不能把相同数组下标误解为同一时刻。

2. \-999、入模值 0 和 mask 分别承担数据缺失、数值输入和位置有效性三个不同职责。

3. 增加有效序列信息比单纯增加模型深度、Token 数量或参数量更重要。

4. SEP、近期 Query、6 层 Backbone 和 100 个 NS-token 均完成了独立或相对集中的验证，但没有产生 AUC 收益。

5. 全 NS-token Concat 单独使用时与最后 Token 读出持平；与深层任务塔组合时出现正向结果，但无法拆分单个组件贡献。

6. DCNv2 与 Dual DIN 混合前端提高了 OneTrans 结果，说明局部显式交叉和目标相关历史聚合具有实际价值。

7. 人工语义分组获得了正向单次结果，表明非序列字段的组织方式会影响 Token 表达质量。

8. Recency Position Embedding 获得正向数值信号，但非有限梯度使该实验未通过质量门禁。

9. 参数量约 179 万的 DCNv2 + Dual DIN Baseline
