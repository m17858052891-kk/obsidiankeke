## 1．输入与候选：用一张工单明确三个输出任务

### 1.1 同一张工单，要回答哪些问题？

继续沿用同一张工单：

> 扣款成功，但订单仍显示失败，请帮我处理。

我们希望回答三个问题：

| 字段 | 问题 | Laya 题型 |
| --- | --- | --- |
| `department` | 应由哪个部门处理？ | `choice`：候选中选一个 |
| `urgency` | 紧急程度如何？ | `score`：对有序等级评分 |
| `needs_human` | 是否需要人工介入？ | `noul`：返回“是”的概率 |

这里要先区分两个东西：

- **状态 `state`：** 要分析的工单内容。
- **问题 `questions`：** 要判断什么，以及有哪些候选或等级。

按照实际接口，可以这样定义：

```python
state = "扣款成功，但订单仍显示失败，请帮我处理。"

questions = {
    "department": {
        "type": "choice",
        "instructions": "这张工单应由哪个部门处理？",
        "criteria": {
            "账单": "扣款、账单、退款",
            "技术": "系统错误、订单状态异常",
            "其他": "不属于以上类别",
        },
    },
    "urgency": {
        "type": "score",
        "instructions": "这张工单的紧急程度如何？",
        "criteria": [
            "不紧急",
            "需要尽快处理",
            "严重影响使用",
        ],
    },
    "needs_human": {
        "type": "noul",
        "instructions": "这张工单是否需要人工介入？",
    },
}
```

这是一份符合接口的教学输入，并不意味着实际模型一定选“账单”。工单同时包含扣款和订单异常信号，真实归属需要业务规则或标签确定。[问题与答案说明](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/docs/questions-and-answers.md)

**字段名、题型和候选由调用者提供，模型负责计算候选的分数。**

### 1.2 候选标签与描述怎样进入模型？

程序会把各题的候选整理成文本。`department` 中的候选为：

```text
账单: 扣款、账单、退款
技术: 系统错误、订单状态异常
其他: 不属于以上类别
```

`urgency` 中的等级为：

```text
level 0: 不紧急
level 1: 需要尽快处理
level 2: 严重影响使用
```

对于没有自定义描述的 `noul`，实际默认候选文本为：

```text
false: no, the statement does not hold
true: yes, the statement holds
```

这些文本对应实际的 `render_options()`。此前已提取并执行这部分原始函数，核对上述渲染结果；这项核对没有涉及模型预测。[候选渲染代码](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/laya/common.py#L127)

候选描述提供语义信息。单独使用 `A`、`B`、`C` 而没有说明，模型无法从标签本身知道哪个代表账单、哪个代表技术。

### 1.3 为什么候选可以动态变化？

候选文字与数量来自本次请求，模型通过共享评分器为每个候选计算一个标量分数。因此，同一接口可以接收不同候选：

```text
请求一：账单、技术、其他
请求二：退款、物流、账号、其他
```

**动态候选表示架构能够接受请求中指定的选项，不等于模型对任意新领域都能可靠判断。** 候选描述、输入长度和领域数据仍会影响结果。

第一章明确了要问什么。训练还需要知道目标是什么，下面先用 `department` 这一题追踪完整链路；其余两题的结果解码在第 5 章展开。

## 2．输入数据：明确模型输入与训练目标

先给第一章的部门问题补充训练目标，仍使用同一张工单：

```text
工单：扣款成功，但订单仍显示失败，请帮我处理。

问题：这张工单应由哪个部门处理？

候选：
账单：扣款、账单、退款
技术：系统错误、订单状态异常
其他：不属于以上类别
```

**训练时，除了这些输入，还需要目标答案。** 为了讲解，假设这条样本已经由业务标注为“账单”。

符合实际训练接口的一条数据可以写成：

```json
{
  "state": "扣款成功，但订单仍显示失败，请帮我处理。",
  "questions": {
    "department": {
      "type": "choice",
      "instructions": "这张工单应由哪个部门处理？",
      "criteria": {
        "账单": "扣款、账单、退款",
        "技术": "系统错误、订单状态异常",
        "其他": "不属于以上类别"
      }
    }
  },
  "expected": {
    "department": "账单"
  }
}
```

这条数据分成两部分：

| 部分 | 内容 | 用途 |
| --- | --- | --- |
| 模型输入 | `state`＋`questions` | 让模型计算候选分数 |
| 训练目标 | `expected` | 评价预测，计算 loss |

程序按照候选顺序：

```text
[账单, 技术, 其他]
```

把“账单”转换成目标向量：

$$
t=[1,0,0]
$$

**目标答案用于计算 loss，不会作为答案提示拼进模型输入。**

实际接口也接受 `gold` 中的目标概率分布，例如教师模型提供的软目标；这时目标可以是 `[0.8,0.15,0.05]`，而不必只有一个 1。[训练数据处理](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/laya/train.py#L324)

输入与目标明确后，可以把它们放进完整的训练与推理流程。

## 3．整体流程：共享模型计算，分别进入训练与推理

以部门题为例，模型先根据工单、问题和三个候选，计算三个候选 logits。随后，训练和推理使用这些分数完成不同任务：

```text
                    工单＋问题＋三个候选
                              ↓
                三个候选 logits：[z账单,z技术,z其他]
                              │
             ┌────────────────┴────────────────┐
             ↓                                 ↓
          训练阶段                          推理阶段
             │                                 │
    ┌────────┴────────┐                        ↓
    ↓                 ↓                 温度缩放＋softmax
 原始 logits       logits 加噪声                  ↓
    ↓                 ↓                  三个候选概率
 softmax          多个扰动分布                     ↓
    ↓                 ↓                 计算两种置信度
 与目标计算       与目标计算奖励                   ↓
 交叉熵               ↓                  argmax＋标签映射
    │              相对优势                       ↓
    │                 ↓                  程序回填结构化结果
    │              策略损失                       ↓
    └────────┬────────┘                   字典／JSON
             ↓
    总 loss＝交叉熵＋策略损失
             ↓
       反向传播、优化器更新
             ↓
    更新编码器、题型表示、
    额外 Transformer 和评分器
```

第二章中的训练目标 $t=[1,0,0]$，同时供交叉熵和奖励计算使用。

**训练时根据目标调整模型；推理时使用已有参数计算结果。** 实际训练 loss 使用原始 logits，推理中的温度缩放属于后处理。[实际训练实现](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/laya/train.py#L493)

总图省略了输入到 logits 的内部计算。下一章沿同一个部门例子展开，再解释候选分数怎样变成概率。

## 4．模型计算：从输入文字到候选概率

### 4.1 输入文字怎样转换成 token ID

先只展开第一章中的 `department` 问题，程序将它的模型输入整理为：

```text
<bos>
choice question: 这张工单应由哪个部门处理？
<eos>
<mask> 账单: 扣款、账单、退款
<mask> 技术: 系统错误、订单状态异常
<mask> 其他: 不属于以上类别
<eos>
扣款成功，但订单仍显示失败，请帮我处理。
<eos>
```

其中，问题说明规定判断任务，候选描述规定选项含义，工单提供判断依据；`<mask>` 用于定位候选表示的读取位置。

为了演示，假设 tokenizer 将它分成 **50 个 token**，位置从 **0** 开始编号：

```text
位置 0～11：
<bos> choice question : 这张 工单 应由 哪个 部门 处理 ？ <eos>

位置12～19：
<mask> 账单 : 扣款 、 账单 、 退款

位置20～28：
<mask> 技术 : 系统 错误 、 订单 状态 异常

位置29～35：
<mask> 其他 : 不属于 以上 类别 <eos>

位置36～49：
扣款 成功 ， 但 订单 仍 显示 失败 ， 请 帮我 处理 。 <eos>
```

再假设教学词表中：

| Token | 教学 token ID |
| --- | ---: |
| `<bos>` | 1 |
| `<eos>` | 2 |
| `<mask>` | 3 |
| `账单` | 20 |
| `扣款` | 21 |
| `技术` | 24 |
| `其他` | 30 |

**注意 token ID 与位置编号的区别：**

```text
<mask> 的 token ID：3
    表示它是哪一种 token

三个 <mask> 的位置：12、20、29
    表示它们分别出现在哪里
```

因此，程序记录：

```text
marker_pos = [12, 20, 29]
```

分别对应账单、技术、其他。

实际代码会在构造序列时记录这些候选标记的位置，具体 token ID 和位置由真实 tokenizer 决定。[输入序列构造](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/laya/common.py#L156)

### 4.2 从 50 个输入位置，得到三个候选分数

下面完整展开模型计算。`…` 只是省略展示中间元素，模型实际会处理完整序列：

```text
你的输入文字
<bos> choice question: …… <mask> 账单 …… <mask> 技术 ……
<mask> 其他 …… 扣款成功，但订单仍显示失败，请帮我处理。 <eos>

                         ↓ tokenizer

token ID 序列：
[1, 10, 11, ……, 3, 20, ……, 3, 24, ……, 3, 30, ……, 2]
               ↑           ↑           ↑
             位置12       位置20       位置29
             账单标记     技术标记     其他标记
                                                    共50个 ID

                         ↓ embedding：按 ID 查表

初始向量序列：
[x₀, x₁, x₂, ……, x₁₂, ……, x₂₀, ……, x₂₉, ……, x₄₉]
                   ↑         ↑         ↑
                E[3]       E[3]       E[3]
                                                    共50个向量

                         ↓ 编码器 Transformer
                           结合上下文与位置信息

编码器输出：
[b₀, b₁, b₂, ……, b₁₂, ……, b₂₀, ……, b₂₉, ……, b₄₉]
                                                    共50个向量

                         ↓ 加入 choice 题型表示
                         ↓ Laya 的额外 Transformer 层

最终上下文向量：
[h₀, h₁, h₂, ……, h₁₂, ……, h₂₀, ……, h₂₉, ……, h₄₉]
                   ↑         ↑         ↑
               账单读出    技术读出    其他读出
                                                    共50个向量

                         ↓ 按 marker_pos 取出向量

候选向量：
                  [h₁₂, h₂₀, h₂₉]
                    ↓     ↓     ↓
                   账单  技术   其他                 共3个向量

                         ↓ 同一个候选评分器

候选 logits：
                  [z账单, z技术, z其他]              共3个数

                         ↓ 温度缩放＋softmax

候选概率：
                  [p账单, p技术, p其他]              共3个数

                         ↓ argmax＋标签映射

                    返回最高概率候选
```

**前半段是 50 个位置各有一个向量；到了“按标记取出向量”这一步，才从 50 个向量中选出三个候选向量。**

三个标记初始都查到 `E[3]`，但它们的位置和周围候选文字不同。经过上下文计算后，`h₁₂`、`h₂₀`、`h₂₉` 可以形成不同的表示。

模型各部分的作用是：

| 模块 | 本例中的作用 |
| --- | --- |
| Embedding | 将 50 个 ID 转成 50 个初始向量 |
| 编码器 Transformer | 综合问题、候选和工单信息 |
| 题型表示＋额外 Transformer | 进一步形成用于决策的上下文表示 |
| 候选位置读取 | 取出 `h₁₂`、`h₂₀`、`h₂₉` |
| 共享候选评分器 | 将三个向量分别变成三个 logits |

**模型并没有在此生成“账单”两个字，而是为账单、技术、其他分别计算一个分数。**[模型实现](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/laya/common.py#L574)

### 4.3 候选分数怎样变成概率？

第一步学过 softmax。这里把它放回实际实现，说明温度参数与归一化怎样连接三个候选分数。

**实际解码包含温度参数。** 对一道题，概率计算为：

$$
p_k=\frac{\exp(z_k/T)}{\sum_{j=1}^{K}\exp(z_j/T)}
$$

| 符号 | 含义 |
| --- | --- |
| $z_k$ | 第 $k$ 个候选的 logit |
| $K$ | 本题候选数 |
| $T$ | 温度参数 |
| $p_k$ | 第 $k$ 个候选的预测概率 |

实际代码还会减去缩放后 logits 的最大值，以提高数值稳定性；这不改变数学上的 softmax 结果。温度优先依据“题型＋候选数区间”选择，否则使用题型默认值，也支持语言覆盖配置。[概率解码代码](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/laya/agent.py#L1331)

**手算一个教学例子。** 假设部门题的 logits 为：

$$
z=[\ln 7,\ln 2,0]
$$

并且 $T=1$。于是：

$$
e^z=[7,2,1]
$$

$$
p=\left[\frac{7}{10},\frac{2}{10},\frac{1}{10}\right]=[0.7,0.2,0.1]
$$

这些 logits 是为了方便手算而设定的，不是实际模型运行结果。程序选择：

$$
a=\operatorname{argmax}_k p_k=\text{账单}
$$

**温度改变什么？** 在其他条件相同时：

- $T>1$：分布通常变得更平缓。
- $0<T<1$：分布通常变得更尖锐。
- $T=1$：保持原始 softmax。

例如，上述 logits 在 $T=2$ 时约得到：

$$
p=[0.5229,0.2795,0.1976]
$$

最高概率候选仍然是账单，但概率从 0.7 降到了约 0.523。对同一道题的全部候选统一使用正温度，不改变 logits 的排序，也不改变最大值所在候选；它改变的是概率值。

到这里，已经得到各题自己的候选分布。接下来说明同一个“分数到概率”的过程，怎样分别形成选择、二值概率和等级评分。

## 5．结果解码：三个题型怎样从概率得到结果？

第一章定义了部门、紧急程度和人工介入三个问题。它们都从候选分布出发，但最终返回值不同。下面继续分析同一张工单；三个分布均为教学假设。

### 5.1 choice：返回概率最大的候选

部门题的预测为：

$$
p=[0.7,0.2,0.1]
$$

对应：

```text
账单：0.7
技术：0.2
其他：0.1
```

程序计算：

$$
a=\operatorname{argmax}_k p_k=\text{账单}
$$

返回的核心信息是候选标签和完整分布。

### 5.2 noul：返回 true 的概率

人工介入题的默认语义顺序固定为：

```text
候选0：false
候选1：true
```

假设得到：

$$
p=[0.2,0.8]
$$

那么：

$$
\text{noul}=p_{\text{true}}=0.8
$$

它表示：模型给“需要人工介入”分配了 80% 的概率。原始 `predict()` 接口返回这个概率，并没有直接返回布尔值 `True`。

如果业务需要布尔决策，还需要确定阈值。比如使用 0.5：

$$
\text{needs\_human}=\mathbf{1}[p_{\text{true}}\geq 0.5]
$$

这个阈值属于决策规则。

### 5.3 score：返回等级索引的期望

对于紧急程度：

```text
0：不紧急
1：需要尽快处理
2：严重影响使用
```

假设等级分布为：

$$
p=[0.1,0.2,0.7]
$$

实际原始接口计算：

$$
\text{score}=\sum_{k=0}^{K-1}k\,p_k
$$

代入：

$$
\text{score}=0\times 0.1+1\times 0.2+2\times 0.7=1.6
$$

| 对象 | 结果 |
| --- | --- |
| 最可能的等级 | 2 |
| 等级期望 | 1.6 |

**`score=1.6` 是等级索引的加权平均，不表示出现了一个新的候选“等级1.6”。**

这也意味着等级间距按索引处理：若业务数值为 10、20、100，原始 `score` 不会自动计算这些业务数值的期望，需要另行明确映射。三类返回值的实际计算见 [`_decode_answers()`](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/laya/agent.py#L1367)。

三个问题已经各自得到返回值。接口还会提供置信度字段，下面明确它们与候选概率之间的关系。

## 6．置信度：confidence 与 answer_confidence 为什么不同？

第一步中采用的置信度定义是：

$$
c=\max_k p_k
$$

但 Laya 的实际字段命名需要区分题型。**选择结果、等级期望、分布集中程度和最大概率，是不同的量。**

### 6.1 choice 和 score：confidence 衡量分布集中程度

当候选数 $K\geq 2$ 时，公式为：

$$
c_{\text{entropy}}=1-\frac{H(p)}{\ln K}
$$

其中：

$$
H(p)=-\sum_{k=1}^{K}p_k\ln p_k
$$

- 分布均匀，熵较大，集中程度较低。
- 分布集中，熵较小，集中程度较高。

对于部门题：

$$
p=[0.7,0.2,0.1]
$$

有：

$$
H(p)=-0.7\ln 0.7-0.2\ln 0.2-0.1\ln 0.1\approx 0.8018
$$

因此：

$$
c_{\text{entropy}}=1-\frac{0.8018}{\ln 3}\approx 0.2702
$$

同一个分布可以同时出现：

```text
最大选项概率：0.7
confidence：0.2702
```

它们没有矛盾，因为衡量的对象不同。只有一个候选时，实际实现直接把此集中程度设为 1。[置信度计算](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/laya/common.py#L802)

### 6.2 answer_confidence：默认对应最大选项概率

在没有额外直方图分箱校准映射时：

$$
c_{\text{answer}}=\max_k p_k
$$

对上面的部门题：

$$
c_{\text{answer}}=0.7
$$

如果配置了额外 `binning_map`，实际返回的 `answer_confidence` 还可能经过该映射调整。[置信度定义](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/laya/common.py#L779)、[分箱映射应用位置](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/laya/agent.py#L1358)

### 6.3 noul：confidence 取真假两侧的最大概率

对于 `noul`：

$$
\text{confidence}=\max(p_{\text{true}},1-p_{\text{true}})
$$

第 5 章的人工介入例子中，true 的概率为 0.8，因此默认两个置信度字段都为 0.8。

如果另一次预测为：

```text
noul = 0.1
confidence = 0.9
```

则表示模型给 true 分配 10%，给 false 分配 90%。**高置信度并不意味着更倾向于 true。**

整理如下，`answer_confidence` 列对应未启用额外分箱映射的默认路径：

| 字段 | choice / score | noul |
| --- | --- | --- |
| `confidence` | $1-H(p)/\ln K$，衡量分布集中程度 | $\max(p_{\text{true}},1-p_{\text{true}})$，取真假两侧的最大概率 |
| `answer_confidence` | $\max_k p_k$ | $\max(p_{\text{true}},1-p_{\text{true}})$ |

对于 `score`，最大概率对应的是最可能等级的概率质量，不能理解成“期望值1.6正确的概率”。字段定义本身也不能证明概率已经校准。

**训练 loss 主要使用候选分布与训练目标，而不是以上两个返回字段。** 下一章回到部门题，说明这些数值怎样参与训练。

## 7．训练：用目标计算 loss，再更新模型

继续使用同一个例子：

```text
当前预测 p：[0.7,0.2,0.1]
训练目标 t：[1,0,0]
```

Laya 这份实现的默认 `rlcd` loss 包含交叉熵和策略损失。

### 7.1 交叉熵：直接让预测接近目标

$$
L_{\mathrm{CE}}=-\sum_k t_k\log p_k
$$

本例：

$$
L_{\mathrm{CE}}=-\log0.7\approx0.357
$$

它直接评价当前预测与目标的差异，并提供调整候选分数的梯度。

### 7.2 策略损失：从概率评分到候选评分更新

对于目标为账单的部门选择题，先用下面的公式评价第 $j$ 组扰动概率分布：

$$
\boxed{R_j=\ln q_{j,\text{账单}}+0.75\frac{q_{j,\text{账单}}}{\|q_j\|_2}}
$$

- $q_j$：第 $j$ 次扰动得到的候选分布，顺序为 `[账单,技术,其他]`；$q_{j,\text{账单}}$ 是其中的账单概率。
- 第一项 $\ln q_{j,\text{账单}}$ 是 log score，账单概率越大，这一项越大。
- 第二项是 spherical score，使用三个候选概率的平方和开根号作为分母；`0.75` 是本训练配置中的权重。

**奖励越大，表示这组分布与本条目标匹配得越好。** 这是本例的 `choice` 奖励，不是所有题型统一使用的完整公式。[实际奖励函数](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/laya/common.py#L719)

下面继续使用同一张工单：目标为账单 $t=[1,0,0]$，当前概率为 `[0.7,0.2,0.1]`。在当前 logits 附近加入不同扰动，按下面的顺序计算：

```text
扰动后的候选分布 → 奖励 R → 优势 A → 策略 loss
```

#### 7.2.1 计算优势：这次尝试比同组平均表现好多少？

先计算平均奖励，再计算归一化优势：

$$
\bar R=\frac{1}{M}\sum_{j=1}^{M}R_j,\qquad A_j=\frac{R_j-\bar R}{s+10^{-6}}
$$

$M$ 是尝试次数，$\bar R$ 是平均奖励；本例只有一道题，$s$ 是这些奖励的样本标准差。**正优势表示高于平均表现，负优势表示低于平均表现。**

#### 7.2.2 四次扰动：同样选账单，评分也可以不同

选取四组教学扰动，取 $M=4$、噪声标准差 $\sigma=0.4$。候选分布的顺序始终为 `[账单,技术,其他]`：

| 尝试 | 扰动 $\varepsilon_j$ | 候选分布 $q_j$ | 奖励 $R_j$ | 优势 $A_j$ |
| --- | --- | --- | ---: | ---: |
| 1 | `[0.4,-0.2,-0.2]` | `[0.8096,0.1269,0.0635]` | 0.5275 | 0.9882 |
| 2 | `[0.2,-0.1,-0.1]` | `[0.7590,0.1607,0.0803]` | 0.4541 | 0.6366 |
| 3 | `[-0.2,0.1,0.1]` | `[0.6335,0.2443,0.1222]` | 0.2322 | −0.4264 |
| 4 | `[-0.4,0.2,0.2]` | `[0.5615,0.2923,0.1462]` | 0.0711 | −1.1984 |

这里：

$$
\bar R\approx0.3212,\qquad s\approx0.2087
$$

**四次都选择账单，但概率评分不同：前两组高于平均表现，后两组低于平均表现。** 因此，训练能够区分这些尝试，而不只是判断是否选对。表中数值是教学算例，不是实际训练日志。

#### 7.2.3 构造策略 loss：用优势指导更新方向

$$
\boxed{L_{\mathrm{policy}}=-\frac{1}{M}\sum_{j=1}^{M}\operatorname{stopgrad}(A_j)\log\rho_\theta(\widetilde z_j)}
$$

其中：

- $\widetilde z_j$：第 $j$ 组扰动 logits。
- $\rho_\theta$：以当前 logits 为中心的高斯形式采样分布，**不是候选概率分布 $q_j$，也不是生成推理文字的概率。**
- `stopgrad`：优势作为固定权重，不通过优势反向传播。

代码中的采样对数密度项省略了不影响当前均值梯度的常数。

最小化这个 loss 时：

| 优势 | 提供的更新方向 |
| --- | --- |
| $A_j>0$ | 靠近该采样 logits，提高其采样倾向 |
| $A_j<0$ | 远离该采样 logits，降低其采样倾向 |

采样结果和优势保持固定，梯度通过采样对数密度中的当前 logits 回传到模型。**本例强化前两组高评分扰动的方向，抑制后两组低评分扰动的方向。**[策略损失实现](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/laya/train.py#L499)

下一节将策略损失与交叉熵相加，说明总 loss 怎样共同指导参数更新。

### 7.3 汇总 loss，反向传播并更新参数

$$
\boxed{L_{\mathrm{total}}=L_{\mathrm{CE}}+L_{\mathrm{policy}}}
$$

```text
总 loss
    ↓ backward
梯度沿评分器、候选表示和上下文网络回传
    ↓ optimizer.step
更新模型参数
```

默认未冻结编码器时，候选训练路径更新编码器、题型 embedding、额外 Transformer 和评分器。参数变化后，下次计算的表示、logits 和概率也可能变化。

这份实现也支持只使用交叉熵的 `soft-ce` 模式。[loss 与训练循环](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/laya/train.py#L493)

训练完成后，使用已有参数进行预测，流程便进入总图右侧的结果解码与回填。

## 8．推理：将候选概率回填为结构化结果

推理时没有训练目标，不计算训练 loss，也不更新参数。

本例得到：

```text
候选顺序：[账单, 技术, 其他]
候选概率：[0.7, 0.2, 0.1]
```

程序依次完成：

```text
argmax 找到索引0
    ↓
索引0映射为“账单”
    ↓
计算 confidence 和 answer_confidence
    ↓
填写 department 对应的答案字典
```

结果片段如下：

```json
{
  "answers": {
    "department": {
      "type": "choice",
      "choice": "账单",
      "probabilities": {
        "账单": 0.7,
        "技术": 0.2,
        "其他": 0.1
      },
      "confidence": 0.2702,
      "answer_confidence": 0.7
    }
  }
}
```

这是根据教学数字构造的输出片段，省略了 `action`、`usage` 等信息，并非实际预测记录。

第 5 章中的另外两种题型沿用候选评分过程，只改变解码规则：

| 题型 | 原始预测接口回填什么 |
| --- | --- |
| `choice` | 最高概率候选的标签 |
| `score` | 等级索引的概率加权平均 |
| `noul` | true 的概率 |

**模型负责计算候选分数；程序负责计算概率、映射标签、填写字段和组织结构。** 需要 JSON 文本时，再将结果字典序列化，模型不需要逐 token 写出括号、逗号和键名。[结构化结果封装](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/laya/agent.py#L1367)

理解结果怎样产生后，再看这种计算方式的速度优势，以及实际使用时影响结果的条件。

## 9．为什么快：省去逐个生成，把多题一起计算

两种方式的计算过程不同：

```text
自回归生成：
生成一个 token → 再生成一个 → …… → 完成推理文字和 JSON

Laya：
输入＋候选 → 批量计算候选分数 → 概率 → 程序填写结果
```

**Laya 直接算“选哪个”，然后由程序填写字段，不需要模型逐字写出答案和 JSON。**

批处理还能提高平均处理效率。项目保存的 T4 多语言模型数据为：

| 调用方式 | 整次调用耗时 p50 | 平均每题耗时 |
| --- | ---: | ---: |
| 一次处理 1 题 | 32.8 ms | 约 32.8 ms |
| 一次处理 10 题 | 72.3 ms | 约 7.23 ms |

这相当于：**一起处理 10 题，总时间增加，但平均每题更省时间。** 7.23 ms 是批处理平均值，不是独立单题请求的延迟。这是项目记录，没有在你的电脑上复现。[原始基准结果](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/research/results/t4_colab_benchmark.json)

## 10．哪些条件影响结果：模型看到什么、能选什么、字段是否一致

| 影响因素 | 直观例子 | 应该怎样理解 |
| --- | --- | --- |
| **工单被截断** | 关键句“请不要退款”在末尾，却没有进入模型 | 模型只能根据实际读到的内容判断；检查 `usage.truncated` 等记录 |
| **候选描述被截断** | 两个候选都是“退款申请……”，区分它们的后半段被删掉 | 标记还在，但候选含义可能已无法区分；描述要简洁、差异要明确 |
| **候选顺序变化** | `[账单,技术,其他]` 改成 `[其他,账单,技术]` | 默认顺序布局中，位置变化可能影响判断；不能假设结果必然不变 |
| **正确答案不在候选中** | 工单实际属于“物流”，候选只有“账单、技术” | 模型仍会从现有候选中选；候选要覆盖业务范围，可设置“其他” |
| **字段之间有矛盾** | `需要人工：否`，但 `处理方式：转人工` | 各字段单独合法，不代表组合符合业务规则；需要跨字段校验 |

长度预算也要看整体：

```text
总输入空间＝问题＋候选＋特殊标记＋工单
```

例如，**教学假设**总预算为 100 token，问题和候选占 40，工单有 80，那么只剩 60 个位置给工单，20 个工单 token 就可能被截掉。

**输出格式正确，只说明程序成功填写了结构；判断是否正确、概率是否可靠、字段是否一致，还需要分别验证。**
