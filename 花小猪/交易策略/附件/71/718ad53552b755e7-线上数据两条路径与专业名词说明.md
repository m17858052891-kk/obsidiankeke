# 线上数据两条路径与专业名词说明

整理日期：2026-10-15  
证据范围：本次对话中核对的 Platform、Argus 接口实现、数仓生产 SQL、数据血缘及样本比对结果。

## 一、先看主线

**同一条线上对话，目前经过两条数据路径：一条用于页面回放，一条用于数仓分析。**

| 路径 | 主要解决的问题 | 主要用途 |
|---|---|---|
| 页面回放路径 | 当时司机问了什么，助手怎么处理、怎么回复？ | 查看会话与 Agent 执行过程 |
| 数仓加工路径 | 对话如何汇总统计，怎样用于分析和评估？ | 数据分析、评估集抽样 |

**已确认：Platform 页面通过 Argus 接口获取数据，没有直接读取 DWS 对话宽表。**

## 二、页面回放路径：查看“当时发生了什么”

```text
Elasticsearch 中的会话和消息记录
    ↓ Argus 审计接口查询、整理
Platform 同步任务
    ↓ 写入 PostgreSQL
Platform 后端查询
    ↓ 前端转换
聊天气泡 + trace 执行时间线
```

### 专业名词的含义和作用

| 专业名词 | 含义和作用 | 通俗理解 |
|---|---|---|
| **Elasticsearch（ES）** | 保存并快速检索会话、司机端消息和 Agent 执行消息的系统。 | 可快速搜索的档案库。 |
| **Argus** | 提供审计查询的服务，查询 ES 并整理会话、轮次和消息。 | 档案查询窗口。 |
| **接口（API）** | 系统间交换数据的约定入口；Platform 提交时间范围或会话 ID，Argus 返回记录。 | 按约定提交查询单、领取结果的窗口。 |
| **审计** | 对已经发生的行为进行记录、追溯和复查。这里指查询已有对话与执行记录。 | 查历史记录，了解过程。 |
| **PostgreSQL** | 数据库软件；保存 Platform 从 Argus 同步回来的数据，供页面查询。 | Platform 查询和回放使用的数据存储库。 |
| **Platform** | 司机助手研发平台；读取数据库，把记录转换成页面上的聊天气泡和执行过程。 | 查看和分析数据的工作台。 |
| **Agent** | 根据司机问题进行处理、调用工具并生成回复的助手程序。 | 处理司机问题的智能助手。 |
| **Trace** | Agent 执行过程的记录，包括输入、System Prompt、思考、回复、工具调用和结果。 | 助手处理问题的过程回放。 |
| **System Prompt** | 提供给模型的角色、目标、规则和行为要求。 | 助手工作的说明书。 |
| **工具调用** | Agent 请求某个业务功能，例如知识检索或奖励查询；记录中包含工具名称、参数和返回结果。 | 助手调用业务功能办事。 |

### 这条路径要记住什么

- Argus 读取已有记录，不会因此让助手重新回答问题或重新执行当时的工具。
- Platform 先把数据同步到 PostgreSQL，页面再读取这份已入库的数据。
- 页面“刷新”重新查询数据库；“同步当前时段”才会提交从 Argus 拉取数据的任务。
- trace 是前端整理后的展示结构，一条原始消息可以展开成多个节点，工具返回也可以合并到对应的调用节点。

## 三、数仓加工路径：统计、分析和构建评估集

```text
MySQL：dm_agent_assist.messages
    ↓ MySQL2Hive 通过 Binlog 同步
ODS：原始消息数据
    ↓ 去重、过滤删除记录、解析正文
DWD：清洗后的消息明细
    ↓ 按对话轮次聚合，关联 Ask 日志、诊断、位置、埋点等
DWS：对话宽表
    ↓
统计分析 / 评估集抽样
```

### 专业名词的含义和作用

| 专业名词 | 含义和作用 | 通俗理解 |
|---|---|---|
| **MySQL** | 业务数据库软件。已确认数仓侧消息的源库是 `dm_agent_assist`，源表是 `messages`。 | 业务系统保存消息的账本。 |
| **数据库 / 数据表** | 数据库用于组织多张表；表按字段和记录保存一类数据。`dm_agent_assist.messages` 表示 `dm_agent_assist` 库中的 `messages` 表。 | 一个文件柜，以及柜中按类别整理的表册。 |
| **Binlog** | MySQL 记录新增、修改、删除等数据变化的日志，可供同步任务读取。 | 账本的变更记录。 |
| **MySQL2Hive** | 把 MySQL 数据同步到 Hive 的任务；当前查到的消息同步任务使用 `BinlogLauncher`。 | 数据搬运流程。 |
| **Hive** | 面向大量历史数据进行离线加工和分析的数仓系统。 | 用于大规模统计分析的数据系统。 |
| **数仓** | 数据仓库，将业务数据整理后用于统计、分析和评估。 | 分析用的数据中心。 |
| **ODS** | 原始数据层，保留同步回来的消息以及更新、删除、去重等标识。 | 原始材料区。 |
| **DWD** | 明细数据层，对原始数据去重、清洗、解析，形成逐条消息明细。 | 整理好的逐条消息。 |
| **DWS** | 汇总数据层，按对话轮次聚合消息，并关联其他业务信息。 | 每轮对话的综合档案。 |
| **宽表** | 将多个方面的信息组织到同一行，减少分析时反复关联多张表。 | 信息较全的汇总表。 |
| **Ask 日志** | 司机助手请求处理的日志；DWS 以这类请求为主，关联消息和其他信息。 | 助手收到并处理请求的记录。 |
| **埋点** | 客户端对展现、点击、反馈等行为产生的事件记录。 | 用户操作留下的行为记录。 |
| **血缘** | 数据从哪里来、经过什么加工、最终流向哪里的关系。 | 数据的来源和加工路线图。 |

### 三层数仓表分别是什么

| 层次 | 完整表名 | 作用 |
|---|---|---|
| ODS | `kflower_marketplace.ods_binlog_messages_h_whole` | 保存 Binlog 同步得到的原始消息。 |
| DWD | `kflower_strategy.dwd_driver_assistant_message_di` | 保存清洗后的消息明细。 |
| DWS | `kflower_strategy.dws_driver_assistant_dialogue_di` | 按对话轮次汇总，并关联请求、诊断、埋点等信息。 |

**这三层是逐步加工的关系，不是三份格式完全相同的数据。** ODS 可能包含同一消息的多个更新版本；DWD 按规则清洗去重；DWS 再将多条消息聚合到一轮对话中。

## 四、用同一条真实会话理解两条路径

样本问题：**“取消的订单能不能拉黑？”**  
会话 ID：`2377900603251852070`

### 1. 页面侧：组织成执行过程

这条会话包含 8 条 Agent 审计消息：

| 消息 ID | 角色 | 内容或作用 |
|---|---|---|
| `184036` | user | 司机问题。 |
| `184038` | user | 本轮时间等 `runtime_context`。 |
| `184040` | system | System Prompt。 |
| `184048` | assistant | 第一次思考、处理中回复，以及第一次知识检索调用。 |
| `184050` | tool | 第一次知识检索结果。 |
| `184052` | assistant | 第二次思考、处理中回复，以及第二次知识检索调用。 |
| `184054` | tool | 第二次知识检索结果。 |
| `184056` | assistant | 第三次思考和最终回复。 |

前端将它们整理成 **3 个聊天气泡**：司机问题、时间上下文、助手气泡。助手气泡内部包含 **9 个 trace 节点**：

```text
System Prompt
→ 第一次思考
→ 处理中回复
→ 第一次知识检索（含结果）
→ 第二次思考
→ 处理中回复
→ 第二次知识检索（含结果）
→ 第三次思考
→ 最终回复
```

**8 条原始消息不等于 8 个气泡或 8 个 trace 节点：前端会拆分、关联和合并展示。**

### 2. 数仓侧：保留明细，再汇总一轮对话

- ODS 中找到 8 条对应记录，原始同步键为 `dm_agent_assist||messages||消息ID`。
- DWD 中找到对应的 8 条消息。
- DWS 中找到对应轮次，记录了 **8 条消息、2 次工具调用**。

例如消息 `184048` 的 ODS 同步键为：

```text
dm_agent_assist||messages||184048
      源库          源表       消息主键
```

经逐条核对，这 8 条消息的 ID、角色和正文与 Argus 样本一致；原始正文的 SHA-256 哈希也全部一致。SHA-256 可以理解为内容指纹，本次用于检查两边正文是否完全相同。

## 五、最终结论与待确认边界

### 已确认

1. **页面路径**是 `ES → Argus → PostgreSQL → Platform`，没有直接读取 DWS 宽表。
2. **数仓路径**是 `dm_agent_assist.messages → MySQL2Hive → ODS → DWD → DWS`。
3. 示例会话在两条路径中可以对应到同一批消息，8 条消息的正文哈希全部一致。

### 尚未确认

**ES 索引的具体写入任务，以及它是否与 MySQL2Hive 读取同一个物理 MySQL 实例。**

当前证据可以确认样本消息一致，也可以确认 MySQL2Hive 侧的源库和源表；不能仅凭这些结果，就认定 ES 的写入方式或两边的物理源实例已经查明，也不能推断两边全量数据覆盖和保留规则完全相同。
