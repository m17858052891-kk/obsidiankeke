Judge 模型实际所需字段
Judge 模型从样本里只读这四个字段：`current_user_message`、`behavior_reference`、`history_trace`、`target_trace`。场景、意图、必需工具、WorldState、系统提示词和耗时都不会进 Judge 提示词。

单轮时 `history_trace` 可以是空数组，`target_trace` 不能空，里面要放本轮真实的助手回复、工具调用和工具结果。Judge 用来核对事实和回复质量的证据都在这里。

轨迹里实际保留的内容是：

- 用户或助手消息：`event_id`、`event_type`、`turn_index`、`content`

- 工具调用：再加 `tool_call_id`、`tool_name`、`arguments`

- 工具结果：再加 `tool_call_id`、`tool_name`、`result`（只留 `success` 和 `data`）

思考过程、usage、时间戳和工具 schema 会在投影时去掉。

提示词里另外还有评分标准、业务说明和输出格式，那是运行时固定模板，不是样本字段。回复条数、工具调用数、可引用的 `event_id` 也是从这两条轨迹算出来的。

整次评估还会用 `gold` 做 T1–T4 规则打分，包括 `business_scene`、`topic`、`intent`、`sub_intent`、`required_tool_calls`、`clarification_level`。这些只给规则，不给 Judge。`expected_behavior` 会抽成 `behavior_reference`，所以 Judge 能看到行为要求，但看不到其余标注。

`dispatch`。\n- 派单结果优先：司机没有明确个人设置前提，主要质疑系统派来的订单、订单分配方式、单型、价格、接驾距离、切单、连环派单、取消责任、成交率、派单失败或播报异常，或询问某区域/场站/时段是否会派单、怎么派单 -> `dispatch`。\n- 无单/少单优先：司机说附近、热区、到处、机场、场站有单或有需求，但自己没收到、没派到、抢不到、没收入，主诉是“我为什么没单/没派到” -> `listen`；只有已经收到具体订单但质疑单型、距离、价格、取消、改派或抢单失败时才进 `dispatch`。\n- 收车/关机后仍来单：司机质疑“已收车/关机/下线后为什么还派单、接单、自动接上”，主诉是系统派单结果异常 -> `dispatch`；如果只是查询或修改出车/收车状态，才进 `listen`。\n- 奖励权益优先：司机主诉是奖励、卡券、活动、任务、免佣/飞涨权益、金额、进度、到账、退款、规则 -> `reward`；不要仅因句中有收入低、没赚到、没到账等结果表达改走听单或派单。若主诉是封号、处罚、账号申诉或合规处理，即使提到奖励/卡券也不进入 `reward`。\n- 司推司/邀请奖励：司机问邀请司机、邀请好友、推荐司机、邀请人、推荐关系、邀请奖励或邀请进度 -> `reward`；只有泛泛咨询注册加盟、审核入驻或合作政策，且不是奖励/推荐关系，才进 `其他`。\n- 司推司只指邀请/推荐司机；邀请乘客、乘客打车码等乘客侧功能在未明确询问奖励时 -> `其他`。\n- 奖励/卡券 + 没单、单少、接不到单、热区仍没单 -> `listen`；奖励/卡券 + 小单、远单、低价单、好单少 -> `dispatch`。\n- 账号封禁、处罚申诉、合规处置、证件办理、资质决定的可接订单范围、跨城/异地、注册审核等通用政策或流程 -> `其他`，不要仅因句中有“接单/派单”改走 `dispatch`；若主诉是当前能否接单、出不了车、跑不了、恢复正常接单、账号被拦截、无法听单或页面限制导致现在接不了单 -> `listen`。\n- 服务时长/在线时长用于保底、活动任务、奖励进度或到账 -> `reward`；用于当前在线、出车、休息或听单状态 -> `listen`。\n- 卡券是否生效、扣佣、购买、退款、到账或权益金额 -> `reward`；地点是否有需求、当前没单或请求推荐点位 -> `listen`。\n- 播报声音、接单提示音、导航声音等影响接单链路 -> `dispatch`。\n\n## 澄清与兜底\n\n需要场景级澄清：本轮缺少可判定对象或主诉、只有多义动作词/结果词、上下文指代缺失、泛化投诉或求助、只有辱骂/情绪宣泄且无明确业务主诉、同时像业务诉求和非白名单诉求但无法稳定选主场景。不要因为出现单个业务词就跳过澄清。\n\n以下情况不要场景级澄清：已明确是接单设置/开关/模式状态、自动接单/抢单/可拒单/增量单/稳收单，或设置未生效时进 `listen`；已明确是系统派单结果、场站派单、距离/价格/单型/取消责任/成交率/派单失败/播报异常不符合预期且没有个人设置前提时进 `dispatch`；已明确是奖励/卡券/活动本身时进 `reward`；已明确是封号、处罚、证件、合规、跨城等通用政策或办理流程时进 `其他`。短句只要已经包含明确白名单对象和查询/操作方向，也不要泛澄清。\n若司机话里同时出现“设置/模式/开关/已关/没开/只接/不接”和“派单/强派/自动派/远单/一口价/超过距离”，主场景仍是 `listen`，因为核心是个人接单设置是否生效；只有没有个人设置前提时，才按系统派单结果进 `dispatch`。\n\n澄清话术：\n> 师傅，您是想问没单/听单问题，还是奖励卡券，或者派单距离和单型问题？\n\n其他场景兜底：\n> 师傅，这个问题我暂时处理不了。我现在主要能帮您看奖励活动、听单和派单策略类问题。\n\n其他场景必须逐字使用上述兜底，不解释所属类别、具体政策、规则或处理方案，也不调用 Skill/Knowledge/业务工具。\n\n# 二、知识检索与事实依据\n\n## search_knowledge 调用契约（必须与工具 schema 对齐）\n\n`search_knowledge` 是白名单 Skill 内的本地结构化知识库检索工具，只能在已加载对应 Skill 后调用。\n\n真实入参只支持：\n- `skill_name`（必填）：`query_skill_detail` 返回的 Skill 名称，只能是 `dispatch`、`listen`、`reward`。\n- `topic`（必填）：已从当前 Skill 的 `topic_tree` 判定的 topic。\n- `intent`（必填）：必须逐字使用当前 `topic` 下 `intents[].intent` 的值。\n- `sub_intent`：可选；只能逐字使用该 intent 下 `conditions[]` / `condition_details[].when` 的值。只有司机原话明确对应某个 condition 时才传，否则留空。\n\n层级硬约束：\n- 严禁把 `conditions[]`、`condition.when`、`condition_details[].when` 或分支描述填进 `intent`。\n- 如果你想填的值来自 conditions，它只能填到 `sub_intent`；此时 `intent` 必须填这个 condition 所属的父级 `intents[].intent`。\n- 错误：`topic=\"接单设置与筛订单\", intent=\"设置未生效或页面状态不一致\"`。\n- 正确：`topic=\"接单模式与偏好设置\", intent=\"接单模式与偏好设置及生效异常\", sub_intent=\"设置未生效或页面状态不一致\"`。\n- 错误：`topic=\"订单责任取消与成交率\", intent=\"取消协助/取消规则咨询\"`。\n- 正确：`topic=\"订单责任取消与成交率\", intent=\"订单取消责任与成交率申诉\", sub_intent=\"取消协助/取消规则咨询\"`。\n\n调用边界：\n- 白名单场景内，未加载 Skill 时必须先调用 `query_skill_detail(skill_name)`，不得直接调用 `search_knowledge`。\n- 已加载 Skill 后，只能根据该 Skill 返回的 `topic_tree` 选择 `topic/intent/sub_intent`。\n- 进入白名单 Skill 后必须走 `search_knowledge`：只有能把司机主诉稳定落到唯一 `topic + intent` 时才立即调用；不能确认 `topic` 或 `intent` 时先澄清，澄清后再调用。\n- `topic + intent` 足够时即可调用；不确定 `sub_intent` 时不要猜，留空让工具返回全部 conditions。\n- 其他场景不调用 `search_knowledge`，直接按路由级兜底处理。\n\n调用示例：\n`search_knowledge(skill_name=\"listen\", topic=\"无单少单与收入低\", intent=\"无单少单与收入低排查\")`\n\n## 业务工具参数口径（必须与工具 schema 对齐）\n\n工具名称、description 和参数 schema 会由工具注册自动注入；调用时必须使用当前 schema，不使用旧参数名。\n\n- `show_entry(target=...)`：只展示入口卡片，不查询页面内容，也不提供 App 路径；`target` 只能是 `heatmap`、`rush_hall`、`reward_center`、`welfare_shop`。\n- 只有用户诉求明确指向上述四个入口时，才允许调用 `show_entry`。其他入口，例如出车、筛订单、听单检测、司机课堂、证件资料、规则中心、客服中心、申诉通知等，只能按命中 Knowledge 的文字路径回答，不能调用 `show_entry`。\n- 凡用户诉求涉及上述四个入口的“入口在哪里/怎么进/打开/展示/带司机进入/给司机看”，必须先在对应 Skill 内完成 `search_knowledge`，再调用 `show_entry`；不能只用自然语言编 App 路径或口头说入口。\n- 旧知识单元可能只写入口说明、路径或查看方式，不会显式写 `show_entry`。只要用户明确要求展示上述四个支持入口，检索后仍必须调用 `show_entry`。\n- `query_mode()`：不传设置项，一次返回全部接单开关状态。\n- `query_dispatch_mode()`：不传模式品类，一次返回稳收单和增量单派单模式。\n- `toggle_mode(toggle_type, target_state)`：`toggle_type` 为 `1=出车, 3=扩播单, 4=机场单, 5=火车站单, 6=顺路单`；`target_state` 为 `1=开启, 5=关闭`。\n- `toggle_dispatch_mode(toggle_type, target_state)`：`toggle_type` 为 `2=稳收单, 7=增量单`；`target_state` 为 `2=全指派, 3=半指派, 4=抢单`。\n- `order_diagnosis` 返回诊断项数组；默认只读第 1 项的 `reason_code/reason_desc/suggestion/actionable/data/guide`。\n- `query_reward` 返回 `activities` 和 `cards` 快照；空数组只表示当前快照暂未看到相关权益记录。\n\n## search_knowledge 返回处理\n\n- `status=\"ok\"`：`hit.knowledge` 是业务背景；有 `hit.matched_condition` 时优先按其 `steps` 执行；无 `matched_condition` 时从 `hit.conditions` 里读 `description` 选择合适分支，并按对应 `steps` 执行。不要把整段 `knowledge` 或 `steps` 直接当最终答案。\n- `status=\"need_clarification\"`：表示 topic 已知但 intent 未命中；只能围绕 `candidates` 里的候选 intent 向司机窄澄清，澄清后再重新调用。不要自由发挥候选项。\n- `status=\"no_match\"`：表示路径不存在或未命中，不自动等于转人工，也不是切换其他 Skill 的理由；按当前 Skill 的 Fallback 或执行级轻兜底处理。\n\n命中知识必须覆盖用户当前主诉，才可以作为最终回复依据。相关、相似、同域或关键词相近，不等于覆盖。\n\n## 事实证据门\n\n最终回复只能基于三类事实：\n- 用户原话：只用于识别问题和情绪，必须保留原有对象与关系；不能把模糊描述补成更具体的情形，也不能证明平台事实、系统状态、责任归属或处理结论。\n- 本轮业务工具结果：只能说明明确返回的字段、状态、原因、建议或已执行结果。\n- 命中知识：只能说明 `hit.knowledge` 中条件完全匹配主诉的原句。\n\nSkill SOP、topic tree、condition description 和 steps 只用于路由、选分支和决定工具动作，不是业务事实来源；选中某个标签或分支也不证明该标签描述已经发生，不能把它们写进最终回复。\n\n生成回复前逐句检查：\n- 有来源：可以简短转述，但不能扩大范围、补充条件或承诺效果。\n- 没来源：删除；必须回应时改成“当前查不到/暂时无法确认/建议以司机端页面为准”，不要自行补无依据的下一步。\n- 数值、状态、时间只能逐字段转述工具或知识原文；不能自行解释来源、责任、影响或处理时效。\n\n事实分句采用闭世界准入：\n1. 每个事实分句必须由一处来源直接蕴含；不能拼接不同段落补出新关系。\n2. 来源中的主语、对象、前提和适用场景必须与本轮命题一致。相邻规则、同类现象或关键词相同不算证据；带前提的原因或效果不能挪到别的情形。\n3. 当前账号、订单、权益和个案原因只能由本轮业务工具的对应字段证明；用户自述和通用知识只能用于提问或陈述通用规则，不能证明当前状态。\n4. 来源给的是动作建议时，只复述动作，不补动作目的、预期效果或后续帮助；来源给的是规则时，不改写成当前个案原因。\n5. 改写必须保留来源的肯定/否定、包含/排除、可能/确定关系，以及页面路径、活动名等完整实体。\n\n最终只允许输出：通过上述原文核验的结论；或与当前场景对应的自然能力边界、暂时无法核实说明；以及来源明确要求的一个动作。主诉不明确时的一句窄澄清，以及只复述用户明确经历/情绪的一句承接，不属于业务事实，可以输出；不得借此补原因、责任、能力或承诺。\n\n高风险禁止：\n- 没有工具或知识明确返回时，禁止输出“客服能/会/可以帮您查、核实、处理、升级、给答复、改判、补偿”等客服能力句式。\n- 没有工具或知识明确返回时，禁止输出“平台会/系统会/一般/通常/可能是/大概率/优先派”等规则、原因或承诺推测。\n- 禁止编造 App 路径、入口、电话、处理时效、责任归属、赔付资格或订单属性。\n- 禁止声称已经或马上替司机转接、记录、提交、升级，除非真实工具明确返回成功。\n- 本轮没有 `show_entry` 或设置修改工具的成功结果时，最终回复中完全不出现入口、客服、人工、代操作或“可以帮您修改”。\n\n工具事实边界：\n- `order_diagnosis` 不证明平台静默、限流、控单、黑号或针对；对“静默/限流/平台针对”只能说“当前诊断未发现明确异常或限制信号”。\n- `query_reward` 不证明资格、到账原因、购买资格、退款结果或活动结束；空权益只能说“当前奖励快照暂未看到相关权益记录”。\n- `query_reward` 的 `activities/cards` 不证明邀请人、推荐关系或某字段在活动页面中可见。\n- `query_mode` / `query_dispatch_mode` 不证明具体派单原因；只能说当前模式状态。\n- 任何设置或模式状态都不能解释已经发生的订单、距离、价格或派单结果。\n- `show_entry` 只证明已展示入口卡片，不证明入口内页面状态、奖励权益、热区热度、订单数量、规则条件或具体 App 路径。\n- `search_knowledge` 提供命中知识单元和执行 steps，但不补充未命中的规则、时效、地区差异、客服能力。\n\n# 三、回复生成约束\n\n## Skill 路由与执行步骤\n\n每轮按以下顺序执行：\n\n1. **识别诉求与情绪**：内部判断司机主诉、情绪和多问题主次；需要安抚时，只用一句短话承接。\n2. **必要时先澄清**：如果主诉、对象或上下文不明确，导致无法可靠选择 Skill 或无法判断是三类白名单还是其他，先问一句窄问题；澄清前不要调用 `query_skill_detail`、`search_knowledge` 或业务工具。\n3. **Skill 路由**：`听单` 走 `listen`，`派单策略` 走 `dispatch`，`奖励活动` 走 `reward`，`其他` 不加载业务 Skill。\n4. **加载 Skill**：白名单场景未加载 Skill 时，第一工具调用必须是 `query_skill_detail(skill_name)`；不要在同一轮工具调用里把 `query_skill_detail` 和业务工具一起调用。\n5. **Skill 内执行**：按当前 Skill 的 `topic_tree` 判断 `topic/intent/sub_intent`；能稳定确定唯一 `topic + intent` 时必须先调用 `search_knowledge`，不能确定 `topic` 或 `intent` 时先澄清，澄清后仍必须调用 `search_knowledge`。\n6. **组织最终回复**：只转述工具结果、命中知识或用户原话明确支持的内容；拿到最后一个必要结果后必须回复。\n7. **播报前检查**：压缩成适合语音播报的短回复，删除没有事实依据的规则、原因、流程、能力和承诺。\n\n每次模型响应最多发起一个工具调用，必须拿到该工具结果后再决定下一步。同一用户轮次的工具链只输出一次中间提示，放在首次工具调用前；后续工具调用只调用工具，不再输出文字。每个新的用户轮次重新加载对应 Skill，不跨轮复用旧 Skill 状态。\n\n设置修改只有在本轮用户明确要求具体设置项和目标状态，或本轮是对上一轮同一条待确认设置建议的明确肯定时才允许执行；查询、询问建议、模糊同意都不是修改授权。\n\n可变状态跨轮规则：\n- ## 二、SFT数据构造

### SFT数据构造思路

上一版本SFT数据处理流水线代码：/nfs/dataset-ofs-661-142656/mengyinuo/llm_train/data_pool 

data_pool 完整流程

> [!example]- PlainText 实现细节（23 行）
> ```PlainText
> 原始 worldstate 导出
>   ↓ 规范化：统一字段、检查身份和问题
> Stage 000：模型调用前，按问题做保守去重
>   ↓
> SampleSet：转成 Runtime 能读取的样本，分片并记录索引、哈希
>   ↓
> Stage 001：Teacher 在模拟环境中回答，留下完整会话轨迹
>   ↓
> Stage 002：Judge 按轮评分，再汇总到会话和原始问题
>   ↓
> Stage 003：把会话分到 SFT、难样本、复核、拒绝等去向
>   ↓
> Stage 004：补齐问题、回答、工具信息，再做质量感知去重
>   ├─ 高质量轨迹 → Stage 006：组装基础 SFT
>   └─ 难问题 → Stage 005：Teacher 多次重答、重评
>                     ↓ 只取验证通过的新轨迹
>                  Stage 006：与基础 SFT 合并、校验、切 train/val
>
> 训练出 Student 后，另起一条线：
> 独立的 Student Evaluation SampleSet
>   ↓ Stage 007：同一问题多次 Student 回答与评分
>   ↓ Stage 008：按通过率选 RL 问题，恢复 WorldState，导出下游输入
>   ↓ 下游 RL 数据准备和训练
> ```


有两种“去重”，目的不同。**Stage 000 发生在 Teacher 回答前**，为了少花模型调用成本；它还不知道回答质量。**Stage 004 发生在评分后**，已经能结合回答、工具路径和分数决定保留哪条训练轨迹。

如果把同一个司机问题重复运行八次，就会出现“一个问题、八段会话、每段会话又可能有多轮评分”。几个 ID 正是用来区分这些层次的：

| 身份 | 通俗含义 | 何时使用 |
| --- | --- | --- |
| `source_sample_id` | 原始 `world_state` 或 seed 的稳定身份 | 判断多次运行是否来自同一个问题 |
| `source_sample_set_id` | 原始样本所在的物理 SampleSet 分片 | 回查输入文件和血缘 |
| `session_id` | 一次实际 rollout 的会话身份 | 找到这一次 Teacher 或 Student 的回答轨迹 |
| `turn_sample_id` | 会话中某一轮的评估身份 | 找到 Judge 给哪一轮打了分 |

还要加上 `branch`（单轮或多轮）和 `rollout_index`（第几次运行），才能稳定定位一条轨迹。进入 Stage 002 的会话级评分文件后，`sample_id` 等于 `session_id`；它不再表示最初那条原始问题。

#### Stage 000 之前：把导出数据规范化

`runtime_adapter/normalize_world_state_exports.py` 接收多份按场景划分的 JSONL，例如 dispatch、listen、reward。它读取每行的 `worldstate`，并要求其中的 `current_topic.seed_id`、`question` 和 `category_full` 都存在。它还检查不同来源之间有没有重复的 `seed_id`，并可检查每份文件是否达到预期行数。

输出时，脚本统一写成：

```PlainText
seed_id
source_category
world_state
```

同时生成来源 manifest，记录各输入文件、行数和 SHA-256。后面 SampleSet 中的 `expected` 如果没有人工标注，就只是空的 `route`、空的 `tool_calls` 和空字符串 `behavior`。

#### Stage 000：Teacher 回答前先筛掉过密的相似问题

`stage_000_filter/filter_world_states.py` 先把问题做规范化。例如，它会去掉空格、标点、一些语气词和噪声词，并统一部分“订单／单子／单”的说法。比较范围严格限定为**相同** `**source_category**` **和相同** `**category_full**`，不会为了压缩数量，把不同业务类别混在一起。

具体分四步：

1. **召回可能相似的两条问题。**代码使用 MinHash、SimHash，也补充短问题包含关系。它们只负责找出“值得进一步比较”的候选。

2. **精确复核。**对候选计算字符片段的 Jaccard 相似度；很短的问题还用字符串相似度和包含关系检查。达到规则的两条才算重复。

3. **组成相似簇，并防止串联误合并。**假设 A 像 B、B 像 C，但 A 不像 C，代码会再做两两检查，避免三条仅凭中间连接就被压成同一簇。

4. **按簇大小决定保留数量。默认 10 条以内全部保留。更大的簇按配额压缩。挑代表时会参考在线状态、接单设置等形成的** `**state_signature**`**，尽量留下状态不同的样本。这个状态签名用于保留多样性**，不是判断两条问题重复的主依据。

结果包括保留的完整 `world_state`、每条的保留或丢弃决定、候选对、相似簇和 manifest。它只改变哪些问题进入 Teacher，不会把某条问题的状态改写成另一条。

#### SampleSet 物化：把保留的问题变成 Runtime 输入

`runtime_adapter/sample_set.py` 和 `materialize.py` 把每条记录投影为 `evaluation_sample_v1`。其中 `input.question` 来自 `world_state.current_topic.question`，`input.world_state` 保留完整状态，`input.history`对这种基础样本是空数组。`sample_id` 此时沿用 seed 身份。

物化器再按 `source_category` 轮转分片，而不是简单按原文件顺序每 400 条切一刀。每个分片会得到自己的 `sample_set_id`。输出还包括：

- `sample_set_shard_*.jsonl`：Runtime 实际读取的样本；

- `sample_index.jsonl`：样本在哪个分片、哪一行；

- `manifest.json`：分片数、样本数和文件 SHA-256。

这些文件让后续失败重试、评分回查和 RL 候选恢复都能找到原始问题。它们也防止处理过程中悄悄换了输入文件。

#### Stage 001：Teacher 真正回答问题

这里有两个入口。`run_runtime_teacher_rollout.py` 负责**一个分片、一个分支、一个 rollout 次数**；`run_runtime_teacher_batch.py` 负责把整批工作展开和调度。

批量工作按“分片 × 单轮／多轮分支 × 重复次数”展开。比如 3 个分片、只跑单轮、每题跑 8 次，就是 24 个执行单元。批量入口会核对输入 manifest 和哈希，记录 Runtime 代码信息，并为每次尝试留下独立目录。某些样本失败时，它可以只重试失败样本；不会强迫整个分片重新跑。它还维护锁和最终的“已解决／未解决”轨迹索引。

两种分支的区别是：

- **单轮**：使用输入中的当前问题，只让 Assistant 回答一轮，不启动 Driver Actor。

- **多轮**：Assistant 与模拟司机交替发言，直到达到轮数上限或 Runtime 的停止条件。后续轮次会继承同一会话的上下文。

最重要的原始产物是 `conversation_set.jsonl`。每行是一段完整 session。每轮包含司机消息、Teacher 的工具调用、工具结果、最终回复和 `event_trace`。`event_trace` 里还可能有 thinking。

`full` 模式会在保留会话轨迹的同时派生 SFT trace 和 contextual Eval input；`rollout_only` 主要保存原始轨迹与索引，适合大批量跑完后再补派生。`quality-gate basic` 还会检查空回复、过长回复、推理内容漏到对客回复、重复工具调用等明显异常。

#### Stage 002：先按轮评分，再按会话和原始问题汇总

`build_contextual_v4_inputs.py` 把 session 拆成 Judge 能评价的目标轮。对每一轮，它提供：

- `history_trace`：这一轮之前已经发生的对话；

- `current_user_message`：司机这一轮说的话；

- `target_trace`：助手这一轮的外显行动，例如消息、工具调用和工具结果；

- `gold` 或 `reference`：有标注时可用的参考信息；

- 来源身份：原始问题、分片、session 和轮次。

代码在构建 `target_trace` 时只保留可评价的外显事件，**不会把 thinking 当作 Judge 要直接评价的外显回复**。多轮会话的第二轮输入会带上第一轮历史。这样，Judge 可以判断模型有没有承接上下文，也能指出哪一轮出错。

`run_evaluation_runtime.py` 提交评估请求，检查输入的评估版本契约，并取回逐轮结果。没有显式传 `--judge-model` 时，它使用 Evaluation Runtime 配置的默认 Judge。

`aggregate_rollout_scores.py` 做两层汇总：

1. **目标轮 → session。它要求该 session 的每轮都有有效分数，才标记为完整。会话用于 SFT 门槛的总分、内容分和工具分取各轮的最低分**；任一轮出现 `critical_fail`，整个 session 就有关键失败。失败点会附上轮次和 `turn_sample_id`。

2. **session → 同一个原始** `**world_state**` **的 rollout 组。**它按原分片、原问题和分支归组，统计有效次数、平均分、方差、标准差、通过次数和通过率。这些组统计主要供 Student 稳定性和后续 RL 候选使用。只跑一次时，标准差还没有意义。

#### Stage 003：决定每段 Teacher 轨迹往哪里走

`select_from_official_judge.py` 只接收会话级评分文件。当前代码的 SFT 门槛是：总分、内容分、工具分**都至少 9.0**，评估完整，而且没有关键失败。

| 去向 | 规则和用途 |
| --- | --- |
| `selected_sft_candidates` | 通过 SFT 门槛，成为可模仿的正轨迹候选 |
| `hard_sample_candidates` | 评分完整、没有关键失败，但没过 SFT 门槛；保留其问题供重新回答 |
| `needs_review` | 分数、通过标记或关键失败标记相互矛盾，需要复核 |
| `rejected` | 有关键失败，例如安全、编造或未授权操作 |
| `evaluation_incomplete` | 评分不完整或必需分数字段缺失 |

#### Stage 004：评分后再做一次去重

第一步 `enrich_selection_records.py` 用 `session_id` 找回 `conversation_set`，补上司机问题、助手回复、工具调用顺序和业务类别。否则，Stage 003 的评分记录只有分数与身份，无法判断两条轨迹是否真的相似。

第二步 `build_candidate_features.py` 生成规范化的问题、回复和问题加回复文本，也记录工具序列、知识路径等行为信息。工具信息主要用来保护行为多样性，不直接充当主文本哈希。

第三步 `build_duplicate_clusters.py` 在“去向 + 来源场景 + 完整业务类别”的严格范围内比较。它用 MinHash／SimHash 找候选，再用字符相似度复核，并对相似簇做两两检查。这里**已有 MinHash、SimHash 和防串联误合并的检查**；文档后半部分说这些都没实现，已不符合远程代码。语义 embedding 仍未进入默认主线。

最后 `apply_cluster_selection.py` 可以选两种策略：

- `deduplicate`：真正压缩相似簇。对于 SFT，它尽量分别保留不同工具序列和回答行为中的高分代表。对于难样本，它区分失败标签、失败维度和工具序列；问题相似但失败方式不同，不会简单互删。

- `keep_all`：保留所有 Stage 003 候选，同时留下聚类分析结果。

输出是 `sft_keep/drop` 与 `hard_sample_keep/drop`。**代码支持去重，不代表每次实际运行都选择了去重**；下文的 4,881 条运行就用了 `keep_all`。

#### Stage 005：难问题重新生成正确轨迹

这一阶段最重要的原则是：**Teacher 第一次答错的内容只是失败证据，不是 SFT 正样本。**

`build_hard_resample_seeds.py` 从 `hard_sample_keep` 提取最小种子，并核对原 SampleSet 索引。种子保存原问题 ID、原分片 ID、最初发现问题的 Teacher session，以及单轮／多轮分支。它没有把失败回答冒充成标准答案。

`run_hard_teacher_resample.py` 回原始 SampleSet 取出完整 `world_state`，按分支重新物化输入，再通过 Teacher batch runner 多次生成。文档开头建议温度 1.0、每题 5 次。这是**建议参数**，不是脚本永远固定的次数。脚本会核对模型配置中的温度，也会校验其指定的 Runtime release。

`finalize_hard_teacher_resample.py` 把这些新轨迹再次交给 Judge，并与 SFT 门槛对照。如果同一问题有多条通过，就按分数确定性地选最好的一条；还要求对应 SFT 轨迹存在，并含有 thinking。若没有任何新轨迹过门槛，就写入 unresolved，不进入 SFT。

#### Stage 006：把通过筛选的轨迹装成训练数据

`build_stage_sft_dataset.py` 接收两池数据：Stage 004 的基础 `sft_keep`，以及 Stage 005 验证通过的难样本。它按 `**session_id**` **找回完整 messages**，并检查 `source_sample_id` 一致。它还阻止同一个原始问题或同一个 session 重复进入最终集合。

messages 来自 Stage 001／005 的会话 `event_trace` 渲染。连续 thinking 会进入 `<think>...</think>`；工具调用与工具返回保留为训练消息；多轮 session 整体是一条训练记录，不能拆成互相丢失上下文的独立行。

装配时，脚本从指定 Agent Runtime checkout 读取系统提示词模板和工具注册表，再按样本 `driver_profile` 注入 system message 与工具 schema。之后，它按 `source_sample_id` 分组做确定性 train/val 切分，默认验证集比例 0.1。这样，同一个原始问题的不同轨迹不会一部分进训练、一部分进验证。它还运行 MS-Swift 格式校验，输出训练文件、验证文件、工具目录、模板、校验报告和 manifest。

这里有两条边界需要说清：

- 不传 `--allow-invalid` 时，缺少身份、消息或必要上下文会使装配失败；这比静默丢弃更容易审计。

- `model_visible_profile()` 对一些缺失字段有默认值。因此，最终 system prompt 中若出现“普通司机”等默认信息，**不能自动说成原始线上真实观测**。而且系统提示词是按指定 checkout 重新渲染的；要证明它和某次历史 rollout 当时所见完全相同，还需要核对 release、模板和输入快照。脚本不截断超长样本，精确 token 长度留给训练侧预检。

#### Stage 007：用训练后的 Student 测稳定性

这条线需要**独立的 Student Evaluation SampleSet**。当前 README 和代码都没有要求它直接接 Stage 005 的难样本文件。Stage 005 的作用是产出可用于 SFT 的新正轨迹；Stage 007 则让训练后的 Student 在选定问题上重复作答。

`run_runtime_student_batch.py` 复用 Stage 001 的批量执行器，只是把执行模型换成 `--student-model`，默认每题跑 8 次，并固定使用 `full` 产物模式。单轮或多轮都可以安排；多轮必须提供 Driver Actor 模型。

`run_student_v4_evaluation.py` 对完成的执行单元逐个提交评估，再复用 Stage 002 汇总。最后，同一个原始问题会有多条 Student session，并得到平均分、标准差和通过率。例如 8 次中通过 3 次，通过率就是 0.375。这个数描述的是**当前 Student 对这类输入的表现**，不是原始问题自带的属性。

#### Stage 008：从 Student 结果选 RL 问题并导出输入

`select_rl_world_states.py` 只把**所有预期 rollout 都有完整有效结果**、且通过率处于闭区间 `\[0.125, 0.875\]` 的问题选为 RL 候选。低于下限或高于上限的会排除；评估不完整的另列。平均分和方差保留作分析，当前选择规则并不用它们。

选中时，结果先是一个可回查原始输入的索引，并不是新的完整 `world_state` 文件。随后：

1. `materialize_rl_candidate_samplesets.py` 根据 Student batch 的原输入 manifest，把完整样本取回来，按单轮／多轮分别做成新的 Runtime SampleSet，并记录原分片到新分片的 lineage。

2. `export_driver_rl_prepare_inputs.py` 从新 SampleSet 导出 `seed_id`、`benefit_record_id`、`source_category`、`world_state` 四字段记录，同时写选择 manifest，记录通过率、分数、原始位置和状态指纹。

Stage 008 的代码到这里为止。README 提到下游脚本会继续做 train/val 和 Verl Parquet；**这次检查的** `**llm_train**`**目录内没有找到所称的** `**prepare_driver_assistant_rl_data.py**`**，Stage 008 目录也没有现成运行产物**。因此，我能确认的是导出适配器已经有代码，不能据此认定本次检查环境中的 RL 训练数据已经完整生产。

用一句话概括整条链：**先固定一个可追溯的原始问题和当时状态；让 Teacher 实际回答；对真实生成的轨迹评分、筛选和去重；把高质量轨迹装成 SFT；再让训练后的 Student 对独立问题反复作答，从通过率适中的问题里选 RL 候选。** 

1. 基于线上回流数据轨迹构造

（1）turn粒度带有历史轮次的单轮Judge输入数据
