## 一. 背景介绍

联合决策目前目前所依赖的的AR模型存在以下一些问题，难以在基于XGB模型的架构下得到解决，所以期望对AR模型进行迭代，由XGB模型迭代到深度模型，同时由对AR的预估迭代到对CR的预估：

1. 在联合决策v2版本的迭代中，AR模型的预测概率会在决策阶段和ECR、DSAR模型的输出概率一起求解，由于三个模型在建模时是分开的，不同模型输出概率需要符合真实概率才会具有可比性。目前的AR模型是基于XGB构建的，输出概率需要依赖校准才能符合真实概率分布，但是概率校准会面临严重的OOD问题，迭代和维护成本较高，且从实际校准结果来看，预测概率分布并不合理。

2. 联合决策在计算gmv和cost时，依赖于预测的商家应答率，但是这里的应答率是“单勾应答率”，不是在“竞争状态下的应答率”，这会使得gmv和cost的计算产生偏差。所以期望模型输出在不同勾选下每个商家在竞争态下的应答率。

3. 联合决策目前使用的是AR模型，但优化求解时不论是最大化完单，还是最大化GMV的目标，应该依赖于CR而不是AR，在修改目标的条件下，需要模型能够输出不同勾选条件下每个trace的完单概率，基于XGB的模型难以完成这样的任务。

## 二. acc_CR模型介绍

### 2.1 模型设计

结合业务逻辑，以及联合决策的整体流程，模型需要解决三个任务：

1. Trace finish：预测每一单的完单概率

2. CP finish：在发单的商家中，最终会以哪个商家完单，以及每个商家完单的概率

3. CP ans：每一个商家的应答概率

同时在解决每个任务时，模型需满足以下条件：

1. **盒子内外差异化**：模型需要能区分同一商家以盒子外发单、以盒子发单之间完单率的差异，且不同盒子之间的完单率也存在差异；

2. **CR与商家顺序无关**：对于价格列表上的cp，输出概率和列表上的顺序无关（价格相同的情况下）

	1. 假设有a、b、c三个商家，商家顺序从abc变为bac时，输出的概率不变，以及预测的最终完单的cp也不会变

3. **能输出加权系数且系数能反应竞争关系**：输出具体以哪个商家完单的概率，用于联合决策计算gmv和cost（说明一下），且对于同一商家，不同勾选组合下加权系数不一样

	1. 勾选a、b、c三个商家和勾选a、b、c、d四个商家时，a商家的完单概率是不一样的，不同商家之间有竞争关系

### 2.2 离线训练及在线使用流程介绍

- Trace finish任务预测

每个商家的特征会过一次模型，得到一个1x3的向量（向量每个元素都大于0），表示每个商家在不同发单状态下对最终完单率的贡献，每个商家发单只会有三种状态：单勾特价盒子发单、盒子外发单、特快盒子发单（暂时不考虑幸运盒子）。例如，商家A如果同时勾选了**特价盒子**和**盒子外**并发单，那么实际发单只会按照**盒子外**发单，这时候A商家从对应位置取出相应的元素。所以，模型会输出一个**商家数\*3**的矩阵。

| 商家 | uabox | 盒子外 | ufbox | 发单状态 |
| :---: | :---: | :---: | :---: | :---: |
| A | ==a1== | a2 | a3 | 特价盒子 |
| B | b1 | ==d2== | d3 | 盒子外 |
| C | c1 | c2 | ==c3== | 特快盒子 |

按照不同的发单状态取出对应元素之后，by trace聚合得到最终对于这一单的完单预测*，*即predict1= ( sigmoid(a1 + b2 + c3) - 0.5 ) \* 2，这里的计算主要是因为，模型输出值都是大于0的，为了把聚合后的结果归一化0～1之间作为概率值使用。

**Loss计算：**有了预测的这一单的完单概率predict，根据是否完单的label，计算bce loss。

**在线使用：**线上使用时，所有商家会过一次模型，随着勾选数的变化，商家的发单状态会随之改变，每个商家根据当前的勾选数以及发单状态，取出对应元素后聚合成当前勾选状态下完单率的预估

- CP finish任务预测

整体逻辑和「trace完单率预测」任务一样，只是模型外的计算方式不一样。举例来说，首先还是所有商家特征过模型，得到**商家数 \* *3****的矩阵，然后根据当前商家的发单状态，选出对应位置的值。*

| 商家 | uabox | 盒子外 | ufbox | 发单状态 |
| :---: | :---: | :---: | :---: | :---: |
| D | ==d1== | d2 | d3 | 特价盒子 |
| E | e1 | ==e2== | e3 | 盒子外 |
| F | f1 | f2 | ==f3== | 特快盒子 |

按照不同的发单状态取出对应元素之后，不同商家的完单概率预测值为predict2=softmax(d1，e1，f1)，计算结果是一个概率分布，根据概率分布，取出预测概率最高的那个cp，就是预测的最终完单的cp。

**Loss计算：**预测最终完单的cp的任务当成一个多分类的任务，每个trace只会由一个cp完单，总共的类别数就是这个trace呼叫的cp数，那么label就是完单的cp对应的index，有了predict2的概率分布之后，就可以计算ce loss。离线计算loss时，只计算完单的trace。

**在线使用：**线上使用时，所有商家会过一次模型，随着勾选数的变化，商家的发单状态会随之改变，每个商家根据当前的勾选数以及发单状态，取出对应元素后，聚合成概率分布，然后根据概率分布计算加权的cost和gmv。

- CP ans任务预测：联合决策中不会使用这部分结果，主要起辅助作用，同时会透传给下游任务使用

channel应答任务对每一个cp会预测一个值，同时每一个cp也会有对应的label，预测的目标和原本的XGB模型相同，即“单勾商家的应答率”，输出的结果就是商家的应答概率，不需要做额外计算。

**Loss：**不需要by trace聚合，每个cp都有一个label和一个输出，输出的结果就是每个cp的单勾应答率，直接和label计算bce loss即可。

**线上使用：**透传给下游任务使用

- 当前任务采用的是Hard Shared架构，同时也对比了不同架构下的模型效果，但是综合来看，Hard Shared的效果较好，所以最终采用该架构。

- trace finish任务，最后一层采用不同计算公式对比

公式1：predict = (sigmoid(a1 + b2 + c3) - 0.5) \* 2

公式2：predict = tanh(a1 + b2 + c3)

公式3：predict = 1 - exp(-(a1 + b2 + c3))

### 2.4 特征工程

模型由AR过度到CR，主要增加应答后取消相关的特征，但是从交易链路上看，用户发单之后，还存在举手、pk等中间过程，所以也参考交易侧使用的特征。但是冒泡阶段拿不到司机信息，所以在acc_CR模型中，在商家维度聚合历史统计特征。

**trace维度特征**

| | 说明 |
| --- | --- |
| 基本特征 | 城市id、小时、订单里程等，离散特征，embedding后使用，连续特征直接使用 |
| 供需特征 | 参考熔断侧SDS特征，包括城市和格子的呼叫数、应答数、司乘取消数等，以及由这些特征聚合的ar、cr、取消率等 |
| 乘客侧聚合特征 | 乘客维度聚合7d、14d的聚合应答、完单、取消等相关特征 |

**商家维度特征**

| | 说明 |
| --- | --- |
| 价格特征 | 考虑到盒子内外价格的差异，所以对每个商家而言，价格特征分成特价盒子、盒子外、特快盒子等维度，同时价格特征也会衍生出cpm、iph等价格相关的特征 |
| 商家维度聚合特征 | 商家维度聚合7d、14d的聚合应答、完单、取消，以及应付和实付价等相关特征 |
| 实时运力特征 | 这部分特征和原来的ar模型一致 |
