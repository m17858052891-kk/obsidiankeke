## 不同口径的计算方式

### OLD

> [!example]- SQL 实现细节（26 行）
> ```SQL
> mogou as 
> (
>     select  passenger_id
>             ,city_id
>             ,count(distinct a.order_id) as mogou_call_cnt
>             ,sum(only_selected_call_cnt) as only_mogou_call_cnt
>     from    (
>         select  order_id
>                 ,only_selected_call_cnt
>                 ,city_id
>         from    kflower_dw.dwm_kf_trd_order_bubble_di
>         where   dt = '${BIZ_DATE_LINE}'
>           and   form_type = 3
>           and   order_type = 0
>           and   source_type <> 2
>           and   size(selected_bub_product_arr) > 0
>     ) a
>     left join (
>         select  distinct order_id
>                 ,passenger_id
>         from    kflower_dw.dwd_kf_trd_order_base_di
>         where   dt = '${BIZ_DATE_LINE}'
>     ) b
>     on      a.order_id = b.order_id
>     group by passenger_id, city_id
> )
> ```


- 订单粒度统计，乘客维度汇总输出

- 依赖于统计表==发单冒泡订单粒度指标表（中间表）(仅含小猪端内订单) kflower_dw.dwm_kf_trd_order_bubble_di==，这张表在订单粒度上，把两组品牌集合算出来：

	- ==selected_bub_product_arr==：默认勾选品牌数组

	- ==call_product_arr==：最终呼叫品牌数组

- 同时这张表中也直接定义了 ==only_selected_call_cnt = 1，条件是====只有当==**最终呼叫品牌集合和默认勾选品牌集合完全一致**==时，这个订单才算“仅呼叫默勾”。==

- 过滤条件

	- ==form_type = 3==：聚合表单

	- ==order_type = 0==：实时单

	- ==source_type <> 2==：非改派单

	- ==size(selected_bub_product_arr) > 0==：该订单必须存在默认勾选

- 输出字段

	- ==mogou_call_cnt = count(distinct a.order_id)==

	- ==only_mogou_call_cnt = sum(only_selected_call_cnt)==

- ==指标计算==

	- ==默勾接受度：仅呼叫默勾的订单数 / 有默认勾选的订单数==

### NEW

> [!example]- SQL 实现细节（29 行）
> ```SQL
> mogou_new as 
> (
>     select  passenger_id
>             ,city_id
>             ,sum(mogou_cnt_box_as_one) as mogou_cnt_box_as_one
>             ,sum(called_cnt_box_as_one) as called_cnt_box_as_one
>             ,sum(is_mogou_accept) as is_mogou_accept
>             ,sum(is_jiagou) as is_jiagou
>             ,sum(is_fangou) as is_fangou
>             ,count(distinct trace_id) as call_cnt_new_mogou
>     from    (
>         select  city_id
>                 ,trace_id
>                 ,size(selected_list) as mogou_cnt_box_as_one
>                 ,size(called_list) as called_cnt_box_as_one
>                 ,if(size(jiagou_list) == 0 and size(fangou_list) == 0, 1, 0) as is_mogou_accept
>                 ,if(size(jiagou_list) > 0, 1, 0) as is_jiagou
>                 ,if(size(fangou_list) > 0, 1, 0) as is_fangou
>         from    kflower_strategy.dwm_kf_trd_order_bubble_di_cgh
>         where   dt = '${BIZ_DATE_LINE}'
>     ) a
>     left join (
>         select  distinct bubble_trace_id
>                 ,passenger_id
>         from    kflower_dw.dwd_kf_trd_order_base_di
>         where   dt = '${BIZ_DATE_LINE}'
>     ) b
>     on      a.trace_id = b.bubble_trace_id
>     group by city_id, passenger_id
> ```


- may from  [冒泡页默勾看板更新](https://cooper.didichuxing.com/knowledge/2199610335356/2203315133405)

- 上游数据依赖于国华的表 kflower_strategy.dwm_kf_trd_order_bubble_di_cgh

- ==先按== **trace 粒度** ==重建一次用户的勾选和发单行为。具体做法是：从冒泡明细里，针对每个== ==trace_id== ==看每个品牌两种状态：==

	- ==selected_status = 1==：默认勾选了

	- ==is_send = 1==：最终发单了

- 然后把盒子类压成一个整体来算：

	- 特价盒子 ==105 -> -1==

	- 特快盒子 ==200 -> -2==

	- 幸运盒子 ==107 -> -3==

- 在这个基础上，生成 ==cgh== 表里的几个核心字段：

	- ==selected_list==：默认勾选的品牌

	- ==called_list==：最终发单的品牌

	- ==fangou_list==：默认勾选了但没发的品牌

	- ==jiagou_list==：默认没勾选但发了的品牌

- 同时还会统计：

	- ==mogou_cnt_box_as_one = size(selected_list)==：默认勾选品牌数

	- ==called_cnt_box_as_one = size(called_list)==：最终发单品牌数

- 最后，再通过 ==trace_id = bubble_trace_id== 关联订单表拿到 ==passenger_id==，按乘客汇总：

	- 接受默勾的 trace 数

	- 加勾的 trace 数

	- 反勾的 trace 数

	- 总 trace 数

### DS

> [!example]- SQL 实现细节（130 行）
> ```SQL
> with bubble_call as 
> (
>     select
>         passenger_id,
>         sum(can_reverse_cnt) as can_reverse_cnt,
>         sum(had_reverse_cnt) as had_reverse_cnt,
>         sum(can_append_cnt) as can_append_cnt,
>         sum(had_append_cnt) as had_append_cnt,
>         sum(only_selected_call_cnt) as only_selected_call_cnt
>     from
>     (
>         select
>             passenger_id,
>             dt,
>             count(case when is_can_reverse = 1 then a.order_id end) as can_reverse_cnt,
>             count(case when is_had_reverse = 1 then a.order_id end) as had_reverse_cnt,
>             count(case when is_can_append = 1 then a.order_id end) as can_append_cnt,
>             count(case when is_had_append = 1 then a.order_id end) as had_append_cnt,
>             count(case when only_selected_call_cnt > 0 then a.order_id end) as only_selected_call_cnt
>         from
>         (
>             select
>                 order_id,
>                 max(passenger_id) as passenger_id,
>                 max(dt) as dt
>             from
>                 kflower_dw.dwd_kf_trd_order_base_di
>             where
>                 dt between '${begin_date}' and '${end_date}'
>                 and start_city_id in (${city})
>                 and is_td_call = 1
>                 and source_type <> 2
>                 and product_1level not in (3, 4)
>             group by
>                 order_id
>         ) a
>         left join
>         (
>             select
>                 order_id,
>                 max(only_selected_call_cnt) as only_selected_call_cnt,
>                 max(if(selected_bubble_cnt > 0, 1, 0)) as is_can_reverse,
>                 max(if(selected_cp_cnt > size(both_bub_call_product_arr), 1, 0)) as is_had_reverse,
>                 max(if(bubble_cnt - selected_cp_cnt > 0, 1, 0)) as is_can_append,
>                 max(if(call_cp_cnt > size(both_bub_call_product_arr), 1, 0)) as is_had_append
>             from
>                 kflower_dw.dwm_kf_trd_order_bubble_di
>             where
>                 dt between '${begin_date}' and '${end_date}'
>                 and form_type = 3
>                 and order_type = 0
>                 and source_type <> 2
>             group by
>                 order_id
>         ) b
>         on a.order_id = b.order_id
>         group by
>             passenger_id,
>             dt
>     ) t
>     group by
>         passenger_id
> ),
>
> call as 
> (
>     select
>         passenger_id,
>         sum(call_cnt) as call_cnt
>     from
>     (
>         select
>             passenger_id,
>             a.dt,
>             count(distinct case when is_compete_call = 1 then a.order_id end) as call_cnt
>         from
>         (
>             select
>                 *
>             from
>                 kflower_dw.dwd_kf_trd_unity_order_anycar_di
>             where
>                 dt between '${begin_date}' and '${end_date}'
>                 and start_city_id in (${city})
>                 and passenger_id <> 0
>                 and is_hxz_call = 1
>                 and to_date(call_time) = dt
>                 and product_id <> 26
>         ) a
>         left join
>         (
>             select
>                 dt,
>                 order_id,
>                 estimate_id,
>                 product_id,
>                 call_car_level_id,
>                 is_compete_call
>             from
>                 kflower_dw.dim_kf_trd_unity_order_anycar_label_di
>             where
>                 dt between '${begin_date}' and '${end_date}'
>         ) c
>         on a.order_id = c.order_id
>         and a.estimate_id = c.estimate_id
>         and a.product_id = c.product_id
>         and a.call_car_level_id = c.call_car_level_id
>         and a.dt = c.dt
>         group by
>             passenger_id,
>             a.dt
>     ) t
>     group by
>         passenger_id
> )
>
> select
>     sum(nvl(bubble_call.only_selected_call_cnt, 0)) as `仅呼叫默勾订单数`,
>     sum(nvl(call.call_cnt, 0)) as `竞争呼叫订单数`,
>     sum(nvl(bubble_call.can_reverse_cnt, 0)) as `可反勾订单数`,
>     sum(nvl(bubble_call.had_reverse_cnt, 0)) as `反勾订单数`,
>     sum(nvl(bubble_call.can_append_cnt, 0)) as `可加勾订单数`,
>     sum(nvl(bubble_call.had_append_cnt, 0)) as `加勾订单数`,
>     sum(nvl(bubble_call.only_selected_call_cnt, 0)) / sum(nvl(call.call_cnt, 0)) as `默勾接受度`,
>     sum(nvl(bubble_call.had_reverse_cnt, 0)) / sum(nvl(bubble_call.can_reverse_cnt, 0)) as `反勾率`,
>     sum(nvl(bubble_call.had_append_cnt, 0)) / sum(nvl(bubble_call.can_append_cnt, 0)) as `加勾率`
> from
>     bubble_call
>     full join call on bubble_call.passenger_id = call.passenger_id
> ;
> ```


- bubble_call 部分 统计默勾、加勾、反勾的相关订单数

	- 先从 ==dwd_kf_trd_order_base_di== 里筛出当天：

		- 发单成功 ==is_td_call = 1==

		- 非改派 ==source_type <> 2==

		- 非预约/非特殊业务 ==product_1level not in (3,4)==

	- 再关联 ==dwm_kf_trd_order_bubble_di==，只保留：

		- 聚合表单 ==form_type = 3==

		- 实时单 ==order_type = 0==

		- 非改派单 ==source_type <> 2==

	- 在这个范围内定义：

		- ==仅呼叫默勾订单数==

			- ==only_selected_call_cnt > 0== 的订单数

		- ==可反勾订单数==

			- ==selected_bubble_cnt > 0==，即存在默认勾选

		- ==反勾订单数==

			- ==selected_cp_cnt > size(both_bub_call_product_arr)==，即默认勾选里有品牌最终没被呼叫

				- 其中 ==both_bub_call_product_arr 为既是默认勾选、又是最终呼叫的品牌数组==

				- selected_cp_cnt 为默认勾选车型数 / 品牌数

		- ==可加勾订单数==

			- ==bubble_cnt - selected_cp_cnt > 0==，即存在默认未勾选的候选品牌

		- ==加勾订单数==

			- ==call_cp_cnt > size(both_bub_call_product_arr)==，即最终呼叫里包含默认勾选之外的品牌

				- call_cp_cnt 为最终呼叫车型数 / 品牌数

- call 部分统计默勾接受度的分母，即竞争呼叫订单数

- 最终 SQL 把两部分做全量汇总，输出 3 个核心比例：

	- ==默勾接受度 = 仅呼叫默勾订单数 / 竞争呼叫订单数==

	- ==反勾率 = 反勾订单数 / 可反勾订单数==

	- ==加勾率 = 加勾订单数 / 可加勾订单数==

### 3. 核心结论

#### 3.1 看板的默勾接受度与 `new` 基本一致

在日期顺序修正后，看板默勾接受度与 `new` 几乎逐日对齐：

- 2026-04-30：看板 `46.53%`，`new` `46.51%`

- 2026-05-01：看板 `50.03%`，`new` `50.01%`

- 2026-05-02：看板 `51.64%`，`new` `51.63%`

- 2026-05-03：看板 `55.87%`，`new` `55.86%`

- 2026-05-04：看板 `57.76%`，`new` `57.75%`

- 2026-05-05：看板 `55.56%`，`new` `55.55%`

- 2026-05-06：看板 `56.01%`，`new` `56.00%`

因此可以认为：

- 看板的“默勾接受度”就是 `new` 口径，或者与 `new` 口径几乎完全一致

相对地，看板与 `old`、`ds` 差异都在 `7` 到 `13` 个百分点左右，明显不是同一口径。

#### 3.2 看板加勾率与 `new` 基本一致

看板加勾率与 `new` 逐日几乎完全一致：

- 看板：`4.28% ~ 6.59%`

- `new`：`4.28% ~ 6.59%`

这说明看板加勾率大概率采用的是：

- 类似 `new` 的“总 trace 为分母”的行为占比口径

而不是 `ds` 的：

- `加勾订单数 / 可加勾订单数`

#### 3.3 看板反勾率与 `new` 基本一致

看板反勾率与 `new` 也几乎逐日对齐：

- 看板：`36.85% ~ 50.27%`

- `new`：`36.87% ~ 50.28%`

这也支持同一个判断：

- 看板反勾率更像 `new` 的行为占比口径

- 而不是 `ds` 的条件转化率口径

#### 3.4 看板单独展示了跳勾率，现有 SQL 中没有直接同口径字段

当前 3 套 SQL 中：

- `old` 没有跳勾率

- `ds` 没有跳勾率

- `new` 也没有直接输出跳勾率

因此看板中的 `跳勾率` 需要单独追溯定义，不能直接从现有 3 份 SQL 结果中一一映射。

### 5. 建议口径判断

结合修正后的日期顺序，当前更合理的判断是：

- 看板的默勾接受度、加勾率、反勾率与 `new` 基本一致

- 看板大概率直接采用 `new` 口径，或与其使用同一套核心定义

- `old` 和 `ds` 更适合作为“订单结果口径”参考

- `new` 可以直接作为“看板行为口径”参考

如果后续要与看板完全对齐，建议优先排查：

- 看板中“跳勾率”的精确定义

- 看板是否只统计特定业务子集或特定表单类型
