# 默勾接受度：定义、口径修复与目标讨论

先确认“把什么看作一个选择单元”，再判断用户是否接受默勾，最后讨论接受度与完单的关系。

## 先读这些

- **行为分类**：在统一的选择单元上比较默认集合和呼叫集合，区分默勾接受、仅反勾、仅加勾、同时反勾和加勾；仅反勾、仅加勾再按是否跳勾细分，形成六个互斥主类。
- **尚需区分的口径**：定义讨论提出 `behavior_unit`，用于避免 `box_name` 磨平盒内变化、`product_2level` 混淆盒内外自营品类；修复需求仍按“盒子算一个平台品类”组织看板，并将盒内局部操作计为跳勾。这是两份材料的不同层次，不能视为已经统一上线。
- **样本范围**：定义稿列出等待页冒泡、DIDI 运力和底部折叠的排除项；修复需求列出等待页冒泡、PBD 端及未进入盒子的底部折叠车型。两份原文的排除表述均保留，使用时应与实际 SQL 对齐。
- **特殊场景**：盒子扩展进入盒子的车型需纳入默勾集合；历史拉黑车型的处理仍有待评估项。新旧跳勾定义及具体 case 均在修复需求中保留。
- **目标讨论**：接受度要与完单和长期体验一起看。合理区间的三段关系是原文的分析框架；trace 分流的短期实验与长期留存判断分开记录。

## 行为单元与六类定义

**来源**：[默勾接受度定义](https://cooper.didichuxing.com/knowledge/2199610335356/2207768659596)

### 基本行为单元

对于每条 trace_id，用户被展示的表单盒子扩展和同价车型合并后的默勾结果，但是用户的最基本行为单元却不只是用户被展示的结果，用户还可以进入同价车型合并的 tab 进行加勾或取消的操作。

现状是用 `box_name` 作为行为单元，但是会磨平同价合并和盒内变化。

也不能直接用 `product_2level` 作为行为单元，因为现在自营单一品类在盒子内外共享 `product_2level` ，会导致相关的品类被误判为接受。

可以构造一个新的 `behavior_unit` 作为基本行为单元并后续维护，用于表示“乘客可感知、可操作、可归因的展示选择单元”。

对于基本行为单元，可以根据默勾结果和呼叫结果将其分为 4 类：

| 基本单元 | 默勾结果 | 呼叫结果 | 定义 |
| --- | --- | --- | --- |
| M | 1 | 1 | M  默勾且被呼叫的基本单元（默勾接受） |
| J | 0 | 1 | J 未默勾但被呼叫的基本单元（加勾） |
| F | 1 | 0 | F 默勾但未被呼叫的基本单元（反勾） |
| W | 0 | 0 | W 未默勾且未被呼叫的基本单元（接受未默勾） |

对于 trace_id 属于何种类别的判断就是根据上面的集合进行的。

### trace_id 维度的默勾接受

首先计算总集应该排除：

- 等待应答页冒泡

- DIDI 运力

- 底部折叠

在这个基础上计算竞争呼叫数、默勾呼叫数等。

建议将发生呼叫的 `trace_id` 分为以下 6 个互斥主类：

| 主分类 | 定义 | 是否跳勾 |
| --- | --- | --- |
| 默勾接受 | 默认勾选集合与最终呼叫集合完全一致 | 否 |
| 仅反勾-非跳勾 | 只有默认勾选项被减少，且减少方式连续、未跨锚点 | 否 |
| 仅反勾-跳勾 | 只有默认勾选项被减少，但出现非连续放弃、盒内局部反勾或跨锚点行为 | 是 |
| 仅加勾-非跳勾 | 只有默认之外的项被补充，且补充方式连续、未跨锚点 | 否 |
| 仅加勾-跳勾 | 只有默认之外的项被补充，但出现非连续补勾、盒内局部加勾或跨锚点行为 | 是 |
| 又反勾又加勾 | 同时存在默认勾选项被放弃和默认外项被呼叫 | 是 |
