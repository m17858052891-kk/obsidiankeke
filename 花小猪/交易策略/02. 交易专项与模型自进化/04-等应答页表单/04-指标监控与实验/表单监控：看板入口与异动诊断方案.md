# 表单监控：看板入口与异动诊断方案

查现有看板时看第一部分；设计自动诊断时沿指标关系、排查步骤和技术方案继续阅读。

## 先读这些

- **已有入口**：冒泡总看板、折叠率和默勾接受度看板，以及对应底表、监控任务，集中在“看板与任务入口”。
- **排查顺序**：先核对数据与口径，再找主要贡献切片，沿业务链路和变更记录定位，最后用对照、回放或重算验证。
- **方案边界**：第一版技术方案提出 T+1 诊断、全指标扫描与分层诊断深度，重点关注默勾接受度、ECR、CR 和完单；输出可审计的异常证据初稿。
- **实现分工**：字段、指标口径、SQL 模板、诊断规则和审计由配置及工具承载，Agent 负责选择工具、补齐参数和解释结果。业务 DAG 用于指导排查，归因结论仍需要验证。

现有看板链接与后续技术方案分节记录；方案中的目标、建议表名和演进项保留其提议性质。

归因：

- 进行全国(or城市框)推断，训练数据可用city_id X hour

1. **先确认是不是“真异常”**

	- 是否超过历史波动区间、同比/环比是否异常

	- 是否有节假日、流量结构、实验分流、埋点延迟等干扰

	- 先排除监控口径、数据延迟、埋点丢失

2. **做指标拆解**

	- 总指标拆到城市、渠道、用户类型、商家类型、场景、版本、实验组

	- 比如 GMV 异动，可以拆成：流量 × 转化率 × 客单价 × 履约率

	- 找出“贡献最大”的切片，而不是只看跌幅最大

3. **沿业务链路定位**

	- 用户曝光 -> 点击 -> 下单 -> 支付 -> 履约 -> 退款/取消

	- 每一层看漏斗转化是否异常

	- 如果某一层开始断崖，就继续下钻到它的上游输入和下游影响

4. **看系统和策略变更**

	- 最近是否发版、改配置、上线实验、调整模型、换流量、改 SQL、改特征

	- 很多线上异动不是“模型变差”，而是配置、过滤条件、数据延迟、特征缺失、召回变少、实验污染

5. **做归因验证**

	- 用 holdout/control group 对比

	- 用回放或离线重算复现异常

	- 对可疑因素做反事实分析：如果去掉这次改动，指标会不会恢复

	- 最终要能回答：异常从哪个时间点开始、影响哪些人/货/场、由哪个链路变量驱动、证据是什么

## 第一版诊断技术方案

**来源**：[表单指标监控&异动归因体系设计](https://cooper.didichuxing.com/knowledge/2199610335356/2208131197275)

### 表单指标异动诊断系统：第一版技术方案

#### 1. 目标

第一版建设一个 T+1 的表单指标异动诊断系统，不做万能问数 Bot，也不让 LLM 直接自由归因。

系统每天自动完成：

```PlainText
数据质量检查 -> 全指标扫描 -> 异常事件聚合 -> 重点指标诊断 -> 近期变更关联 -> 诊断卡片生成
```

第一版目标是产出“可审计的异动证据初稿”，帮助把人工排查从 1-2 小时缩短到 5-10 分钟。

设计上参考了 [LinkedIn ThirdEye](https://www.linkedin.com/blog/engineering/analytics/introducing-thirdeye-linkedins-business-wide-monitoring-platfor) 这类业务指标监控平台的思路：先稳定发现业务异常，再通过维度拆解、链路关系和反馈闭环辅助定位原因。

复杂分析方法不通过 prompt 临时教给 Agent，而是沉淀为配置和工具。Agent 负责选择工具、补齐参数和解释结果；字段识别、指标口径、分组对比、异常规则和输出模板由诊断服务执行。

#### 2. 第一版范围

##### 2.1 指标范围

第一版采用“全指标扫描、分层诊断深度”：

| 层级 | 指标 |
| --- | --- |
| 基础流量层 | 请求数、曝光数、冒泡数、发单数、完单数 |
| 平台联合决策 | 特征覆盖率 / 缺失率、模型输出均值、模型 acc / auc、默勾 CR 阈值、幸运盒子 CR 阈值、目标权重、补贴率、幸运盒子水位 |
| 表单策略 | 折叠率、盒子扩展触发率、呼返熔断触发率 |
| 直接影响层 | 默勾平均车型数、默勾单勾率、默勾全勾率、表单最低价 vs 特惠、默勾水位 vs 特惠、幸运盒子展现率 |
| 间接影响层 | 默勾接受度、ECR、幸运盒子份额 |
| 目标与护栏 | CR、冒泡数、完单数、完单率、补贴成本、补贴率、ROI |

其中，默勾接受度、ECR、CR、完单作为第一版重点诊断指标；其他指标先进入异常扫描和关联解释。

##### 2.2 维度范围

第一版固定支持：

```PlainText
dt、hour、city_id / city_frame、experiment_group、strategy_version
```

如数据已具备，可追加 `app_version`、`user_type`、`scene`，但不作为第一版强依赖。

#### 3. 总体架构

> [!example]- PlainText 实现细节（29 行）
> ```PlainText
> T+1 调度任务 / 用户追问
>   ||
>   v
> Agent 编排层
>   |-- 读取指标 DAG / 口径配置
>   |-- 调用分析模块
>   |-- 通过 DataTools MCP 受控取数
>   ||
>   v
> Python 分析服务 / 脚本
>   |-- 数据质量检查
>   |-- outlier / incident 检测
>   |-- 异常事件聚合
>   |-- 看板组件分析
>   |-- 贡献拆解与异常维度解释
>   |-- 上游链路追踪
>   |-- 变更关联与人工反馈
>   ||
>   v
> DataTools MCP / 数仓 / Cooper / 看板
>   ||
>   v
> 结构化分析结果
>   ||
>   v
> LLM 报告生成器
>   ||
>   v
> Cooper 日报 / 群消息 / 诊断卡片
> ```


这里的边界不是“Agent 不能取数”，而是“Agent 不能自由取数”。==Agent 可以通过公司已有的 DataTools MCP 自主取数，但必须走受控工具、白名单表、参数化 SQL 模板和查询审计；LLM 不直接自由访问原始表、不自行定义指标口径、不执行未校验 SQL、不直接下因果结论。==

第一版优先使用 DataTools 的 native MCP 路径，例如 `mcp__dclaw_mcp__nl2data`、`mcp__dclaw_mcp__sql2data`、`mcp__dclaw_mcp__queryDataBySlice`、`mcp__Cooper__readContent`；如果宿主没有暴露 native MCP，再回退到 `mcporter call`。这与 DataTools 的推荐调用路径保持一致。

其中 `queryDataBySlice` 适合复用已建设的数易看板组件数据，但它的输入只有 `reportId` 和 `sliceId`，不作为动态筛选接口使用。需要动态筛选日期、城市、实验组、策略版本时，优先通过受控 SQL 模板调用 `queryDataByDatasetSql`、`nl2data` 或 `sql2data`。

#### 4. 数据建设

##### 4.1 指标小时宽表

表名建议：

```PlainText
dws_form_metric_hour_di
```

推荐粒度：

```PlainText
dt × hour × city_id × city_frame × experiment_group × strategy_version
```

核心字段：

| 类型 | 字段 |
| --- | --- |
| 维度字段 | dt、hour、city_id、city_frame、experiment_group、strategy_version |
| 可选维度 | app_version、user_type、scene |
| 流量指标 | request_cnt、exposure_cnt、bubble_cnt、order_cnt、finish_cnt、finish_rate |
| 模型指标 | feature_coverage_rate、feature_missing_rate、model_score_mean、model_acc、model_auc |
| 配置指标 | default_cr_threshold_v3、lucky_box_cr_threshold_v3 / v4、target_weight_v4、target_reach_weight_v4、special_box_subsidy_rate_v3 / v4、lucky_box_water_level_v4 |
| 表单策略 | fold_rate、box_expand_trigger_rate、fuse_trigger_rate |
| 默勾指标 | default_car_cnt、default_single_select_rate、default_full_select_rate、default_accept_rate、default_water_level_vs_discount_price |
| 盒子指标 | lucky_box_show_rate、lucky_box_share、form_min_price_vs_discount_price |
| 目标与成本 | ecr、cr、subsidy_rate、subsidy_cost、roi |

如果部分模型或配置字段只能按日、实验组或策略版本粒度产出，第一版允许在查询层做粒度对齐，并在报告中标注数据粒度。

##### 4.2 变更日志表

表名建议：

```PlainText
dwd_form_change_event_di
```

字段：

```PlainText
change_id、change_time、change_type、owner、city_scope、experiment_group、
strategy_version、affected_metric、description、link
```

第一版优先接入：

```PlainText
实验扩量 / 缩量、策略阈值调整、配置变更、模型版本更新、SQL 口径变更、发版、数据延迟
```

##### ==4.3 指标 DAG 配置==

文件名建议：

```PlainText
metric_dag.yaml
```

配置内容包括：

```PlainText
指标分组、指标中文名、默认拆解维度、上游指标、下游指标、重点诊断等级
```

示例链路：

```PlainText
默勾 CR 阈值 -> 默勾平均车型数 -> 默勾接受度 -> ECR -> CR -> 完单
盒子扩展触发率 -> 幸运盒子展现率 -> 幸运盒子份额 -> ECR / CR
补贴率 / 水位 -> 表单价格关系 -> ECR / CR
```

这里的 DAG 是“业务诊断 DAG”，用于指导排查路径，不直接等同于因果证明。类似 [ThirdEye anomaly analysis](https://www.linkedin.com/blog/engineering/analytics/analyzing-anomalies-with-thirdeye) 中的多维 drill down，第一版通过 DAG 和维度拆解帮助回答“异常从哪一层开始”。

##### 4.4 诊断反馈表

第一版保留人工反馈入口，先不做复杂自动学习。这个设计吸收了业务监控系统常见的 human-in-the-loop 思路：先让人确认误报、已知变更、数据问题和真实异常，再沉淀为后续 Case memory。

表名建议：

```PlainText
dwd_form_diagnosis_feedback_di
```

字段：

```PlainText
event_id、metric、dt、diagnosis_result、human_feedback、confirmed_root_cause、
action_taken、owner、feedback_time、note
```

`human_feedback` 建议枚举：

```PlainText
valid_anomaly、false_positive、known_change、data_issue、needs_followup
```

==这部分也可以输入 DS 历史的分析文档和表单规则相关的文档，采用类 kapathy llm wiki 或 RAG 的方式沉淀分析经验和业务背景。==

##### 4.5 MCP 取数适配配置

第一版不从零建设通用取数平台，而是接入公司已有的 DataTools MCP。为避免 Agent 自由发挥，需要增加一份取数适配配置：

```PlainText
data_access.yaml
```

配置内容：

```PlainText
允许调用的 MCP 工具：nl2data、sql2data、queryDataBySlice、Cooper.readContent
允许查询的表：dws_form_metric_hour_di、dwd_form_change_event_di、dwd_form_diagnosis_feedback_di
允许查询的字段：以指标字典和 metric_dag.yaml 为准
SQL 模板：指标时序、同环比、贡献拆解、上游指标、变更查询
结果限制：默认聚合查询，明细查询禁用；大结果集只返回摘要和下载链接
审计字段：user、query、tool、params、time_range、row_count、download_url
```

Agent 可以基于这份配置自主选择取数动作，但不能绕过指标口径、白名单和 SQL 校验。

##### 4.6 看板组件分析配置

已建设的数易看板可以作为低成本数据入口。对关键看板组件，新增一份配置：

```PlainText
board_slice_registry.yaml
```

配置内容：

```YAML
board_slices:
  abs_gap_by_exp_group:
    report_id: 470799
    slice_id: 15784469
    title: 实验组 abs_gap 趋势
    metric_col: abs_gap
    time_col: dt
    dimension_cols:
    - 实验组，全城不区分城市组的时候，用all
    metric_type: ratio
    higher_is_worse: true
    analysis_methods:
        - trend
            - group_compare
            - latest_day_compare
    output_template: group_trend_card
```

这类配置解决的问题是：看板组件返回的字段名、指标含义、分组维度和分析方法不交给 Agent 猜，而由 `BoardSliceAnalyzer` 固化执行。

#### 5. 分析模块

第一版做 10 个轻量模块：

| 模块 | 职责 |
| --- | --- |
| DataQualityCheck | 检查分区完成度、小时缺失、分母异常、埋点 / 口径变更、实验分流异常 |
| DataToolsMCPAdapter | 封装 DataTools MCP 调用、SQL 模板渲染、权限白名单、结果摘要和查询审计 |
| MetricQuery | 通过 DataTools MCP 或离线宽表查询指标时序、同环比、分城市 / 时段 / 实验组 / 策略版本结果 |
| BoardSliceAnalyzer | 基于 `board_slice_registry.yaml` 拉取看板组件数据，并按固定方法输出趋势、分组对比和组件级诊断 |
| AnomalyDetect | 两阶段检测：先识别 outlier，再判断是否构成 incident |
| AnomalyEventBuilder | 将同时间、同范围、同策略版本上的多指标异常聚合成一个业务事件 |
| SliceAttribution | 计算 Top 贡献切片和异常维度解释，优先看对大盘变化的贡献 |
| UpstreamTrace | 根据指标 DAG 检查上游指标是否同步异常 |
| ChangeLookup | 查询异常前后 1-3 天的实验、配置、模型、SQL、发版等变更 |
| FeedbackRecorder | 记录人工确认、误报、数据问题、已知变更等反馈 |

`AnomalyDetect` 采用两阶段检测：先识别 outlier，再判断是否构成需要处理的 incident。这个设计参考 [Uber Argos](https://www.uber.com/en-CA/blog/argos-real-time-alerts/) 中“快速发现异常 + 再判断业务影响”的思路，避免小流量、短持续的噪声直接进入强告警。

`AnomalyEventBuilder` 会把同时间、同城市框、同实验组、同策略版本上的多指标异常聚合成一个业务事件，避免日报变成一堆分散告警；这类 incident 聚合能力可参考 [Anodot Incident Detection](https://www.anodot.com/incident-detection/) 的产品思路。

`SliceAttribution` 除了计算 Top 贡献切片，还输出“异常维度解释”，即哪些城市框、实验组、策略版本、app_version 或场景在异常样本中过度代表；这个设计参考 [Datadog Watchdog Insights](https://docs.datadoghq.com/watchdog/insights/) 对异常 tag / 维度的定位方式。

`BoardSliceAnalyzer` 只接收已登记的 `reportId + sliceId`，通过 `queryDataBySlice` 获取组件数据；如果用户临时要求换筛选条件，则转为调用受控 SQL 模板，不直接让 Agent 改写组件 SQL。

贡献拆解第一版采用简化口径：

```PlainText
大盘指标变化 ~= Σ 分组流量占比 × 分组指标变化 + 结构变化项 + residual
```

异常事件严重度第一版采用可解释打分：

```PlainText
severity = 异常幅度 × 流量占比 × 持续时间 × 目标指标影响权重
```

#### 6. 每日运行流程

```PlainText
1. T+1 调度任务启动。
2. 先做数据质量检查，排除数据延迟、分区缺失、分母异常、实验分流异常。
3. 读取 metric_dag.yaml，确定全量扫描指标和重点诊断指标。
4. Agent 通过 DataTools MCP 或离线宽表拉取昨日聚合数据。
5. 对已登记的关键看板组件，按 board_slice_registry.yaml 运行组件级分析。
6. 对所有指标做 outlier 扫描。
7. 将同时间、同城市框、同实验组、同策略版本的相关异常聚合成 incident。
8. 按严重度排序，过滤小流量、短持续、低影响异常。
9. 对重点 incident 做贡献拆解、异常维度解释和上游 DAG 检查。
10. 查询异常前后 1-3 天的相关变更。
11. 记录取数工具、查询参数、结果规模和下载链接，形成审计日志。
12. 将结构化结果交给 LLM 报告生成器。
13. 输出 Cooper 日报、群消息或诊断卡片。
14. 人工确认后写入反馈表。
```

#### 7. 输出卡片

标准输出：

> [!example]- PlainText 实现细节（26 行）
> ```PlainText
> 【异常指标】
> 指标当前值、环比 / 同比变化、历史波动区间、异常等级。
>
> 【影响范围】
> 异常主要集中在哪些城市框、时段、实验组、策略版本。
>
> 【Top 贡献】
> 列出贡献最大的切片和贡献占比。
>
> 【异常维度】
> 列出异常中显著过度代表的城市框、实验组、策略版本、app_version 或场景。
>
> 【链路定位】
> 上游哪些指标同步异常，方向是否符合业务链路。
>
> 【近期变更】
> 列出异常时间附近的实验、配置、模型、SQL、发版等变更。
>
> 【初步判断】
> 主因 / 副因 / 待确认项，必须带置信度。
>
> 【证据】
> SQL、看板、变更记录、实验链接。
>
> 【建议动作】
> 观察、补数、修口径、做 control 对比、灰度降量或回滚。
> ```


LLM 输出约束：

```PlainText
没有证据不下确定性结论。
归因必须区分主因、副因、相关但未验证、待确认。
每条结论必须能回溯到数据、链路或变更证据。
存在数据质量、口径或实验分流疑点时，优先标记待确认。
```

#### 9. 第一版不做

```PlainText
不做实时监控。
不做复杂前端。
不做自动最终定责。
不对所有指标做同等深度自动归因。
不做完整 request 级 trace 归因。
不做自动反事实回放。
不自动把 bot 结论写入长期记忆。
不让人工反馈自动改写指标口径或归因规则。
不允许 Agent 绕过 DataTools MCP、白名单和 SQL 模板自由访问原始表。
不依赖 prompt 让 Agent 自行理解看板 SQL、字段含义和分析方法。
不把 `queryDataBySlice` 当作动态筛选接口；动态筛选走受控 SQL / 数据集查询。
```

#### 10. 后续演进

第一版跑通后，再逐步补充：

```PlainText
业务 Wiki / RAG：指标口径、SQL 模板、策略说明、实验说明、常见口径坑。

Case memory：沉淀人工确认后的历史异动案例。
看板组件资产库：沉淀更多 reportId / sliceId 与业务指标的映射。
ExperimentTool：自动做 control / treatment 对比。
CounterfactualTool：支持离线回放和反事实模拟。
交互式 Agent：支持多轮追问和证据解释。
```

#### 11. 一句话总结

第一版就是：

```PlainText
T+1 数据质量检查 + 看板组件复用 + 全指标扫描 + 异常事件聚合 + 重点指标贡献拆解 + 上游链路检查 + 变更关联 + 诊断卡片生成
```

先把可审计的诊断闭环跑通，再建设更完整的 RAG、memory、RCT learning 和交互式 AI bot。
