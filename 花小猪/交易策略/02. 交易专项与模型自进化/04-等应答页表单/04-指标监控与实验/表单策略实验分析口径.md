# 表单策略实验分析口径

[Cooper 原文](https://cooper.didichuxing.com/knowledge/2199610335356/2208698219165)

## 表单策略实验分析口径整理

### 1. 适用范围

本文整理表单策略相关实验的通用分析口径

### 2. 标准分析链路

#### 2.1 明确实验样本

优先先确认实验样本来源和分流粒度：

| 样本来源 | 常见场景 | 关键校验 |
| --- | --- | --- |
| `apollo.pre_flow_data_etl` | 盒子扩展、价格取整等 Apollo 分流实验 | 同一 `pid/passenger_id` 在实验期只能命中一个 `group_name`；城市维度要与实验分流一致。 |
| `kflower_strategy.pltf_union_stg_exp_evaluation_pas_tag` | 联合决策、熔断、补贴、盒子策略实验 | 按 `pid + city_id` 去重，过滤跨组用户。 |
| `pid` 尾号规则 | 等待应答页默勾/补勾灰度类实验 | 需要做 AA/AB 或基线差异校正，不能只看 AB 期 raw gap。 |
| 评估大师/核心评估底表 | 常规实验读数 | 适合读大盘，但涉及表单行为、盒子份额、补贴拆解时要回明细表校验。 |

推荐每个实验都保留三类结果：

- 分组样本数：`pnum`、`passenger_city_day_cnt`、日期覆盖。

- 跨组污染校验：`COUNT(DISTINCT exp_group)` 是否为 1。

- 口径声明：实验期、城市范围、分流表、对照组、是否按 pid / city / day 聚合。

#### 2.2 主评估先用可加和原子指标

主评估表优先输出原子计数和 sum/cnt，再在查询层计算 rate。不要直接对日级 rate 或城市级 rate 求平均。

常用原子指标：

| 指标族 | 原子指标 | 查询层派生 |
| --- | --- | --- |
| 流量规模 | `pnum`, `bubble_cnt`, `call_cnt`, `dedup_call_cnt`, `demand_call_cnt` | 人均冒泡、人均呼叫、ECR、呼叫率 |
| 成单转化 | `ans_cnt`, `fin_cnt`, `charge_cnt`, `finish_cnt`, `order_cnt` | 应答率、CR、完单/冒泡、完单/呼叫 |
| 取消体验 | `cancel_cnt`, `grab_before_cancel_cnt`, `grab_after_pas_cancel_cnt`, `grab_after_dri_cancel_cnt` | 应答前取消率、应答后乘客取消率、应答后司机取消率 |
| 收益补贴 | `gmv`, `subsidy_c`, `subsidy_c_nodd`, `lucky_box_subsidy_c`, `uabox_subsidy_c`, `pltf_subsidy_c` | 人均 GMV、人均补贴、补贴率、平台供需 C 补率、FROI |
| 表单行为 | `mg_box_car_cnt`, `call_box_car_cnt`, `bubble_trace_cnt`, `call_bubble_trace_cnt`, `mg_call_bubble_trace_cnt`, `jg_call_bubble_trace_cnt`, `fg_call_bubble_trace_cnt` | 默勾水位、呼叫车型数、默勾接受度、加勾率、反勾率 |
| 盒子结构 | `lucky_box_compete_call_cnt`, `uabox_compete_call_cnt`, `ufbox_compete_call_cnt`, `lucky_box_fin_cnt`, `uabox_fin_cnt`, `ufbox_fin_cnt` | 幸运盒子/特价盒子/特快盒子竞呼份额和完单份额 |
| 价格水位 | `min_price_div_didi_special_sum/cnt`, `anchor_price_div_didi_special_sum/cnt` | 最低实付价/滴滴特惠价、默勾价格锚点/滴滴特惠价 |
| 时效体验 | `call_to_firstcharge_dur`, `call_to_lastcharge_dur`, `call_to_charge_duration_sum/cnt` | 呼叫到开始计费时长、呼叫到末次计费时长 |

#### 2.3 统一粒度和分母

表单策略最容易出错的是分母混用：

| 分析问题 | 推荐粒度 | 分母 |
| --- | --- | --- |
| 乘客实验效果 | `passenger_id + city_id + dt` 后按实验组汇总 | 实验命中的乘客城市日或 `pnum` |
| 冒泡页默勾行为 | `trace_id` | `bubble_silent` 过滤后的冒泡 trace |
| 冒泡去重口径 | `distinct_bubble_id` | 统一冒泡去重后 trace；适合大盘冒泡数 |
| 呼叫/完单 | `order_id` 或 `origin_order_id` | 当日有效呼叫订单，改派场景要去重 |
| 盒子份额 | `order_id + level_type` 或冒泡明细回溯 | 竞呼/完单各自分母，不能混用 |
| 折叠率 | `trace_id` 或车型行 | `total_count`，按 `car_dim + fold_type` 拆分 |
| 等待应答页补勾 | `order_id + wait trace` | 等待页追加链路订单 |

如果一个实验同时使用评估底表和明细回溯，结论里必须说明两套口径的关系：评估底表负责主读数，明细回溯负责解释和校验。

### 3. 表单行为口径

#### 3.1 默勾、加勾、反勾

基础定义：

- 默勾车型数：冒泡页默认勾选车型数量，建议以 `box_name` 或 `equivalent_merge_name` 维度去重。

- 呼叫车型数：用户最终呼叫车型数量，建议与默勾车型使用同一维度。

- 默勾接受：呼叫集合与默勾集合一致，或没有加勾/反勾。

- 加勾：呼叫集合中存在默勾集合之外的车型。

- 反勾：默勾集合中存在最终未呼叫的车型。

注意：历史平台指标中的 `jg_call_bubble_trace_cnt` 和 `fg_call_bubble_trace_cnt` 是命中型标签，不天然互斥。同一个 `trace_id` 可以同时命中加勾和反勾。因此当需要行为构成占比加总为 100% 时，应使用互斥主分类，而不是直接相加历史三类指标。

#### 3.2 跳勾

跳勾不建议只按展示位序不连续定义。实验复盘中至少要区分两层：

- 技术跳勾：最终呼叫车型在 `car_rank` 上不连续。

- 业务跳勾：用户放弃默认集合中的中间选项，或出现又反勾又加勾，或盒内同价合并后的选择变化体现为跨锚点行为。

如果 SQL 只实现了技术跳勾，结论里要写明它低估了业务跳勾。

#### 3.3 盒子扩展对加勾/反勾的影响

盒子扩展可能把原始默勾盒子外的车型带入展示集合，容易在粗粒度口径里被误记为加勾。盒子扩展实验需要额外校验：

- `level_type = 107` 的幸运盒子 trace 是否仍有非空 `enter_box_lists`。

- `level_type = 105/201/200/107` 对应的特价/特快/幸运盒子份额是否与评估表字段一致。

- 盒子内车型是否被归回原始盒子，避免把盒内扩展误判为用户主动加勾。

### 4. 价格与盒子口径

#### 4.1 价格水位

价格取整、同价车型合并、默勾水位类实验至少保留两组价格比值：

- `min_pay_price_amt / didi_special_pay_amt`：表单最低实付价相对滴滴特惠价。

- `price_anchor_pay_amt / didi_special_pay_amt`：默勾价格锚点相对滴滴特惠价。

计算时要求 `didi_special_pay_amt > 0`，且最好输出 sum/cnt，避免日均或组均比例二次平均。

#### 4.2 盒子份额

盒子份额建议分开读：

- 竞呼份额：`lucky/uabox/ufbox_compete_call_cnt / call_cnt`。

- 完单份额：`lucky/uabox/ufbox_fin_cnt / fin_cnt`。

- 原始明细校验：基于 `level_type` 重算，常见映射为幸运盒子 `107`、特价盒子 `105/201`、特快盒子 `200`。

当评估表字段和明细重算不一致时，优先保留两套结果并说明差异来源，不要静默替换。

### 5. 补贴、ROI 与熔断联动口径

#### 5.1 补贴拆解

`subsidy_c` 往往包含多个补贴来源。分析平台供需 C 补时要明确是否扣除了幸运盒子补贴：

- 总 C 补：`subsidy_c`。

- 去幸运盒子 C 补：`subsidy_c - lucky_box_subsidy_c`。

- 平台供需 C 补近似：`uabox_subsidy_c + pltf_subsidy_c`，或订单补贴明细中 `subsidy_type = 81 and subsidy_party = 1 and is_cheap_lane_order = 1`。

如果要按小时或低/中/高 CR 分桶拆补贴，日粒度评估表通常不够，需要回订单补贴明细。

#### 5.2 ROI / FROI

ROI 结论要写清基准组：

- `blank`：空白组，适合衡量策略整体价值。

- `control`：线上逻辑组，适合衡量新策略相对当前线上增量。

无车赔和补贴类实验尤其要区分“相对空白组的价值”和“相对线上组的增量”，否则容易把现有策略收益误读为新增策略收益。

### 6. 等待应答页与无车赔口径

等待应答页默勾/补勾实验不应直接复用冒泡页主表口径。建议：

- 使用 `dwd_kf_trd_wait_scene_di` 和 `dwd_kf_trd_order_append_di` 回溯等待页勾选与追加行为。

- 对 pid 尾号分组类实验做 AA/AB DID：`(AB实验组 - AB control) - (AA实验组 - AA control)`。

- 把 raw gap 和 DID 净效果分开呈现。

无车赔实验额外区分：

- 无车赔投保订单数、投保覆盖率、单均承诺金额、单均等待门槛秒。

- 投保指标不等于真实赔付、核销、投诉、等待体验或留存，需要后验数据另行补齐。

### 7. 折叠与监控口径

折叠口径建议拆成两层：

- 监控主题表：`dt + hour + time_bucket + city_id + city_frame + experiment_group + car_dim + fold_type`。

- 异动看板：T 日和 T-7 同粒度对比，输出 `fold_rate_t`、`fold_rate_t7`、差值和方向。

折叠类型常见映射：

| `sub_select_status` | 折叠类型 |
| --- | --- |
| 4 | 无车折叠 |
| 5 | 品类折叠 |
| 7 | 实付价格折叠 |
| 11 | 应付价格折叠 |
| 其他非 0 | 其他折叠或配置折叠，需结合策略说明确认 |

折叠率要同时保留 `fold_count` 和 `total_count`，查询层计算 `fold_rate`。如果需要按城市框下钻，城市框来源应固化为 `dim_form_city_frame` 或等价维表，不建议在每条 SQL 里重复手写城市名单。

### 8. 推荐实验报告结构

每次表单策略实验复盘建议固定输出：

1. 实验信息：实验名、实验期、城市范围、分流方式、对照组、实验组、是否跨组过滤。

2. 样本校验：分组人数、乘客城市日、跨组用户数、AA 期差异。

3. 主指标：人均完单、人均 GMV、ECR、CR、人均补贴、补贴率、FROI。

4. 表单行为：默勾水位、呼叫车型数、默勾接受度、加勾率、反勾率、跳勾率。

5. 结构拆解：盒子竞呼/完单份额、价格水位、城市框、时段、低/中/高 CR、折叠类型。

6. 诊断校验：评估表字段与明细回溯是否一致、关键字段是否缺失、补贴口径是否包含幸运盒子。

7. 结论：主结论、可放量条件、风险、需要回源核验的动态项。

### 9. 按策略分析 Playbook

#### 9.1 折叠策略

折叠策略实验不要只看整体折叠率。更应该回答：折叠率变动来自哪类折叠、哪类车型、哪个城市框、哪个时间段，以及折叠变化是否影响默勾、呼叫、完单和价格水位。

重点问题：

- 折叠率是否整体上升或下降。

- 变化主要来自无车折叠、品类折叠、应付折叠还是实付折叠。

- 变化集中在哪些 `car_dim`，例如幸运盒子、特价盒子、特快盒子、盒子外车型。

- T 日相对 T-7 是否存在异常波动。

- 折叠变动是否伴随默勾水位、加勾率、反勾率、盒子份额、CR 变化。

核心指标：

| 指标 | 分母 | 用途 |
| --- | --- | --- |
| `fold_count / total_count` | 同一 `car_dim + fold_type` 的 `total_count` | 判断折叠率。 |
| `fold_rate_t - fold_rate_t7` | T 和 T-7 同粒度 | 判断异动。 |
| `mg_box_car_cnt / bubble_trace_cnt` | 冒泡 trace | 看折叠是否改变默勾水位。 |
| `call_box_car_cnt / call_bubble_trace_cnt` | 呼叫 trace | 看用户是否通过加勾补回车型。 |
| `fin_cnt / call_cnt` | 呼叫订单 | 看折叠对 CR 的影响。 |

SQL 示例：按折叠类型和车型维度看 T vs T-7。

> [!example]- SQL 实现细节（29 行）
> ```SQL
> SELECT
>     t.dt,
>     t.city_id,
>     t.city_frame,
>     t.time_bucket,
>     t.car_dim,
>     t.fold_type,
>     t.fold_count AS fold_count_t,
>     t.total_count AS total_count_t,
>     t.fold_count / NULLIF(t.total_count, 0) AS fold_rate_t,
>     t7.fold_count AS fold_count_t7,
>     t7.total_count AS total_count_t7,
>     t7.fold_count / NULLIF(t7.total_count, 0) AS fold_rate_t7,
>     (
>         t.fold_count / NULLIF(t.total_count, 0)
>     - t7.fold_count / NULLIF(t7.total_count, 0)
>     ) AS fold_rate_delta
> FROM form_fold_hour_di t
> LEFT JOIN form_fold_hour_di t7
>   ON t.city_id = t7.city_id
>  AND t.time_bucket = t7.time_bucket
>  AND t.car_dim = t7.car_dim
>  AND t.fold_type = t7.fold_type
>  AND t7.dt = date_sub(t.dt, 7)
> WHERE t.dt = '${biz_date}'
> ORDER BY ABS(
>     t.fold_count / NULLIF(t.total_count, 0)
>         - t7.fold_count / NULLIF(t7.total_count, 0)
> ) DESC;
> ```


#### 9.2 熔断策略

熔断策略分析不能只看“熔断触发率”。熔断通常和幸运盒子、平台供需 C 补、CR 分桶、badcase、空白组/不熔断组强耦合。分析时需要把“策略是否触发”和“触发后是否值得”分开。

重点问题：

- 熔断触发率是多少，按城市、10 分钟时间片、小时、CR 分桶是否集中。

- 被熔断 trace 是否真的处在低 CR 或差供需场景。

- 熔断对 ECR、CR、完单、人均 GMV、人均补贴、平台供需 C 补的影响。

- 熔断是否误伤幸运盒子或改变盒子份额。

- 不熔断组、熔断展示组、熔断不展示组之间的差异是否来自补贴拆解而不是策略本身。

核心指标：

| 指标 | 分母 | 用途 |
| --- | --- | --- |
| `fuse_distinct_bubble_cnt / distinct_bubble_cnt` | 去重冒泡 | 熔断触发率。 |
| `badcase_cnt / fuse_distinct_bubble_cnt` | 熔断冒泡 | 看触发是否误伤。 |
| `platform_supply_subsidy_c / gmv` | GMV | 平台供需 C 补率。 |
| `lucky_box_subsidy_c / subsidy_c` | 总补贴 | 判断幸运盒子补贴混入程度。 |
| `fin_cnt / call_cnt` | 呼叫 | 观察 CR 变化。 |

SQL 示例：按城市和时间片看熔断触发率。

> [!example]- SQL 实现细节（38 行）
> ```SQL
> WITH bubble_scope AS (
>     SELECT
>         dt,
>         city_id,
>         trace_id,
>         distinct_bubble_id,
>         concat(
>             lpad(hour(bubble_time), 2, '0'),
>             ':',
>             lpad(floor(minute(bubble_time) / 10) * 10, 2, '0'),
>             ':00'
>         ) AS time_slice_10min
>     FROM bubble_base
>     WHERE dt = '${biz_date}'
>       AND is_anycar_form = 1
>       AND COALESCE(is_from_waiting_response, 0) <> 1
> ),
> fuse_log AS (
>     SELECT
>         trace_id,
>         MAX(CASE WHEN is_fuse = 'true' THEN 1 ELSE 0 END) AS is_fuse
>     FROM platform_call_return_public_log
>     WHERE dt = '${biz_date}'
>       AND call_return_scene_type = 1
>     GROUP BY trace_id
> )
> SELECT
>     b.dt,
>     b.city_id,
>     b.time_slice_10min,
>     COUNT(DISTINCT b.distinct_bubble_id) AS distinct_bubble_cnt,
>     COUNT(DISTINCT CASE WHEN f.is_fuse = 1 THEN b.distinct_bubble_id END) AS fuse_distinct_bubble_cnt,
>     COUNT(DISTINCT CASE WHEN f.is_fuse = 1 THEN b.distinct_bubble_id END)
>         / NULLIF(COUNT(DISTINCT b.distinct_bubble_id), 0) AS fuse_rate
> FROM bubble_scope b
> LEFT JOIN fuse_log f
>   ON b.trace_id = f.trace_id
> GROUP BY b.dt, b.city_id, b.time_slice_10min;
> ```


SQL 示例：拆平台供需 C 补和幸运盒子补贴。

```SQL
SELECT
    exp_group,
    SUM(gmv) AS gmv,
    SUM(subsidy_c) AS subsidy_c,
    SUM(lucky_box_subsidy_c) AS lucky_box_subsidy_c,
    SUM(uabox_subsidy_c + pltf_subsidy_c) AS platform_supply_subsidy_c,
    SUM(subsidy_c - lucky_box_subsidy_c) AS subsidy_c_without_lucky_box,
    SUM(uabox_subsidy_c + pltf_subsidy_c) / NULLIF(SUM(gmv), 0) AS platform_supply_subsidy_rate,
    SUM(lucky_box_subsidy_c) / NULLIF(SUM(subsidy_c), 0) AS lucky_box_subsidy_share
FROM experiment_core_daily_metrics
WHERE dt BETWEEN '${start_date}' AND '${end_date}'
GROUP BY exp_group;
```

#### 9.3 盒子扩展策略

盒子扩展策略分析的重点不是“扩展后指标是否变好”这么粗，而是扩展是否改变了候选车型结构、是否污染幸运盒子门控、是否把盒内变化误记成用户主动加勾。

重点问题：

- 扩展组和对照组的竞呼份额、完单份额是否变化。

- `extend_v2` 是否保证有幸运盒子的 trace 不再进入盒子扩展列表。

- 盒子扩展是否使加勾率上升，但实际来自扩展列表暴露而非用户主动选择。

- 特价盒子、特快盒子、幸运盒子份额变化是否一致。

核心指标：

| 指标 | 分母 | 用途 |
| --- | --- | --- |
| `lucky_box_compete_call_cnt / call_cnt` | 呼叫 | 幸运盒子竞呼份额。 |
| `uabox_compete_call_cnt / call_cnt` | 呼叫 | 特价盒子竞呼份额。 |

#### 9.4 默勾与补勾策略

默勾/补勾策略要区分冒泡页和等待应答页。冒泡页关注默认勾选集合是否合适，等待应答页关注追加策略是否真的产生增量，而不是分组基线差异。

重点问题：

- 默勾水位是否变化，变化是由更多车型、盒子合并、价格锚点还是折叠导致。

- 用户行为是默认接受、加勾、反勾、又加又反，还是跳勾。

- 等待应答页策略必须做 AA/AB 或其他基线校正，避免把 pid 尾号分组差异当策略效果。

- 补勾策略是否带来完单、应答、等待体验增量，而不是只提高追加订单率。

核心指标：

| 指标 | 分母 | 用途 |
| --- | --- | --- |
| `mg_box_car_cnt / bubble_trace_cnt` | 冒泡 trace | 默勾水位。 |
| `mg_call_bubble_trace_cnt / call_bubble_trace_cnt` | 呼叫 trace | 默勾接受度。 |
| `jg_call_bubble_trace_cnt / call_bubble_trace_cnt` | 呼叫 trace | 加勾率。 |
| `fg_call_bubble_trace_cnt / call_bubble_trace_cnt` | 呼叫 trace | 反勾率。 |
| `AB_delta - AA_delta` | 组间差异 | 等待应答页净效果。 |

SQL 示例：等待应答页做 AA/AB DID。

> [!example]- SQL 实现细节（40 行）
> ```SQL
> WITH period_metrics AS (
>     SELECT
>         CASE
>             WHEN dt BETWEEN '${aa_start_date}' AND '${aa_end_date}' THEN 'AA'
>             WHEN dt BETWEEN '${ab_start_date}' AND '${ab_end_date}' THEN 'AB'
>         END AS period,
>         exp_group,
>         SUM(append_order_cnt) / NULLIF(SUM(wait_order_cnt), 0) AS append_order_rate,
>         SUM(default_accept_order_cnt) / NULLIF(SUM(wait_order_cnt), 0) AS default_accept_order_rate,
>         SUM(fin_cnt) / NULLIF(SUM(wait_order_cnt), 0) AS finish_per_wait_order
>     FROM wait_page_experiment_metrics
>     WHERE dt BETWEEN '${aa_start_date}' AND '${ab_end_date}'
>     GROUP BY
>         CASE
>             WHEN dt BETWEEN '${aa_start_date}' AND '${aa_end_date}' THEN 'AA'
>             WHEN dt BETWEEN '${ab_start_date}' AND '${ab_end_date}' THEN 'AB'
>         END,
>         exp_group
> ),
> delta_vs_control AS (
>     SELECT
>         t.period,
>         t.exp_group,
>         t.append_order_rate - c.append_order_rate AS append_order_rate_delta,
>         t.finish_per_wait_order - c.finish_per_wait_order AS finish_per_wait_order_delta
>     FROM period_metrics t
>     JOIN period_metrics c
>       ON t.period = c.period
>      AND c.exp_group = 'control'
>     WHERE t.exp_group <> 'control'
> )
> SELECT
>     ab.exp_group,
>     ab.append_order_rate_delta - aa.append_order_rate_delta AS append_order_rate_did,
>     ab.finish_per_wait_order_delta - aa.finish_per_wait_order_delta AS finish_per_wait_order_did

> JOIN delta_vs_control aa
>   ON ab.exp_group = aa.exp_group
> WHERE ab.period = 'AB'

#### 9.5 价格取整策略

价格取整策略要把“展示体验变化”和“交易转化变化”分开。只看人均完单会漏掉价格锚点、同价合并、TPO、默勾水位的结构性变化。

重点问题：

- 最低实付价和默勾价格锚点相对滴滴特惠价是否上移或下移。

- 同价车型合并率、展示车型数、默勾车型数是否变化。

- TPO 或投诉体验收益是否以人均完单、CR、GMV 损失为代价。

- 城市框或车型数多/中/少分层是否存在不同结论。

核心指标：

| 指标 | 分母 | 用途 |
| --- | --- | --- |
| `min_price_div_didi_special_sum / cnt` | 有滴滴特惠价样本 | 最低价水位。 |
| `anchor_price_div_didi_special_sum / cnt` | 有价格锚点样本 | 默勾价格锚点水位。 |
| `display_car_cnt_sum / bubble_cnt` | 冒泡 | 展示车型数。 |
| `default_car_cnt_sum / bubble_cnt` | 冒泡 | 默勾车型数。 |
| `fin_cnt / bubble_cnt` | 冒泡 | 规模结果。 |

SQL 示例：价格水位按实验组输出 sum/cnt。

```SQL
SELECT
    exp_group,
    SUM(min_price_div_didi_special_sum) AS min_price_ratio_sum,
    SUM(min_price_div_didi_special_cnt) AS min_price_ratio_cnt,
    SUM(min_price_div_didi_special_sum)
        / NULLIF(SUM(min_price_div_didi_special_cnt), 0) AS min_price_ratio,
    SUM(anchor_price_div_didi_special_sum) AS anchor_price_ratio_sum,
    SUM(anchor_price_div_didi_special_cnt) AS anchor_price_ratio_cnt,
    SUM(anchor_price_div_didi_special_sum)
        / NULLIF(SUM(anchor_price_div_didi_special_cnt), 0) AS anchor_price_ratio
FROM form_metric_hour_di
WHERE dt BETWEEN '${start_date}' AND '${end_date}'
GROUP BY exp_group;
```

#### 9.6 无车赔策略

无车赔策略要拆成“是否投保”“承诺多少”“是否真的改善应答/完单/等待体验”。投保覆盖率和承诺金额不是最终收益，需要后验赔付、核销、投诉、留存等指标补充。

重点问题：

- 策略组是否提升无车赔投保覆盖率。

- 单均承诺金额和等待门槛是否变化。

- 投保增加是否带来应答率、完单、等待体验提升。

- 相对空白组和相对线上组要分别看，不能把线上已有收益当新增收益。

核心指标：

| 指标 | 分母 | 用途 |
| --- | --- | --- |
| `nocar_order_cnt / call_cnt` | 呼叫 | 无车赔投保覆盖率。 |
| `nocar_order_amt_yuan / nocar_order_cnt` | 投保订单 | 单均承诺金额。 |
| `nocar_order_period_sum / nocar_order_cnt` | 投保订单 | 单均等待门槛秒。 |
| `fin_cnt / call_cnt` | 呼叫 | 策略是否改善 CR。 |
| `subsidy_c / gmv` | GMV | 补贴成本变化。 |

SQL 示例：无车赔投保指标拼到主评估。

> [!example]- SQL 实现细节（34 行）
> ```SQL
> WITH main_eval AS (
>     SELECT
>         exp_group,
>         SUM(call_cnt) AS call_cnt,
>         SUM(fin_cnt) AS fin_cnt,
>         SUM(gmv) AS gmv,
>         SUM(subsidy_c) AS subsidy_c
>     FROM experiment_core_daily_metrics
>     WHERE dt BETWEEN '${start_date}' AND '${end_date}'
>     GROUP BY exp_group
> ),
> nocar_eval AS (
>     SELECT
>         exp_group,
>         COUNT(DISTINCT order_id) AS nocar_order_cnt,
>         SUM(promise_amount_yuan) AS nocar_order_amt_yuan,
>         SUM(promise_wait_seconds) AS nocar_order_period_sum
>     FROM nocar_compensation_order_detail
>     WHERE dt BETWEEN '${start_date}' AND '${end_date}'
>     GROUP BY exp_group
> )
> SELECT
>     m.exp_group,
>     m.call_cnt,
>     m.fin_cnt,

>     n.nocar_order_amt_yuan / NULLIF(n.nocar_order_cnt, 0) AS avg_promise_amount_yuan,

#### 9.7 实时预算控制策略

实时预算控制策略更关注“预算曲线是否按预期消耗”和“补贴率是否在城市、时段、供需状态上合理”。它和表单策略的交集主要是补贴率、GMV、COST、幸运盒子/特价盒子决策和默勾剪枝。

重点问题：

- 预算控制是否改变各城市、时间片的 GMV/COST 分布。

- 规划补贴率和实花补贴率是否匹配。

- 是否出现某些城市或时段补贴率过高但 CR/完单收益不足。

- 默勾剪枝或幸运盒子决策是否改变了预算消耗结构。

核心指标：

| 指标 | 分母 | 用途 |
| --- | --- | --- |
| `cost / gmv` | GMV | 实花补贴率。 |
| `gmv` | 城市 + 时间片 | 收入规模。 |
| `cost` | 城市 + 时间片 | 成本规模。 |
| `valid_cnt / total_cnt` | trace | 可用样本稳定性。 |
| `prune_by_mogou_flag` | trace | 默勾剪枝影响。 |

SQL 示例：城市时间片 GMV/COST 分布。

```SQL
SELECT
    dt,
    city_id,
    slice_idx,
    subsidy_rate,
    SUM(gmv) AS gmv,
    SUM(cost) AS cost,
    SUM(cost) / NULLIF(SUM(gmv), 0) AS actual_subsidy_rate,
    COUNT(DISTINCT trace_id) AS trace_cnt,
    COUNT(DISTINCT CASE WHEN prune_by_mogou_flag = 1 THEN trace_id END) AS prune_by_mogou_trace_cnt
FROM budget_control_sim_detail
WHERE dt BETWEEN '${start_date}' AND '${end_date}'
GROUP BY dt, city_id, slice_idx, subsidy_rate;
```

>             WHEN dt BETWEEN '${ab_start_date}' AND '${ab_end_date}' THEN 'AB'
>         END,
>         exp_group
> ),
> delta_vs_control AS (
>     SELECT
>         t.period,
>         t.exp_group,
>         t.finish_per_bubble - c.finish_per_bubble AS finish_per_bubble_delta,
>         t.mg_accept_rate - c.mg_accept_rate AS mg_accept_rate_delta
>     FROM period_metrics t
>     JOIN period_metrics c
>       ON t.period = c.period
>      AND c.exp_group = 'control'
>     WHERE t.exp_group <> 'control'
> )
> SELECT
>     ab.exp_group,
>     ab.finish_per_bubble_delta - aa.finish_per_bubble_delta AS finish_per_bubble_did,
>     ab.mg_accept_rate_delta - aa.mg_accept_rate_delta AS mg_accept_rate_did
> FROM delta_vs_control ab
> JOIN delta_vs_control aa
>   ON ab.exp_group = aa.exp_group
> WHERE ab.period = 'AB'
>   AND aa.period = 'AA';
> ```
