## 2. 背景与目标

> 当前平台 [[wiki/concepts/履约率.md\|CR]] 已达高水平，PK 环节继续优化 CR 的边际收益小。
> 转变 PK 优化目标：**约束完单不显著负，最小化 ETP + 司机接驾时长**。
>
> 当前履约率模型为 [[wiki/models/Wide&Deep.md\|Deep&Wide]]，存在 3pp [[wiki/concepts/AUC.md\|AUC]] 提升空间，且双任务建模存在协变量偏移。

### 收益预估（V1.0/V1.1 一致）

| 指标 | 预期 |
|---|---|
| 完单 / CR | 不显著负 |
| ETP + 司机接驾时长 | ==-0.5%== |
| 履约率模型 AUC | ==+3pp== |

## 3. PK 在线分配机制（核心数学）

### 3.1 优化问题（V1.0 vs V1.1）

| 版本 | 决策变量 | 优化问题 | 备注 |
|---|---|---|---|
| **V1.0** | $x_{ij} \in \{0,1\}$ 订单 i 选司机 j | $\min \sum d_{ij}x_{ij}$  s.t.  $\sum f_{ij}x_{ij} \geq C \sum f^0_{ij}x^0_{ij}$，C=0.998 | by 总和约束（履约率作为预算）|
| **V1.1** | $x_j \in \{0,1\}$ 该订单选司机 j | $\min d_j$  s.t.  $f_j \geq C \max_k f_k$，C=0.998 | **by 订单约束** |

> [!note] V1.0 → V1.1 转向理由
> - V1.0 by 订单约束的"一个司机选一个订单"约束在 PK 阶段不存在（订单间司机隔离），离线求 λ 复杂度高
> - 朱正丹评审："全天是否需要把履约当作资源做优化问题需要讨论"
> - V1.1 改为 by 订单约束：每个订单独立判断，胜出司机的履约率 ≥ 当前最高履约率司机的 99.8%

### 3.2 拉格朗日推导（V1.1）

```
L(j, λ) = d_j + λ(C·max_k f_k − f_j)
        = λC·max_k f_k + (d_j − λf_j)
```

对偶问题求 min 等价于：

$$\min_j (d_j - \lambda f_j) \Leftrightarrow \max_j (\lambda f_j - d_j)$$

⇒ **PK 分 = λf − d**（与 V1.0 相同结论）

### 3.3 V1.1 解法对比

| 解法 | 思路 | 测算结果 | 结论 |
|---|---|---|---|
| **解法一：硬约束** | 直接 by 订单判断 `f_j ≥ 0.998·max_k f_k` | 0324-0330 数据：可选司机 0.56% 订单，更近距离司机 0.26% 订单，整体降距 <1m | ❌ 收益空间小；且在线无法知道 max f_k（司机陆续举手）|
| **解法二：拉格朗日松弛 + 全局 λ** | 离线遍历 λ，二分法求解 | λ=5340 时：满足约束订单 96.39%，能选到更近司机的订单 3.81%，距离 -20m (-1.21%)，CR -0.14pp | ✅ **采纳** |

### 3.4 λ 求解（V1.1）

```
对每个订单 i，存在 λ_i 使硬约束被满足
对所有 λ_i 排序，取 x% 满足率分位 → λ_x
```

| 期 | 时间 | 用途 |
|---|---|---|
| Train | 2026-03-24 ~ 2026-03-30 | 求 λ |
| Valid | 2026-03-31 ~ 2026-04-06 | 模拟两种 PK 过程对比 |

**关键转换**（V1.1）：

$$\lambda = 5340 \Rightarrow d^0 - d^* > \frac{1}{5340}(f^0 - f^*) \Rightarrow \boxed{5.34\,m \text{ 接驾距离} \leftrightarrow 0.1\,pp \text{ 履约率}}$$

### 3.5 V1.0 的熔断机制（V1.1 已划掉）

V1.0 设计：

- by 城市记录 `Σ(f' - f)/f'`，f' = 履约率最大司机，f = PK 胜出司机
- 当 ΔF > 0.2% → 该城市 PK 分降级为 `f`（最大化履约率）
- 恢复：减少至阈值内 → 恢复 PK 分 = `λf − d`
- 工程：策略产出小时级 hive 表 + PID 反馈控制（迭代项）

**V1.1 状态**：熔断机制及 hive 小时表全部~~划掉~~，hive 简化为天级别。

## 4. 履约率模型优化（V1.0/V1.1 一致）

### 4.1 旧模型问题：协变量偏移

V4 Deep&Wide 双任务建模：

| 模型版本 | 建模目标 | 所有样本 | 正样本 | 负样本 | PK 分 |
|---|---|---|---|---|---|
| V4 原模型（is_d_finish）| 司机履约 | PK 获胜且乘客未取消 | 完单 | 司机取消/拒单 | $\alpha\cdot P(\text{is\_o\_finish}) + (1-\alpha)\cdot P(\text{is\_d\_finish})$ |
| V4 原模型（is_o_finish）| 乘客履约 | PK 获胜且司机未取消/拒单 | 完单 | 乘客取消 | 同上 |

**问题**：以乘客履约率为例，
- 训练空间：$P(Y=1 \mid \text{司机未取消}, X)$
- 推理空间：$P(Y=1 \mid X)$

特征 X 的分布被"司机未取消"事件过滤，发生**协变量偏移**。

> 例：恶劣天气 + 远距离订单 → 司机取消概率高 → 训练集中此类样本少 → 线上遇到时模型预测不准。

### 4.2 新模型：3 分类多任务

```
P1 = P(司机取消 | X)
P2 = P(乘客取消 | X)
P3 = P(完单 | X)

派生：
乘客履约率 = P3 / (P2 + P3)
司机履约率 = P3 / (P1 + P3)
履约率 f = α · 乘客履约率 + (1 − α) · 司机履约率,    α = 0.9
```

**保留 α=0.9 的理由**：站在乘客视角增加乘客履约权重（与原 PK 一致）。

### 4.3 模型结构：多域多专家

| 模块 | 设计 | Gate NU 输入 |
|---|---|---|
| **多域**（EPNet 风格 Gate NU）| 是否连环派 × 派单模式（全指派/半指派/抢单）× 时段 × 长短单 × 供需 | 连环派类型、派单类型、发单星期/时段、订单距离、供需 |
| **多专家**（PEPNet/PLE 风格）| 多个 Expert 并行解单任务，gate 决定权重 | 所有底层特征编码 |

> 图示：原文档插入了一张多域多专家结构图（链接 didistatic.com/...image.png）

### 4.4 评估指标：OvR Macro AUC

```
A = 司机取消, B = 乘客取消, C = 完单
AUC_C = AUC(C 为正样本，A∪B 为负样本)
Macro AUC = (AUC_A + AUC_B + AUC_C) / 3
```

### 4.5 可解释性：LR 蒸馏

「可解释」定义（pair 级）：

> 对相同订单 o 的两个司机 (i, j)，深度模型打分 $(v_{i1}, v_{j1})$，LR 模型打分 $(v_{i2}, v_{j2})$，
> 若排序一致 $(v_{i1}-v_{j1})(v_{i2}-v_{j2}) \geq 0$，则 LR 可解释该 pair。

- 用 LR 蒸馏深度模型在训练集上的预测概率（软标签）
- 整体可解释率 ≥ **80%**
- 城市 × 商家维度 ≥ **95%**（评审建议附加）

### 4.6 特征空间（保持不变）

| 维度 | 特征 | 是否需建设 |
|---|---|---|
| 订单 | 城市、呼叫时间、订单里程等 | ✅ 已建设 |
| 司乘 | 是否连环派、指派模式、接驾距离、预估价等 | ✅ 已建设 |
| 供需 | 格子和周围格子近 X 分钟发单数、空车司机数等 | ✅ 已建设 |
| 司机 | 近 X 天（分场景）拒单率、取消率、完单数等 | ✅ 已建设 |
| 乘客 | 近 X 天应答后取消率、完单数、平均订单里程等 | ✅ 已建设 |

## 5. 工程改造

### 5.1 PK 分公式

```
PK 分 = 履约率 − (1/λ) · 司机接驾距离
      = α · P3/(P2+P3) + (1−α) · P3/(P1+P3) − (1/λ) · d
```

| 项 | 来源 |
|---|---|
| P1, P2, P3 | 模型输出 |
| α | 常数 |
| 1/λ | hive 表（V1.0 小时表 → V1.1 天级表）|
| 配置方式 | dufe（V1.0 候选 dufe 或 apollo，V1.1 确定 dufe）|

### 5.2 改造点

| 改造 | V1.0 | V1.1 |
|---|---|---|
| PK 分形态 | 双项加权 → 单项 | 同 V1.0 |
| 落日志 | 模型日志 | 模型日志（含履约率分数 f 和 PK 分）|
| 熔断 | ✅ 小时级 hive 表 + 城市维度熔断 + PID 反馈 | ❌ 划掉 |

## 7. AI 互动 Top2 问题（仅 V1.0）

### Q1：优化目标的帕累托边界假设过于理想化

**问题**：方案假设「完单率 vs 平均接驾距离」存在清晰的帕累托前沿，但实际可能是**非凸、多峰**的关系。

**V1.0 解决**：将 λ 求解方式从「根据曲线求帕累托最优（粗糙）」修改为「根据历史数据遍历 λ + 二分法」。

### Q2：λ 缺乏在线自适应调节机制

**问题**：λ 通过离线历史数据求解，存在风险：
1. **突发场景**：恶劣天气、爆单、节假日下，历史 λ 可能失效
   - 例：暴雨天司机取消率飙升，原"允许 0.2% CR 下降"约束可能过宽松或过严格
2. **分布漂移**：λ 更新频率？日级 hive 表 = 每天重新计算？降级策略？

**V1.0 解决**：
- (a) λ 每周用前一周数据更新，hive 表小时级（实现熔断）
- (b) 城市维度熔断机制
- (c) PID 反馈控制（后续迭代）

**V1.1 实际**：(a) hive 改天级别；(b)(c) 取消。详见 [[wiki/entities/约束履约率最小化接驾距离策略.md#4. 工程改造\|工程改造]]。
