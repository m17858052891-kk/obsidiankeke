# 多任务学习迭代方向分析

基于 2025–2026 年多任务学习前沿方法综述，结合 PK 决策系统当前技术栈和业务痛点，提炼出具备落地价值的迭代方向。

> [!info] 当前技术基线
> - PK 打分：==LR 逻辑回归==在线（AUC ~0.756），Wide&Deep v1.2 实验中
> - PK 窗口：==PLE 多任务模型==（4 任务，AUC 0.779）+ DQN RL 5% 在线
> - 核心矛盾：可解释性需求 vs 模型精度提升空间

---

## 一、方向评估总表

| # | 方向 | 来源方法 | PK 落地场景 | 优先级 | 难度 | 预期收益 |
|---|------|----------|-------------|--------|------|----------|
| 1 | Sparse MoE 多商家建模 | 快手 IPA+MoE | PK 打分 — 商家差异化 | ⭐⭐⭐ 高 | 中 | 精度 + 商家公平 |
| 2 | 动态损失权重 | MTLPT | PLE 多任务训练 | ⭐⭐⭐ 高 | 低 | 缓解跷跷板 |
| 3 | 双编码器异构建模 | Dual-Encoder | 连环派/非连环派分场景 | ⭐⭐ 中 | 中 | AUC 提升 |
| 4 | 偏好对齐 DPO/IPA | 快手 IPA | PK 从拟合 CR → 对齐长期体验 | ⭐⭐ 中 | 高 | 长期指标 |
| 5 | Model Merging 部署优化 | 模型合并范式 | 多版本 LR/Deep 统一部署 | ⭐ 低 | 低 | 降本增效 |
| 6 | 统一缩放范式 | 腾讯幂律发现 | 模型规模扩展策略 | ⭐ 低 | 高 | 长期储备 |

## 二、高优方向详析

### 方向 1：Sparse MoE 多商家/多场景差异化建模

#### 动机

当前 PK 打分使用统一 LR 模型服务所有商家（花小猪、宏鹄、自营、API 商家），但不同商家的司机行为模式和履约特征差异显著：
- 自营司机完单率高但接驾距离敏感
- API 商家（曹操/T3）司机拒单率较高
- 花小猪价格敏感型乘客取消率高

统一模型在"商家公平性"和"精度最大化"之间存在结构性矛盾。

#### 技术方案

借鉴快手 Sparse MoE 架构（主站用户观看时长 ==+1.6%==）：

```
输入特征 → Shared Expert (通用表征)
         → Expert_花小猪 (价格敏感场景)
         → Expert_宏鹄 (出租车场景)
         → Expert_自营 (高履约场景)
         → Expert_API (第三方场景)
         → Gate Network (商家 id + 城市 id 门控)
         → 融合 → Tower → PK 打分
```

#### 与现有架构的衔接

- [[wiki/models/PLE多任务模型.md]] 已有 PLE 分场景设计（连环派/非连环派），可复用 Expert 分组经验
- [[wiki/models/组件技术.md]] 中 SENet 注意力机制可作为 Gate Network 的候选实现
- 兼容 [[wiki/models/Wide&Deep.md]] 的 Wide 侧保留可解释性

#### 关键风险

- Expert 数量增加带来的训练数据稀疏（小商家样本不足）
- Gate 坍缩问题（所有输入路由到同一 Expert）
- 需验证 MoE 结构下可解释性是否可保留

#### 验证计划

1. 离线：在 Wide&Deep 基础上增加 MoE 层，对比统一模型 vs 分商家 Expert 的 AUC
2. 离线分群分析：各商家子集上的 AUC 分别是否提升
3. 在线 AB：==预期 CR +0.1~0.3pp==，接驾距离持平或略降

### 方向 2：动态损失权重优化 PLE 多任务训练

#### 动机

[[wiki/models/PLE多任务模型.md|PLE 模型]]当前 4 任务使用固定 BCE loss 权重，存在：
- **跷跷板效应**：OD 任务（AUC 0.779）与 T 任务（AUC 0.899）精度差异大，统一优化互相拖累
- **数据不平衡**：司机取消样本远少于完单样本，D 任务标签稀疏
- **任务冲突**：乘客履约(O)与司机履约(D)的梯度方向可能冲突

#### 技术方案

引入 MTLPT 论文的动态权重损失函数：

```python
# 动态权重调整（每 epoch 更新）
w_i(t) = w_i(t-1) * exp(loss_i(t) / loss_i(t-1) - 1) / temperature
# 归一化
w_i(t) = N * w_i(t) / sum(w_j(t))
```

或更简单的 Uncertainty Weighting（Kendall et al.）：

```python
# 学习每个任务的 homoscedastic uncertainty
loss = sum(1/(2*sigma_i^2) * loss_i + log(sigma_i))
```

#### 预期效果

- OD 任务（核心）AUC 从 0.779 → ==0.785+==
- 缓解 D 任务数据稀疏导致的精度波动
- 训练收敛更稳定，减少调参成本

#### 实施难度：低

- 不需改变模型结构，仅修改 loss 计算逻辑
- 可在现有 EVE 训练流程中直接集成
- ==建议作为最先验证的方向==

### 方向 3：双编码器异构场景建模

#### 动机

[[wiki/concepts/连环派.md|连环派]]与非连环派场景下，==接驾距离==的物理含义完全不同：
- 连环派：接驾距离 = 司机完成当前订单后到下一乘客的距离（不确定性大）
- 非连环派：接驾距离 = 司机当前位置到乘客的直线/路线距离（确定性高）

当前 PLE 通过 `is_serial` 特征和分 Expert 部分解决，但共享编码器仍存在特征语义混淆。

#### 技术方案

借鉴 Dual-Encoder 异构编码框架：

```
连环派特征 → Encoder_serial (专属表征空间)
非连环派特征 → Encoder_normal (专属表征空间)
共享特征 → Encoder_shared (通用表征空间)
                    ↓ 拼接
              → Prediction Tower
```

#### 与现有 PLE 的对比

| 维度 | 当前 PLE | Dual-Encoder 升级 |
|---|---|---|
| 场景隔离 | Expert 组分离（软隔离） | 编码器物理隔离（硬隔离） |
| 特征语义 | 同一 embedding 空间 | 异构潜因子空间 |
| 参数共享 | Gate 学习共享比例 | 仅在 Shared Encoder 共享 |

#### 关键考量

- 连环派样本约占 ==30-40%==，两个编码器的数据量是否足够
- 硬隔离可能丧失跨场景迁移能力（连环派经验无法帮助非连环派）
- 可作为 PLE 的结构改进，而非完全替换

## 三、中期储备方向

### 方向 4：偏好对齐 — 从拟合 CR 到对齐长期体验

#### 核心思路

当前 PK 模型优化目标是**单次完单概率最大化**（CR），但长期用户体验还涉及：
- 接驾等待时长
- 服务质量（评分、投诉）
- 用户留存和复购

借鉴快手 IPA（迭代偏好对齐）：

```
Stage 1: 标准 CR 预测模型（当前）
Stage 2: 训练 Reward Model 建模"用户长期满意度"
Stage 3: DPO 对齐 — 模型从 max(CR) → max(长期满意度)
```

#### 落地挑战

- **Reward 定义**：需要明确"长期满意度"的量化指标（复购率？NPS？）
- **数据成本**：需要用户级纵向追踪数据，超出当前 Hive 表记录范围
- **与 RL 窗口的关系**：[[wiki/models/DQN.md|DQN]] 已在做类似的长期优化，如何协同？

#### 建议

作为 2026 Q4 – 2027 的探索方向，先在窗口策略（DQN reward 设计）中试验偏好对齐思路。

---

### 方向 5：Model Merging 降低多版本维护成本

#### 场景

PK 系统当前维护多个独立模型：
- LR（PK 打分）
- PLE（窗口决策）
- DQN（RL 窗口）
- Wide&Deep（实验中）

未来若模型进一步增加（MoE、Dual-Encoder），部署成本将快速膨胀。

#### 可探索路径

- 将已收敛的单任务模型（CR 预测、取消预测、距离预测）通过 Task Arithmetic 合并
- 降低推理时的模型数量和 latency
- ==适合在模型结构稳定后引入，当前优先级较低==

---

## 四、不建议跟进的方向

| 方向 | 原因 |
|---|---|
| LLM 化（URM 范式） | PK 场景对 latency 要求极高（<50ms），LLM 推理不适用 |
| 多模态融合 | PK 特征全部是结构化数值/ID 类，无图文多模态需求 |
| Emu3 统一生成 | 与分类预测任务无直接关联 |

```
          └─ [方向1] MoE 分商家方案设计 + 离线原型 (4 周)

          └─ [方向4] 偏好对齐 POC
```
