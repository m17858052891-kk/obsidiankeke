# 交易策略介绍

本文面向交易效率方向新人和跨方向协作者，沉淀交易方向的基础业务流程、核心概念和常见策略模块。完整方案、线上配置和最新模型细节仍需回到对应 Cooper、代码仓库和看板复核。

## 1. 交易系统目标

交易系统的本质是连接和撮合：在乘客呼叫和司机供给之间，选择合适的交易机制、召回范围、匹配算法和平台 PK 规则，让订单尽可能高效、稳定、公平地完成。

在聚合打车场景下，交易系统同时服务四类目标：

| 角色 | 核心诉求 | 交易系统需要解决的问题 |
| --- | --- | --- |
| 乘客 | 更快应答、更短等待、更稳定履约、更少取消 | 控制应答时长、接驾距离、接驾时长、改派和应答后取消 |
| 司机 | 多劳多得、优劳优得、减少空驶和低效等待 | 提升听单效率、匹配合适订单、控制接驾成本和无效播单 |
| 商家 | 获得公平可解释的流量、稳定经营、可诊断可优化 | 提供清晰的流量分配规则、交易漏斗和经营诊断能力 |
| 平台 | 公平可感、撮合高效、生态健康、经营指标提升 | 在体验、效率、毛利、合规和生态之间做多目标权衡 |

交易效率方向更关注呼叫后到乘客上车前的撮合效率和体验，包括召回、分单、举手、PK、播单、应答、接驾、改派、换车、升舱等链路。

## 2. 核心交易链路

### 2.1 小猪端聚合链路

小猪端聚合交易可以抽象为：

```text
乘客呼叫
  -> 进入各商家/运力分单系统
  -> 商家召回可用司机
  -> 商家内部匹配并选出候选司机
  -> 候选司机向平台举手
  -> 平台 PK 决策最终胜出司机
  -> 播单给司机
  -> 司机应答
  -> 司机接驾
  -> 开始计费/送驾
  -> 完单
```

关键点：

- 一个乘客呼叫可能同时进入自营、宏鹄、API 商家等多个分单系统。
- 商家分单系统先在自己可控的司机池里做召回和匹配，找到候选司机后向平台举手。
- 平台 PK 在多个举手司机或商家之间选择最终胜者；胜出后才进入播单/应答链路。
- 应答后若司机取消或乘客取消，可能触发改派、换车、取消挽留或其他应答后策略。

### 2.2 DD / 外部平台链路差异

外部平台或 DD 入口中，小猪可能只是一个运力提供方。核心差异在于最终 PK 决策权可能不在小猪平台：

| 场景 | 决策权 | 典型链路差异 |
| --- | --- | --- |
| 小猪端 | 小猪平台侧 PK | 商家举手后由小猪聚合决策模块选胜者 |
| DD / 特惠联盟 | DD 侧聚合决策 | 小猪内部胜出后还需参与 DD 侧决策 |
| 腾讯出行、百度地图、同程、携程等 | 外部平台侧 PK | 小猪上报候选运力，外部平台决定是否胜出；异步平台中司机可能无感知失败 |

因此，同一个“举手”动作，在不同入口下可能对应不同的司机感知、失败原因和指标归因。

## 3. 核心概念

| 概念 | 说明 | 关注点 |
| --- | --- | --- |
| 呼叫 / 发单 | 乘客在端内选择品类并发起用车需求 | 呼叫量是交易漏斗起点 |
| 竞争呼叫 | 在多商家、多品类竞争环境中，某商家或品类有机会参与竞争的呼叫 | 用于分析商家流量机会和竞争环境 |
| 召回 | 根据司机状态、距离、时间、服务范围、交易模式等约束找出可候选司机 | 召回不足会影响匹配率/举手率 |
| 匹配 | 在候选司机和订单之间计算匹配关系，选出商家内部最优司机或司机集合 | 影响接驾距离、接驾时长、司机效率和后续履约 |
| 举手 | 商家找到候选司机后，把司机信息提交给平台参与聚合决策 | 平台 PK 的输入；也常用于商家维度漏斗诊断 |
| PK / 聚合决策 | 平台在一个或多个举手司机之间选择最终胜者 | 决定流量分配、履约导向和商家竞争结果 |
| 播单 | 平台将订单展示或派给司机 | 播单模式决定司机是否需要主动决策 |
| 应答 | 司机接受订单，订单进入接驾阶段 | 应答率、应答时长、应答后取消是核心指标 |
| 接驾 | 司机从当前位置到乘客上车点 | 司机视角占用时间；影响司机效率和乘客体验 |
| 送驾 / 计费 | 乘客上车后开始计费到结束计费 | 送驾占比衡量司机有效载客时间 |
| 完单 / 履约 | 订单没有在应答后被司机或乘客取消并最终完成 | 履约稳定性直接影响 PK 模型和商家经营 |
| 改派 | 应答后司机取消后，平台重新为乘客寻找司机 | 改派会拉长乘客真实等待链路 |

## 4. 商家分单系统

商家分单系统负责在自身可用运力内，把乘客呼叫和司机进行两两匹配。它的核心动作包括召回、匹配价值计算、排序/指派和举手。

### 4.1 召回

召回是从司机池中找到“有资格参与本单”的候选司机，通常会考虑：

- 司机是否在线、可听单、非忙碌、非封禁或非限制状态。
- 司机当前位置到上车点的距离和时间。
- 司机服务品类、服务城市、听单范围和接单开关。
- 是否支持连环派、扩播、预分单、顺路、选单等特殊交易场景。
- 司机历史行为、取消/拒单规则、商家侧管控规则。

召回策略过窄会导致找不到司机、举手不足；召回过宽会带来远接驾、长等待和应答后取消风险。

### 4.2 匹配与分单算法

常见分单思路包括：

| 方法 | 业务含义 | 优点 | 风险 |
| --- | --- | --- | --- |
| 就近贪心 / topspeed | 订单产生后优先找最近可用司机 | 简单、响应快、局部接驾成本低 | 多订单多司机同时存在时，可能不是全局最优 |
| 轮次分单 / KM | 周期性收集一批订单和司机，构造订单-司机二分图后求整体匹配 | 能降低整体接驾成本，适合批量匹配 | 需要处理实时性、等待窗口和目标权重 |
| GS / 稳定匹配 | 同时考虑司机和乘客偏好，追求更稳定的司乘匹配 | 有利于降低取消、改善个体体验 | 可能带来接驾距离或效率上的权衡 |
| 动态价值分单 / MDP | 把司机接当前单的短期收益和未来时空价值一起考虑 | 能优化平台长期效率和司机效率 | 依赖时空价值模型和策略评估 |

交易效率方向在评估分单策略时，不能只看接驾距离或完单率单点指标，需要同时关注乘客 ETP、司机接驾时长、应答后取消、CR、GMV 和司机效率。

### 4.3 匹配价值

匹配价值可以理解为“一个司机接一个订单后，对司乘和平台带来的综合价值”。常见价值项包括：

- 乘客侧：应答概率、应答时长、接驾距离、接驾时长、应答后乘客取消概率、到达上车点时间。
- 司机侧：接驾成本、空驶距离、司机未来可获得订单机会、司机履约概率、司机取消/拒单行为。
- 商家侧：商家履约能力、流量竞争能力、司机密度、商家经营目标。
- 平台侧：完单、GMV、毛利、供需平衡、生态公平、合规管控。

实际线上通常不会把所有目标直接相加，而是通过模型分、规则倾斜、硬约束和分层策略组合实现。例如 PK 分可以以预估履约率为基础，再叠加平台策略倾斜；分单可以以接驾成本为主目标，同时对取消风险、连环派、扩播等场景做修正。

## 5. 派单 / 接单模式

派单模式决定订单如何被司机感知，以及司机是否需要主动决策。

| 模式 | 说明 | 适用场景 | 主要关注指标 |
| --- | --- | --- | --- |
| 全指派 | 系统直接把订单派给司机，司机默认接单；应答后取消受规则约束 | 管控强、履约要求高的自营或强约束运力 | 应答率、履约率、司机取消率、接驾距离 |
| 半指派 | 司机有一段决策时间，可接、拒或不操作；不操作通常按愿意接单处理 | 兼顾司机选择权和平台效率 | 拒单率、举手率、应答时长、履约率 |
| 抢单 | 订单播给多个司机，司机主动抢单 | 运力自由度高、供需不稳定场景 | 举手率、抢单响应、接驾成本、取消率 |
| 选单 | 司机在选单大厅主动选择订单 | 补充司机收入和长尾订单消化 | 选单量、完单、应答后取消、司机效率 |
| 调度 | 平台主动引导司机去更可能接单的时空位置 | 差供需、无单司机、供需牵引 | 调度接受、调度完单、司机 TSH、补贴效率 |

半指派中常见“提前举手”逻辑：为了避免等待司机完整决策导致应答变慢，商家可能在司机决策同时先带司机信息参与平台 PK。后续会出现四类结果：司机拒单且 PK 成功则重新下一轮；司机拒单且 PK 失败则拒单成功；司机接单/无操作且 PK 成功则应答；司机接单/无操作且 PK 失败则接单失败。

## 6. 平台 PK 机制

### 6.1 PK 的作用

平台 PK 负责在多个举手司机之间选择最终胜者。它既是短期完单效率工具，也是长期生态牵引工具：

- 短期：为每个订单选择更可能履约、接驾成本更合理的司机。
- 长期：通过流量分配规则牵引司机、商家提升履约、降低取消、减少违规和挑单。
- 体验：在司机效率与乘客等待之间权衡，控制远接驾、长等待和应答后取消。

### 6.2 PK 流程

平台 PK 通常可以抽象为：

```text
T0: 第一个司机举手，订单进入 PK 窗口
T0 ~ T0+N: 持续收集举手司机，新举手司机与当前胜者比较
T0+N: 关闭 PK 窗口，输出最终胜者并进入播单/应答
```

如果只有一个司机举手，通常直接胜出；如果有多个司机举手，则通过 PK 分排序决策胜者。

### 6.3 PK 分与履约率

PK 分常以预估司乘履约率为基础，再叠加业务倾斜或管控项。履约率模型会综合司机、乘客、订单和场景特征，例如：

- 预计接驾距离、预计接驾时长。
- 司机历史拒单率、司机历史取消率、司机历史完单数。
- 司机有责乘客取消、恶意取消、特殊场景取消。
- 乘客历史取消行为、乘客有责取消、场景下取消风险。
- 连环派、扩播、预分单、选单等特殊场景标识。

需要注意：特殊场景下的取消不一定都按普通取消处理。例如连环派无责窗口内的司机取消，通常应单独计入连环派场景特征，不影响常规场景 PK 胜率；乘客在连环派或扩播场景下的取消，也应结合场景归因，避免错误惩罚司机或商家。

### 6.4 动态 PK 窗口

PK 窗口时长 `N` 不是只能固定配置。动态窗口会根据场景在一定范围内调整：

- 已有足够司机参与，继续等待收益小，则缩短窗口，提高司机流转效率并降低乘客等待。
- 举手司机较少且乘客仍有耐心，则适当延长窗口，增加找到更优司机的机会。

动态窗口本质是在“多等一会儿带来的更优匹配收益”和“乘客应答前等待成本”之间做权衡。

## 7. 常见交易场景

### 7.1 连环派

连环派指把新订单播给正在送驾中的司机。司机当前送驾订单终点为 `B`，新订单起点为 `C`，司机当前位置为 `A`，策略需要同时约束 `A -> B -> C` 和 `B -> C` 的距离/时间。

连环派的价值在于提前衔接下一单、提升司机效率，但风险是乘客等待变长、司机取消风险上升。因此连环派通常需要独立统计取消和履约表现，不宜简单混入常规场景。

### 7.2 扩播

扩播是在供需错配时扩大召回半径，为订单寻找更多可匹配司机。扩播可以提升应答机会，但可能带来更远接驾、更长等待和更高取消风险。

扩播策略需要明确：

- 扩播触发条件：如送驾距离、供需状态、等待时长、品类。
- 成本补偿：是否给司机接驾补贴，补贴如何计算。
- 归因规则：扩播导致的取消、远接驾和体验损失如何在平台、商家、司机之间归因。

### 7.3 预分单

预分单是在乘客自行选择品类之外，平台在后台为乘客增加水下呼叫。找到可用司机后，平台再询问乘客是否接受；乘客接受后进入应答。

预分单的关键特征：

- 水下呼叫不一定计入普通看板呼叫数。
- 可能出现应答数大于呼叫数的统计现象。
- 需要关注乘客是否接受、补贴成本、等待体验和商家流量影响。

### 7.4 升舱

升舱与预分单类似，都是在乘客未主动勾选的品类中寻找额外运力。差异在于：升舱找到运力后，可以通过平台或商家补贴差价，直接让乘客获得更高等级或更合适的运力。

升舱要同时评估应答率提升、乘客等待改善、补贴成本、商家流量影响和完单增量。

### 7.5 换车

换车发生在应答后，当接驾距离远、接驾时间久、司机明显不来接乘客等场景触发，平台重新为乘客寻找更合适司机。

换车的目标是降低乘客后续等待和取消风险，但也可能带来司机侧感知、商家侧归因和平台成本问题。需要把换车前后的呼叫、应答、取消、改派和完单链路串起来评估。

### 7.6 调度

调度是平台主动引导无单或低效司机去更可能接单的位置，通常会配合里程补贴、无单补贴或商家共补。调度不等同于分单，它发生在司机还没有被具体订单匹配之前，目标是改善供需空间分布。

## 8. 交易诊断框架

### 8.1 基础漏斗

交易漏斗可以抽象为：

```text
呼叫 -> 匹配/找到运力 -> 举手/参与 PK -> 应答 -> 完单
```

常见指标：

| 指标 | 口径 | 主要解释 |
| --- | --- | --- |
| 成交率 | 完单数 / 呼叫数 | 乘客需求最终被满足的比例 |
| 应答率 | 应答数 / 呼叫数 | 呼叫后是否能获得司机应答 |
| 履约率 | 履约数 / PK 获胜数，或完单数 / 应答数，需按具体场景统一口径 | 应答后订单是否稳定完成 |
| 匹配率 | 匹配量 / 呼叫量 | 商家是否能找到可用司机 |
| 举手率 | 举手数 / 播单数，或举手量 / 呼叫量，需按商家看板口径统一 | 司机是否对订单产生有效响应 |
| PK 胜出率 | 胜出订单数 / 参与 PK 数 | 参与平台竞争后是否胜出 |

对于商家经营诊断，可将完单拆为：

```text
完单 = 竞争呼叫 * 匹配率 * PK 胜出率 * 履约率
```

其中：

- 竞争呼叫受价格、默勾策略、排序位置、流量入口影响。
- 匹配率受司机密度、司机在线时长、有效司机在线时长、商家内部竞争力影响。
- PK 胜出率受单勾/both 举手结构、绝对 PK 胜出率、接驾距离、履约率、竞争商家数量影响。
- 履约率受应答时预估接驾距离/时长、司机取消、乘客取消、司机 CPM、拒单与特殊场景影响。

### 8.2 诊断顺序

定位交易波动时，建议按漏斗顺序拆解：

1. 先看呼叫侧：总呼叫、竞争呼叫、勾选分布、价格、入口流量是否变化。
2. 再看匹配/召回：可召回司机、在线司机、有效司机时长、召回半径、商家内部胜出是否变化。
3. 再看 PK：only 举手、both 举手、参与 PK 数、绝对 PK 胜出率、平均参与商家数是否变化。
4. 再看应答：应答率、单均应答时长、司机拒单/抢单响应是否变化。
5. 最后看履约：应答后司机取消、应答后乘客取消、改派、换车、接驾距离和接驾时长是否变化。

不要只看成交率总结果；需要把“有没有流量”“有没有司机”“有没有举手”“有没有胜出”“胜出后有没有履约”拆开。

## 9. 交易效率方向关注边界

交易效率方向重点负责或重点参与：

- 召回 / 分单 / 匹配主流程优化。
- 平台 PK 排序、PK 窗口、PK 价值建模和履约率模型应用。
- 司机接驾效率与乘客等待体验之间的权衡。
- 乘客侧交易策略，如换车、升舱、预分单透传。
- 交易体验指标，如 ETP、单均呼叫-计费时长、单均应答时长、单均接驾时长、接驾距离、改派和应答后取消。

与其他方向的边界：

- 交易生态更关注取消治理、判责、司机/商家生态、公平规则和 bad-case 治理。
- 司机与调节更关注司机侧长期价值、供需调节、动调、无单调度和弹性评估。
- 行业/公共指标方向维护跨方向通用指标口径；交易效率只维护本方向特有口径和解释。

## 10. 常见问题

### Q1：商家内部匹配和平台 PK 有什么区别？

商家内部匹配是在单个商家或运力池内，决定“我把哪个司机拿出来参与竞争”；平台 PK 是在多个商家/司机举手后，决定“最终哪个司机胜出并服务乘客”。前者影响举手质量，后者决定最终流量分配。

### Q2：为什么取消率下降后，PK 胜出率不一定立刻上升？

PK 是相对竞争结果。如果所有商家或司机履约率同步上升，单个商家的相对优势可能不变；同时 PK 分还受接驾距离、司机密度、竞争商家数量、策略倾斜等因素影响。因此需要看 both 举手场景下的绝对 PK 胜出率、履约率模型分位和竞争结构，而不是只看取消率单点。

### Q3：为什么应答数可能大于呼叫数？

预分单等水下呼叫可能不计入普通呼叫数，但后续如果乘客接受并应答，会进入应答统计。因此在包含预分单的场景中，需要明确呼叫口径和应答口径是否同源。

### Q4：远接驾一定不好吗？

远接驾通常会增加乘客等待、司机空驶和取消风险，但在供需错配、长距离订单、扩播或高价值订单中，适度远接驾可能换来更多应答和完单。判断策略好坏时应同时看 CR、GMV、乘客取消、司机取消、接驾补贴和司机效率。

### Q5：only 举手和 both 举手为什么要分开看？

only 举手表示只有一个司机或商家有效响应，通常直接胜出；both 举手表示存在竞争，平台 PK 的排序能力和商家竞争力才会充分体现。拆开后可以区分“没有竞争自然胜出”和“竞争中真正胜出”。
