## 一、背景

当前司乘履约模型采用多任务结构，联合预测司机履约、乘客履约和订单完单三个目标。三个任务具有业务关联，但其影响因素及在连环派、非连环派场景下的表现存在差异，现有线上模型预测 AUC 仍有提升空间，因此，本次从特征补充、历史序列行为建模和多任务多专家结构优化三个方面开展离线探索。

**（**1）AutoFE：补充具有业务意义的历史统计特征

现有特征主要依赖人工设计，难以充分覆盖司机、乘客在不同业务场景下的行为差异。为拓展候选特征的覆盖范围，本次借鉴基于 LLM 的自动特征工程思路，结合任务目标、数据表生成候选统计特征，再通过数据质量检查和模型筛选来确定补充新特征。

（2）序列建模：补充聚合统计难以保留的历史行为信息

历史统计特征能够反映司乘在一定时间窗口内的整体表现，但会弱化单次订单信息及行为趋势。相似的历史完单率或取消率，可能对应不同的近期行为过程。为利用这些差异，本次引入司乘历史订单序列，探索 OneTrans、HyFormer 等结构，学习历史序列行为内部，以及历史序列行为与当前订单之间的关联，为预测履约提供更充分的上下文表示。

（3）多任务多专家模型结构优化：改善共享信息与场景差异的建模

多任务建模能够利用三个履约目标之间的关联，但任务间共享结构和门控机制是否有效，仍需结合业务数据验证。现有线上模型的门控诊断中，不同任务的专家权重集中于少数专家，对专家的利用不足。因此，本次首先优化线上模型的门控机制，使专家分配更好地结合连环派、非连环派场景；进一步探索PEPNet结构，通过EPNet引入场景个性化、PPNet引入用户个性化，并结合序列特征形成联合表示。通过模块消融验证各项设计对三个预测任务的实际贡献。

#### 3.1.1 历史统计特征

现有历史统计特征主要依赖人工经验设计。当统计对象、业务场景、时间窗口和统计方式不断组合时，候选空间会迅速扩大，人工探索的成本较高，也容易遗漏具有业务意义的组合。因此，本次借鉴基于 LLM 的自动特征工程思路，利用其对业务描述和字段语义的理解能力，辅助构造候选特征，再通过数据与模型验证完成筛选。流程如图所示，为了提高迭代效率，选择小部分训练集和验证集进行迭代筛选：

（1）结合业务任务与数据字段，生成候选特征

向 LLM 提供预测司机履约、乘客履约和订单完单的任务说明，以及可用数据表、字段含义和已有特征，让其围绕“哪些历史行为可能影响当前订单履约”提出候选统计方案。特征构造主要从四个维度展开：

| 构造维度 <br> | 设计内容 <br> |
| --- | --- |
| 统计对象 <br> | 司机、乘客、目的地格子等 <br> |
| 场景粒度 <br> | 与 POI、发单时段、行程距离段、接驾距离段、派单类型等组合 <br> |
| 时间窗口 <br> | 近 7 天、近 28 天 <br> |
| 统计方式 <br> | 事件计数与比率、时长和距离的分布、活跃度、最近事件间隔等 <br> |

除司机整体取消率外，进一步构造司机在相同出发场景POI、行程距离下的历史履约表现；除乘客整体完单率外，补充乘客在相同时段、相似接驾条件下的历史取消与等待情况。通过这些组合，刻画更细粒度的特征。

（2）XGBoost 初筛与候选反馈迭代

LLM生成的候选特征具有业务解释，但是否包含有效预测信息仍需通过数据验证。考虑到直接使用多任务模型逐一验证的成本较高，因此采用多个XGBoost在小规模训练和验证数据上进行初筛，评估候选特征，结合验证集AUC、Gain重要性和特征缺失情况，筛除重要性均为0或特征缺失率80%以上的特征。若当前候选集合未达到预设的AUC增量要求，则将结果反馈给LLM，继续调整统计对象、场景组合或时间窗口，生成下一轮候选。通过模型反馈引导特征探索，逐步聚焦于有预测价值的方向。

（3）增量特征评估与特征规模选择

XGBoost生成的Gain能够提供候选特征的重要性排序，但不能直接确定保留多少个特征最合适。增加特征可能带来预测增益信息，也会增加计算、存储和维护成本，因此需要评估模型效果是否存在边际效应。按照Gain重要性排序逐批加入候选特征，比较验证集AUC的变化，判断继续扩大特征规模是否仍有足够收益，综合收益与成本生成候选集合。

（4）目标模型验证，确认特征实际收益

筛选阶段使用的模型与多任务模型在结构和特征交互方式上存在差异，因此，候选特征在筛选模型中的增益，不一定能迁移到多任务模型。需要验证新增这些特征后，是否能改善实际预测效果。将入选特征接入多任务模型，在保持训练配置一致的条件下，对比新增特征前后的验证集表现，分别评估司机履约、乘客履约和订单完单三个任务的增益，据此确定最终保留的特征集合。

### 3.2 模型结构

#### 3.2.1 PLENet

##### 3.2.1.1 gate场景化路由与专家归一化

现有 PLE 的专家权重集中于少数共享专家，连环派与非连环派专家的作用未得到充分体现，因此调整 Gate 输入，引入明确的场景信息以改善专家分配。同时，不同专家体现为使用不同数值变换方法，导致输入的分布存在差异，因此引入 BatchNorm，减轻分布差异对专家训练及后续融合的影响。

（1）以场景标识作为gate输入

原有gate使用订单相关的稀疏特征与稠密特征共71维生成专家权重。考虑到专家网络已经包含这些特征的表达交互，本方案将gate输入简化为“是否连环派”这一二元标识，明确gate与专家网络的分工：

- 专家网络：利用订单、司乘等特征，学习样本层面的履约表示。

- Gate网络：根据场景标识，为不同预测任务学习对应的专家组合权重。

（2）保留任务独立，区分场景的专家融合方式

专家池仍划分为连环派专家组（S）、共享专家组（C）和非连环派专家组（N）。每组包含五个专家，分别处理原值、平方、开方、对数和高斯变换后的数值特征。OD、O、D三个预测任务分别设置连环派和非连环派分支。各分支独立生成权重，并限定可访问的专家范围：

| 任务分支 <br> | 可访问专家 <br> |
| --- | --- |
| 连环派分支 <br> | 连环派专家组 S＋共享专家组 C <br> |
| 非连环派分支 <br> | 共享专家组 C＋非连环派专家组 N <br> |

（3）在专家网络中增加BatchNorm

针对原值、平方、开方、对数及高斯变换形成的专家各路表示，在进入专家网络前分别设置BatchNorm。各专家对输入进行归一化，再送入后续网络提取特征，在保留不同变换表达的同时，减轻其数值分布差异。

（1）建模思路

方案借鉴 OneTrans 的建模思路，将司机历史订单序列、乘客历史订单序列与当前订单的共享非序列特征统一转换为 token，使用Transformer学习三类信息之间的交互关系，再将融合后的表示引入 PLE 共享专家组。

（2）统一特征表示

司机、乘客两侧分别输入长度为20、每条订单包含15个字段的历史序列。两侧使用各自的tokenizer，将每条历史订单编码为token，得到两组序列表示；非序列特征同样也编码为token，并叠加标识向量来区分序列表示；此外，引入一个独立的共享聚合token，用于汇总司乘历史与当前订单的联合信息。

（3）序列与非序列特征联合交互

将司机序列、乘客序列、非序列特征和聚合token拼接放入transformer，通过注意力机制联合学习：

- 历史行为内部的关联：识别司机或乘客在连续订单中的履约变化。

- 历史行为与当前订单的关联：结合当前订单条件，提取具有参考价值的历史信息。

最后取出更新后的非序列特征切片和聚合 token，补充信息上下文。

#### 3.2.2 PEPNet

PLE 通过Gate调整专家组合，表达场景差异。考虑到特征也可能在不同场景或用户条件下具有不同作用，本方案进一步探索 PEPNet，在特征维度引入多个门控调制。PEPNet主要由EPNet（Embedding Personalized Network）和PPNet（Parameter Personalized Network）两部分组成。EPNet 在embedding层引入场景信息，调整不同特征的重要性；PPNet在网络中引入个性化信息，逐层调整隐藏表示，使共享特征能够适应不同用户的预测需求。其模型结构如下：

![](https://s3-ep-inter.didistatic.com/didoc2-upload-file-prod/images/1791613040110/6VkLeOn8gEoQIGh1ALYxH/image.png?X-Amz-Algorithm=AWS4-HMAC-SHA256&X-Amz-Credential=AKDD00000000000EBLCTZNRBJHX6ZS%2F20261104%2Fgzep%2Fs3%2Faws4_request&X-Amz-Date=20261104T093600Z&X-Amz-Expires=86400&X-Amz-SignedHeaders=host&X-Amz-Signature=ad4480ba7c3bac93587d712444c6ed35bf9423a3195c7899e8e168e161ad11d2)

图中输入分三类：General Input提供通用的离散与连续特征，EPNet Input提供场景先验，PPNet Input提供用户等个性化先验。各类特征经过编码后，分别进入主预测路径和门控路径。

（1）Gate NU：生成个性化缩放权重

EPNet和PPNet都通过Gate NU生成门控权重。其结构为两层神经网络，第一层使用 ReLU，第二层使用 Sigmoid，并将输出乘以 2：$$g(x)=2\sigma\!\left(W_2\operatorname{ReLU}(W_1x+b_1)+b_2\right)$$。门控权重位于0到2之间，小于1时抑制对应维度，大于1时增强对应维度，等于1时保留原表示。各维权重独立生成，无需总和为 1。

（2）EPNet：根据场景调整输入特征表示

同一特征在不同场景下的重要性可能不同。EPNet 将场景先验与输入特征表示结合，通过 Gate NU 生成逐维缩放权重，再与输入特征逐元素相乘，形成适应当前场景的特征表示，送入后续任务网络。

（3）PPNet：根据个性化先验逐层调制任务网络

不同个体对特征的依赖程度可能不同。PPNet 将个性化先验与主干网络结合，通过各层Gate NU生成缩放权重，逐层调整主干网络的中间表示，使各任务能够根据样本特征选择性地增强或抑制不同维度的信息。整体上，EPNet负责输入表示层的场景适应，PPNet负责主干网络内部的个性化调制，两者共同支持多场景、多任务建模。

##### 3.2.2.1 EPNet/PPNet实验

EPNet和PPNet分别引入场景与个性化信息，但其在履约任务中的贡献及所需特征需要通过实验确认。因此，本方案围绕两个问题开展实验：一是EP、PP两类门控是否发挥作用；二是不同类型的特征应该放在哪条路径中。

（1）通过模块消融，验证 EPNet 和 PPNet 的作用

以完整 PEPNet 为基线，分别移除 EP门控、PP门控，以及同时移除。移除EP后特征向量直接进入任务网络；移除PP后，保留主干网络的DNN，取消逐层的个性化调制。

（2）对比不同特征在 General、EPNet 和 PPNet 中的输入组合

包括向 EPNet 增加场景特征，离散特征；向 PPNet 增加司机行为特征，以及让离散特征同时进入General，评估不同输入方式对预测效果的影响。综合模块消融与后续输入复验，最终决定输入组合。

##### 3.2.2.2 适配序列特征

统计特征能够描述当前订单条件和司乘整体表现，但难以充分保留历史行为的先后关系及单次订单的具体信息。因此，分别引入 OneTrans 和 HyFormer，学习司乘历史序列与当前订单特征之间的关联，形成融合历史序列信息的General特征表示，再通过EPNet和PPNet完成场景调制与任务个性化建模。

（1）onetrans改造：

（a）建模思路

历史统计特征能够描述司机、乘客的整体履约水平，但聚合过程会弱化行为发生的先后顺序以及单次订单的具体信息。为补充这些信息，方案借鉴 OneTrans 的统一建模思路，将司机历史订单序列、乘客历史订单序列与当前订单的非序列特征统一转换为 token，通过 Transformer 学习历史行为与当前订单之间的关联，将融合后的表示作为PEPNet的General输入，接入多任务预测网络。

（b）统一特征表示

司乘两侧使用各自的tokenizer对历史序列编码，叠加位置编码，保留历史订单的顺序信息。非序列数值特征也编码为token，并与序列表示保持维度一致。此外，在司机与乘客序列之间加入一个可学习的分隔 token，用于标识两侧历史的边界。

（c）序列与非序列特征联合交互

按照“司机历史序列 → 分隔 token → 乘客历史序列 → 非序列特征”的顺序拼接，输入两层单向Transformer（使用单向注意力，目的是保留历史行为的先后关系，并让当前订单特征能够吸收历史信息，本方案对 Transformer 的信息读取范围进行限制：每个 token 只能读取自身及排列在它之前的有效 token，不能读取后面的 token。），并通过补齐掩码屏蔽无效历史位置。注意力机制主要学习：

- 历史行为内部的关联：结合历史订单的先后关系，提取连续行为中的履约信息。

- 历史行为与当前订单的关联：非序列 token 位于输入末尾，能够读取前面的司乘历史，形成融合历史信息的当前订单表示。

最后，移除分隔 token，保留更新后的非序列特征及司乘两侧历史表示送入EPNet，完成订单完单、乘客履约和司机履约预测。

（2）hyformer改造

![](https://s3-ep-inter.didistatic.com/didoc2-upload-file-prod/images/1791719742889/ukmqFs04IMfv6wAjlrTm5/mermaid-diagram_%282%29.png?X-Amz-Algorithm=AWS4-HMAC-SHA256&X-Amz-Credential=AKDD00000000000EBLCTZNRBJHX6ZS%2F20261104%2Fgzep%2Fs3%2Faws4_request&X-Amz-Date=20261104T093600Z&X-Amz-Expires=86400&X-Amz-SignedHeaders=host&X-Amz-Signature=9aa79605cb326a01bb27cb68809a6dfa4a0cd699ef94bf9beb08c489d60c2500)

（a）建模思路

不同订单条件和派单场景下，司乘历史中具有参考价值的信息可能不同。因此，引入 HyFormer，将当前订单与场景信息作为历史提取的条件，使模型能够有针对性地关注相关行为。具体而言，将非序列特征组织为语义 token，并结合当前订单信息、司乘历史信息、序列行为和场景信息，分别生成司机、乘客 Query，由 Query 从对应历史序列中提取与当前预测相关的信息。使用融合后的表示完成三个履约任务的预测。

（b）统一特征表示

司乘两侧使用各自的tokenizer对历史序列编码，并叠加位置与角色编码，得到两组历史序列表示。非序列特征按字段及业务含义组织为不同语义 token：10 个离散字段分别编码为一个 token；稠密特征、连环派、非连环派等特征分别映射为token，并叠加类型编码。随后，分别对司机、乘客的有效历史行为序列取均值，得到两侧的历史行为序列摘要，再与非序列特征及场景编码结合，生成司机和乘客各自的查询向量（Query）。这两个向量用于引导模型结合当前订单和场景，从对应历史中提取有参考价值的信息。

（c）序列与非序列特征联合交互

模型采用两层 HyFormer，每层依次完成以下处理：

- 学习历史订单之间的关系：司机、乘客的历史订单序列分别进行交互，使每条历史订单能够结合其他历史订单的信息。目的是让模型有机会区分这次取消是相对孤立的行为，还是历史中反复出现的模式？它与其他订单条件有什么关联？

- 提取与当前预测相关的历史信息：司机、乘客各自的 Query 对对应历史进行加权汇总，形成司乘各自融合后的历史query向量，由模型根据当前订单和场景学习。

- 融合历史与当前订单信息：将司乘两侧历史向量与静态特征向量共同输入Query Boosting（token-mixing），使不同来源的信息相互补充。

最后，第二层输出的司机 Query、乘客 Query 和 14 个静态 token，归一化并展平送入EPNet，完成订单完单、乘客履约和司机履约预测。
