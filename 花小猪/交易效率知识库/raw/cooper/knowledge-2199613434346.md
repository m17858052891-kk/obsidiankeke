# 状态Input的设定

## 1. Temporal时间状态分量

state第一个维度，time zone的划分，在v1版的特征选取里设计为

- 时间状态起始：call_time

- 时间状态终止：end_time = call_time + eta_second_pick_dur + estimate_dur

可能存在两类问题：

- call_time是订单生成时间，匹配启动后司机多长时间内接单、是否拒绝或者改派在gmv衰减里物理意义没有answer_time更可解释。把answer_time作为起始状态点可以认为是司机接受订单安排  
再前往空间起始位置接驾并完成订单，这段耗时在gmv的分片衰减计算中更具备实际物理意义；

- end_time如果是订单产生和两个预估时间的总和会出现司机决定是否接单这段时间空白，并且两个预估时间会造成在后续其他特征计算时出现“单内套单”的情况，比如在两端预估时间内，新订单的  
call_time已经产生，这样一次订单内的状态转移未完成时下一个新状态就已经出来，那么即使不考虑空跑的idle状态转移，时间维度分量也出现倒流了。

v2版本里考虑的是把时间维度的起始和结束状态分别设定为

- 时间状态起始：answer_time

- 时间状态终止：finish_time

这样，订单生成后我们可以认为司机接受订单开始到实际前往接驾并送达目的地的total_dur具有更合理的物理意义，前提是在小猪平台上目前没有连环派单功能，这样即使制作订单间转移的空跑单，

只要时间差是在单位时间片内(比如5min)也不会带来衰减。

# 衰减reward计算

## Recap:

[奖励值计算](http://wiki.intra.xiaojukeji.com/pages/viewpage.action?pageId=529395444)给的示例可以增加一个时间片非整除的case

## 改进：

参考[paper](https://didoc-upload-file-prod.s3.didiyunapi.com/1653034091739/860100235.pdf)的gmv reward在整个trip当中的均匀分布假设：

首先定义iph = gmv / (total_dur)，也就是论文当中的k_t，那么对于一个单位时间(5 min), k_t表示 the number of time units in the given total_dur，

则 iph = gmv / (total_dur / time unit)， time_unit = 5 min for example.

那么计算mod的最后一个分片里的衰减值时，因为是均匀的，所以最后一个reward = surplus \* (gamma \*\* (total_dur // time_unit - 1)), where surplus = gmv - iph \* (total_dur // time_unit),

在size比较大的数据集上，pandas并行化算这个discounted reward非常快，1M的数据量3分钟以内能全部算完reward和gamma对应的power.

# 时空状态转移避免出现倒流

## 订单内

首先对于订单内的时间分量转移，v2强制要求了一个epsiode时间控制在2h内，这部分在处理时发现了gmv = 0 的5%左右的异常订单，也发现了当total_dur小于一个time_unit时计算真实reward的bug，

可以再多关注下这部分。或者砍掉订单时长在5min以下和2h以上的

## 订单之间

生成idle订单，可以提升对数据集的利用效率，根据episode完成的label来生成每个episode内订单之间的状态转移空跑订单，这些订单有助于检查是否会出现前后两个有gmv的订单是否会出现时间倒流。

同时通过这个可以发现未检测出的异常订单，比如同一个司机在同一时刻接了2单且都完成订单的case：3月9号的driver_id == 580544893575705 和3月11号的driver_id == 580545285922687，

有助于我们在比较新的数据集上观察是否出现这样的情况并同步给工程部门检查原因。
