从这个意义上说，召回的目的之一是**召回尽量多可匹配的资源**，为后续的流程提供更多的材料。

# 2. hxz分单新方案设计

hxz分单策略新方案主要考虑因素：

- 模块间关系梳理：把召回的作用单一化，把其他的计算模块加入到价值和匹配中，重新定义各模块间的协同关系；

- 项目整合：将召回内部项目进行整合，方便编号和评估；

- 司乘价值体现：在分单策略中，更多体现司乘价值。

## 2.1 召回

召回的核心在于更多的提供可匹配的司乘对，供之后的流程使用。

**召回的产出为do对，具体来说，是一个 n元组 <司机,订单,产品形态（半指派、抢单）>。**

### 2.1.1 过滤规则

结合产品/运营形态，首先需要定义召回的硬规则约束，包括：

1) 半指派产品形态下的最大播单距离，如 3km 或 5km；

2) 一对多产品形态下的最大播单距离，如 5km 或 10km；

3) 连环派单产品形态下，未完单的司机和未播订单。未完单司机最多还剩多久完单，如10min；

4) 过滤规则，如设置实时目的地的司机和非顺路订单；

5) 其他补贴形态下的特殊要求，如超过3km有补贴，则可以扩到5km。

### 2.1.2 空召回

为了将召回和价值解耦，需要在召回里特殊加入司机不接订单和订单不分给司机的召回，即司乘分别都有一个空节点。

我们称之为 广义DO对。

加入空召回后，实际上召回还原成了下图。

具体实施例

- 召回

	- 首先定义在每种产品形态下，平台和司乘约定的最大播单距离

		- 半指派5km

		- 抢单（一对多）10km

	- 以下定义每个可召回的（广义）DO对

		- 对订单侧，找到所有路面距离5km以内，符合过滤规则的司机，半指派模式；10km以内，一对多模式；以及**不分单**这一广义召回

		- 对司机侧，找到所有路面距离5km以内，符合过滤规则的订单，半指派模式；10km以内，一对多模式；以及**不分单**这一广义召回

	- 最终产出：n元组 <司机,订单,产品形态（半指派、抢单）>

		- 注：这里假设所有补贴策略先于分单进行，故先不需要考虑天降B补

Note

在此情况下，召回更多为业务规则以及产品形态，不存在显式的“召回策略”。

现存的召回策略，如策略播单等，转而进入价值策略中考虑。

现存项目中，动态播单距离和动态播单间隔项目不再存在，转为对司乘“空召回”价值的详细设计中考虑。

##   
2.2 价值

![](https://s3-ep-inter.didistatic.com/didoc-upload-file-prod/1653033105181/860099810.png?X-Amz-Algorithm=AWS4-HMAC-SHA256&X-Amz-Credential=AKDD00000000000EBLCTZNRBJHX6ZS%2F20261104%2Fgzep%2Fs3%2Faws4_request&X-Amz-Date=20261104T102148Z&X-Amz-Expires=86400&X-Amz-SignedHeaders=host&X-Amz-Signature=c87c2faa8fcc956ae708700980cc05bc90ab6125569e40f25d37752850d0f9ad)

价值模块，顾名思义为计算召回得到的匹配对的“价值”。

**价值模块的输出，为 V(司机,订单,产品形态（半指派、抢单）)。 \* V可能会区分乘客视角、司机视角和平台视角。**

wyc的价值模块有接驾距离、订单IPH、MDP价值更多种尝试。

*\* 实际上，接驾距离为乘客视角的价值，订单IPH和MDP主要是司机视角的价值。*

### 2.2.1 乘客视角价值

乘客交易侧核心价值：能走 > 接驾近 > 应答快

#### 2.2.1.1 DO对价值

历史版本中，使用接驾距离函数的STR版本（上图右上角），即综合考虑了成交和接驾距离。

但此版本的问题在于，它只能达到这一轮分单的最优，而无法考虑时间轴上（多次分单轮次下）的最优。

在新方案中，对订单侧，我们定义价值为预估成交率。

则，对每个DO对，设计价值为（参考 [STR设计 —— 乘客侧](/pages/createpage.action?spaceKey=XYW&title=%E3%80%90deprecated%E3%80%91STR%E8%AE%BE%E8%AE%A1+%E2%80%94%E2%80%94+%E4%B9%98%E5%AE%A2%E4%BE%A7)）

```PlainText
(1 - 司机拒单率(d,o)) * (1 - 应答后取消率(d,o))
```

#### 2.2.1.2 空召回价值

对空召回**（订单这一轮不分单对应的成交率期望（即价值））****：**

- 对订单生存时间分档，如0-10s, 10-30s, 30-60s, 60-120s, 120-300s, ...。定义为t0, t1, ...

- 假设目前订单生存时间分档为ti，则空召回价值为：

```PlainText
与应答前取消、应答后取消、应答概率相关的期望


（to be deleted:）  1 - 应答前取消概率（ti→ti+1) - 应答后取消率（时空内/乘客均值）
```

### 2.2.2 司机视角价值

司机交易侧核心用户价值为：收入高 > 有单 > 接驾近

#### 2.2.1.1 DO对价值

历史版本存在订单IPH和MDP价值等多种。

详细可参考相关wiki。

#### 2.2.1.2 空召回价值

对司机，**这一轮不分订单的价值**为：

```PlainText
订单IPH_期望  或  MDP_期望
```

  
  
其中IPH\_期望 为hold策略算出的阈值 （[司机Hold策略调研](https://cooper.didichuxing.com/cooper_gateway/metis/v1/knowledge/2199610335356/wikiFile/860100387.html?taskId=2199613477654)）。

特别的，对IPH\_期望 预估不准的情况，使用T_hold做体验兜底。在T_hold时间之上，接受所有订单。

故也可对司机的生存周期（连续在线时长）进行分档，如0s,30s, 60s, 5min, 10min, 30min等等，计算司机如果在未来一个时间段没有分单的话，下线的概率是多少。

## 2.3 倾斜

倾斜与匹配直接相关。

在KM匹配的模式下，倾斜的表现形式为：

- 在价值的基础上，乘以一定倍数；

- 这个倍数并不直接对应物理意义（如距离等）。

在GS匹配的情况下，倾斜的表现形式为

- 对核心乘客

	- 用天降B补在订单IPH上进行调整

- 对核心司机

	- 可在接驾距离上进行调整

# 3. 版本号定义与实施方案

对2的方案，初期没有历史数据积累的情况下，简化为：

- 初步召回：对所有do对距离 < 3km 以及 符合业务过滤规则的进行召回

- 对一些低价值召回进行过滤（即初期继续将召回和价值融在一起，后续再做分离）

	- 订单侧

		- 假设司机拒单率为0（补贴很高的情况下）

		- 假设应答后取消率和DD数据一致，可直接复用模型

		- 使用平均应答前取消时间作为ti档位，只进行一次计算 应答前取消概率（ti→ti+1)。对ti前后，分别用两个应答后取消率的阈值来卡；

		- 结果：ti前，应答后取消 > 10%（阈值1，可调）的过滤； ti后，应答后取消 > 30%（阈值2，可调）的过滤。

	- 司机侧
