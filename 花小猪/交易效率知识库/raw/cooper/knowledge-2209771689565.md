# 2. Arbor 的研究任务

2.1 固定数据与评价契约

Arbor 的目标是在不改变数据和评价方法的前提下，提高完整验证集的 Mean AUC。模型输入为 727 维：167 个静态字段、20×14 的司机历史和 20×14 的乘客历史。输出是 OD、O、D 三个二分类概率，最终指标为三头 AUC 及其平均值。

训练表、验证表、样本过滤、标签、mask、字段顺序、随机种子、loss 和 AUC 计算均被冻结。smoke 只用于检查 forward、loss、反向、验证和 checkpoint 链路，结果不可排名；只有 full validation 的 \`valid=true\` 结果可以进入候选排名。

2.2 Domain 是硬约束

业务上存在连环派与非连环派两个 domain，由 binary 字段标识。binary 不能只作为普通数值拼进 DNN。候选必须说明：哪些参数跨域共享，哪些参数按域隔离，binary 如何控制 query、adapter、归一化、专家或输出 head，以及如何避免两个 domain 的负迁移。

这一要求与 OD/O/D 三任务是两个不同维度。任务建模解决三个目标之间的共享与冲突，domain 建模解决连环派与非连环派之间的分布差异。候选必须同时说明这两条轴，不能用三个 task tower 代替 domain 区分。

2.3 架构搜索边界

前几轮优先探索新的多任务关系建模方式，不把 PEPNet、PLE 或 STAR 作为默认主干，也不把改深度、改宽度、改激活、改正则或普通学习率调参当成一个研究周期。DCNv2、FiBiNET 和 WuKong 可以作为特征交叉模块，OneTrans 或其他 Transformer 可以作为时序模块，但都必须服务于新的多任务骨架，不能只是把旧模块直接拼接后换名。

每个候选需要回答：多任务主干是什么；与 PEPNet、PLE、STAR 的本质差异是什么；静态交叉和司乘时序如何处理；为什么适合 OD/O/D；如何处理两个 domain；预计参数量、显存、训练时间和实现风险；本轮相对已有实验新增了什么信息。

2.4. Arbor 的自动执行方式

Arbor 由 \`arbor_controller.sh\` 统一管理，不再要求人工为两张 GPU 分别创建 tmux 窗口。controller 使用 \`nohup + setsid\` 脱离 SSH 和 Codex 生命周期，SSH 断开不会终止训练。tmux 只用于查看日志或临时排障，不是实验调度器。

controller 的标准流程如下：

1. 检查 protected 文件、仓库状态、运行目录容量和 GPU；

2. 在新机器上用双卡 DDP 运行统一 baseline；

3. 生成候选并进行 review；

4. 运行 smoke，验证输入、loss、反向、验证和 checkpoint；

5. smoke 通过后自动启动 full；

6. 读取候选独立的 \`result.json\`，记录三头 AUC、Mean AUC、commit、配置和模型哈希；

7. 清理失败或非最优 checkpoint，保留可复现实验记录；

8. 根据结果进入下一轮候选生成和 review，初始预算最多三轮。

每次实验必须有独立的 run-id、store-dir、输出目录和 checkpoint 路径。controller 记录资源采样、阶段状态和错误位置。超时后先发送终止信号并等待，再强制结束进程树；失败结果写入 \`valid=false\`，不能悄悄丢失，也不能覆盖其他候选状态。
