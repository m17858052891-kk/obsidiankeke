# OD连边现状梳理


# 一、背景

- 目的：看清D选O方式优化的收益空间

- 核心：看每轮分单有多少D连的O的数量>1

# 二、数据分析

## 1、唯一连边

**结论**

- **D选O：自营&宏鹄GS分单矩阵中连到的O数量大于1的司机比例均为6%左右，D选O挑单空间有限。**

- **O选D：连到的D数量大于1的订单比例 GS分单模式下约30%，TopSpeed模式下约50%**

- **整体结论：**

	- 目前D对O连边数大于1的比例低，D选O挑单空间小，因此**通过在GS分单中优化D对O打分方式带来的收益空间小**。（关于D对O打分优化的历史实验文档：[订单价值重构](https://cooper.didichuxing.com/knowledge/2199610335356/2202363461600) [D对O打分优化](https://cooper.didichuxing.com/knowledge/2199610335356/2202292344853) [gs订单价值计算迭代收益上限分析](https://cooper.didichuxing.com/knowledge/2199610335356/2201262562766)）

	- **目前的匹配结果是由O主导的：D反选O的空间仅有6%，意味着绝大多数的匹配结果仅由O对D打分决定**。也就是说，绝大多数情况，**GS分单和TopSpeed分单得到的匹配结果一致**。而TopSpeed可以将分单时间从2s缩短到0.3s，更快举手从而获得更高PK胜率。**因此，在这样一个更快举手将提高PK胜率、且94%的匹配结果完全由O对D打分决定的匹配市场中，商家的合理策略是全部使用由O直接选对O来说最优司机的TopSpeed分单模式。**

```SQL
with base as (
    select distinct
        param ['orderid'] order_id,
        param ['driverid'] driver_id,
        param ['uuid'] uu_id, --轮次（不同轮次的编码不一样，类似 d300d101c37b44f1）
        param['rgs_pair_match_flag'] as rgs_pair_match_flag, --层级（int）
        param['broad_source'] as broad_source, --播单来源
        concat_ws('-', year, month, day) as dt
    from
        kflower_marketplace.ods_log_kflower_stgmatrix_hh
    where
        concat_ws('-', year, month, day) between '2026-01-11' and '2026-02-07'
        -- and param ['broad_source'] in ('hh_hxz_stg','hh_hxz_speed','hh_stg','hh_speed')  --stg是GS分单，speed是topspeed；hh是宏鹄，hh_hxz是自营
        -- and param ['broad_source'] in ('hh_hxz_stg','hh_hxz_speed') --只看自营
        -- and param ['broad_source'] in ('hh_stg','hh_speed') --只看宏鹄
        and param ['broad_source'] in ('hh_hxz_stg','hh_stg') --只看GS分单

)


--司机连订单数
select
    dt,
    broad_source,
    count(if(order_cnt =1 , driver_id, null)) / count(driver_id) as ratio
from
    (
        select
            dt,
            uu_id, 
            rgs_pair_match_flag, 
            driver_id,
            broad_source,
            count(distinct order_id) as order_cnt
        from
            base
        group by 1,2,3,4,5
    ) t
group by 1,2
```

> 「唯一连边司机占比」= 只连了一个O的司机数量 / 所有有连边的司机数量

Q：为什么TopSpeed分单模式下所有的司机都只有一个连边（或者没有连边，未进分单矩阵），而不存在多个？

A：因为TopSpeed模式没有「轮次」的概念；且TopSpeed是订单选O视角下的最优司机，不存在D选O、无司机挑单空间，所以看TopSpeed模式下司机连O数量无意义，只有GS模式下司机连O数量才有意义（用于判断司机挑单的收益空间）。

**结论：连到的O数量大于1的司机比例平均为6%，在3%～9%之间波动，D选O挑单空间有限。**

> 「唯一连边订单占比」= 只连了一个D的订单数量 / 所有有连边的订单数量

Q：为什么TopSpeed的唯一连边订单占比都明显小于GS分单？

A：两者的差异主要是因为**召回半径**。目前GS使用的召回半径比TopSpeed更短（参考[【LR25004】商家TopSpeed分单模式建设](https://cooper.didichuxing.com/knowledge/2199610335356/2204304953766)，目前TopSpeed播单半径为2.5km，GS播单半径为3km），更大的召回半径会导致进分单矩阵的订单数变多、分母增大，新增了唯一连边订单数（原先无连边），同时也少量地减少了部分唯一连边订单数（原先已有连边，新增连边后连到D数量大于1），最终导致召回半径扩大后唯一连边订单占比变高。

**结论：连到的D数量大于1的订单比例 GS分单模式下约30%，TopSpeed模式下约50%**

## 2、匹配模式

现在是tp和gs并行的模式；现在哪些o走tp：送驾距离>4.5km

```SQL
with base as (
    select distinct
        param ['orderid'] order_id,
        param ['driverid'] driver_id,
        param ['uuid'] uu_id, --轮次（不同轮次的编码不一样，类似 d300d101c37b44f1）
        param['rgs_pair_match_flag'] as rgs_pair_match_flag, --层级（int）
        param['broad_source'] as broad_source, --播单来源
        cast(substring(param['timestamp'],12,2) as int) as hour_int,
        concat_ws('-', year, month, day) as dt
    from
        kflower_marketplace.ods_log_kflower_stgmatrix_hh
    where
        concat_ws('-', year, month, day) between '2026-03-15' and '2026-03-15'
        -- and param ['broad_source'] in ('hh_hxz_stg','hh_hxz_speed','hh_stg','hh_speed')  --stg是GS分单，speed是topspeed；hh是宏鹄，hh_hxz是自营
        and param ['broad_source'] in ('hh_hxz_stg','hh_hxz_speed') --只看自营
        -- and param ['broad_source'] in ('hh_stg','hh_speed') --只看宏鹄
        -- and param ['broad_source'] in ('hh_hxz_stg','hh_stg') --只看GS分单

)

,tag as (
    SELECT 
        order_id,
        CASE 
            WHEN COUNT(DISTINCT broad_source) = 1 AND MAX(broad_source) = 'hh_hxz_stg' THEN 'gs'
            WHEN COUNT(DISTINCT broad_source) = 1 AND MAX(broad_source) = 'hh_hxz_speed' THEN 'tp'
            WHEN COUNT(DISTINCT broad_source) = 2 THEN 'both'
            -- 可选：处理source为NULL或非a/b的情况
            ELSE 'other' 
        END AS source_tag
    FROM base
    WHERE broad_source IN ('hh_hxz_stg', 'hh_hxz_speed') -- 可选：如果只需要处理a/b，可加此条件
    GROUP BY order_id
)



SELECT 
    source_tag,
    COUNT(order_id) AS order_cnt,
    COUNT(order_id) * 1.0 / SUM(COUNT(order_id)) OVER () AS proportion
FROM tag
GROUP BY source_tag
ORDER BY order_cnt DESC;
```
