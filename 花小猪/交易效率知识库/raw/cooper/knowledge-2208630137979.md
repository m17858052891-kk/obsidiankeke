## 1 背景

现状下，API 商家在平台 PK 中的运力只有「单次举手」机会：一旦 API 司机在某一轮 PK 中失败、或在自营宏鹄半指派/预分单链路中被拒绝，该订单上 API 商家便失去了继续参与竞争的机会，API 运力无法被充分利用。

\- **想解决的问题**：API 失败/被拒后运力提前退出竞争，导致 API 完单规模与平台整体完单规模存在损失。 

\- **根因**：平台 PK 与半指派/预分单链路仅支持 API 商家对一个订单举手一次，缺少「二次/多轮举手」机制。

## 2 目标 & 约束

**策略目标**

- 核心指标：平台 CR、平台完单量、API 完单份额/API 完单量。<!--评论:[{"u":"menchang","c":"这里格式似乎有问题？"}] --> 

- 验证「允许 API 商家对同一订单多轮举手不同司机」能为 API 完单带来正向收益，并观察是否对大盘 CR 有正向拉动。<!--评论:[{"u":"menchang","c":"这里格式似乎有问题？"}] -->

**约束 & 观测指标**

- 平台侧花小猪端核心指标不得显著负向：花小猪应答率、竞争成交率、完单量。<!--评论:[{"u":"menchang","c":"这段格式似乎也有问题？"}] --> 

- 应答后乘客取消率、应答后司机取消率（含改派）不显著恶化。 - 接驾距离、接驾时长不因多轮举手而显著拉长。<!--评论:[{"u":"menchang","c":"这段格式似乎也有问题？"}] -->

## 3 技术方案

在原有平台 PK 与半指派/预分单链路基础上，放开 API 商家对同一订单的多轮举手能力：

1\. API 司机在平台 PK 中失败后，API 商家可再次举手司机上报平台参与 PK。

2\. API 司机在（自营宏鹄）半指派决策过程中举手的司机立即失败、且该半指派司机拒单后，API 商家可再次举手司机上报平台 PK。 

3\. API 司机在预分单被乘客拒绝后，API 商家可再次举手司机上报平台 PK。 

4\. 平台 PK 在半指派司机获胜后不立即结束，PK 正常进行，直到出现更高 PK 分司机（此时对半指派司机展示「订单已被抢走」）、或半指派司机接受/拒绝、或达到 PK 窗口时间上限。

> 与需求/评审方案的差异：本期落地范围为花小猪端、T3 出行 / 享道出行 / 如祺出行三家 API 商家的接入城市；其余与方案一致，如有偏差以此处为准。

### 4.4 收益链路归因

允许 API 多轮举手 → API PK 模块举手订单数 & 平均参与司机数↑（+19.7%）→ API PK 获胜订单数↑（PK 胜率 +0.87pp）→ API 应答率↑（+0.30pp）→ API 竞争成交率↑（+0.27pp）→ API 完单量↑（+1.6%）。链路各环节均显著为正，与预期收益路径一致。

### 4.5 其他过程分析

\- 举手侧数据（实验组 vs 对照组）：API handsup 数 6,600,098 vs 5,503,249，多轮举手带来举手量明显增加，而 API PK 参与订单数基本持平（4,469,999 vs 4,461,530），说明增量主要来自「同一订单多轮举手更多司机」，符合策略设计。 

\- 接驾距离/时长不升反降，说明多轮举手引入的新增竞争司机整体未拉低接驾体验。
