## 系统整体框图

实际系统中订单及司机数据量极大，会拖慢与策略的交互过程，进而影响训练类算法的上线速度。因此系统所调用的模拟环境（之后简称服务端）是基于C＋＋进行开发的，而匹配策略端（之后简称策略端）考虑了训练算法调用上的方便性，仍使用python。服务端会建立一个带端口的服务器平台，提供socket传输服务。通过thrift的数据交互功能，策略端的python脚本可直接调用服务端的函数，输入及取得系统的相关状态及参数。

### C++ based Environment （服務端）

服务端主要包含以下模拟功能，并提供部分数据接口及指令接口给策略端使用，主要功能实现在share_simulation_env/server/src/service/thrift/路徑底下的 simulation_env_handler.h和simulation_env_handler.cpp中

##### 环境参数

time: 当前时间

 driver_pool: unordered_map<driver>型态，包含当前所有司机的池

 order_pool: unordered_map<order>型态，包含当前所有订单的池

 all_assigned_pairs: unordered_map<int64, int64>型态，当前进行中的司机及订单配对

 active_d_mode_cnt: unordered_map<string, int64>型态，当前空间司机数量总和

 active_o_type_cnt: unordered_map<string, int64>型态，当前未分配订单数量总和

 active_d_ids: unordered_set<int64>型态，当前空间司机id集合

 active_o_ids: unordered_set<int64>型态，当前空间订单id集合

 rand_num: queue<double>型态，利用指定种子预先产生取消模块的取消率

 pair_cancel_rate: vector<double>型态，储存以下取消率分桶拟合结果，每个x坐标\*200就是实际的距离分桶范围

##### 模拟功能(Intra-modules)

主要是服務端內部实现模仿实际订单及司机变化情况的相关功能

- update_order_pool

- 输入：当前时间  
更新所有等待应答中的订单的等待时间，并调用应答前取消率模型随机取消订单

- update_driver_state

- 输入：经过时间  
设计空闲司机的游走模式，在每个时间步长改变司机的经纬度位置，依难易度可分为三个方案：

	- 直接在当前位置加上随机噪声位移（最简单，拟真度最低），目前采用方案1

	- 给个朝向，让司机延固定朝向随机速度走（司机状态变化较稳定，但延直线走仍会有不少问题要解决）

	- 依真实路况让司机延地图道路走（难度大，需与地图引擎对接）

- 设计忙碌司机的状态变化模式，若当前时间减掉订单开始时间小于一域值则按一定机率完成订单，并将司机当前位置更新为订单完成位置，状态改为空闲

	- 司机接单后若没取消则位置经纬度变化将会延着起点及终点进行等速直线运动

- cal_life_time

-  输入：\[0,1\]之间的一个乱数

- 利用订单生存时间模型给订单添加life_time属性

- cal_paired_cancel_prob

- 输入：司机，订单id  
寻找接驾距离所处的桶，判定当前从rand_num pop出的值是否小于该桶的取消率，是就回传true

##### 接口(Client API)

将环境的相关状态信息按指定格式、数据型态传输给策略端或用户端

- get_observation  
回传当前状态（司机状态、订单状态），包含以下回传值：

	- active_drivers  
为unordered_map<id, driverFeature>的型态，若以python调用则是dict的形式。提供使用者空闲司机的状态。

	- active_orders  
为unordered_map<id, orderFeature>的型态，若以python调用则是dict的形式。提供使用者空闲订单的状态。

	- busy_drivers  
为unordered_map<id, orderFeature>的型态，若以python调用则是dict的形式。提供使用者忙碌中司机的状态。

	- busy_orders  
为unordered_map<id, orderFeature>的型态，若以python调用则是dict的形式。提供使用者已接单订单的状态。

	- time_stamp  
回传函数调用当下的模拟系统时间戳

- get_reward  
回传距上一次调用此函数之间累积的配对数量及GMV，当前未完成的配对数量及GMV，还有累积的总体配对数量及GMV。  
另外也会将当前结果一并存入saved_xxx_cnt和saved_xxx_gmv中，这样save_result就不用强制在get_reward之后调用了。

	- matched_pairs  
为unordered_map型态，包含了当前进行中司机与订单的id

	- matched_cnt  
为int64型态，统计距上次调用get_reward之间累积的成功匹配订单数量

	- matched_gmv  
为double型态，统计距上次调用get_reward之间累积的成功匹配订单GMV

	- assigned_cnt  
为int64型态，统计策略距上次调用get_reward之间累积的指派订单数量（仅指派，不代表会匹配成功），可以用来计算matched/assigned的比值

	- total_matched_cnt  
为int64型态，统计当前已完成+进行中订单的数量

	- total_matched_gmv  
为double型态，统计当前已完成+进行中订单的GMV

	- total_assigned_cnt  
为int64型态，统计当前已指派订单的数量（包含匹配成功及被取消的所有订单），可以用来计算total_matched/total_assigned的比值

	- ongoing_cnt  
为int64型态，统计当前进行中订单的数量

	- ongoing_gmv  
为double型态，统计当前进行中订单的GMV

- 注意：必须在set_time_pass（或者第二个参数>0的set_action）之后调用，否则调用存档功能时会出现偏差，目前尚未找到原因

	- set_action  
输入：action, 经过时间  
回传：匹配失败的订单  
提供策略端用來发送action用，环境端依据action的匹配结果改变订单及司机状态，并调用set_time_pass  
action是thrift定义的类别，包含了匹配司机id的list，匹配订单id的list，以及两者对应的pair map

- set_time_pass  
输入：经过时间  
更新当前时间，并调用环境内部的系统模拟相关函数（主要调用update_order_pool及update_driver_state更新系统状态，并将observation所需的司机及订单各自存入active_d_ids及active_o_ids之中）

- get_time  
输出：int64型态当前时间  
取得当前时间

- get_done  
输入：int64型态结束时间段  
输出：bool  
判断是否到达事件结束时间，这边不需输入实际的结束时间， 只需输入结束时间段（0-2hr）

- reset  
输入：CSV路径(string)，订单司机比(double)，开始时间(int64)，结束时间(int64)  
建构司机及订单生成函数，初始化时间，司机池及订单池

- get_state_by_driver  
输入：司机id list  
输出：driverState类别，包含drivers，与drivers配对的orders，以及呼叫函数时的时间戳  
获取接送中订单状态

- get_state_by_order  
输入：订单id list  
输出：orderState类别，包含orders，与orders配对的drivers，以及呼叫函数时的时间戳

- save_result  
输入：user_name, policy_name, test_name(皆為string)  
储存此次模拟结果（累积的saved_xxx_cnt, saved_xxx_gmv和total_xxx_cnt,total_xxx_gmv）到server的CSV output路径  
注意：必须在set_time_pass（或者第二个参数>0的set_action）之后调用，否则调用存档功能时会出现偏差，目前尚未找到原因

##### 其他功能函数(Other utilities)

- update_active_driver_modes  
统计空闲司机所属类别（"active","busy"）数量。deprecated，目前虽然可调用但没有参与result的计算，之后会移稌。

- update_active_order_types  
统计空闲订单所属类别（"done", "none"）数量。deprecated，目前虽然可调用但没有参与result的计算，之后会移稌。

- to_time_stamp  
将时间（时-分-秒）字符串转化为时间戳

- get_sphere_dis  
将经纬度转化为公里，用的是简易转换算法计算直线距离，再乘上一个MAGIC_NUMBER，因此在极端纬度会有较大误差，但误差约为米级，在可接受范围

- clear_data  
计时归零，清除所有订单司机数据，配对数据，环境內部数据

- read_driver_data  
输入：CVS路径，开始时间，结束时间  
依据输入的开始与结束时间\[0, 2hr\]，读入所有符合区间的真实司机数据

- read_order_data  
输入：CVS路径，开始时间，结束时间  
依据输入的开始与结束时间\[0, 2hr\]，读入所有符合区间的真实订单数据

- sample_do  
输入：订单司机比（订单/司机）  
依据订单司机比随机去除多余司机或订单，确保区间内整体数量满足订单司机比，若输入0则按原始数据

##### 自定义类别（这边只列出大致会有的，详细仍以idl/server_demo.thrift为主）

- Driverfeature

- 1: i64 id：司机id

8: i64 next_order：连环派单下一单id，若无则为-1  

- Orderfeature

- 1: i64 id：乘客id  
2: string call_time：出现时间  
3: double start_lat：起点纬度  
4: double start_lng：起点经度

6: double dest_lng：终点经度

8: i64 est_dur：预估时间  
9: string type：订单状态（done说明完单，none说明取消）  
10: string assigned_to：送达中（以on表示还在途中，未接单为空字符）  
11: i64 wait_time_pass：等待时长（秒）  
12: double answer_lat：应答纬度  
13: double answer_lng：应答经度  

- Observation

- 1: map<i64, Driverfeature> active_drivers：空闲司机id及属性  
2: map<i64, Orderfeature> active_orders：空闲订单id及属性  
3: map<i64, Driverfeature> busy_drivers：忙碌司机id及属性（仅回传未被连续派单的忙碌司机）  
4: map<i64, Orderfeature> busy_orders：忙碌订单id及属性  
5: i64 time_stamp：函数调用当下系统时间戳  

- Action

- 1: list<i64> assigned_d_ids\_：指派的司机id  
2: list<i64> assigned_o_ids\_：指派的订单id  
3: map<i64,i64> assigned_pairs\_：指派司机-订单 id map  

- result

- 1: map<i64,i64> matched_pairs：配对成功的司机-订单map  
2: i64 matched_cnt：配对成功数量  
3: double matched_gmv：配对成功的总gmv  
4: i64 assigned_cnt：实际指派的数量  
5: i64 total_matched_cnt：总配对成功数量（含所有已完成，进行中）  
6: double total_matched_gmv：总配对成功gmv（含所有已完成，进行中）  
7: i64 total_assigned_cnt：总指派数量（环境每次调用set_action时会累计）  
8: i64 ongoing_cnt：当前进行中的订单数（含此次指派的）  
9: double ongoing_gmv：当前进行中的订单gmv（含此次指派的）  

- driverState

- 1: map<i64, Driverfeature> drivers：司机id的属性查询结果  
2: map<i64, Orderfeature> orders：司机id对应的订单查询结果，仅返回有接到单的配对  
3: i64 time_stamp：调用当下时间戳  

- orderState  
1: map<i64, Orderfeature> orders：订单id的属性查询结果  
2: map<i64, Driverfeature> drivers：订单id对应的司机查询结果，仅返回有配对到的订单  
3: i64 time_stamp：调用当下时间戳

### python based agents （策略端）

##### 环境配置

目前是在conda 的python3运行client_test.py，至少需安装以下库(待补充)

- conda install thrift、conda install numpy

- 若想使用pointer network，需額外安裝pytorch

##### GS策略

有分为无cutoff及有cutoff版本，后者多了5公里截断判定。

包含以下功能

get_prefer:

输入司机和订单，生成P_driver和P_order两组二维偏好数组，cutoff版本各行的长度是不一致的

dispatch:

1.输入P_driver和P_order(不一定从get_prefer取得)，执行自适应GS(按照司机和订单数量调整)

2.创建二个一维的free 向量，一个二维的proposed矩阵

3.每次从匹配发起端(以司机为例)，找到第一个free的司机，寻找它的最靠前，且未被proposed过的订单，将此组配对设为proposed

4.如果该订单目前尚未有配对，则将这对司机订单配在一起，回到3

5.如果该订单已有配对，则比较目前司机和该订单已配对的司机谁对于订单的偏好比较高，若目前司机较靠前则取代，回到3

6.重复上述流程直到司机端皆找到匹配，此算法能保证发起端一定是稳定匹配

##### Pointer network 策略

actor首先利用gs算法代码里的get_prefer取得偏好排序，利用排序结果将司机和订单连边

对于所有连边结果，我们将司机和订单主要特征拼接在一起，输入连边序列

actor中的forward每次会从序列中指向一个边，然后将这个边以及和它相关的所有边都mask上，确保之后不会再选到重复司机/订单

最后输出一组匹配边和log-likelihood值

critic会将GS算法的匹配结果做为Q函数的基线函数，进行单步更新(此方案理论上能使Q函数学会对GS算法的估值)

actor利用Q函数的估值和GS算法的匹配价值以及前面的log-likelihood计算策略梯度并更新

注：目前仅将大致训练流程跑通，要能稳定收敛估计还需要加入许多训练方法，如batch update, target network等等
