# 一、背景

当前链路下，平台智能呼返先决策出平台补贴的折扣，然后默勾策略在平台补贴已经确定的基础上，by单求解出最优的价格锚点。

这种情况下，无论是对于平台智能呼返，还是默勾策略，都是**局部最优**。但如果我们能将平台补贴和默勾策略放在一起进行**联合决策**，是否可以达到**全局最优**呢？答案是肯定的！

- 首先，优化目标一致。平台补贴策略和平台流量分发策略，本质上都是为了平台规模服务的，优化目标都是平台完单。

- 其次，二者共同影响最终完单。平台补贴的两个抓手中，盒子呼返侧重于通过创造最低价来提升ECR，平台呼返则倾向于通过改变价格分布提升用户默勾接受度进而提升平台CR，而无论是最低价还是价格分布，都是默勾接受度的重要影响因素，最终决定用户呼叫的车型，影响CR。

因此，为了能让平**台补贴和默勾策略相互感知&协同提效**，**提升平台补贴的效率（adjust-FROI）和平台规模（完单），**我们开启了盒子呼返&平台呼返&默勾策略的联合决策。

**预期收益**：基于业务认知，预计本需求能提升完单+1.5%（折合4.8w单），平台呼返ROI +10%，盒子呼返ROI +15%

# 三、技术方案

## 3.1 业务抽象

> **假设1**：ECR只与折扣相关，与默勾无关，即默勾车型的多少不影响用户是否发单（数据支持：随机默勾实验表明，在默勾比例为80%以内，默勾车型的多少基本上不影响ECR）
>
> **假设2**：当用户不接受平台默勾的时候，会反勾到只勾选最低价进行发单（数据支持：反勾case分析表明，反勾订单最终呼叫车型个数，超过54%都是以最低价呼叫，70%呼叫车型数小于3）
>
> **假设3**：暂时不考虑应答后取消的影响（应答率的预估能利用到更多交易过程中的分单信息，能提升模型精度，因此用AR替换CR）；

如上图所示，补贴和默勾抓手，对于完单的影响链路如下：

- 折扣组合，通过影响价格分布（如最低价），从而改变用户的冒泡发单意愿，即影响ECR；

- 同时，折扣组合决定了表单的价格分布，在确定的Price List下，用户对于不同的平台默勾推荐会有不同的反应，这里我们简化为两种：

	- 接受默勾，即最终以平台默勾推荐的车型进行发单；

	- 不接受默勾，用户会反勾到最低价再发单，最终以最低价车型进行呼叫；

- 最终呼叫的车型的运力情况，决定了当前订单以当前折扣组合和默勾被呼叫的情况下，是否能完单（忽略应答后取消，退化为conditional accumulated AR）；

- 结合ECR和conditional accumulated AR，最终决定当前冒泡能否完单

对偶问题为广义拉格朗日函数的极大极小问题。在lambda确定的情况下，最小化L，即对于每一个冒泡，最小化$$L(z,\lambda)$$，通过迭代，我们即可求解出全局最优化的lambda。

通过以上对偶问题的转换，我们将原问题（对每一个冒泡求解最优决策），转换成了对于lambda的求解。

我们假设冒泡分布不发生改变的情况下，在求解出lambda之后，线上就可以根据模型预测值和lambda，实时得出对于任一冒泡的最优决策。

*附当前优化问题的强对偶性证明*

> 强对偶性证明

> 首先，当前的优化问题为整数规划，不便于强对偶性的证明。因此，我们先对$$Z_{ijk}$$进行松弛，转换成线性规划；

> 松弛后的优化问题和约束条件为凸函数，因此根据slater条件，我们只需要证明松弛条件和规划补贴率约束，能找到内点满足条件即可。

> 松弛条件，为满足内点要求，我们取无限趋近于0的值；

> 规划补贴率约束，我们只需要对所有的冒泡，取折扣为100-100（即不打折），默勾取全勾（acc_AR约束剪枝后一定会存在不打折组 ✖️ 全勾的决策空间），满足规划补贴率约束；

> 因此，松弛后的优化问题具有强对偶性。

> 原问题与松弛后的优化问题的解，因为都是按照ROI进行倒排，因此在budget约束下，假设会命中N个冒泡，N个冒泡按照ROI进行排序之后，前N-1个冒泡的解都一致，仅最后一个冒泡因为整数规划和线性规划的差异，存在一点差异，基本不影响整体的求解，如下图所示。因此，我们可以大胆地将松弛后的优化问题看成是原问题的解，原问题也具有强对偶性。

本次任务的主要挑战在于，我们需要同时对特价盒子和盒子外可控运力的价格弹性进行建模（**多品类联合建模交叉弹性**），以及需要有一个合理且高效的离线评估指标对ECR进行评估。

- 针对第一个挑战，我们结合业务上对于交叉弹性的理解，对delta function进行了探索和改造，尝试了以下多种结构：

	1. 基础方程$$axy + bx + cy +d$$

	2. $$(a+2b)x+b(x-y)^2+(c+2b)y + d$$

	3. $$ax+b(x^2+y^2)+cy + d$$

	4. $$(a+2b)x^{0.5}+b(x^{0.5}-y^{0.5})^2+(c+2b)y^{0.5} + d$$

	5. 交换求和和sigmoid位置：先与delta相加,再过sigmoid

最后上线的版本为b，取得了不错的离线收益，MTAUCC达到了**0.2662，**基于xgboost的s-learner模型，其MTAUCC仅为**0.1478。**

![](https://s3-ep-inter.didistatic.com/didoc-upload-image-prod/1746441170088cacdbf028e8d42f4b7bb842505972d09/%E7%94%BB%E5%B8%831%283%29.png?X-Amz-Algorithm=AWS4-HMAC-SHA256&X-Amz-Credential=AKDD00000000000EBLCTZNRBJHX6ZS%2F20261104%2Fgzep%2Fs3%2Faws4_request&X-Amz-Date=20261104T120144Z&X-Amz-Expires=86400&X-Amz-SignedHeaders=host&X-Amz-Signature=fb8cb2a43eea4b9dce592924b2addb65bdd88d20e4d5069d8d0f23d19c91a65f)

联合决策中，因为是全空间（折扣组合空间 ✖️ 默勾车型）求解最优，相较于默勾策略V1中单次求解默勾最优，对于计算资源的要求急剧上升（是之前的17倍）。对于默勾策略V1中基于xgboost的架构，线上耗时肯定是无法满足要求的。

另外，默勾策略V1中基于xgboost的模型，虽然在特征中加入了当前表单价格的分布特征（价格分位点），但这种价格分布的统计特征对于价格分布的表征肯定是有损的，这无疑会制约模型性能的天花板。

因此，本次DSAR迭代，我们转向了**深度网络**，其优势在于：

1. 对于一个确定的Price List，只需要过一次模型（需要将商家个数padding到指定个数），即可预测出默勾到不同车型的DSAR，大幅改善耗时问题；

2. 引入Transformer结构，通过各车型（价格）之间的attention，实现每个车型对于表单价格分布的感知，提升模型对于DSAR预测的准确性。

DSAR模型结构如上图所示。

- 样本构造：基于所有呼叫冒泡构造样本，每个呼叫订单生成一个样本，label为该订单用户是否有反勾行为，默勾为平台推荐的车型。另外，为了纠正默勾样本可能的偏差，我们增加了随机默勾实验的数据；

- 特征工程：如图7所示，DSAR模型主要有三个类别的特征

	- P维度特征：基于用户历史呼叫订单生成的用户行为特征，如加勾率、反勾率、呼叫车型比例等；

	- 订单维度特征：起终点特征，城市，订单预估距离，表单价格统计特征等；

	- 每个商家的序列特征：排序、价格、与冒泡最低价的比例、当前价格等；

- 损失函数：对于每个呼叫，选取平台推荐默勾对应的预测值，与真值求BCE；

- 离线效果：模型的评估指标为AUC，最终上线版本的AUC为**0.886**

### 3.5.3 AR模型

#### 3.5.3.1 样本构造

AR模型用于预测，「如果乘客**单勾呼叫**了某商家，订单是否能够**被应答**」。而事实上，线上的真实数据中，仅有极少数品牌存在被单独呼叫的情况，能够获得其在被单独呼叫情况下的应答结果。对于大多数其他品牌，应该如何构建其单勾呼叫下的应答Label呢？

为了解决这一问题，我们深入聚合交易模块，试图从中获取更多表征运力「应答能力」的信息。对于小猪端，目前的交易过程如下：

#### 3.5.3.2 特征工程

模型用到的特征主要包含三类：订单基础特征、商家实时运力特征、商家历史时空上的统计特征。

```SQL
with trace_info as (
    select
        *
    from
        kflower_strategy.pltf_union_stg_daily_exp_by_traceid
    where
        dt between '${begin}'
        and '${end}'
        and city_id in (2,5,6,8,9,12,13,14,15,16,17,18,19,21,22,24,25,26,29,32,33,34,35,38,44,50,60,74,81,83,85,86,133,134,153,254)
),
mogou_info as (
    select
        city_id,
        trace_id,
        show_merge_num,
        selected_merge_num,
        called_merge_num,
        size(selected_list) as selected_num_box_as_one,
        size(called_list) as called_num_box_as_one,
        if(selected_merge_num=1, 1, 0) as is_single_select,
        if(selected_merge_num=1 and selected_list[0] = -1, 1, 0) as is_single_select_box,
        if(called_merge_num=1, 1, 0) as is_single_call,
        if(selected_merge_num=1 and called_list[0] = -1, 1, 0) as is_single_call_box
    from
        kflower_strategy.dwm_kf_trd_order_bubble_di_cgh
    where
        dt between '${begin}'
        and '${end}'
        and city_id in (2,5,6,8,9,12,13,14,15,16,17,18,19,21,22,24,25,26,29,32,33,34,35,38,44,50,60,74,81,83,85,86,133,134,153,254)
)
,mogou_by_product as (
    select
        bubble_trace_id,
        selected_cp_cnt,
        call_cp_cnt
    from
        kflower_dw.dwm_kf_trd_order_bubble_di
    where
        dt between '${begin}'
        and '${end}'
        and form_type = 3
        and order_type = 0
        and source_type <> 2
        and size(selected_bub_product_arr) > 0
        and city_id in (2,5,6,8,9,12,13,14,15,16,17,18,19,21,22,24,25,26,29,32,33,34,35,38,44,50,60,74,81,83,85,86,133,134,153,254)
)
,agg_info as (
    select
        a.*, b.exp_group, c.selected_cp_cnt, c.call_cp_cnt
    from
        mogou_info a
        left join trace_info b on a.city_id = b.city_id
        and a.trace_id = b.trace_id
        left join mogou_by_product c on a.trace_id=c.bubble_trace_id
)
select exp_group, 
    count(distinct trace_id) as trace_cnt,
    sum(selected_merge_num) / sum(show_merge_num) as `平均默勾车型比例`,
    sum(called_merge_num) / sum(show_merge_num) as `平均呼叫车型比例`,
    avg(selected_cp_cnt) as `平均默勾车型数`,
    avg(call_cp_cnt) as   `平均呼叫车型数`,
    avg(selected_num_box_as_one) as `平均默勾车型数（盒子算一个）`,
    avg(called_num_box_as_one) as `平均呼叫车型数（盒子算一个）`,
    avg(selected_merge_num) as `平均默勾车型数（展现）`,
    avg(called_merge_num) as `平均呼叫车型数（展现）`,
    count(distinct if(is_single_select=1, trace_id, null )) / count(distinct trace_id) as `默勾单勾占比`,
    count(distinct if(is_single_select_box=1, trace_id, null )) / count(distinct trace_id) as `默勾单勾且为特价盒子占比`,
    count(distinct if(is_single_call=1, trace_id, null )) / count(distinct trace_id) as `呼叫单勾占比`,
    count(distinct if(is_single_call_box=1, trace_id, null )) / count(distinct trace_id) as `呼叫单勾且为特价盒子占比`
from agg_info group by exp_group order by exp_group;
```

上表是各个实验组默勾和呼叫的数据，可以看出，**联合决策实验组默勾单勾率有显著提升**，且默勾单勾的基本上都是特价盒子。

因此，我们有理由推断：联合决策通过补贴的合理分配，降低了盒子实付倒挂率，同时在不影响CR的前提下，通过**提升特价盒子的默勾单勾比例**，提升特价盒子的完单份额，从而降低大盘的实付CPM。

with raw as (
    select
        city_id,
        trace_id,
        size(selected_list) as select_cp_cnt,
        size(called_list) as call_cp_cnt,
        choosable_cp_num,
        if(size(jiagou_list) > 0, 1, 0) as is_jiagou,
        if(size(fangou_list) > 0, 1, 0) as is_fangou,
        if(size(jiagou_list) =0 and size(fangou_list) = 0, 1, 0) as is_mogou
    from
        kflower_strategy.dwm_kf_trd_order_bubble_di_cgh
    where
        dt between "${begin}"
        and "${end}"
        and city_id in (6,8,9,12,13,14,16,19,21,22,25,26,29,32,33,34,42,44,50,58,60,74,81,85,125,133,134,157,160,254)
),
exp_info as (
    select
        city_id,
        trace_id,
        if(
            exp_group = 'stg_platform_uabox_fix',
            'stg_bucket_1206',
            exp_group
        ) as exp_group
    from
        kflower_strategy.pltf_union_stg_daily_exp_by_traceid
    where
        dt between "${begin}"
        and "${end}"
        and exp_group not like 'stg_g5_bucket%'
),
order_info as (
    select
        bubble_trace_id,
        max(is_td_finish) as is_td_finish
    from
        kflower_dw.dwd_kf_trd_order_base_di
    where
        dt between "${begin}"
        and "${end}"
        and is_td_call = 1
        and start_city_id in (6,8,9,12,13,14,16,19,21,22,25,26,29,32,33,34,42,44,50,58,60,74,81,85,125,133,134,157,160,254)
    group by
        bubble_trace_id
),
subsidy_info as (
    select bubble_trace_id, gmv_amt, pltf_subsidy_c+uabox_subsidy_c as plat_subsidy_c  
    from 
        kflower_strategy.pltf_union_stg_subsidy_detail_by_order 
    where 
        dt between "${begin}" and "${end}"
        and is_fuse = 'false'
),
agg_info as (
    select
        a.*,
        b.exp_group,
        c.is_td_finish,
        ceil(select_cp_cnt / choosable_cp_num * 10)  as select_cp_ratio,
        ceil(call_cp_cnt / choosable_cp_num * 10) as call_cp_ratio,
        gmv_amt,
        plat_subsidy_c
    from
        raw a
        join exp_info b on a.city_id = b.city_id
        and a.trace_id = b.trace_id
        join order_info c on a.trace_id = c.bubble_trace_id
        join subsidy_info d on a.trace_id = d.bubble_trace_id
)
select
    exp_group,
    select_cp_ratio,
    count(distinct if(is_td_finish=1, trace_id, null)) / count(distinct trace_id) as cr,
    sum(call_cp_cnt) / count(trace_id) as avg_call_cp_cnt,
    sum(select_cp_cnt) / count(trace_id) as avg_mogou_cp_cnt,
    sum(is_jiagou) / count(trace_id) as jiagou_ratio,
    sum(is_fangou) /  count(trace_id) as fangou_ratio,
    sum(is_mogou) / count(trace_id) as mogou_ratio,
    count(distinct trace_id) as trace_cnt,
    count(*) as total_num,
    sum(plat_subsidy_c) / sum(gmv_amt) as subsidy_rate
from
    agg_info
group by
    exp_group,
    select_cp_ratio

# 五、后续规划

1. **ECR模型迭代**：目前ECR模型还存在一定的提效空间，包括MTAUCC评估指标、细化补贴粒度等；

2. **acc_CR模型优化**：当前策略暂时不考虑应答后取消的影响，但其实应答后取消会很大程度上影响最终的CR，因此，后续会迭代acc_CR模型，目前已提需求并介入开发；

3. **引入特价盒子动态智能定价**：在当前补贴率收紧的大环境下，很多城市会没有补贴，有补贴的城市，补贴率也很浅，限制策略收益空间，后续会引入特价盒子智能定价，以提升策略收益；

4. **收拢幸运盒子出价**：当前链路miss掉了幸运盒子的定价，会导致默勾决策的时候，不能感知到幸运盒子的价格，而幸运盒子出现的时候又是最低价，影响用户加反勾，后续会将幸运盒子出价收拢到联合决策中；
