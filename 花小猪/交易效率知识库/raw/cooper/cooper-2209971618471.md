# 需要讨论的问题

顺路与选单现在的问题，本质上都是工具的滥用导致挑单——削弱平台对供给的调节力。一方面可以拉长TSH、另一方面影响司机派单的公平性。

设计的导向：通过顺路或选单来挑单的行为，需要和收入互斥。1.真顺路司机才划算；2.出车接受正常派单的司机收入更高

1. 顺路单

	1. 准入门槛（权益？额度？）

	2. 顺路单是否进入履约考核、冲单奖励等

	3. 事后校验——治理

	4. 风险

		1. 司机侧：下线；真收车司机无法选择

2. 选单

	1. 分不出去的单

		1. 让选，召回与排序的逻辑

	2. 溢出的订单

		1. 不让选，要求出车；同时收紧大厅准入

	3. 风险

		1. 司机侧：下线

		2. 乘客侧：取消、体验

# 顺路单

### **1. 通用顺路硬过滤**

通过接驾距离、绕远距离和角度判断订单是否顺路：

- 接驾距离 `AB ≤ 3km`

- 总绕远距离 `AB + BC + CD ≤ 1.5 × AD`

- 接驾角 `≤ 45°`

- 绕路角 `≤ 95°`

- 共享比：`share_ratio = BC / (AB + BC + CD)`，数值越大代表司机空跑和绕路成本越低

这是“能不能进入顺路候选”的基础判断。

A==：司机起点/当前位置== B==：订单起点（乘客上车点） C：订单终点（乘客下车点） D：司机原目的地==

### **Alpha 角**

**订单方向** `B→C` **与司机原行驶方向** `A→D` **的夹角：**

```PlainText
Alpha = angle(向量 BC, 向量 AD)
```

它衡量的是：**乘客行程方向与司机原目的地方向是否一致**。  
由于两条向量起点不同，它不是一个以某点为顶点的标准三点角，而是把两个向量平移到同一原点后计算方向夹角。

### **Beta 角**

**司机从当前位置直达订单终点的方向** `A→C`**，与司机原行驶方向** `A→D` **的夹角：**

```MATLAB
Beta = angle(向量 AC, 向量 AD) = ∠CAD
```

它衡量的是：**司机为了送到 C，相对原本前往 D 的方向偏离了多少**。

示意如下：

```CSS
司机原路线：A ─────────────────→ D
                    ↗
订单路线：      B ─────────────→ C

Alpha：BC 与 AD 的方向夹角
Beta ：AC 与 AD 的方向夹角，即 ∠CAD
```

# 选单

### **1. 延迟进大厅策略**

订单不会发出后立即进入选单大厅，而是先留给普通轮次分单消化。

结合前面刚查询的 `prod_kf` 配置：

- `order_into_cyborg.open = 1`

- `hold_time = 7`

即订单发出 **7 秒后仍未分出**，并满足其他准入条件，才具备进入大厅的资格。7 秒只是等待时间，不代表一定进大厅。

### **2. 开城与司机准入策略**

司机端展示选单入口时，会综合判断：

- 城市、司机、区域、车型是否合法；

- 选单大厅是否开城；

- 是否命中实验控制；

- 必要时检查司机是否在线；

- 是否超过大厅访问次数限制。

需要注意：**开关查询、订单列表查询、司机点抢是三条独立入口**，不是完全共用一套准入逻辑。

### **3. 订单召回与过滤策略**

选单大厅由司机主动拉取订单，不走普通 GS 全量匹配：

- 使用 `CyborgIndex` 按司机实时位置和召回半径找订单；

- 召回后走独立的 Cyborg CMR 过滤链；

- 补充订单详情和司机端展示价格；

- 最后执行低 CPM 等过滤。

### **4. 低 CPM 过滤策略**

为了避免低价订单大量展示：

text

```PlainText
CPM = 司机端展示价格 / 送驾里程
```

低于阈值的订单不向司机展示。其特点是：

- 使用司机实际看到的展示价，不是订单原价；

- 阈值按城市、业务线独立配置；

- 覆盖自营和宏鹄司机；

- 过滤结果有日志和城市维度监控。

### **5. 多种排序策略**

大厅支持司机按不同维度排序：

| 排序方式 <br> | 主要规则 <br> |
| --- | --- |
| 价格最高 <br> | 价格降序，接驾距离升序 <br> |
| 接驾最近 <br> | 接驾距离升序，价格降序 <br> |
| 行程最远 <br> | 送驾距离降序，价格降序 <br> |
| 出发最早 <br> | 出发时间升序，价格降序 <br> |
| 最顺路 <br> | 顺路度降序，价格降序 <br> |

同等条件下，还会优先普通实时订单，再比较出发时间。

### **6. 刷新、缓存与防作弊策略**

为防止司机高频刷大厅：

- 同一会话短时间连续请求可能直接返回缓存；

- 会话变化、超过刷新间隔或切换排序方式时重新召回；

- 单司机并发查询使用短时锁控制；

- 区分真实大厅流量与“听单诊断”流量，诊断请求不计入真实分单；

- 服务端可按进入次数或点击次数限频，防作弊控制可独立降级。

具体限次阈值由 ECP/配置控制，不能把代码默认值当成当前线上值。

### **7. 点抢与 PK 仲裁策略**

司机点击订单后：

- 使用选单专用抢单模式；

- 进入聚合 PK，而不是点击后直接拿到订单；

- 同一订单可以同时存在于选单大厅和普通轮次分单；

- 当前基线认知是 **4 秒 PK 窗口**，但动态窗口或特殊模式可能提前结束。

因此，订单后续又被普通分单召回，**不会因此自动退出选单大厅**，最终由聚合 PK 决定归属。

### **8. 延迟透出与历史去重策略**

为减少司机点到已不可用订单：

- 订单整体延后进入大厅；

- 同一订单一旦已经在选单大厅透出，原则上不再重复透出；

- 通过聚合 PK 统一处理大厅与轮次分单的竞争；

- 订单最终被分走或状态失效后，不再作为可抢订单展示。
