## 1. 先说明结论

这段 SQL 没有计算一个单一的“未来司机价值”标量，也没有使用 GMV、司机收入、折现率或长期累计收益。它回答的是一个更具体的问题：

> 当订单当前轮没有匹配成功、并进入紧邻的下一个可观测分单轮次时，下一轮唯一有效赢家的履约分和距离价值，在同城、同首发时段下的无条件期望是多少？

任务按“城市 × 订单首发小时”输出两个参数：

- `f_next`：下一轮唯一有效赢家的模型预估履约率的无条件均值。

- `rd_next`：下一轮唯一有效赢家的接驾距离经过 `[0,1]` 价值化后的无条件均值。

这里的“无条件”很关键：下一轮没有匹配、存在多个不同赢家、履约分越界或距离缺失时，该转移的两个值都按 0 进入平均。因此两个参数同时包含“下一轮能否形成唯一有效匹配”的概率，以及“匹配后赢家质量”的条件均值。

最终表没有 `driver_id`，所以它不是某个具体司机的个性化长期价值，而是城市和时段层面的下一轮赢家期望。当前任务也没有定义如何把 `f_next` 和 `rd_next` 再加权成单一分数；这一步如果存在，发生在下游策略中。

## 3. 输入数据与样本筛选

### 3.1 STG 分单矩阵

来源表：`kflower_marketplace.ods_log_kflower_stgmatrix_hh`。

读取字段：

| 字段 <br> | 作用 <br> |
| --- | --- |
| `orderid` <br> | 订单标识 <br> |
| `uuid` <br> | 分单轮次标识 <br> |
| `driverid` <br> | 候选司机标识 <br> |
| `area` <br> | 城市 ID <br> |
| `lumian_dis` <br> | 司机接驾距离 <br> |
| `do_feature_lvyue_rate` <br> | 当前候选边的模型预估履约率 `f` <br> |
| `timestamp` <br> | 日志时间，用于轮次排序和订单首发小时 <br> |

代码只保留以下来源：`hh_hxz_stg`、`hh_hxz_speed`、`hh_stg`、`hh_speed`，并要求 `order_origin = 3`。订单、轮次、司机、距离和时间不能为空，距离必须大于等于 0。

同一个 `order_id + uuid + driver_id` 如果有多条 STG 日志，只保留时间最早的一条，避免同一 O-D 边重复计数。

### 3.2 真实播单结果

来源表：`kflower_marketplace.ods_log_kflower_orderbroadcast_hh`。

播单日志沿用相同的四类 `broad_source`，排除明确标记为回家单的记录，即只保留 `is_home_dispatch` 为空或等于 0 的记录。代码以 `order_id + uuid + driver_id` 精确连接 STG 候选边和真实播单结果，用来识别每轮真实赢家。

## 4. 从日志还原订单轮次

计算分为四步。

### 4.1 确定订单的城市和时段

对每个订单：

- 城市取 STG 记录中的 `max(city_id)`。

- 首次发单时间取 `min(sample_timestamp)`。

- `call_hour` 取首次发单时间所在小时。

后续所有轮次都沿用订单首次发单的城市和小时，不使用下一轮实际发生时刻重新分桶。

### 4.2 给轮次编号

对每个 `order_id + uuid`，先取该轮最早日志时间作为 `round_timestamp`；再在订单内部按 `round_timestamp, uuid` 排序，生成从 1 开始的 `round_no`。`uuid` 只在时间相同时用于稳定排序。

### 4.3 识别每轮结果

每个“订单 × 轮次”汇总为一行：

- `matched_flag`：该轮是否至少存在一条与播单日志精确匹配的候选边。

- `winner_log_cnt`：该轮匹配到的不同赢家司机数量。

- `winner_f`：匹配赢家边的最大预估履约率。

- `winner_d`：匹配赢家边的最大接驾距离。

正常口径要求一轮只有一个不同的真实赢家。若日志识别出多个不同赢家，该轮会在后续有效性判断中被判为异常。

### 4.4 构造相邻轮次转移

只保留满足以下条件的转移：

1. 当前轮 `N` 的 `matched_flag = 0`；

2. 同一订单存在紧邻的下一个可观测轮次 `N+1`。

每条 `N → N+1` 是一个等权样本。当前轮未匹配但没有后续可观测轮次的订单不会进入均值，也不会作为 0 样本。

因此这里是“转移等权”，不是“订单等权”或“司机等权”。一个订单如果连续多轮未匹配，例如 `N → N+1 → N+2`，可以贡献多条相邻转移，在最终均值中的权重会高于只贡献一条转移的订单。

## 5. 两个未来价值参数的公式

对转移样本 `i`，定义下一轮有效赢家指示量：

```text
I_i = 1，当且仅当：
      下一轮 matched_flag = 1
      且 winner_log_cnt = 1
      且 winner_f ∈ [0, 1]
      且 winner_d 非空；
否则 I_i = 0。
```

### 5.1 履约价值 `f_next`

先为每条转移定义：

```text
y_f,i = I_i × winner_f,i
```

再对城市和候选时间桶内的全部转移取平均：

```text
f_next = (1 / n) × Σ y_f,i
       = P(I = 1) × E[winner_f | I = 1]
```

所以 `f_next` 不是“匹配成功后的平均履约率”。下一轮没有唯一有效赢家的转移会以 0 进入分母，它同时编码下一轮有效匹配概率和有效赢家的履约质量。

### 5.2 距离价值 `rd_next`

赢家距离先经过线性价值变换：

```text
r(d) = 1 - min(d, 5000) / 5000
```

因此：

- `d = 0` 时，距离价值为 1；

- `0 < d < 5000` 时，价值随距离线性下降；

- `d ≥ 5000` 时，价值为 0。

代码没有在本任务内声明 `lumian_dis` 的单位；`5000` 与该字段使用相同单位。

每条转移的距离价值为：

```text
y_rd,i = I_i × r(winner_d,i)
```

桶内参数为：

```text
rd_next = (1 / n) × Σ y_rd,i
        = P(I = 1) × E[r(winner_d) | I = 1]
```

因此不能直接用 `5000 × (1 - rd_next)` 反推出“匹配后的平均接驾距离”，因为 `rd_next` 已经乘入下一轮有效匹配概率。

### 5.3 一个仅用于说明口径的例子

假设某城市时段共有 5 条 `N → N+1` 转移，其中 3 条有唯一有效赢家：

| 转移 <br> | `winner_f` <br> | `winner_d` <br> | 是否有效 <br> |
| --- | ---: | ---: | --- |
| 1 <br> | 0.8 <br> | 1000 <br> | 是 <br> |
| 2 <br> | 0.7 <br> | 2000 <br> | 是 <br> |
| 3 <br> | 0.9 <br> | 5000 <br> | 是 <br> |
| 4 <br> | — <br> | — <br> | 否 <br> |
| 5 <br> | — <br> | — <br> | 否 <br> |

则：

```text
f_next  = (0.8 + 0.7 + 0.9 + 0 + 0) / 5 = 0.48
rd_next = (0.8 + 0.6 + 0.0 + 0 + 0) / 5 = 0.28
```

3 条有效赢家的条件平均履约率其实是 0.8，但最终 `f_next` 为 0.48；差异来自 60% 的有效赢家概率。

## 6. 城市小时的自适应扩窗

单小时样本可能不足，因此同一批转移会同时展开到六种时间桶：

| 桶宽 <br> | 划分方式 <br> |
| ---: | --- |
| 1 小时 <br> | 每个小时单独统计 <br> |
| 3 小时 <br> | 0–2、3–5、…、21–23 <br> |
| 6 小时 <br> | 0–5、6–11、12–17、18–23 <br> |
| 12 小时 <br> | 0–11、12–23 <br> |
| 18 小时 <br> | 0–17 和 6–23 两个重叠窗口 <br> |
| 24 小时 <br> | 0–23 全天 <br> |

对每个城市的每个原始小时，代码按 `1h → 3h → 6h → 12h → 18h → 24h` 依次选择最细可用桶：

- 1–18 小时桶要求 `bucket_transition_cnt ≥ 100`；

- 24 小时桶无论是否达到 100 都作为最终兜底；

- 样本量门槛统计全部 `N → N+1` 转移，包括下一轮无有效赢家、最终取值为 0 的转移。

18 小时桶的选择规则是：0–11 点使用 0–17 窗口，12–23 点使用 6–23 窗口。

例如某城市 8 点的单小时样本数为 72，而 6–8 点所在的 3 小时桶有 160 条转移，则 8 点采用 3 小时桶的均值。如果所有较细桶都不足 100，则使用全天桶。

## 7. 刷新和继承逻辑

任务每天写入 `dt='${BIZ_DATE_LINE}'`：

- **周日**：扫描原始 STG 和播单日志，重新计算整套城市小时参数。

- **周一至周六**：不扫描原始日志，直接把昨日分区复制到今日分区。

当前可执行代码中的实际样本窗口为：

```text
sample_start_date = parameter_refresh_date - 13 天
sample_end_date   = parameter_refresh_date
```

即包含首尾在内的 14 个自然日。SQL 顶部注释仍写着“截至周六的完整 28 天样本”，与实际实现不一致；解释和复现应以 `date_sub(..., 13)` 的 14 天代码为准。代码的结束日期也是刷新日，而不是注释所写的周六，实际调度日数据是否完整需要结合批次业务日期再核验。

当前 V12 代码直接使用桶内 `bucket_f_next` 和 `bucket_rd_next`，没有额外乘以 1.2 或其他统一放大系数。

## 8. 数据流总览

```text
STG 候选边日志
  └─ 按 order + uuid + driver 去重
       └─ 生成订单轮次并排序

真实播单日志
  └─ 按 order + uuid + driver 识别每轮赢家

轮次结果
  └─ 选择“当前轮未匹配 → 紧邻下一可观测轮次”
       └─ 有效赢家：写入 winner_f 和距离价值
       └─ 无效/无赢家：两项写 0
            └─ 城市 × 首发小时自适应扩窗求均值
                 └─ 生成 24 小时 f_next / rd_next JSON
                      └─ Hive 表 cba_param_f_d_next
                           └─ 在线特征 kflower.city.fdnext
```

## 9. 正确解读与边界

1. **这是下一轮代理价值，不是长期 LTV。** 代码只看紧邻的 `N+1` 可观测轮次，没有多轮递推、时间折现或长期累计收益。

2. **这是城市时段均值，不是司机个性化值。** 输出没有司机维度，同一城市同一小时共享参数。

3. **“下一个可观测轮次”不一定等于固定等待时长后的下一次决策。** 零候选或未落 STG 的中间轮次可能不可见。

4. **只观察存在下一轮的当前未匹配样本。** 没有后续轮次的订单被排除，可能带来可观测性选择偏差。

5. **自然未匹配不一定代表策略主动等待。** 当前样本来自历史上自然未匹配的轮次，用于估计主动过滤后的反事实未来机会时，需要额外验证可迁移性。

6. **异常下一轮按 0 处理。** 多赢家、履约分越界、距离缺失和无匹配都会同时压低两个参数。

7. **距离价值不是条件平均距离。** 它包含有效匹配概率，且 5000 以上被统一截断为 0 价值。

8. **最终策略公式不在该任务内。** 当前 SQL 没有 CBA、权重 `w`、bias 或单一价值合成逻辑；不能仅凭本任务断言线上如何组合两个参数。

9. **覆盖范围有限。** 样本只包含四类鸿鹄来源和 `order_origin = 3`，迁移到其他运力或分单来源前需要单独验证。

10. **城市字段存在数据质量假设。** 代码没有显式过滤空 `city_id`；同一订单如果出现多个城市值，会直接取最大值，而不是报错或剔除。

## 10. 建议补充的校验

为了让参数可审计并降低口径漂移风险，建议增加：

1. 修正“28 天 / 截至周六”的旧注释，或调整代码使注释与实际窗口一致。

2. 将每个城市小时最终选中的 `bucket_hours`、`bucket_transition_cnt` 和有效赢家数一起落表，便于判断参数来自单小时还是全天兜底。

3. 分开落盘 `P(I=1)`、`E[winner_f|I=1]` 和 `E[r(winner_d)|I=1]`，避免把匹配概率变化误读为司机质量变化。

4. 单独统计“无下一轮”“下一轮无匹配”“多赢家”“履约分越界”“距离缺失”的比例。

5. 校验刷新日的业务日期与源表完整性，并让调度依赖覆盖代码实际扫描的多日分区。

6. 在下游策略文档中补充 `f_next`、`rd_next` 的读取、边界校验、加权和兜底公式，形成从离线统计到线上决策的完整闭环。
