# 商家交易漏斗排查

## 排查顺序

1. **举手数下降**：先查抢单/半指派/全指派比例，再查召回数、播单数、缩播实验和 TopSpeed 播单；交易模式突变通常优先于单一模型解释。
2. **PK 胜率下降**：先确认平台 PK 规则或特征是否变更，再看接驾距离、履约取消、商家举手规模、only/both 举手和商家间竞争强度。
3. **应答后履约下降**：检查连环派/扩播占比、交易模式和接驾距离，区分乘客取消、司机取消与改派。
4. **连环派占比上升**：核对连环派召回距离、线上模型和 Apollo 配置，同时检查非连环派召回半径是否收窄。

## 最小漏斗

召回 → 播单 → 拒绝/举手 → PK 胜出 → 应答 → 取消/改派 → 完单。按城市、渠道、交易模式、车型、扩播、连环派和真实目的地分层；先确认订单、司机和商家 ID 映射与去重，再解释指标。

## 数据边界

来源列出大聚合发单、分单召回矩阵、分单播单、商家举手、PK 胜出和司机在线时长等历史表名及 SQL。它们是排查入口，不保证 2026 字段仍有效；监控链接、权限、口径和代码需 owner 现场复核。正文中的长 SQL、外链、图片和附件未执行或解析。

## 监控入口分工

- 交易模式看板用于先定位渠道与模式结构是否变化。
- 实时召回监控检查候选规模与过滤链；实时播单监控检查交易模式、接驾距离、扩播和连环派等播出结构。
- 日志漏斗可下钻拒绝、举手、PK 胜出、应答、完单、取消与改派，但必须先确认订单—司机去重、渠道映射与事件最晚记录规则。

这些入口和 SQL 是历史排查资产，不代表权限仍可用、字段未变或任务已调度；本 Wiki 未执行 SQL，也未复制内部表名与完整代码。
