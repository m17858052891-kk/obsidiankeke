# 预分单数据血缘与口径

## 主链路

| 环节 | 表 | 关键字段 |
| --- | --- | --- |
| 平台呼叫 | `dwd_kf_trd_unity_order_anycar_di` | `order_id`, `source_id`, `product_id`, `is_pre_dispatch` |
| 订单与履约 | `dwd_kf_trd_unity_order_di` 及标签表 | TD 应答/完单/取消，含改派与剔除改派两套口径 |
| 预分单发单 | `dwd_kf_trd_pre_dispatch_order_di` | `order_id`, `product_id` |
| 举手 | `dwd_kf_trd_pre_dispatch_strivetender_di` | `is_first_strive`（0 否、1 是、-1 未知） |
| 乘客决策 | `dwd_kf_trd_pre_dispatch_decision_di` | `is_refused`：0 接受、1 拒绝、3 默认拒绝 |
| 端内履约 | `dwm_kf_trd_hxz_order_base_view_di` | `extend_feature.pre_dispatch`, 应答、完单、取消类型 |
| 升舱识别 | `dwm_kf_trd_order_index_di` | `is_upcabin_ans` |

## 必须锁定的口径

- 平台表中 `order_id` 不应单独用于跨来源去重或关联，需与 `source_id` 组合。
- 应答、司机取消、乘客取消应分别报告“含改派”与“剔除改派”，不可混用。
- 预分单实验需同时报告触发、可用运力、乘客接受、应答、完单与应答后取消，并补充去重呼叫；否则 CR 可被取消后重发扭曲。
- 按品牌、平台、代理商分层时，需使用产品线和商户代理关系表，避免把自营、宏鹄和 API 商家腾挪解读为平台净增。
- 享道接入实验还需分别核对享道正常分单、补勾与预分单完单；只报预分单完单会遗漏内部替代。
- “去重呼叫”需先固定去重键和重发窗口。需求稿提出取消后重发可能抬高呼叫数、压低 CR，但未给出已验收的去重规则。

## 未解析与待校验

原文中预分单发单表的图片未解析，字段列表可能不完整。`extend_feature.pre_dispatch` 与平台呼叫表 `is_pre_dispatch` 的粒度、对应关系仍是原文中的待确认问题，不应在 SQL 中默认等价。另需核验只用 `order_id` 连接预分单子表时是否会跨来源串单。
