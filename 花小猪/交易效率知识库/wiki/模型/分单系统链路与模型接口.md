# 分单系统链路与模型接口

> 历史架构串讲的模型接口卡。服务名和链路只表示材料记录时的设计，不代表当前生产拓扑。

## 调度与匹配边界

历史 STG 链路按城市维护订单池和可听单司机池；调度器取得城市互斥锁后，读取司机/订单分片，组装候选对，经召回过滤与打分，再合并分片运行 GS 匹配，最后锁定并推送。材料特别说明，分片用于取数和计算，不应在合并前改变城市级全局匹配域。

模型能力位于候选对特征、过滤和打分阶段；GS 接收偏好分数求稳定匹配。由此需分别版本化：候选召回域、特征快照、过滤规则、打分模型、匹配算法和推送锁状态，不能把最终分单结果全部归因于某一个模型。

## 数据与一致性合同

- 城市锁避免同一城市被多个任务并发调度；司机锁避免重复播单。锁超时、重入和降级策略未在正文形成完整合同。
- 订单/司机状态在 API 持久化侧与分单内存池侧承担不同职责，模型特征需声明读取来源、时效、丢失与默认值。
- 聚合端、滴滴端和外部流量的发单、举手与 PK 路径不同；调用位置差异不能用一个“全局线上模型”概括。

## 历史漏斗排查证据

一份端间应答差异排查把呼叫至应答拆为：到达分单、召回、找到司机播单、有效举手、PK 胜出和应答；并把“播单到有效举手”继续拆成司机端过滤、后端拉单以及举手后的 API 过滤。材料中的历史点值显示两端漏斗存在明显差异，但这只是特定样本期的描述性对比，样本量、时间范围、置信区间和随机实验均未给出。

排查当时基本排除后端拉单与举手过滤，把主要差异定位到司机端过滤，并计划增加流量来源标识持续观察；城市和时间分布差异也被初步排除。这里的“排除”和“定位”是历史排查结论，不是因果证明：司机版本、流量构成、连环派过滤、埋点丢失和跨端口径仍可能混杂。后续标识是否发布、对应服务版本、监控看板及修复效果均未提供。

## 证据缺口

正文含多张架构图、流程图和内部链接未解析；缺少当前服务版本、流量比例、延迟、容量、故障演练、回滚和线上验收。材料是串讲文档，没有离线模型指标或 AB 收益。

漏斗排查页的流程图和城市/时段图未解析，相关链路表只能视为历史监控入口清单；Wiki 不复制内部表名为生产查询合同。该页未给附件、样本量、显著性或修复后线上结果。
